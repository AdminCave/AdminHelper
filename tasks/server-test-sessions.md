## Prüfung (Planer, 2026-10-21)
- **T1: Warum eine Schranke an der Engine und nicht eine zentrale Bindung von `SessionLocal`?** Eine autouse-Bindung an die Test-Verbindung in jedem `db_session`-Test änderte, was viele Tests sehen. `get_db` hängt ebenfalls an `SessionLocal`. Code in Threads (`run_in_threadpool` im Stream) teilte sich eine Verbindung mit dem Test. Tests ohne `db_session` erreichten die App-Engine weiter. Die Probe fand eine einzige ungebundene Stelle. Die Schranke macht jede weitere zum roten Test, gebunden wird dort, wo ein Test die Daten braucht. Der Planer von R-0520 hat die zentrale Bindung aus denselben Gründen verworfen (`tasks/server-test-events.md`, Prüfung).
- **T1: Warum die Engine und nicht `SessionLocal`?** `app/main.py:30` und `app/cli.py:30` binden den Namen beim Import, `scheduler_main.py:46` und `test_db_session_utc.py` nutzen die Engine direkt. Nur an der Engine laufen alle Wege zusammen.
- **T1, nicht verifiziert:** Wie SQLAlchemy auf eine Ausnahme aus einem `do_connect`- oder `checkout`-Listener reagiert, sagt die Doku nicht (Core Events, Stand 2.0: dokumentiert sind nur der Rückgabewert von `do_connect` und `DisconnectionError` in `checkout`). Belegt wird es durch Fall (a) des neuen Tests. Probe-Versionen: pytest 9.1.1, SQLAlchemy 2.0.54 (Dev-Venv; der Lock pinnt 2.0.50).
- **T1, testcontainers-Zweig:** Die Schranke greift vor jedem Verbindungsversuch, unabhängig davon, wohin die App-Engine zeigt. Der neue Test braucht keine Datenbank und läuft in beiden Zweigen gleich.
- **T2: Warum ein eigenes Passwort für die bestehende Rolle?** Eine Rolle je Worktree bräuchte `CREATEROLE`. Die Rolle der Anleitung hat nur `CREATEDB` (`DEVELOPMENT.md:194`), und der Haupt-Checkout behielte seine URL. Eine zweite Rolle für die Tests bräuchte sudo. Das eigene Passwort setzt die Rolle selbst, die Worktrees folgen über das Sourcen ohne Migration. Das Passwort wählt Kevin (CLAUDE.md §2); `worktree-setup.sh` erzwingt nur, dass es nicht der Benutzername ist.
- **T2, nicht verifiziert:** `\password` in einem per `-c` übergebenen psql-Aufruf. Die Anleitung nennt deshalb die interaktive Sitzung.
- **Nicht-Ziel:** Der testcontainers-Zweig nutzt die Vorgaben von `PostgresContainer` (testcontainers 4.15.0: Benutzer und Passwort `test`), auf einem Container mit zufälligem Port, der mit der Sitzung endet; die CI-Dienste nutzen ein eigenes Passwort (`.github/workflows/ci.yml:42-43`).
