## Prüfung (Planer, 2026-10-19)
- **Warum nicht an die Test-Verbindung binden und synchron ausführen?** Dann müsste `database.SessionLocal` in jedem `db_session`-Test an die Test-Verbindung gebunden werden, und das träfe auch andere direkte Nutzer (`connections/storage.py`, `hooks/scheduler.py`, `notifications/stream.py`). Der Dispatch liefe im Request statt danach. Ein Event-Hook startete den Script-Worker als Subprozess, und der öffnet eine eigene Verbindung, also wieder außerhalb der Klammer. Jeder API-Test mit Admin und Abo schriebe Benachrichtigungen. Das wäre ein eigenes Vorhaben mit sichtbaren Folgen für bestehende Tests.
- **Warum der Tausch von `_executor` und nicht von `_run_event`?** `test_hooks.py:274` und `test_notification_bridge.py:76` rufen `_run_event` direkt; ein getauschtes `_run_event` machte beide leer. Ein getauschtes `fire_event` erreichte die Router nicht, die den Namen beim Import binden.
- **Warum der Marker?** Die Teardown-Probe aus R-0509 braucht den echten Pool. Ohne Opt-in hätte die Barriere vor `drop_all` keinen Test mehr, der ohne sie rot wird.
- **Verwandt, nicht in diesem Paket:** Andere direkte `SessionLocal()`-Nutzer (`app/main.py:350`, `connections/storage.py:19`, `hooks/scheduler.py:110`, `notifications/stream.py:53`, `cli.py:153`) treffen in Tests ohne eigenen Patch dieselbe App-Engine. Für den SSE-Stream ist das in `tests/schemathesis_exclude.toml:176` beschrieben.
