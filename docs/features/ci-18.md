# ci-18 — apt-Archiv-Cache der CI, der Fortschritt hält

Roadmap: R-1602 (REF). Ledger: `tasks/ci-18.md`.

## Problem / Motivation
Die Jobs `rust` (Tauri system dependencies), `tauri-build-smoke`, `rdp-embedded` und `ops-scripts` (minisign,
gnome-keyring) laden ihre Debian-Pakete unter `retry.sh 3 180` aus dem Ubuntu-Spiegel. Kriecht der Spiegel (gemessen
~55 kB/s, je Versuch ~10 MB), fehlen 36–70 MB, und alle drei Versuche enden mit Exit 124 (PR #567, #568, #569, #586,
#591, main-Merges #570, #579, #586). Der Archiv-Cache hilft nicht:
- Der Key rollt wöchentlich (`apt-tauri-…-v2-<KW>`). Ein exakter Treffer speichert nie neu: Was nach dem ersten
  Speichern der Woche dazukam, lädt jeder Lauf erneut.
- `actions/cache` speichert nur bei Erfolg. Ein roter Lauf verliert, was er schon geladen hat.
- `ops-scripts` hat gar keinen Cache.
- Ein veralteter Index liefert 404 (libegl-mesa0 auf 24.04, PR #591). Die Versuche wiederholen den Download mit
  demselben Index.

## Ziel & Nicht-Ziele
Ziel:
- Der Cache-Key folgt der Paketmenge. Er ist ein Hash über die Ausgabe von `apt-get install --print-uris`, also über
  Dateinamen, Größen und Hashes. Ein Treffer heißt: Alles Nötige liegt im Cache.
- Restore und Save laufen getrennt (`actions/cache/restore`, `actions/cache/save`).
- Ein gescheiterter Download sichert seinen Teilstand unter `<key>-partial-<run_id>`. Der nächste Lauf nimmt ihn
  über das Präfix in `restore-keys` und lädt nur den Rest.
- Nach einem gescheiterten Versuch frischt `apt-get update` den Index auf, bevor der nächste Versuch läuft.
- `ops-scripts` bekommt denselben Cache.

Nicht-Ziele:
- kein anderer Spiegel
- keine eigenen Paket-Images
- keine längeren Timeouts
- keine Änderung an `apt_archives_verify.sh`: Die SHA256-Prüfung gegen den signierten Index bleibt, wie sie ist.

## Betroffene Komponenten & Dateien
- `.github/scripts/apt_cache.sh` (neu, SPDX). Unterbefehl `key <prefix> <pkgs…>`: `apt-get update` unter retry, dann
  den Key aus `--print-uris` drucken. Unterbefehl `install <dir> <pkgs…>`:
  - verify
  - `--download-only` mit drei Versuchen zu je 180 s, nach jedem roten Versuch ein `update`
  - install
  - autoclean
  - chown
- `.github/workflows/ci.yml`: die vier Jobs auf key → restore → install → save umstellen. Save läuft mit
  `if: always()`, aber nicht bei exaktem Treffer.
- `apps/server/tests/test_apt_cache.py` (neu, SPDX): hermetische Tests des Skripts mit Attrappen für `sudo` und
  `apt-get` im PATH, dazu Strukturtests der vier Jobs in ci.yml.
- `docs/developer/cicd.html` und `docs/en/developer/cicd.html`, `changelog.d/ci-18.md`.

## Externe Integrationen
- `actions/cache/restore` und `actions/cache/save`: Unteraktionen von `actions/cache`, gepinnt auf denselben SHA
  (v6.1.0). Doku: https://github.com/actions/cache/tree/main/restore und …/save.
- Versucht ein Save einen bestehenden Key zu schreiben, meldet die Aktion nur eine Warnung (`rust` und `rdp-embedded`
  teilen ihren Key). Das ist vor dem Bau an der Doku zu prüfen.

## Trade-offs & Alternativen
- **Skript statt Inline-Shell (empfohlen):**
  - vier Jobs, eine Logik
  - hermetisch testbar
  - shellcheck läuft im Job ops-scripts schon über `.github/scripts/*.sh`
- **Composite-Action:** Der Save bei Fehlschlag hinge an Statusfunktionen innerhalb der Composite. Das ist schwerer zu
  belegen.
- **Key = Wochen-Key plus Save immer:** Das speichert jeden Lauf neu, ohne Bezug zur Paketmenge. Verworfen.
- Der Testort ist pytest unter `apps/server/tests`, wie die übrigen Workflow-Tests. Ein neuer `_test.sh` müsste in die
  Liste von `scripts/tests/run.sh`, einen Harness-Pfad.

## Risiken & Rollback
- **Cache-Vergiftung:** Ein PR-Lauf speichert nur in den Scope seines Refs. `main` liest ihn nicht. Jedes restaurierte
  `.deb` prüft `apt_archives_verify.sh` gegen den signierten Index, wie bisher.
- **Platz:** Teilstände belegen Cache-Speicher. GitHub verdrängt nach LRU (10 GB je Repo).
- **Rollback:** den Merge-Commit reverten.
