# Workflows: Download-Wiederholung und Job-Grenzen (ci-22)

Roadmap: R-1799 · Kevin 2026-11-26 („Zwei Zuege, jetzt bauen“; Kevin merged, Workflows)

## Problem / Motivation
Die Limits-Inventur vom 2026-11-26 fand in `.github/workflows/release.yml` fuenf frpc-Downloads (`curl -fsSL`)
ohne Wiederholung: ein einzelner Aussetzer von GitHub Releases bricht einen Release-Lauf ab. Die Jobs in
`audit.yml`, `docker.yml` und `release.yml` (bis auf einen) tragen kein `timeout-minutes`; ein haengender Schritt
haelt den Runner bis zum GitHub-Default von 360 Minuten.

## Ziel & Nicht-Ziele
- Ziel: jede curl in `release.yml` wiederholt (`--retry 5 --retry-connrefused --retry-all-errors
  --connect-timeout 30`); jeder Job der drei Workflows hat eine Grenze, grob das Dreifache der laengsten
  gemessenen Dauer.
- Nicht-Ziel: `ci.yml` (eigene Grenzen), Aenderung an Schritten oder Pins.

## Betroffene Komponenten & Dateien
`.github/workflows/release.yml`, `.github/workflows/audit.yml`, `.github/workflows/docker.yml`;
Test `apps/server/tests/test_ci_workflow.py`.

## Externe Integrationen
GitHub Actions `jobs.<job_id>.timeout-minutes` (Default 360). curl(1) `--retry`; lokal 2026-11-26 belegt, dass
`--retry` auch den Abbruch eines stehenden Transfers wiederholt (kern-netretry-1 T2).

## Trade-offs & Alternativen
Grenzen aus den letzten vier Laeufen je Workflow (max: Desktop Linux 16 min, Desktop Windows 20 min, uebrige
unter 3 min): desktop-linux 60, desktop-windows 90, agent 30, image-pins 15, release 30, audit-Jobs je 20,
docker build 60, latest 10. Knapper waere ein Fehlalarm bei kaltem Cache; der Gewinn liegt im Ende des
360-Minuten-Haengers, nicht in Minuten.
