Hooks & Events

Das Hook-System ist der Haupt-Integrationspunkt nach außen. Jedes relevante Ereignis im Server feuert ein Event, registrierte Scripts laufen in einer sanitisierten Subprozess-Umgebung mit harter Timeout-Grenze.

Architektur

tree
apps/server/app/modules/hooks/
├── router.py          /api/hooks CRUD
├── models.py          Hook
├── schemas.py         Pydantic-Schemas
├── scheduler.py       Schedule-Hook-Cron + Notification-Outbox
├── script_runner.py   Subprocess-Spawn (blockierend)
└── script_worker.py   Child-Prozess: stdin=JSON, stdout/stderr capture

Event-Katalog

EventPayload (Auszug)
connection.created / updated / deletedConnection-Objekt
connections.importedcount, mode
server.created / updated / deletedid, name (bei created zusätzlich hostname)
server.startup(kein event_data)
user.created / deletedid, username (bei created zusätzlich is_admin); created feuert POST /api/users und ebenso python -m app.cli create-admin (mit is_admin true)
user.promotedid, username — feuert, wenn PUT /api/users/{id} einem Benutzer das Admin-Recht gibt (is_admin von false auf true); eine Herabstufung feuert kein Event
frp.config.created / updated / deletedid, name
frp.tunnel.created / updated / deletedid, name (bei created zusätzlich serverId)
playbook.created / updated / deletedid, name
alert.triggeredserver_id, severity, title, message — feuert bei einem Übergang nach critical (monitoring.check.transition) eines Checks mit severity critical; Checks mit severity warning oder info und Entwarnungen (critical → ok) feuern nicht. Eine Sammelmeldung über mehrere Server (etwa mehrere stumme Agents) feuert ihn einmal je Server, jeweils mit dessen server_id; title und message sind dann bei allen Aufrufen gleich und nennen keinen Server. Der Hook folgt der Glocke und damit ihrem Cooldown von 30 Minuten je Check (Admin-Doku Monitoring, Cooldown): Geht ein Check binnen 30 Minuten erneut nach critical, etwa critical → ok → critical, feuert er nur beim ersten Mal, und ein Server, dessen Heartbeat bei einer Sammelmeldung im Glocken-Cooldown steht, bekommt keinen Aufruf; die Eskalation warning → critical feuert auch im Cooldown

Hook-Definition

json
{
  "name": "Slack-Alert",
  "hook_type": "event",
  "event_triggers": ["server.updated"],
  "script": "http_post('https://hooks.slack.com/services/T000/B000/XXX', json_data={'text': f'AdminHelper: {event_type}'})\nresult['notified'] = True"
}

Das script-Feld ist Python (kein Shell), das der Worker per exec() ausführt. Die Context-Keys des Events stehen als Variablen bereit (bei event-Hooks event_type und event_data, bei schedule triggered_at/last_run als RFC-3339-Strings in UTC mit Z, last_run vor dem ersten Lauf None, bei webhook payload/headers/params); Ausgaben laufen über das result-Dict und log(...), alle bereitgestellten Namen stehen unter Helfer im Script. Aus Sicherheitsgründen ist headers auf eine Safe-Liste beschränkt (content-type, user-agent, x-hook-source) — client-gesetzte Header wie Authorization, Cookie und X-Forwarded-* gelangen nie ins Script. Der gesamte Context wird als JSON an den Worker übergeben (json.dumps mit default=str), daher überleben nur JSON-native Typen — nicht-native Werte in event_data (datetime, Decimal, bytes, ORM-Objekte) erreichen das Script als ihre str()-Form, nicht als Originaltyp.

Helfer im Script

Neben den Context-Keys stellt der Worker (apps/server/app/modules/hooks/script_worker.py) jedem Script diese Namen bereit:

  • load_connections() liefert alle Verbindungen als Liste von Dicts. save_connections(list) gleicht die Verbindungen mit der Liste ab (Upsert): vorhandene IDs werden aktualisiert, neue eingefügt, und Verbindungen, die in der Liste fehlen, gelöscht. uuid4() liefert eine neue UUID als String.
  • http_get(url, headers=None, timeout=10) und http_post(url, json_data=None, headers=None, timeout=10) liefern ein Dict mit status, body und json (None, wenn der Body kein JSON ist). Sie lehnen ein Ziel ab (SSRF-Schutz), wenn eine seiner aufgelösten Adressen privat, Loopback, Link-Local, reserviert, Multicast oder unspezifiziert (0.0.0.0, ::) ist oder in 0.0.0.0/8 oder 100.64.0.0/10 liegt; IPv4-gemappte IPv6-Adressen zählen wie ihre IPv4-Adresse. Abgelehnt wird auch eine URL, die sich nicht lesen lässt oder keinen Host hat, und ein Name, der sich nicht binnen 5 s auflösen lässt. Sie folgen keinem Redirect. Ein abgelehntes Ziel und eine Antwort über 1 000 000 Bytes werfen einen ValueError. Bei einem abgelehnten Ziel nennt sein Text vom Ziel nur den Hostnamen, ohne Port, Pfad, Query und Zugangsdaten (?, wenn die URL keinen lesbaren Host hat). Die Anfrage geht an eine der bei der Prüfung aufgelösten Adressen, der Reihe nach, bis eine die Verbindung annimmt, und Host-Header und TLS-Name (SNI und Zertifikatsprüfung) bleiben der Hostname der URL; ist für das Schema der URL ein Proxy gesetzt (HTTP_PROXY oder HTTPS_PROXY, die der Hook-Runner durchreicht), verbindet wie bisher der Proxy und löst den Namen selbst auf, geprüft wird das Ziel auch dann vorher; ein Ziel, das wegen NO_PROXY nicht über den Proxy geht, verbindet wie ohne Proxy zu einer der geprüften Adressen.
  • result (Dict) geht an den Aufrufer zurück. log(msg) und print(...) schreiben eine Zeile in logs (Liste), nicht nach stdout; gespeichert werden höchstens 1000 Zeilen zu je 4096 Zeichen, längere Zeilen werden gekürzt, weitere verworfen.
  • Trägt ein Context-Key den Namen eines dieser Helfer, bricht der Hook mit Fehler ab, bevor das Script läuft.

Environment-Modell

Hook-Scripts laufen in einem eigenen Python-Subprozess mit reduziertem Environment, den run_hook_script in apps/server/app/modules/hooks/script_runner.py startet — das ist Crash-/Timeout-Isolation, kein Security-Sandbox:

  • Reduziertes Env: Der Worker bekommt PATH, HOME (fehlt es dem Server, DATA_DIR/hooks-home: beim ersten Lauf mit Modus 0700 angelegt, weitere Rechte nimmt der Runner wieder weg; ist das Verzeichnis nicht nutzbar, scheitert der Lauf mit einem Fehler), LANG (fehlt es dem Server, C.UTF-8), PYTHONPATH (das Server-Verzeichnis), PYTHONNOUSERSITE=1, DATABASE_URL und DATA_DIR. Der Worker startet mit python -s und lädt keine Python-Pakete aus dem Benutzerverzeichnis ($HOME/.local/lib/python3.X/site-packages, samt usercustomize); PYTHONNOUSERSITE=1 gilt ebenso für Python-Prozesse, die das Script startet. Pakete für Hooks gehören ins Image. HTTP_PROXY, HTTPS_PROXY und NO_PROXY, auch kleingeschrieben, reicht der Runner nur durch, wenn der Server sie gesetzt hat, damit http_get und http_post einen konfigurierten Proxy nutzen. Alles andere fällt weg, etwa ADMIN_PASSWORD, MONITOR_API_KEY und REDIS_URL. SECRET_KEY und die DB-Zugangsdaten bleiben aber erreichbar (über DATA_DIR/.secret_key bzw. DATABASE_URL) — kein Secret-Jail.
  • CWD ist das Server-Verzeichnis (server_dir), kein Temp-Verzeichnis.
  • Timeout: Default 30 s. Der Worker läuft in einer eigenen Prozessgruppe (start_new_session=True); läuft der Timeout ab, killt der Runner die ganze Gruppe. Damit sterben auch Kindprozesse, die das Script gestartet hat, außer solchen, die eine eigene Session oder eine eigene Prozessgruppe öffnen. Der Hook endet dann mit success: false und error: "Timeout nach 30s". Nach dem Ende des Workers wartet der Runner höchstens 2 s auf den Rest der Ausgabe; hält ein Kindprozess stdout oder stderr länger offen, killt er die Gruppe und wartet noch einmal höchstens 2 s. Danach wertet er aus, was er bis dahin gelesen hat: Hat der Worker sein Ergebnis vor seinem Ende geschrieben, kommt es auch dann an, wenn ein Kindprozess in eigener Session die Ausgabe weiter offen hält. Den Payload schreibt der Runner nebenläufig; liest der Worker stdin nicht, begrenzt der Timeout auch das Schreiben. Ein Lauf dauert so höchstens 34 s und endet vor dem Lese-Timeout des Gateways von 60 s.
  • Ausgabe-Limit: Der Runner liest stdout und stderr des Workers je bis 8 388 608 Zeichen, bei ASCII 8 MiB. Liest er mehr, killt er die ganze Prozessgruppe des Workers; der Hook endet dann mit success: false und error: "Hook-Ausgabe zu gross (Limit ueberschritten)". Auf stdout schreibt der Worker seine JSON-Antwort samt result und logs; ein sehr großes result zählt also mit.
  • Kein User-Switch: Der Worker läuft als derselbe Benutzer wie der Server.
  • Parallelität: Jeder Server-Prozess lässt höchstens 8 Hook-Prozesse gleichzeitig laufen; die Grenze gilt je Prozess, nicht für den ganzen Server. Hooks laufen in jedem Uvicorn-Worker (WEB_CONCURRENCY, Default 1) und im eigenen Scheduler-Dienst (RUN_MODE=scheduler), der die Schedule-Hooks startet; jeder dieser Prozesse hat seine eigenen 8 Plätze. Sind alle Plätze eines Prozesses belegt, wartet ein weiterer Aufruf nicht, sondern endet sofort mit success: false und error: "Server ausgelastet (Hook-Limit erreicht)".
Kein vollständiger Sandbox

Die Hook-Isolation ist Defense-in-Depth, nicht ein Seccomp/Namespace-Jail. Admins mit Hook-CRUD-Rechten können beliebigen Code auf dem Server-Host ausführen. Hook-Zugriff daher nur vertrauenswürdigen Rollen geben.

Fehlerverhalten

Scheitert ein Event- oder Schedule-Hook (success: false, etwa durch eine Exception im Script, einen Exit-Code ungleich 0, einen Timeout, das Ausgabe-Limit oder das Hook-Limit), schreibt der Server eine Zeile auf WARNING mit dem Namen des Hooks, bei Event-Hooks dem Event, und dem error-Text; von einem Text über 1 000 Zeichen steht nur dessen Ende im Log, die letzten 1 000 Zeichen hinter …. Event-Hooks loggen unter app.core.events im Log des server-Dienstes, Schedule-Hooks unter app.modules.hooks.scheduler im Log des scheduler-Dienstes. Ein Webhook-Trigger und ein Lauf über POST /api/hooks/{id}/run melden den Fehler nur in der Antwort (success: false, error), nicht im Log. Einen automatischen Retry oder ein hook.failed-Meta-Event gibt es aktuell nicht; ein fehlgeschlagener Hook blockiert weder andere Hooks noch den auslösenden Request.

Bricht ein Hook mit einem Fehler der Datenbankanbindung ab (sqlalchemy.exc.SQLAlchemyError oder psycopg.Error), nennen error und die Log-Zeile Fehler: … in logs nur den Typ des Fehlers, etwa OperationalError, nicht den Text des Treibers. Jeder andere Fehler eines Hooks erscheint dort mit seinem Text.

Eigene Events feuern

Interner Code kann jederzeit Events feuern:

python
from app.core.events import fire_event

fire_event("server.updated", {"id": server.id, "name": server.name})

fire_event ist non-blocking: Der Dispatch läuft im Thread-Pool, der Aufruf kehrt sofort zurück. Die HTTP-Response des Auslösers wartet also nicht auf den Hook.

Test-Execution

Im Web-Panel startet „Ausführen“ einen Hook von Hand über POST /api/hooks/{id}/run; der Endpunkt verlangt Admin-Rechte. Der Context enthält dabei keine Event-Daten, er ist so belegt, wie die API-Referenz es für diesen Endpunkt beschreibt. Sobald der Lauf endet, zeigt ein Dialog das Ergebnis als JSON: success, result, logs und bei einem Fehler error. Eigene Felder für stdout, stderr oder exit_code gibt es nicht; endet der Worker-Prozess mit einem Exit-Code ungleich 0, steht sein stderr in error und logs.
