CI/CD & Release

GitHub Actions baut und testet alle Komponenten, pusht die Server- und Monitoring-Images in die GitHub Container Registry (ghcr.io) und legt bei einem Versions-Tag ein Draft-Release mit Desktop- und Agent-Artefakten an.

Workflows

WorkflowAufgabe
ci.ymlLint & Tests aller Komponenten: Server-pytest (Postgres-Service, Python 3.12/3.13), Monitoring-pytest (Postgres-Service für den Migrations-Smoke-Test), Go-Agent (gofmt/vet/test), Desktop-UI & Web-Panel (svelte-check/eslint/vitest, Playwright-E2E), Rust/Tauri (fmt/clippy/test). Zusätzliche PR-Gates gegen „grün-aber-kaputt": cargo test --locked auf Windows, die Go-Suite nativ unter Windows (Job agent-windows: go test -v ./..., Build und version-Smoke der .exe), cargo tauri build-Smoke auf Linux (Debug, nur deb), Docker-Builds beider Images ohne Push, FRP-Pin-Konsistenz-Check (FRP_VERSION + SHA-256 in ci.yml/release.yml/docker-compose.yml/crabbox_bootstrap.sh). Coverage läuft in den Test-Jobs report-only mit (kein Gate). Auf main-Pushes + manuell (bewusst noch kein PR-Gate, da Image-Build + 5-Container-Boot): ein From-outside-Integrationstest (scripts/tests/integration_stack_test.sh), der den echten Stack mit erzwungenem mTLS hochfährt und nur über das nginx-Gateway den vollen Pfad prüft – Enrollment-Token, CSR → Enroll-Plane (:8444) → Client-Cert, certless → abgewiesen, Cert+JWT → 200. Der Desktop-E2E (WebdriverIO + tauri-driver unter xvfb, apps/desktop/e2e/) läuft bewusst nicht in CI, sondern lokal/manuell (cd apps/desktop/e2e && xvfb-run -a npm test): die headless-WebKit-Kette (tauri-driver → WebKitWebDriver → WebKit) driftet mit Runner-Image + ungepinnten Upstream-Tools und färbte main rot ohne echten Defekt. Der schwere Tier (Multi-Host-Stack, mTLS über einen echten Netz-Hop, Desktop-GUI) läuft stattdessen auf crabbox (ephemere Proxmox-VMs) – siehe DEVELOPMENT.md und die /test-Skill
docker.ymlServer- + Monitoring-Image bauen & nach ghcr.io/admincave/adminhelper/{server,monitoring} pushen; jeden Digest schlüssellos mit cosign signieren (+ SLSA-Provenance/SBOM)
release.ymlDesktop-DEB/RPM/Binary, Go-Agent-DEB/RPM + Linux/Windows-Binaries, Windows-MSI (best-effort), SHA256SUMS (+ minisign-Signatur), Draft-Release. Jobs: desktop-linux, agent, agent-windows-smoke (hart – führt die gebaute .exe einmal aus), desktop-windows (best-effort, installiert und deinstalliert das MSI), release. Die Assertionen stehen unten unter „Release-Assertionen".
audit.ymlWöchentlicher Dependency-Audit (Montag früh, auch manuell per workflow_dispatch): pip-audit (Server- + Monitoring-Locks), cargo audit (Desktop), govulncheck (Agent), npm audit (Web + Desktop-UI)

Test-Aggregator (scripts/tests/run.sh)

Ein Einstiegspunkt für alle Suiten – lokal, auf einer crabbox-VM und im CI-Job ops-scripts. Der Aufruf ist bash scripts/tests/run.sh [layer] [flags]; Layer sind lint, unit, quick (Default), integration, e2e, all. Die schweren Layer verweigern ohne AH_ALLOW_REAL=1.

Flag / EnvWirkung
--strictEin SKIP eines Pflicht-Schritts ist ein Fehler, kein PASS. Ebenso ein strenger Lauf, in dem überhaupt kein Schritt lief.
--only <keys…>Beschränkt lint/unit auf Komponenten (server monitoring ca-issuer agent desktop desktop-rs desktop-ui desktop-e2e web scripts). Unter --strict gilt ein so angeforderter Schritt als Pflicht. Env-Form: AH_ONLY.
--step <name>Genau ein Schritt (Teilstring seines Namens). Ein unbekannter oder mehrdeutiger Name wird in einem Trockenlauf abgelehnt, bevor eine Suite startet.
AH_REQUIREDDie Pflicht-Menge dieses Rechners (Step-Ids, Leerzeichen-getrennt), überschreibt AH_REQUIRED_DEFAULT; gehört in die gitignorete .devenv.sh. Die wirksame Menge steht unter --strict in der Summary.
AH_ARGSZusätzliche Argumente für die Suite selbst (so reicht verify.sh <komp> -- <args> sie durch).

Exit 75 heisst SKIP. Ein Skript, dem eine Voraussetzung fehlt, endet mit 75 (EX_TEMPFAIL) und wird als SKIP gezählt. Ein blankes exit 0 wäre ein grünes PASS, obwohl nichts lief – so blieben die sieben Desktop-GUI-Suiten und agent_install_test.sh monatelang unsichtbar. Die minisign-Weichen in install_test.sh / update_test.sh waren der schärfere Fall: sie meldeten PASS, nachdem sie den Signaturpfad neutralisiert hatten. SKIP heisst nicht verifiziert.

test-skips. Auch innerhalb einer grünen pytest-Suite kann ein einzelner Test stillschweigend übersprungen werden. Unter --strict laufen die Python-Suiten mit -rs, und run.sh wertet die Skip-Zeilen aus: ist die Vorbedingung eines Pflicht-Tests erfüllt und er skippt trotzdem, endet der Lauf mit strict-failed: <test> (test-skip). Vorbedingungen sind das, worauf der Test selbst prüft – DATABASE_URL für test_migrations_smoke, ein erreichbares Redis für test_stream_redis, ein Postgres in AH_TEST_DB für test_db_token_store, eine erreichbare Datenbank (oder Docker) für test_auth_token_lifecycle. Auf einer Box, die einen Test wirklich nicht fahren kann, bleibt er ein sichtbarer SKIP.

Die Summary lautet deshalb N passed, M failed, K skipped, J test-skips, R reruns. reruns bleibt bewusst 0: der Wochenlauf wiederholt einen roten Schritt selbst und klassifiziert ihn, statt die Suiten heimlich retryen zu lassen (siehe „Wochenlauf").

Go unter -race. Der Go-Schritt fährt go test -race -cover, wenn die Box einen C-Compiler mit aktivem cgo hat – der Agent ist nebenläufig (Monitor, frpc, Config), und ein Data-Race ist die Fehlerklasse, die weder ein Review noch ein einfädiger Test sieht. Fehlt der Compiler, läuft die Suite wie bisher und der Lauf sagt es (race: off (no gcc)) – ein grüner Lauf, der weniger geprüft hat, muss unterscheidbar bleiben. Der CI-Job agent hat cgo immer und fährt -race unbedingt.

Upgrade-Pfad. Der integration-Layer enthält scripts/tests/upgrade_path_test.sh – die einzige Suite, die nicht bei null anfängt: sie fährt den Stack aus den Images des letzten veröffentlichten Releases hoch, seedet ihn über die Admin-API, wechselt auf die aus dem Checkout gebauten Images (beide Dienste migrieren beim Start) und prüft, dass die Seeds lesbar bleiben und ein frischer Agent-Report ankommt (UPGRADE_OK). Danach läuft scripts/update.sh --ref <tag> real gegen ein zweites Install-Verzeichnis (UPDATE_SH_OK, oder UPDATE_SH_SKIP, wenn das Release kein Runtime-Bundle hat). Ohne Docker oder Netz endet sie mit 75.

Evidenz. Jeder Lauf schreibt $AH_OUT_DIR/last-<layer>.json (Default .crabbox-out/, gitignored) mit Layer, Flags, Pflicht-Menge, Zeitstempeln, jedem Schritt samt Ergebnis und Dauer, den test-skips – und mit head plus tree_hash. Den Tree-Hash liefert scripts/dev/tree-hash.sh: er wird in einem Wegwerf-Index gebildet, sieht also auch untracked Dateien, während tasks/ und die Ausgabeverzeichnisse ausgeklammert bleiben. Ein Haken im Ledger ändert die Evidenz eines Laufs damit nicht, eine neue, noch nicht committete Quelldatei sehr wohl.

Wochenlauf (scripts/tests/heavy.sh)

Der schwere Tier lief bisher, wenn jemand daran dachte, und seine Ergebnisse wurden nirgends festgehalten. heavy.sh ist ein Wrapper um die vorhandenen crabbox-Skripte, der genau das nachträgt: einen Report, eine Historie und eine mechanische Klassifikation der roten Schritte der all-Ebene. (Wiederholung, Quarantäne und Zweit-VM hängen an dieser Ebene; die Capstone-Ebene meldet ihre roten Assertionen direkt als fail.) Er startet nie von selbst – Kevin startet ihn, üblicherweise in tmux, und liest hinterher den Report.

tmux new -d -s ah-weekly 'bash scripts/tests/heavy.sh weekly'

bash scripts/tests/heavy.sh all|capstone|weekly [--base <sha>] [--no-second-vm] [--notify]

all = warme Box → run.sh all --strict; capstone = crabbox_multibox.sh --capstone --strict; weekly = beides seriell. Der Capstone entfällt nur, wenn die all-Ebene UNVERIFIED endete (sieben VMs brennen sonst in eine kaputte Umgebung) – ein reines FAIL stoppt ihn nicht. Vorab prüft er crabbox doctor und crabbox list: eine fremde Box heißt, die Kapazität ist nicht da, und der Lauf bricht ab, bevor er eine VM verbraucht.

Der Report liegt unter .crabbox-out/weekly/<jjjj-mm-tt-hhmm>/report.md. Seine erste Zeile ist das Urteil und wird wörtlich zitiert, nie paraphrasiert; danach folgen die Summary-Zeilen der Wrapper wörtlich, die Schritt-Tabelle, der Abschnitt „Kevin sichtet", die Notizen, die audit.yml-Zeile und die VM-Liste. Nie eine Bewertung, nur Fakten. Die Historie steht in tasks/private/history.csv (datum,commit,tree_hash,ebene,schritt,ergebnis,sekunden,vm) und wird im privaten Repo committet, nie gepusht.

ErgebnisWie es zustande kommtWas es heißt
infradie Box war nicht zu bekommen oder der Schritt konnte nicht laufen: keine warme Box, Warm-Pond nicht bereit, fehlgeschlagenes Server-Lease, strict-failed: no step ran, strict-failed: … (SKIP), Wrapper-Exit 74Nie eine Regression; der Report-Kopf lautet UNVERIFIED.
flakyinnerhalb von drei Wiederholungen auf derselben Box grün (AH_NO_SYNC=1, Desktop-Suiten spec-genau)Quarantäne-Zeile in tasks/private/seen.md; der Lauf fällt deswegen nicht durch.
unbestaetigt3× rot, aber grün auf einer frischen zweiten VM – oder die Gegenprobe war nicht möglich: kein PASS-Commit in history.csv, --no-second-vm, Worktree nicht anlegbar, zweite Box nicht leasbar, Basis-Commit nicht auscheckbarKevin sichtet; nie eine REG-Zeile.
externrot auf der zweiten VM und auf dem letzten PASS-CommitUmgebung, Abhängigkeit, Netz – nicht der Code seit dem letzten PASS.
regrot auf der zweiten VM, grün auf dem letzten PASS-CommitRoadmap-Zeile (Klasse REG, Status neu) plus Kurz-Ledger tasks/reg-<datum>-<schritt>.md. Die Freigabe bleibt Kevins Haken.
failalle drei Wiederholungen rot, aber jedes Mal anders; jede rote Capstone-Assertion; die Ebenen-Zeile, wenn Schritte nach den Wiederholungen rot bleibenReproduzierbar kaputt, aber ohne die stabile Signatur, die eine Regressions-Behauptung braucht – keine Zweit-VM.

Die zweite VM ist ein Worktree .crabbox-worktrees/w2 mit eigener Lane (AH_LANE=w2, Pond ah-warm-w2); heavy.sh reapt diesen Pond und entfernt den Worktree selbst. Kevins eigene Warm-Box (ah-warm) bleibt unberührt. --base <sha> setzt den Vergleichs-Commit (Default: die jüngste history.csv-Ebenen-Zeile mit ebene=all,schritt=-,ergebnis=pass, nicht die eines einzelnen Schritts), --no-second-vm überspringt die Gegenprobe, --notify postet Urteilszeile und Report-Pfad an AH_NOTIFY_URL (Default aus).

Exit-Codes: 0 = PASS, 1 = FAIL, 74 = UNVERIFIED, 2 = Usage. UNVERIFIED heißt: die Infrastruktur ließ den Lauf nicht stattfinden, über den Code ist damit nichts bekannt. Genau diese Unterscheidung ist der Zweck: „SKIP heißt nicht verifiziert" gilt auch für einen ganzen Lauf.

Verify-Konvention (scripts/dev/verify.sh)

Die Verify:-Zeile einer Task ruft eine Komponenten-Suite immer in dieser Form auf:

bash
bash scripts/dev/verify.sh <komponente> [--strict] [--tree <pfad>] [-- <args>]

Das Skript sourct .devenv.sh (bzw. $AH_DEVENV), löst AH_TEST_DB auf, delegiert an run.sh quick --only <komponente> (also Lint und Unit dieser Komponente), läuft mit --tree gegen einen anderen Checkout und schreibt last-verify.json – das Lauf-Artefakt plus component, args, tree. Der Grund für den Wrapper ist die Allowlist: eine Bash-Allow-Regel matcht nie über ein Env-Präfix, source .devenv.sh && DATABASE_URL=… pytest ist also nicht freigebbar. Env-Bedarf löst das Skript auf, der Aufrufer schreibt Flags.

Container-Images (ghcr.io)

Getaggt wird über docker/metadata-action. :latest entsteht nur auf einem (Nicht-Prerelease-)Semver-Tag – nicht bei jedem main-Push:

text
ghcr.io/admincave/adminhelper/server:0.24.0      # Release-Tag
ghcr.io/admincave/adminhelper/server:latest      # letzter Semver-Release
ghcr.io/admincave/adminhelper/server:main        # letzter main-Build
ghcr.io/admincave/adminhelper/server:sha-abc1234 # pro Commit
# analog: ghcr.io/admincave/adminhelper/monitoring:…
Package-Sichtbarkeit

Neu erzeugte ghcr-Pakete sind privat. Nach dem ersten erfolgreichen docker.yml-Lauf müssen server und monitoring in den GitHub-Package-Einstellungen einmalig auf public gestellt werden – sonst schlägt docker compose pull für externe Nutzer mit unauthorized/manifest-unknown fehl.

Release-Artefakte

release.yml läuft auf Tag v* und hängt die gebauten Artefakte an ein Draft-Release (nicht veröffentlicht, bis ein Mensch „Publish" drückt):

  • Desktop-Client: .deb + .rpm (Tauri) + ELF-Binary
  • Go-Agent: .deb + .rpm + linux/windows-Binaries
  • Agent-Paket-Repo: adminhelper-agent-repo-<tag>.tar.gz (GPG-signiertes apt+rpm-Repo, sobald REPO_GPG_PRIVATE_KEY gesetzt) — zusätzlich der Archive-Keyring adminhelper-archive-keyring.gpg als eigenständiges Asset (zweiter Kanal, um seinen Fingerprint gegen SHA256SUMS + minisign zu prüfen)
  • Desktop-Client Windows-.msi (best-effort – blockiert das Release nicht, wenn der Windows-Build fehlschlägt)
  • SHA256SUMS über alle Assets – plus SHA256SUMS.minisig (minisign-Signatur), sobald scharf geschaltet

Die Agent-Version wird aus dem Tag abgeleitet (${GITHUB_REF_NAME#v}) und per -ldflags "-X main.version=$VERSION" in die Binaries geschrieben. Die tauri-cli wird in CI und Release auf eine exakte Version gepinnt (cargo install tauri-cli --locked --version …), damit ein neues CLI-Release keinen Tag-Build brechen kann.

Release-Assertionen

Alle sechs release-blockierenden Defekte der 0.43.x/0.44.0-Reihe kamen aus Ausführung, keiner aus statischer Review. release.yml prüft deshalb das Ergebnis, nicht das Rezept:

  • Agent statisch. Nach dem Build muss file das Binary als statically linked melden und objdump -T darf kein GLIBC_-Symbol liefern. Das Makefile pinnt CGO_ENABLED=0, aber geprüft wurde das Ergebnis nie: ein inline gebautes go build lieferte ein dynamisch gegen glibc 2.39 gelinktes Binary, das auf älteren Distributionen nicht startete – während die crabbox-Tests, die make benutzen, grün blieben.
  • Ausgeliefertes .deb. ar t auf dem Artefakt, das hochgeladen wird: kein .zst-Member. build-deb.sh prüft seine eigene Ausgabe; hier wird geprüft, was tatsächlich im Release landet.
  • Signatur gegen den gepinnten Key. Direkt nach minisign -S wird die frische Signatur mit dem MINISIGN_PUBKEY aus scripts/update.sh verifiziert. Ein rotiertes oder falsches MINISIGN_SECRET_KEY erzeugt eine völlig gültige Signatur, die install.sh/update.sh ablehnen – das fällt sonst erst auf Nutzer-Maschinen auf, nach dem Veröffentlichen.
  • Windows-Binary läuft. Der harte Job agent-windows-smoke (windows-latest, nur auf Tags) lädt das Agent-Artefakt und führt adminhelper-agent-windows-x86_64.exe version aus; die Ausgabe muss die Tag-Version nennen. Der Draft-Job gated darauf.
  • MSI installiert und deinstalliert. desktop-windows installiert das MSI still (msiexec /i … /qn /norestart /l*v), prüft die Erfolgszeile im Log und die installierte adminhelper.exe (deren Installationspfad noch unverifiziert ist – der Job sucht deshalb ProgramFiles, ProgramFiles(x86) und LOCALAPPDATA\Programs ab) und deinstalliert wieder; msi.log geht als eigenes Artefakt hoch (nie als Release-Asset). Der Job bleibt continue-on-error bis zur Windows-VM – ein rotes MSI ist sichtbar, blockiert aber nicht.
  • Versions-Stellen. bash scripts/release/check-versions.sh ${GITHUB_REF_NAME#v} prüft alle sechs handgepflegten Stellen statt nur tauri.conf.json und druckt je Stelle ok/MISSING. Genau dieser Aufruf gehört vor den Tag – was dort rot ist, bricht hier den Draft ab.

Release-Signatur (Supply-Chain)

Die curl|bash-Installation/-Updates sollen Authentizität belegen, nicht nur Transport-Integrität (Bundle und SHA256SUMS kommen sonst aus derselben Quelle). Zwei Mechanismen:

  • Container-Images: docker.yml signiert jeden gepushten Image-Digest schlüssellos mit cosign (GitHub-OIDC, kein privater Schlüssel) und hängt SLSA-Provenance (mode=max) + SBOM an. Prüfen: 
    cosign verify ghcr.io/admincave/adminhelper/server \
  --certificate-identity-regexp 'https://github.com/AdminCave/AdminHelper/.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
  • Release-Assets: release.yml signiert SHA256SUMS mit minisign zu SHA256SUMS.minisig – und verifiziert die frische Signatur sofort gegen denselben Public Key, den scripts/update.sh pinnt, sodass ein falsches Secret den Draft abbricht statt die Nutzer. install.sh/update.sh verifizieren diese Signatur gegen einen im Skript gepinnten Public Key, bevor sie den Checksummen vertrauen (fail-closed).
Scharfschalten (Maintainer, einmalig)

Dieses Repo ist scharfgeschaltet: der Key ist gepinnt, die Prüfung ist damit fail-closed – eine fehlende/ungültige Signatur bricht install.sh/update.sh ab, und der Release-Workflow schlägt ohne MINISIGN_SECRET_KEY fehl. Ein Fork ohne eigenen Key fällt bis zur Aktivierung auf reine Checksummen-Prüfung zurück (mit Warnung). Zum Aktivieren eines Forks:

minisign -G -W                 # passwortloses Keypair erzeugen
# 1) Secret-Key-Datei base64-kodiert als GitHub-Actions-Secret hinterlegen
#    (eine Zeile, paste-sicher — ein roher mehrzeiliger Key wird sonst verstuemmelt):
#    base64 -w0 minisign.key | gh secret set MINISIGN_SECRET_KEY
# 2) Public Key (die "RW…"-Zeile aus minisign.pub) in
#    MINISIGN_PUBKEY in scripts/install.sh UND scripts/update.sh pinnen

Repo-Signatur (Agent-Paket-Repo)

release.yml baut zusätzlich ein GPG-signiertes apt-/rpm-Repo (apps/agent/build-repo.sh: InRelease/Release.gpg, rpm --addsign + repomd.xml.asc) und hängt es als ein Asset adminhelper-agent-repo-<tag>.tar.gz ans Release – in SHA256SUMS + minisign mit abgedeckt. Der Server liefert es über die certless Repo-Plane des Gateways (:8445) aus; install.sh/update.sh ziehen das Asset nach ./repo. Agent-Hosts vertrauen dem GPG-Fingerprint (Vertrauenswurzel), nicht dem Transport (siehe Agent-Deployment).

Scharfschalten (Maintainer, einmalig)

Ohne konfigurierten Schlüssel überspringt release.yml das Repo-Asset (mit Warnung) und /repo liefert 404 – kein Bruch. Zum Aktivieren einen passwortlosen GPG-Schlüssel erzeugen:

# 1) Passwortlosen Signaturschluessel erzeugen
gpg --batch --passphrase '' \
    --quick-generate-key "AdminHelper Repo <repo@admincave.com>" rsa3072 sign 0

# 2) Geheimen Schluessel base64-kodiert als GitHub-Actions-Secret hinterlegen
#    (eine Zeile, paste-sicher):
gpg --export-secret-keys --armor <KEYID> | base64 -w0 | gh secret set REPO_GPG_PRIVATE_KEY

# 3) Fingerprint pinnen: in agent-deployment.html (DE+EN) den Platzhalter
#    <REPO-GPG-FINGERPRINT> durch diesen Wert ersetzen:
gpg --fingerprint <KEYID>
Schlüssel-Rotation (Überlappungsphase)

Bei Ablauf oder Kompromittierung des Signaturschlüssels dürfen die Clients nicht flottenweit brechen: sie pinnen per Signed-By= (apt) bzw. importiertem RPM-Key den alten Schlüssel, und der einzige Nachladeweg für den neuen Keyring ist ausgerechnet das Repo, dem sie ohne Überlappung gerade nicht mehr trauen. Daher in zwei Schritten rotieren:

  1. Überlappen: Neuen Schlüssel erzeugen (wie beim Scharfschalten). Weiterhin mit dem alten signieren (REPO_GPG_KEY_ID=<OLD>), aber beide Public Keys ausliefern: REPO_GPG_EXPORT_IDS="<OLD> <NEW>". Ein Release ausrollen – jeder Host bekommt den neuen Key in seinen Keyring und vertraut ab sofort beiden.
  2. Umschalten (nachdem die Flotte das Überlappungs-Release gezogen hat): mit dem neuen Schlüssel signieren (REPO_GPG_KEY_ID=<NEW>), nur noch den neuen ausliefern (REPO_GPG_EXPORT_IDS=<NEW>) und den Fingerprint in agent-deployment.html (DE+EN) aktualisieren. Der alte Schlüssel kann danach widerrufen werden.

Version-Stellen

Bei einem Release muss die neue Version an mehreren Stellen parallel gesetzt werden – der Tag allein reicht nicht:

  • apps/desktop/src-tauri/tauri.conf.json + Cargo.toml + Cargo.lock – Tauri-Bundle
  • apps/desktop/ui/package.json + apps/web/package.json (+ jeweils package-lock.json) – Vite-Builds
  • apps/desktop/ui/src/components/AppShell.svelte – Sidebar-Badge
  • apps/agent/build-deb.sh + build-rpm.sh – Default-VERSION (CI überschreibt sie aus dem Tag)
  • docs/**/*.html – Footer-<span>v0.24.0</span> + Landing-„Was ist neu" + Code-Samples
  • README.md – Agent-DEB-Install-Befehl
  • CHANGELOG.md – neuer Abschnitt am Anfang + Link-Ref

Der Server selbst hält keine eigene version – das Backend wird über den Docker-Image-Tag identifiziert.

Release-Checkliste

  1. Versionen in den oben gelisteten Dateien auf den Zielwert hochziehen.
  2. Footer-Versionen in docs/**/*.html aktualisieren (Footer-Span + Landing-„Was ist neu" + Code-Samples). Auf die Klasse filtern (grep -rl 'class="sidebar-footer"'), nicht auf das einzeilige Markup: die beiden Landing-Pages schreiben den Footer über zwei Zeilen und hingen deshalb von 0.43.2 bis 0.45.0 fest.
  3. CHANGELOG.md pflegen (Keep-a-Changelog: neuer Abschnitt + Link-Ref).
  4. bash scripts/release/check-versions.sh X.Y.Z – muss 0 missing melden. Derselbe Aufruf läuft im Release-Workflow auf dem Tag.
  5. Commit & Tag: git commit -am "release: v0.24.0" && git tag v0.24.0.
  6. git push --follow-tags.
  7. docker.yml + release.yml beobachten; nach dem ersten Image-Push die ghcr-Pakete (einmalig) auf public stellen.
  8. Im GitHub-Draft-Release die Notes prüfen, Pflicht-Assets gegenchecken und „Publish" drücken.
Draft statt Auto-Publish

Das Release wird bewusst als Draft erzeugt und der Release-Job ist erfolgs-gated auf die Pflicht-Linux-Builds. So lässt sich vor der Veröffentlichung prüfen, ob alle Pflicht-Artefakte (Linux-Desktop + Agent) wirklich angehängt sind – der Windows-MSI-Build ist best-effort und darf fehlen.
