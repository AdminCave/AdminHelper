API-Referenz

Alle HTTP-Endpoints des AdminHelper-Servers. Basis-URL: https://<host>. Das vollständige OpenAPI-Schema steht unter /api/docs (Swagger UI) bzw. /openapi.json.

Authentifizierung

Drei Mechanismen, je nach Aufrufer:

  • JWT-Bearer (Web-Panel, Desktop): Authorization: Bearer <access_token>. Access- und Refresh-Token kommen im JSON-Body; für Browser setzt der Server den Refresh-Token zusätzlich als HttpOnly-Cookie (Secure; SameSite=Strict, Pfad /api/auth) – Desktop/CLI senden ihn weiterhin im Body. Browser-Anfragen, erkennbar am Header Sec-Fetch-Site, bekommen den Refresh-Token nur als HttpOnly-Cookie; refresh_token im Body ist dann "". Für Desktop, CLI und Skripte (ohne diesen Header) bleibt alles unverändert.
  • API-Key (Agents, Drittanbieter): Header X-API-Key. Permission ist read oder read_write.
  • Internal-Key (nur Dienst zu Dienst, Monitoring → Server): Header X-Internal-Key mit dem gemeinsamen Secret MONITOR_API_KEY.

Das OpenAPI-Schema deklariert alle drei als Security-Schemes (HTTPBearer, ApiKey, InternalKey); die Swagger UI bietet sie unter „Authorize“ an.

Wo zwei Verfahren angenommen werden (Connections, FRP-Provisioning: /api/connections, /api/frp/provision), muss jede mitgeschickte Anmeldung gültig sein, sonst 401 – auch wenn die andere gültig ist. Als mitgeschickt gilt ein nicht leerer X-API-Key bzw. ?api_key= und jeder Authorization-Header außer Basic: Basic von einem Proxy oder aus user:pass@ einer Sync-URL wird ignoriert, jeder andere Authorization-Header muss ein gültiger Bearer sein – ein fremdes Schema, ein leerer oder unlesbarer Wert ergibt 401. Sind beide gültig, entscheidet der API-Key. Routen, die nur JWT annehmen, werten einen X-API-Key nicht aus.

Pagination (Listen-Endpunkte)

Die Listen-Endpunkte GET /api/servers, GET /api/connections, GET /api/hooks, GET /api/audit sowie die Monitoring-Listen (/api/monitoring/checks, /api/monitoring/status, /api/monitoring/alerts) akzeptieren optionale Query-Parameter limit (1–1000) und offset (≥ 0) und liefern im Header X-Total-Count die Gesamtanzahl vor der Pagination (der Monitoring-Proxy reicht den Header durch). Ohne Parameter liefern die kleinen Listen (servers/connections/hooks) die volle Liste; GET /api/audit deckelt dagegen ohne limit auf 200 Einträge, da der Trail unbeschränkt wächst (mehr via offset).

Zeitstempel

Zeitstempel in Antworten sind RFC 3339 in UTC mit Z, z. B. 2026-10-05T12:00:00Z – auch dort, wo das Schema sie als string führt. Ausnahmen:

  • lastUsed einer Connection ist ein gespeicherter String und kommt so zurück, wie er geschrieben wurde – der Server selbst schreibt +00:00, ein Client kann den Wert frei setzen.
  • lastStartTime/lastCloseTime von GET /api/frp/status reicht der Server unverändert von frps durch (etwa 09-27 10:00:00, ohne Jahr und Zone).
  • Das result von POST /api/hooks/{id}/run und /api/hooks/trigger ist, was das Skript zurückgibt.
  • data und statusHistory von GET /api/monitoring/checks/{id}/metrics sind Reihen aus VictoriaMetrics; ihre Werte sind Paare [epoch, "wert"] mit der Zeit in Unix-Sekunden.

Auth

POST/api/auth/login

Body: { "username", "password" }. Antwort: { "access_token", "refresh_token", "token_type" }; bei Browser-Anfragen (Header Sec-Fetch-Site) ist refresh_token "", der Token steht nur im HttpOnly-Cookie. Login-Rate-Limit: 5 Fehlversuche / 60 s / IP.

POST/api/auth/refresh

Body: { "refresh_token" } oder HttpOnly-Cookie (Browser, Body darf dann leer sein). Rotiert beide Tokens, blacklisted den alten jti. Antwort wie Login; bei Browser-Anfragen ist refresh_token "" und der neue Token steht nur im Cookie. Reuse eines bereits widerrufenen Refresh-Tokens invalidiert alle Sessions der betroffenen User-Kette.

POST/api/auth/logout

Authentifizierung optional. Blacklisted einen mitgesendeten Access-Token (Bearer) und den Refresh-Token aus Body ({ "refresh_token" }) oder HttpOnly-Cookie und löscht das Cookie. Ohne Bearer wirkt der Logout nur auf den Refresh-Token. Im Audit-Log (auth.logout) steht der Logout nur, wenn er einen Token gesperrt hat; die Antwort ist in jedem Fall 200. Die Bindung an das Client-Zertifikat prüft der Logout bewusst nicht: Er entwertet nur die vorgelegten Tokens, verleiht nichts und geht auch mit einem Zertifikat, das der Server nicht mehr annimmt.

GET/api/auth/me

Aktueller User; benötigt gültigen Access-Token. Antwort: { "id", "username", "is_admin", "idle_timeout_minutes" }; idle_timeout_minutes sind die Minuten ohne Bedienung, nach denen das Web-Panel abmeldet (WEB_IDLE_TIMEOUT_MINUTES, 0 = aus).

POST/api/auth/bootstrap

Legt beim ersten Start den ersten Admin-User per Setup-Token an (Status 201). Body: { "token", "username", "password" } – username 3–64 Zeichen, password 8–128 Zeichen. Antwort: { "access_token", "refresh_token", "token_type" } (wie Login, bei Browser-Anfragen also refresh_token ""). Der Setup-Token wird beim ersten Start ins WARNING-Log geschrieben (Hash unter DATA_DIR/.bootstrap_token) und nach erfolgreichem Bootstrap verbraucht. Es gilt dasselbe Login-Rate-Limit (5 Fehlversuche / 60 s / IP). Sobald ein User existiert, antwortet der Endpoint dauerhaft mit 409 Conflict („Server ist bereits initialisiert"); fehlt der aktive Token, kommt 401.

Users

GET/api/users

Liste aller User (admin).

POST/api/users

Neuen User anlegen (admin). Passwort: SHA-256-Prehash → Bcrypt. Feuert user.created.

PUT/api/users/{id}

User ändern (admin). Audit user.updated; detail nennt in dieser Reihenfolge, durch , getrennt, die geänderten Felder: password, wenn ein Passwort gesendet wurde, is_admin=true|false mit dem neuen Wert, wenn sich das Admin-Recht ändert, und server_ids, wenn sich die Server-Zuordnung ändert; sonst ist detail null. Feuert user.promoted, wenn is_admin von false auf true wechselt.

DELETE/api/users/{id}

User löschen (admin). Feuert user.deleted.

GET/api/users/{id}/devices

Geräte des Users (admin): je Geräte-Linie Art (desktop, browser), ob aus der Zeit vor dem Zertifikats-Register übernommen (legacy), Widerruf mit Grund (replaced, self, admin) und Fingerprint und Ablauf des jüngsten Zertifikats.

DELETE/api/users/{id}/devices/{device_id}

Ein Gerät des Users widerrufen (admin). Seine Zertifikate gelten ab sofort nicht mehr und lassen sich nicht erneuern; die übrigen Geräte bleiben. Audit device.revoked.

GET/api/users/me/servers

Eigene zugewiesene Server.

GET/api/hooks/{id}

Enable/Disable; aktualisiert Scheduler-Registrierung.

Webhook-Token erneuern.

Manueller Test-Lauf. Im Context sind payload, headers, params und event_data leer und event_type ist null; dazu kommen triggered_at (jetzt) und last_run (der letzte geplante Lauf in UTC mit Z, sonst null).

POST/api/hooks/trigger mit X-Hook-Token-Header (bevorzugt – Token nicht in Access-Logs/History), oder /api/hooks/trigger/{token} (Token im Pfad)

FRP – Server-Config

GET/api/frp/server-config
POST/api/frp/server-config

Schreibt zusätzlich frps.toml ins Shared-Volume. bind_port, vhost_https_port und dashboard_port liegen im Bereich 1 bis 65535, max_ports_per_client ist mindestens 0 (0 oder null: Standard 16); ein Wert außerhalb → 422. Ein dashboard_port gleich 443, gleich bind_port (ohne ihn 7000) oder gleich FRP_BIND_PORT → 422 auf dashboard_port, denn eine solche Konfiguration übernimmt frps nicht. extra_config nimmt nur die Schlüssel transport.maxPoolCount, transport.tcpMux, transport.tcpMuxKeepaliveInterval, transport.heartbeatTimeout, transport.tcpKeepalive, userConnTimeout, log.level und log.maxDays an, mit true, false, einer endlichen Zahl oder einem String ohne Anführungszeichen, Backslash, geschweifte Klammern und Steuerzeichen; ein anderer Schlüssel oder Wert → 422. { oder } in subdomain_host, dashboard_user, dashboard_password oder auth_token → 422, die Folge {{ in name oder server_addr ebenso (ein einzelnes { und }} bleiben dort erlaubt). Ein Steuerzeichen (U+0000 bis U+001F, U+007F bis U+009F) oder ein einzelnes Surrogat (U+D800 bis U+DFFF; JSON schreibt es nur als Escape, etwa \ud800) in einem Textfeld oder einem extra_config-Wert → 422.

GET/api/frp/server-config/{id}

Liefert die Tunnel der Config immer mit (tunnels).

PUT/api/frp/server-config/{id}

Übernimmt nur die gesendeten Felder, mit denselben Grenzen und Regeln wie POST (Wert außerhalb → 422). Ein ausdrückliches "bind_port": null → 422; fehlt das Feld, bleibt der Wert. null für vhost_https_port oder dashboard_port schaltet den Port ab. Sendet der PUT dashboard_port oder bind_port, gilt die Dashboard-Port-Regel des POST für den Stand nach dem Update, mit dem Bind Port, den frps bekommt (ein gespeicherter bind_port null oder außerhalb 1 bis 65535: 7000): → 422 auf dem gesendeten Feld (dashboard_port, sonst bind_port), und nichts vom Update wird gespeichert. Ohne beide Felder bleibt ein schon gespeicherter solcher Port unberührt. Ein auth_token mit null oder "" lässt das gespeicherte Token unverändert; ein neues braucht mindestens 16 Zeichen ohne Leerzeichen am Anfang und Ende, sonst → 422.

DELETE/api/frp/server-config/{id}

FRP – Tunnels

GET/api/frp/tunnels

Query: ?server_id, ?frp_config_id. Tunnel-Antworten liefern secretKey als null – hier, in /api/frp/status, /api/frp/server-config/{id} und /api/servers (frpTunnels). Das Secret steht nur in den erzeugten TOML-Dateien (/api/frp/generate/*) und im Provisioning (/api/frp/provision/{server_id}/config). Ein Admin bekommt alle Tunnel in dieser Form, ein Nicht-Admin nur die freigegebenen Tunnel seiner zugewiesenen Server, je nur mit id, serverId, name, tunnelType, protocol, localPort, visitorPort, customDomains, connectionId und enabled (was der Desktop liest); ohne zugewiesenen Server [], die Query-Parameter grenzen nur weiter ein. Die übrigen Tunnel-Routen: Nicht-Admin → 403.

POST/api/frp/tunnels

STCP (mit secret_key, visitor_port) oder HTTPS (custom_domains); ein HTTPS-Tunnel speichert weder Secret noch Visitor-Port, mitgeschickte Werte verwirft der Server. visitor_port ist ein Port von 1 bis 65535; fehlt er oder ist er null, vergibt der Server einem STCP-Tunnel einen freien. Ein anderer Wert, auch 0, → 422, auch bei einem HTTPS-Tunnel. local_port ist ein Port von 1 bis 65535, ein anderer Wert → 422. auto_create_connection=true erzeugt direkt eine passende Connection. Ein Steuerzeichen (U+0000 bis U+001F, U+007F bis U+009F), ein einzelnes Surrogat (U+D800 bis U+DFFF) oder die Folge {{ in name, local_ip, secret_key, custom_domains, auto_connection_username oder einem extra_config-Wert → 422, ebenso im PUT; ein einzelnes { und }} bleiben erlaubt. Ein extra_config-Schlüssel besteht aus Segmenten aus A-Z a-z 0-9 _ -, getrennt durch je einen . (also nicht .a, a. oder a..b); er darf, ohne Rücksicht auf Groß-/Kleinschreibung, weder einem Feld gleichen, das der Server in den Proxy schreibt (name, type, localIP, localPort, secretKey, allowUsers, customDomains), noch einem anderen Schlüssel, noch Präfix eines solchen sein oder einen als Präfix haben (etwa localport, localIP.x, foo neben FOO); eine Ganzzahl liegt zwischen -263 und 263-1. Sonst 422, ebenso im PUT. Ein Schlüssel, dessen erstes Segment plugin ist, gleich ob groß oder klein geschrieben (etwa plugin, plugin.type oder PLUGIN.type), → 422, ebenso im PUT: Proxy-Plugins richtet der Server nicht ein, und der Agent wendet eine frpc.toml mit einem solchen Schlüssel nicht an (siehe Agent). Eine connection_id, zu der es keine Verbindung gibt, ergibt 422.

GET/api/frp/tunnels/{id}
PUT/api/frp/tunnels/{id}

Ein secret_key mit null oder "" lässt das gespeicherte Secret unverändert; wird der Tunnel STCP und hat kein Secret, erzeugt der Server eins. Der Wechsel auf HTTPS löscht Secret und Visitor-Port; der Wechsel zurück auf STCP erzeugt ein neues Secret (sofern keins mitgeschickt wird) und vergibt einen freien Port, wenn der gespeicherte inzwischen belegt ist oder außerhalb 1 bis 65535 liegt. Ein mitgeschickter belegter Port bleibt 409. "visitor_port": null vergibt einem STCP-Tunnel einen freien Port. Ein visitor_port außerhalb 1 bis 65535, auch 0, → 422, und nichts vom Update wird gespeichert. Ein local_port außerhalb 1 bis 65535, auch null, → 422. Eine connection_id, zu der es keine Verbindung gibt, ergibt 422.

DELETE/api/frp/tunnels/{id}

FRP – Generate (TOML/ZIP)

GET/api/frp/generate/frps-toml?config_id=…
GET/api/frp/generate/frpc-toml/{server_id}

404, wenn der Server keinen aktiven, nutzbaren Tunnel hat; ein STCP-Tunnel ohne Secret zählt nicht, ebenso wenig ein gespeicherter Tunnel, dessen extra_config einen Schlüssel der plugin-Familie (erstes Segment plugin) oder einen anderen Eintrag trägt, den die API heute ablehnt; die frpc.toml lässt einen solchen Tunnel weg.

GET/api/frp/generate/visitor-toml?config_id=…&user_id=…

404, wenn kein nutzbarer STCP-Tunnel sichtbar ist, auch wenn die sichtbaren kein Secret oder keinen Visitor-Port von 1 bis 65535 haben: ohne Tunnel gibt es kein auth.token. Einen solchen Tunnel lässt die TOML weg.

GET/api/frp/generate/visitor-bundle?config_id=…

Liefert { toml, pki }; 404 wie bei visitor-toml.

GET/api/frp/generate/bulk-zip?config_id=…

ZIP mit frps.toml + clients/*.toml + visitors/*.toml — nur für Server bzw. Nutzer mit nutzbarem Tunnel (ein STCP-Tunnel ohne Secret zählt nicht, für clients/*.toml auch keiner, dessen gespeichertes extra_config einen Schlüssel der plugin-Familie oder einen anderen Eintrag trägt, den die API heute ablehnt, für visitors/*.toml auch keiner ohne Visitor-Port von 1 bis 65535).

Server-Provisioning (FRP-unabhaengig, ab v0.23.2)

POST/api/servers/{server_id}/provision/token

Admin-only (JWT). Liefert { token, expiresAt, serverId, serverName } – one-time, 24 h TTL. Audit provision.token.minted mit dem Server als Objekt und detail ttl=24h; weder das Token noch sein Hash steht im Eintrag.

GET/api/servers/{server_id}/provision/tokens
POST/api/servers/{server_id}/provision/activate

Header X-Provision-Token. Antwort: { serverName, apiKey, monitorApiKey?, monitorUrl?, frp?, enrollment }. apiKey ist immer der einmalig generierte Server-Read-API-Key. monitorApiKey/monitorUrl sind null, wenn der Monitor-Service nicht erreichbar ist; frp ist null ohne FRP-Config und hat sonst { config, pkiBundle } — config ist die frpc.toml (Base64), derselbe Text wie GET /api/frp/provision/{server_id}/config: Hat der Host keinen aktiven FRP-Tunnel, enthält er weder Tunnel noch frps-Zugangsdaten (siehe config-hash); pkiBundle ist seit A7 immer "" (der Agent enrollt sein Tunnel-Cert selbst). enrollment = { token, subjectId, scope:"tunnel", enrollPort }: der Einmal-Token, mit dem der Agent sein mTLS-Cert am ca-issuer holt (A4). Die Aktivierung löscht die API-Keys früherer Provisionierungen dieses Servers (Audit apikey.deleted); es gilt nur der neue.

POST/api/enrollment/token

JWT-gated, Selbstbedienung: ein angemeldeter User registriert ohne Admin ein weiteres eigenes Gerät. Unter MTLS_ENFORCE=true (Standard) erreicht nur ein Gerät mit gültigem Client-Zertifikat den Endpunkt; ein Gerät ohne Zertifikat registriert sich mit einem Token von /token/for. Mintet ein einmaliges, access-scoped Enrollment-Token für den eingeloggten User (CN = Username). Query ?browser=true → langlebiges Leaf für den Browser-P12-Export (A5). Audit enrollment.token.minted mit (self); bei browser=true vermerkt es wie /token/for das langlebige Leaf, das nur unter MTLS_ENFORCE=true widerrufbar ist. Antwort: { token, subjectId, scope, enrollPort, browser, expiresAt }; expiresAt ist der gespeicherte Ablauf des Tokens in UTC mit Z (hier immer 10 Minuten).

POST/api/enrollment/token/for

Admin-only. Mintet ein Enrollment-Token für eine andere, bereits existierende Identität (Body { username, browser?, ttl_minutes? }) — die entkoppelte Enrollment-Tür (ADR 0003): unter erzwungenem mTLS reicht ein Admin den Token out-of-band weiter, der neue Nutzer löst ihn certless an :8444 ein. CN = der Ziel-Username (issuer-diktiert). ttl_minutes ist die Gültigkeit des Tokens in Minuten, 1 bis 1440 (24 h), Standard 10; ein Wert außerhalb → 422. Audit enrollment.token.minted_for nennt die Gültigkeit (etwa browser=False, ttl=60min). Unbekannter User → 404, Nicht-Admin → 403. Antwort wie oben, expiresAt mit der gewählten Gültigkeit.

POST/api/enrollment/self/revoke

Das aufrufende Gerät widerruft sich selbst: die Geräte-Linie des Client-Zertifikats dieser Anfrage. Nachweis ist das Zertifikat (mTLS), kein JWT. 204; im permissiven Modus ohne verifiziertes Zertifikat 409 (erzwungen weist eine Anfrage ohne Zertifikat schon die Prüfung des Scopes ab); ein schon gesperrtes Zertifikat bekommt 403 ERR_CERT_REVOKED.

FRP – Sync (laufender Betrieb)

GET/api/frp/provision/{server_id}/config

Aktueller frpc.toml-Plaintext (JWT oder API-Key) – nur fuer den laufenden Sync. Ohne aktiven Tunnel des Hosts ist es der allgemeine Teil ohne Tunnel und ohne frps-Zugangsdaten (kein auth.token); ohne FRP-Config 404.

GET/api/frp/provision/{server_id}/config-hash

SHA-256 der frpc.toml zur drift-freien Synchronisation: { hash }, auch ohne aktiven Tunnel des Hosts der Hash genau des Texts, den GET …/config dann liefert. Aktiv ist ein eingeschalteter Tunnel, ein STCP-Tunnel nur mit Secret – genau die Tunnel, die als [[proxies]] in der frpc.toml stehen; die Provisionierung liefert denselben Text in frp.config. Ohne FRP-Config ist hash null statt eines Fehlers (nichts abzugleichen), und GET …/config antwortet mit 404.

FRP – Status

GET/api/frp/status

Merged frps-Dashboard mit DB-Tunneln.

GET/api/frp/supervisor-status

Admin-only. Zustand des frps-Supervisors aus seiner Statusdatei, nur Codes, Zeiten und ein Flag: { state, reason, since, stale, lastEvent, lastEventAt, publishedBindPort }. state ist waiting, running, degraded, stopped oder crashloop; missing, solange keine Statusdatei da ist, und unreadable, wenn sie nicht dem erwarteten Format entspricht – dann sind reason und since null. reason ist none, config_missing, token_invalid, tls_not_forced, cert_paths, cert_missing, cert_expired, cert_key_mismatch, verify_failed, input_unreadable (eine Eingabedatei ist da, aber nicht lesbar, keine reguläre Datei, ein Symlink oder größer als 1 MiB), input_unstable (die Eingabe ändert sich über mehrere Abfragen in Folge und wird nicht übernommen, bis sie gleich bleibt) oder processes_left (Prozesse des frps-Nutzers ließen sich nicht beenden; frps startet nicht, bis sich die Eingabe ändert oder der Container neu startet). lastEvent und lastEventAt sind das jüngste Ereignis (started, applied, rejected, stopped, crashed, copy_changed: die geprüfte Kopie, aus der frps startet, hat sich nach ihrer Übernahme verändert und wurde verworfen, oder start_refused: frps wurde nicht gestartet, Grund wie bei reason) und seine Zeit, ohne Ereignis null. stale ist true, wenn der letzte Herzschlag des Supervisors älter als 60 s ist. publishedBindPort ist der Host-Port, den Compose für frps veröffentlicht (FRP_BIND_PORT, Standard 7000). Nicht-Admin → 403.

Die früheren /api/frp/pki/*-Endpunkte (CA-/Cert-Erzeugung) sind entfernt – der Server signiert keine Zertifikate mehr (D6); die FRP-TLS-Materialien kommen ausschließlich vom ca-issuer.

Monitoring (Reverse-Proxy)

POST/api/monitoring/agent/{server_id}/report

Öffentlich (X-API-Key). Reicht den Agent-Push 1:1 an den Monitoring-Microservice durch.

GET/api/monitoring/{path:path}

Admin-only Reverse-Proxy. Erlaubt sind nur die Pfad-Prefixe checks, alerts, status, templates, maintenance, agent. Path-Traversal wird blockiert. Ist der Monitoring-Dienst nicht erreichbar, antwortet der Proxy mit 502, ohne Antwort binnen 30 s mit 504.

POST/api/monitoring/{path:path}
PUT/api/monitoring/{path:path}
DELETE/api/monitoring/{path:path}

Audit: Jedes POST, PUT und DELETE, auf das der Monitoring-Dienst antwortet, schreibt monitoring.post, monitoring.put bzw. monitoring.delete mit object_type monitoring, dem weitergeleiteten Pfad (kodiert, ohne Query) als object_label, detail status=<HTTP-Status> und status success (unter 400) oder failure. Bricht die Weiterleitung nach dem Senden ab (etwa ein Lese-Timeout), entsteht derselbe Eintrag mit status error und detail error=<Typname>; ein Verbindungsfehler (nichts gesendet), ein abgelehnter Pfad, GET und der Agent-Report schreiben nichts. Der Inhalt der Anfrage steht nie im Eintrag.

Keine eigenen alerts- oder settings-Endpoints im AdminHelper

Alerts und Check-Status werden über den Monitoring-Proxy aus dem separaten Service geliefert.

Notifications (ab v0.38.0)

GET/api/notifications

Glocken-Feed des aktuellen Users, neueste zuerst. Query: unread_only (bool, Default false), limit (1–1000), offset (≥0). Antwort: Liste der Notification-Objekte.

GET/api/notifications/unread-count

Schlanker Badge-Zähler für die Glocke. Antwort: { "count" }.

POST/api/notifications/read

Markiert Benachrichtigungen als gelesen. Body: { "ids": […] } – ids weglassen bzw. null markiert alle als gelesen.

GET/api/notifications/stream

Server-Sent-Events (text/event-stream): pusht ein „refresh"-Signal, sobald der User eine neue Benachrichtigung bekommt (Push statt Polling). Worker-übergreifend via Redis Pub/Sub. Das Gateway proxyt den Stream ungepuffert mit langem Read-Timeout; ein Heartbeat-Kommentar hält die Verbindung offen, die Auth (JWT/mTLS) wird periodisch re-validiert.

GET/api/users/me/notification-prefs

Abo-Regeln + Kontaktdaten des aktuellen Users.

PUT/api/users/me/notification-prefs

Replace-all: setzt email/telegram_chat_id (verbatim, null löscht) und ersetzt die Abo-Menge. Jede Subscription: scope_type (all/tag/server), scope_ref, min_severity (Default warning), optionaler categories-Filter.

POST/api/internal/events

Nur intern (Header X-Internal-Key): Event-Ingress für den Monitoring→Hub-Pfad. Body: { "event_type", "severity", "category", … }. Fächert das Event an die passenden Empfänger auf. Status 202, Antwort { "notified" }. Ein Sammel-Event nennt seine Server in source_ids (1–500 Server-IDs, je 1–256 Zeichen) statt in source_id; beide zusammen ergeben 422. Die source_type-Werte frp_config und frps sind Meldungen des Servers selbst vorbehalten und ergeben 422. Jeder Empfänger bekommt eine Zeile über die Server, die er sehen darf: Titel <title> (<n>), Text body plus eine Zeile je Server. title und body nennen deshalb keinen Server und tragen keine Gesamtzahl – Anzahl und Namen hängt der Server je Empfänger an. Den Hook alert.triggered feuert ein Sammel-Event einmal je Server.

Fehler-Format

json
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json

{
  "detail": [
    { "loc": ["body", "port"], "msg": "ensure this value is less than 65536", "type": "value_error" }
  ]
}

Fehler folgen Pydantic-Validations-Konventionen. Gibt ein 422 eine Eingabe mit einem einzelnen Surrogat zurück, schreibt der Body jedes Zeichen außerhalb von ASCII als JSON-Escape (\uXXXX).

Ein Fehler, auf den ein Client reagieren soll, trägt neben detail das Feld code: stabil, in der Form ERR_…. detail bleibt Text und beginnt aus Kompatibilität mit <code>: ; der Wortlaut dahinter kann sich ändern. Heute tragen die 403 der Zertifikatsprüfung einen Code: ERR_CERT_REVOKED (Zertifikat widerrufen oder nicht registriert), ERR_CERT_USER_MISMATCH (Zertifikat eines anderen Benutzers), ERR_CERT_SERVER_MISMATCH (Agent-Zertifikat eines anderen Servers). Clients verzweigen an code, nie am Text. Alle anderen Fehler haben kein code.

json
HTTP/1.1 403 Forbidden
Content-Type: application/json

{
  "detail": "ERR_CERT_REVOKED: This device certificate is no longer valid. Reset the device identity and register the device again.",
  "code": "ERR_CERT_REVOKED"
}

Rate-Limits

  • Login: 5 Fehlversuche / 60 s / IP (Redis, In-Memory-Fallback).
  • Webhook-Trigger: 20 Anfragen / 60 s / IP.
  • Agent-Push: nicht limitiert; jede Anfrage muss aber per X-API-Key auf die eigene server_id matchen.
