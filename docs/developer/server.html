Server (Backend)

Der Server ist ein FastAPI-Monolith: HTTP-Router, SQLAlchemy-Models, APScheduler-Jobs und FRP-PKI sind ein Code-Monolith — Separation by Module, nicht by Deployment. Für Skalierung laufen die Web-Worker und der Scheduler als getrennte Prozesse desselben Images (siehe Event-Bus & Scheduler).

Auth-Architektur

JWT-Access-Token (HS256, 8h) und Refresh-Token (7d) werden im JSON-Body ausgeliefert; der Refresh-Token wird zusätzlich als HttpOnly; Secure; SameSite=Strict-Cookie (Pfad /api/auth) gesetzt, das Browser-Clients statt localStorage nutzen (Desktop/CLI bleiben beim Body). Browser-Anfragen, erkennbar am Header Sec-Fetch-Site (setzt nur der Browser), bekommen den Refresh-Token nur als Cookie: refresh_token im TokenResponse ist dann "", das Schema bleibt gleich. Token-Claims: uid (ID des Kontos, users.id), sub (Username, nur für Logs), type (access/refresh), exp, iat (Ausstellzeit), jti (UUID). Der Server ordnet einen Token über uid seinem Konto zu; ein Token ohne uid (von einem älteren Server ausgestellt) gilt nicht, nach dem Update melden sich alle einmal neu an.

  1. Login signiert beide Tokens und gibt sie im TokenResponse zurück.
  2. Bei POST /api/auth/refresh prüft der Server Signatur, Ablauf und Blacklist.
  3. Der alte jti wird in token_blacklist eingetragen (Rotation); das neue Paar bekommt nur der Aufruf, der ihn einträgt. Ein zweiter, gleichzeitiger Refresh mit demselben Token zählt als Wiederverwendung wie ein späterer; Clients bündeln ihre Refreshes.
  4. Wird ein bereits widerrufener Refresh erneut eingereicht → Reuse-Detection: alle Sessions der betroffenen User-Kette werden invalidiert (WARNING-Log mit IP); das Konto bestimmt die uid des Tokens, nicht der Name.
  5. Passwort-Reset widerruft Sessions: ein Passwort-Wechsel setzt users.tokens_valid_after; jeder Token mit iat davor (oder ohne iat) wird abgelehnt — ohne dass einzelne jti bekannt sein müssen. Beim Anlegen eines Benutzers steht users.tokens_valid_after auf der Anlegezeit (ganze Sekunde): ältere Tokens auf denselben Namen gelten für ihn nicht.

Passwort-Hashing nutzt SHA-256-Prehash → Bcrypt, weil Bcrypt nur 72 Bytes verarbeitet.

API-Keys werden über den Header X-API-Key akzeptiert; die Dependency ApiKeyOrUser erlaubt JWT oder API-Key am selben Endpoint.

Rate-Limit & IP-Filter

Login-Limit (5 pro 60s/IP) und Webhook-Limit (20 pro 60s/IP) sind Redis-basiert mit In-Memory-Fallback. IP-Filter via ALLOWED_IPS (CIDR-Liste); Proxy-Trust über TRUSTED_PROXIES (sicher) statt TRUST_PROXY_HEADERS (legacy).

Server-Provisioning

Neue Server werden über Einmal-Tokens mit 24-Stunden-TTL onboarded — seit v0.23.2 FRP-unabhaengig im Server-Modul:

  1. Admin ruft POST /api/servers/{server_id}/provision/token auf → erhält {token, expiresAt, serverId, serverName}.
  2. Der Agent löst den Token mit POST /api/servers/{server_id}/provision/activate ein (Header X-Provision-Token) und bekommt zurück: frischen Server-API-Key (immer), Monitor-Agent-Key + URL (wenn Monitor-Service erreichbar), frpc.toml (wenn FRP konfiguriert ist) und einen einmaligen enrollment-Token. Felder sind null, wenn die jeweilige Komponente nicht konfiguriert ist — ein ausgefallener Monitor-Service blockiert das Provisioning nicht. Ein per-Client-PKI-Bundle wird nicht mehr mitgeliefert: der Agent enrollt sein mTLS-/Tunnel-Cert selbst am ca-issuer (A4/A7).
  3. Tokens sind one-time: used_at wird gesetzt, weitere Aktivierungen scheitern.
  4. Im laufenden Betrieb synchronisiert der Agent über GET /api/frp/provision/{server_id}/config + config-hash seinen frpc.toml-Stand. Ohne FRP-Config antwortet config-hash mit {"hash": null} statt mit einem Fehler, es gibt nichts abzugleichen; config bleibt dann 404. Hat der Host keinen aktiven Tunnel (active_tunnels in modules/frp/config_generator.py: eingeschaltet, STCP nur mit Secret, kein gespeichertes extra_config, das die API heute ablehnt, also genau die [[proxies]] des Generators), liefern config und config-hash den allgemeinen Teil ohne Tunnel und ohne frps-Zugangsdaten. Ein Agent dieser Version stoppt und deaktiviert frpc darauf; ein älterer Agent startet frpc damit neu, frpc meldet sich dann nicht an und wird von systemd neu gestartet, bis der Agent aktualisiert ist. Das Provisionierungs-Paket trägt denselben Text wie config, auch ohne aktiven Tunnel, und ein Agent dieser Version speichert dessen Hash: Sein nächster Abgleich hat nichts zu tun. Ein älterer Agent schreibt bei der Provisionierung die Sync-Config mit dem neuen API-Key und diese frpc.toml und startet einen gestoppten frpc damit; ein schon laufender frpc übernimmt sie erst bei seinem nächsten Neustart.

FRP — TOML-Struktur

modules/frp/config_generator.py rendert die FRP-Konfigurationen direkt aus den DB-Modellen zu TOML-Strings — kein Template-Engine, nur String-Listen. Drei Generatoren:

FunktionZielInhalt
generate_frps_toml(config)frps.toml (Server)bindPort, optional vhostHTTPSPort/subDomainHost, maxPortsPerClient (immer gesetzt, Default 16 als Schranke gegen einen kompromittierten Agent), optionaler Dashboard-Block (webServer.* an 0.0.0.0, nur im Compose-Netz erreichbar, da der Port nicht published ist), auth.method = "token" + Token, plus [transport.tls]-Server-Block.
generate_frpc_toml(config, tunnels, frpc_user)frpc.toml (Agent)serverAddr/serverPort/user, Token-Auth, Client-TLS-Block, dann je aktivem Tunnel (active_tunnels) ein [[proxies]]-Block. Einen Tunnel, dessen gespeicherter name, local_ip, custom_domains oder secret_key die API heute ablehnen würde (Zeilen von vor der Prüfung), lässt der Generator aus und loggt Namen und Feld, nie den Wert (without_refused_fields). Die [[proxies]] stehen nach Tunnel-Name sortiert, damit Config und Config-Hash nicht von der Reihenfolge abhängen, in der die Datenbank die Zeilen liefert.
generate_visitor_toml(config, tunnels, visitor_user)Visitor-frpc.toml (Admin-PC)Ein [[visitors]]-Block je übergebenem STCP-Tunnel, der eingeschaltet ist, ein Secret und einen visitor_port von 1 bis 65535 hat (without_secretless_stcp, without_unbindable_visitor, without_refused_fields; einen ausgelassenen Tunnel loggt der Server als Warnung), sortiert nach visitor_port, mit bindAddr = "127.0.0.1" und bindPort = visitor_port. Die Aufrufer übergeben nur STCP-Tunnel, die der Nutzer sehen darf (_visible_stcp_tunnels in modules/frp/generate_router.py, im Bulk-ZIP die Tunnel seiner Server; hat kein Nutzer einen Server, enthält das ZIP stattdessen ein einziges visitor.toml mit allen STCP-Tunneln).

Nur Tunnel mit enabled = true werden gerendert. Zwei Tunnel-Typen sind speziell behandelt:

  • STCP (type = "stcp"): bekommt secretKey und allowUsers (Default ["ops-admin"], sonst die uebergebenen allow_users). allow_users sind die Namen aller dem Host zugeordneten Nutzer und aller Admins (frp/_helpers.py::get_allow_users), je einmal und aufsteigend sortiert, damit Config und Config-Hash nach einem Neustart und in jedem Worker gleich bleiben. Der zugehoerige [[visitors]]-Block setzt serverName, serverUser (= Agent-User, weil FRP Proxies als {user}.{name} registriert) und denselben secretKey.
  • HTTPS (type = "https"): rendert customDomains aus dem komma-getrennten Feld custom_domains.

extra_config (JSON) wird je Tunnel typ-erhaltend angehaengt: Strings gequotet, Bools als true/false, Zahlen roh. Einen Tunnel, dessen gespeichertes extra_config die API heute ablehnt (einen Schlüssel der plugin-Familie, also mit erstem Segment plugin, gleich ob groß oder klein geschrieben, oder einen anderen Eintrag, der die Prüfung von POST /api/frp/tunnels nicht besteht, etwa ein Schlüssel mit leerem Segment oder eine Ganzzahl über 64 Bit, oder Schlüssel, die erst zusammen kollidieren, wie foo neben FOO; dann nennt die Warnung alle; ebenso Text, der kein JSON-Objekt ist), lässt der Generator weg (without_refused_extra_config, in active_tunnels) und schreibt eine WARNING mit Tunnelname und den betroffenen Schlüsseln, nie den Werten. Eine solche Zeile ergäbe sonst eine frpc.toml, die für den ganzen Host nicht gilt; so bleiben die übrigen Tunnel des Hosts in Betrieb. Die Zeile in der Datenbank bleibt, wie sie ist; die Visitor-TOML (ohne extra_config) behält den Visitor.

frpc.toml (STCP-Beispiel)
serverAddr = "frp.example.com"

auth.method = "token"

FRP-PKI & TLS

Seit A7 kommen das frps-Server-Cert und das Agent-Tunnel-Cert aus der tunnel-Intermediate des ca-issuer (ECDSA P-256, eine Vertrauenswurzel): frps mountet das vom Issuer provisionierte Material (frps.crt/frps.key/ca.crt) read-only unter /etc/frp-pki, der Agent nutzt sein bei der Enrollment (A4) erhaltenes Tunnel-Cert unter /etc/adminhelper/identity — ein Cert für Server-Pushes und den frp-Tunnel, auto-erneuert bei ~50 % Laufzeit.

Der Server signiert keine FRP-Zertifikate mehr (D6, F3). Die frühere server-eigene FRP-CA (modules/frp/pki.py + pki_router.py mit den /api/frp/pki/*-Endpunkten + die _ensure_pki()-CA-Erzeugung beim Start) ist mit der PKI-Migration vollständig entfernt, ebenso das frp-pki-Volume und der frühere Master-/Published-Split. _ensure_frps_config() schreibt beim Start nur noch das nicht-geheime frps.toml.

Der Desktop-STCP-Visitor präsentiert seit der Migration (F2) seine enrollte access-Identität als frpc-Client-Cert (der Desktop exportiert Key/Cert/CA aus dem Keyring in Dateien unter identity/). Damit frps diese akzeptiert, trägt der ca-issuer die access-Intermediate zusätzlich in frps' ca.crt ein (ensure_frps_cert(..., extra_trust)); die echte Per-Tunnel-Autorisierung bleibt der STCP-secretKey + die server-seitige Bundle-Filterung, nicht der Cert-Scope.

Die TLS-Verdrahtung in frps.toml/frpc.toml erzeugt der config_generator: Der Server-Block (force = true) zeigt auf das issuer-provisionierte Material unter /etc/frp-pki; der Agent-Block (enable = true) auf das enrollte Tunnel-Cert unter /etc/adminhelper/identity; der Visitor-Block auf die vom Desktop exportierte enrollte Identität ({{IDENTITY_DIR}}-Platzhalter, vom Desktop zur Laufzeit auf absolute Pfade ersetzt).

Event-Bus & Scheduler

APScheduler läuft in einem dedizierten Scheduler-Prozess (app.scheduler_main, RUN_MODE=scheduler), nicht in den Web-Workern — sonst würde mit uvicorn --workers N jeder Job N-mal laufen (doppelte Outbox-Mails, doppelte Hook-Läufe). Genau eine Instanz besitzt damit alle System-Jobs (Cleanups, Outbox-Drain) und den periodischen Hook-Reconcile. Trigger-Typen: vordefinierte Intervalle (1m, 5m, 15m, 30m, 1h, 6h, 12h, 24h) oder Cron (5 Felder). Cron-Ausdrücke gelten in UTC, unabhängig von TZ des Scheduler-Prozesses; next_run ist der nächste Lauf in UTC (R-0756). Der Wochentag zählt wie im Standard-Cron: 0 und 7 = Sonntag, 1 = Montag, 1-5 = Montag bis Freitag. Namen (sun–sat) gelten wie ihre Zahlen, auch in Bereichen und mit Schritt (mon-fri/2 = Montag, Mittwoch, Freitag), wie in Vixie-Cron; ein Schritt auf einem einzelnen Wert (1/2) ist ungültig. Abweichend davon zählt sun am Ende eines Bereichs, der nach Sonntag beginnt, als 7, damit sat-sun gilt. Ebenfalls abweichend müssen Tag-im-Monat und Wochentag beide passen, wenn beide gesetzt sind: 0 9 1-7 * mon läuft am ersten Montag des Monats, 0 9 15 * mon nur an einem Montag, der auf den 15. fällt (R-0274). APScheduler 3.x zählt in from_crontab ab Montag, deshalb übersetzt _parse_trigger das Feld vorher (R-0249).

Weil die Web-Worker keinen laufenden Scheduler haben, registrieren die Hook-CRUD-Router keine Jobs mehr direkt; sie schreiben nur die Hook-Zeile. Der Scheduler-Prozess gleicht die Schedule-Hooks alle 30 s aus der DB ab (reconcile_scheduled_hooks() — neu/geändert/gelöscht) und schreibt next_run zurück. Multi-Worker wird über WEB_CONCURRENCY aktiviert (Default 1); Redis ist dann für global korrektes Rate-Limiting Pflicht, und der DB-Pool gilt pro Worker (DB_POOL_SIZE/DB_MAX_OVERFLOW).

Der Event-Bus in core/events.py verteilt Events über einen ThreadPoolExecutor (4 Worker, fire-and-forget). Aktive Event-Typen:

  • server.created, server.updated, server.deleted, server.startup (beim Start jedes Web-Workers, bei WEB_CONCURRENCY=N also N-mal; der Scheduler feuert es nicht)
  • connection.created, connection.updated, connection.deleted, connections.imported
  • user.created, user.deleted, user.promoted
  • alert.triggered (je betroffenem Server, wenn ein Monitoring-Check nach critical wechselt)
  • frp.config.created, frp.config.updated, frp.config.deleted
  • frp.tunnel.created, frp.tunnel.updated, frp.tunnel.deleted
  • playbook.created, playbook.updated, playbook.deleted

Details siehe Hooks & Events. Eine kuratierte Auswahl dieser Events wird zusätzlich über modules/notifications/event_bridge.py in den Notification-Hub gespiegelt (siehe unten).

Notification-Hub

Der Server ist der Hub für nutzer-zentrierte Benachrichtigungen (modules/notifications/). Begründung: Nur der Server kennt die User↔Server-Zuordnung (user_servers) — das Monitoring bleibt reine Event-Quelle und lernt nichts über Benutzer. Drei Tabellen (Alembic-Migration a7c3efba142a):

TabelleZweck
notification_subscriptionPro-User-Regeln: scope_type (all/tag/server) + scope_ref, min_severity, Kanal-Flags. Ein User kann mehrere haben.
notificationDer Glocken-Feed: eine Zeile pro Empfänger, read_at markiert gelesen.
notification_outboxVersand-Queue für externe Kanäle (E-Mail), mit attempts/next_attempt_at für Retry/Backoff.

Datenfluss:

  1. Quellen rufen service.ingest_event() — der Monitoring-Dienst per POST /api/internal/events (Auth X-Internal-Key = MONITOR_API_KEY, Gegenrichtung des Monitoring-Proxys), und der In-Process-Bus über event_bridge.py (kuratierte user.created/user.promoted/server.deleted/frp.tunnel.created).
  2. Der Resolver (service.resolve_recipients()) bildet server_id → user_servers → users × subscriptions ab — least privilege: ein Nicht-Admin wird nur über ihm zugeordnete Server benachrichtigt, Admins über alle; ein Event ohne Server-Bezug geht nur an Admins. Ein Sammel-Event (source_ids statt source_id, 1–500 Server-IDs zu je 1–256 Zeichen, etwa mehrere stumme Agents auf einmal) löst er Server für Server nach denselben Regeln auf: Jeder Empfänger bekommt eine Zeile mit dem Titel <title> (<n>) und je einer Textzeile pro Server, den er sehen darf und den eines seiner Abos erfasst (Name, sonst ID); source_id bleibt leer. title und body des Sammel-Events nennen deshalb keinen Server und tragen keine Gesamtzahl; der Hook alert.triggered feuert einmal je Server. Unbekannte IDs erreichen nur Admins, kein Nutzer sieht Namen oder Anzahl fremder Server; source_id und source_ids zusammen lehnt der Server mit 422 ab. Tag-Scope matcht gegen die JSON-Tags des Servers zur Laufzeit (bewusst keine Tag-Normalisierung).
  3. Pro Empfänger entsteht eine notification-Zeile (Glocke) plus notification_outbox-Zeilen für aktivierte externe Kanäle, sofern eine Adresse hinterlegt ist. Mehrere passende Subscriptions eines Users werden zu einem Feed-Eintrag mit vereinigten Kanälen zusammengeführt. Bei einem Sammel-Event bekommt jede Outbox-Zeile ihren eigenen Titel und Text (notification_outbox.title/body) mit Anzahl und Namen nur der Server, die eine Subscription mit diesem Kanal erfasst; ein Kanal ohne solchen Server bekommt keine Zeile. Sonst bleiben beide NULL, und der Versand nimmt den Text der notification-Zeile.
  4. Ein APScheduler-System-Job (schedule_outbox_drain, minütlich, im dedizierten Scheduler-Prozess — siehe Event-Bus & Scheduler oben) leert die Outbox via outbox.drain_outbox() + sender.send_email() (smtplib) aus dem Request-Pfad heraus, mit linearem Backoff bis NOTIFICATION_MAX_ATTEMPTS (Default 5), danach Status failed.

Clients holen den Feed über GET /api/notifications (eigener Feed, paginiert) plus /unread-count und POST /api/notifications/read; persönliche Einstellungen über GET/PUT /api/users/me/notification-prefs (Replace-all).

Push (SSE): GET /api/notifications/stream ist ein langlebiger text/event-stream. Nach dem Commit von ingest_event() publiziert der Server ein leichtes „Refresh"-Signal (stream_hub.publish()) auf den Redis-Kanal notif:events; jeder Web-Worker hält eine Redis-Subscription und stellt das Signal seinen lokal verbundenen Streams der betroffenen User zu. Der Stream-Handler ist async und hält keine DB-Connection über seine gesamte Lebensdauer (er liest aus einer asyncio.Queue); er authentifiziert per kurzlebiger Session beim Connect und revalidiert danach etwa einmal pro Minute das Bearer-JWT (Blacklist/Ablauf) und die mTLS-Revocation außerhalb des Event-Loops (im Threadpool), sodass ein Logout oder ein Revoke einen bereits offenen Stream beendet, statt endlos Nudges zu pushen. Das Signal enthält keine Inhalte — der Client lädt die Zeilen per REST nach (kein zweiter Serialisierungs-/Autorisierungs-Pfad). Ohne REDIS_URL gibt es keinen Push; die Glocke fällt auf 30-s-Polling zurück. Der Desktop tunnelt den Stream durch den Rust-Client (src-tauri/src/notifications.rs), weil die WebView gegen das selbstsignierte Zertifikat kein EventSource öffnen kann; er emittiert pro Frame ein notification-Tauri-Event.

Persistenz

Stateful-Daten verteilen sich auf zwei Stellen:

  • PostgreSQL (Compose-Volume postgres-data): zwei DBs adminhelper (Server) und adminhelper_monitor (Monitoring).
  • File-System unter DATA_DIR (Default /app/data): Bootstrap-Token, JWT-Secret, Ansible-Playbook-Dateien.
  • Shared-Volume frp-config (frps mountet es :ro unter /etc/frp): nur das nicht-geheime frps.toml (0600). Die FRP-TLS-Materialien liefert der ca-issuer (Volume frps-certs), das PKI-Kronjuwel ist dessen ca-pki-Volume.

Der Container startet nur kurz als root, um die gemounteten Pfade zu chownen, und droppt dann via gosu auf einen Non-root-User (uid 10001) — uvicorn, Alembic und Hook-Subprozesse laufen unprivilegiert. uvicorn lauscht plain-HTTP auf 8080 (kein Host-Port); TLS terminiert das vorgelagerte gateway (nginx), nicht der Server.

Tests

Pytest-Suite unter apps/server/tests/. Tests laufen gegen ein echtes Postgres 17 via testcontainers (lokal) bzw. services: postgres:17-alpine (CI). SAVEPOINT-Pattern in der db_session-Fixture: Outer-Transaction mit begin_nested + after_transaction_end-Listener — erlaubt commit() im Test-Code, am Ende sauberer Rollback. Kein Test erreicht die Engine der App (app.core.database.engine): Eine autouse-Fixture lässt jeden Verbindungsversuch scheitern und den Test im Teardown fehlschlagen. Code, der selbst SessionLocal() öffnet, bindet der Test an die Verbindung von db_session; ein Test, der die Engine bewusst braucht, trägt den Marker app_engine. Dazu zwei Drift-Detektoren zwischen Base.metadata und den Alembic-Migrationen: test_alembic_builtin.py fährt die eingebauten Tests von pytest-alembic (genau ein Head, jede Revision der Reihe nach, Modelle gleich DDL nach dem vollen Lauf, jede Revision übersteht Down und Up) und eine Datenmigration mit Daten; test_migrations_smoke.py prüft, dass upgrade head auf einer leeren Datenbank die Modelle ergibt.
