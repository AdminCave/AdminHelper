Web-Panel

Das Web-Admin-Panel ist eine eigenständige Svelte-5-SPA mit Hash-Router. Es liegt unter apps/web/, wird via Vite gebaut und im Docker-Image per Multi-Stage in das Python-Runtime-Image kopiert. Seit v0.32.0 deckt es nur noch die Instanz-Verwaltung ab (Benutzer, API-Keys, Hooks, FRP-Server-Konfiguration, Audit-Log); die operative Server-/Verbindungs-/Tunnel-/Monitoring-/Ansible-Verwaltung ist in den Desktop-Client umgezogen (siehe Desktop-Client).

Routing

Hash-Router (kein SSR, kein Client-Router von SvelteKit): Die Pfade sind #/users, #/apikeys usw. Das funktioniert zuverlässig hinter beliebigen Reverse-Proxies, ohne dass der Server SPA-Fallbacks verstehen muss. Implementierung in src/lib/router.ts – ein writable _path mit hashchange-Listener; exportiert den lesbaren Store path und replace().

Produktiv-Routen seit v0.32.0: #/users (Standard-Landing), #/apikeys, #/hooks, #/frp (FRP-Server-Konfiguration), seit v0.35.0 dazu #/audit (Audit-Log). Die früheren operativen Routen (#/connections, #/servers, #/ansible, #/monitoring, Tunnel) sind in den Desktop-Client umgezogen.

Stores

Stores in src/lib/stores/. Jeder Store ist ein writable aus svelte/store, nach außen nur über ein Objekt mit subscribe sichtbar; bei den Daten-Stores trägt es Methoden, die direkt mit dem passenden API-Wrapper sprechen. Die Listen-Stores users, hooks und apikeys entstehen aus listStore.ts: Eine Listen-Antwort, die nach einer neueren Änderung oder einem neueren Laden ankommt, und jede Antwort, die nach dem Abmelden ankommt, ändern die Liste nicht. Die Daten-Stores halten nur, was die Listen- bzw. Leseantwort trägt: Ein einmalig angezeigter Wert aus einer Create-Antwort (API-Key, Webhook-Token) geht nur an den Aufrufer, und authToken und dashboardPassword der FRP-Server-Konfiguration hält frp als null, wie GET sie liefert. Seit v0.32.0 nur noch die Instanz-Verwaltung – die operativen Stores (connections, servers, ansible, monitoring, Tunnel) leben jetzt im Desktop-Client.

StoreZweck
authLogin, Logout, Refresh, aktueller User; der kurzlebige Access-Token liegt nur im Speicher des Moduls client.ts, nie in localStorage/sessionStorage (Kopien älterer Builds löscht der Client beim Laden), der langlebige Refresh-Token in einem HttpOnly-Cookie (vom Server gesetzt, für JS/XSS unlesbar). Nach einem Reload holt restoreSession() den Access-Token über das Cookie neu. Refreshes und die Abmeldung laufen tab-übergreifend nacheinander unter der Web Lock adminhelper-auth-refresh (withAuthLock() in client.ts): Alle Tabs teilen das Refresh-Cookie, und der Server wertet einen zweiten Refresh mit demselben Token als Wiederverwendung und beendet dann alle Sitzungen des Benutzers, ebenso einen Refresh mit einem Token, den eine Abmeldung schon gesperrt hat; ein Tab, der die Lock nach einem anderen bekommt, schickt schon das neue Cookie. Ohne Web Locks (nur in sicheren Kontexten, also HTTPS oder localhost) bündelt der Client Refreshes nur im Tab, und die Abmeldung geht sofort hinaus. Abmelden (Knopf, abgelaufene Sitzung oder 401/403 von /me beim Start) setzt den Zustand sofort zurück und leert die Daten-Stores users, hooks, apikeys und frp; eine neue Anmeldung wartet, bis der Server die Abmeldung beantwortet hat, denn diese Antwort löscht Access-Token und Refresh-Cookie. watchIdle() aus lib/idle.ts meldet nach idle_timeout_minutes Minuten ohne Bedienung (Zeiger, Tastatur, Rad, Touch) in allen Tabs ab; die Tabs teilen die Zeit der letzten Bedienung über localStorage (adminhelper_last_activity, höchstens alle 5 s geschrieben, geprüft alle 15 s und beim Sichtbarwerden des Tabs), bei gesperrtem Speicher zählt jeder Tab für sich. Eine Sitzung, die auth.hydrate() beim Laden über das Cookie wiederhergestellt hat, startet den Wächter mit restored: Liegt die gespeicherte Zeit schon idle_timeout_minutes Minuten oder länger zurück, meldet er sofort ab; sonst, und nach einem Login immer, zählt der Start als Bedienung.
usersBenutzer-CRUD inkl. User↔Server-Mapping (die Zuweisung bleibt im Web-Panel).
apikeysKey-CRUD, einmaliges Anzeigen des Klartext-Keys.
hooksHook-CRUD, Trigger-Test, Token-Rotation.
frpFRP-Server-Konfiguration (frps-Einstellungen), Config-Preview, frps-Status.
notificationsGlobale Toasts.
themeDark/Light-Umschaltung; die Wahl liegt in localStorage.ah-theme (siehe Theming).

API-Wrapper

Alle HTTP-Calls gehen durch src/lib/api/client.ts. Der Client verwaltet Access-Token, hält eine in-flight-deduplizierte tryRefresh()-Promise und triggert automatisch Refresh, wenn ein 401 zurückkommt. Schlägt das fehl, ruft registerAuthFailureHandler() den auth-Store, der zum Login leitet. Ein 401 auf eine Anfrage, die vor dem Ende ihrer Sitzung (Abmelden, dann neue Anmeldung) startete, löst weder Refresh noch Wiederholung noch Abmeldung aus; die Anfrage endet mit Session expired. Ein 2xx, dessen Body sich nicht lesen lässt (etwa weil ein Reload die Übertragung abbricht, oder weil er kein JSON ist), wirft ApiError(status, 'Invalid response body'), statt still null zu liefern; nur 204 und ein gültiges JSON-null ergeben null. Jedes andere Nicht-2xx wirft ApiError(status, message, detail, code): message ist detail, bei einem 422 die msg-Texte, ohne das Präfix <code>: , wenn der Server code schickt; code ist für den Code zum Verzweigen, nicht für die Anzeige. Jede Anfrage hat eine Frist von 15 s, nur der manuelle Hook-Lauf hooks.run wartet 75 s: Der Server führt den Hook synchron aus (bis 30 s Script), das Gateway schneidet nach 60 s. Läuft die Frist ab, wirft der Client ApiError(0, …) mit übersetztem Text (error.timeout).

Domain-Wrapper liegen daneben: auth.ts, users.ts, servers.ts (nur für die User↔Server-Zuweisung), apikeys.ts, hooks.ts, frp.ts (FRP-Server-Konfiguration), audit.ts (Audit-Log lesen, mit Filtern) – jeweils typisiert über types.ts.

i18n

Sprachen: DE und EN. Aktive Sprache wird in localStorage.adminhelper_language persistiert; Browser-Detect dient nur als initialer Fallback. Die t()-Funktion ist als Store implementiert – das verhindert i18n-Leaks in reaktiven Komponenten.

Theming & Design-System

Die Oberfläche folgt dem AdminCave-Design-System (monochrom, True-Black dark-first, Geist-Font, Pill-Radien). Farben/Radien/Schatten sind CSS-Custom-Properties in src/styles/global.css – ein :root-Block (Dark) plus ein :root[data-theme="light"]-Block (Light). Der Theme-Umschalter (Icon-Button im Sidebar-Footer neben EN/DE) kippt über den theme-Store zwischen Dark und Light; die Wahl wird in localStorage.ah-theme persistiert. Das Skript public/theme-init.js, im <head> als Datei geladen, setzt data-theme bereits vor dem ersten Paint (FOUC-frei), damit Light-User beim Laden nicht kurz Dark sehen; als Datei statt inline, weil die CSP des Servers nur script-src 'self' erlaubt. Default = Dark.

Tests

Playwright-E2E decken Login, CRUD, Autorisierung, Navigation und den Theme-Umschalter ab (Specs in tests/e2e/, u. a. login.spec.ts, smoke.spec.ts, theme.spec.ts); das Projekt chromium-build fährt theme.spec.ts zusätzlich gegen vite build + vite preview, das die CSP wie der Server als Header schickt. Visual-Diffs liegen in tests/e2e/*.spec.ts-snapshots/. Toleranz ist maxDiffPixelRatio: 0.02 (2 %). Locale ist de-DE, Viewport 1280×800. Reports landen als CI-Artifact (frontend_e2e-Job).

cd apps/web

Build & Deployment

Der Vite-Build landet in apps/web/dist/ (ohne Sourcemaps, Target ES2022). Im Repo-Root-Dockerfile wird dieser Output via Multi-Stage in /app/frontend/ kopiert, und die FastAPI-App mountet ihn als Static-Route. SPA-Fallback prüft vorher Datei-Existenz, bevor index.html zurückgegeben wird – das verhindert MIME-Fehler auf /assets/*.js.

Im Dev-Modus läuft Vite auf Port 5173 und proxied /api auf http://127.0.0.1:8080, den lokal gestarteten Server (Lokale Entwicklung).
