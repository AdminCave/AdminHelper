Monitoring-Stack

Monitoring ist ein Zusammenspiel aus drei Ebenen: der AdminHelper-Server agiert als Reverse-Proxy und reicht UI-Queries weiter, der separate monitoring/-Service hält Checks/Alerts/Templates und führt Scheduler-Checks aus, VictoriaMetrics speichert die Zeitreihen (Retention konfigurierbar über VM_RETENTION, Default 90 Tage).

Daten-Fluss

flow
[Agent]                                [Monitoring-Service]            [VictoriaMetrics]
   |                                          |                                |
   | POST /agent/{server_id}/report --------->|  agent_resources, service_     |
   |   (X-API-Key)                            |  process, docker_health,        |
   |                                          |  proxmox_backup, zfs_health,    |
   |                                          |  smart_health -> evaluate +     |
   |                                          |  format_line() ---------------->|
   |                                          |                                |
                                              |  APScheduler -> http / ping /  |
                                              |  tcp / agent_ping ------------>|
                                              |
[Desktop-Client] -> /api/monitoring/* (admin) -> AdminHelper-Server -> {MONITOR_SERVICE_URL}/{path} (X-Internal-Key) -> Monitoring-Service

Der Server reicht ohne Präfix weiter: Aus /api/monitoring/{path} wird {MONITOR_SERVICE_URL}/{path} (Default http://monitoring:8080), denn der Monitoring-Service hängt seine Router ohne prefix ein (apps/monitoring/app/main.py).

AdminHelper-seitig: monitoring_proxy

Im AdminHelper-Server gibt es kein eigenes Monitoring-Modul mehr; alles läuft durch apps/server/app/modules/monitoring_proxy/router.py:

  • POST /api/monitoring/agent/{server_id}/report – öffentlich (X-API-Key), reicht 1:1 an den Service
  • GET/POST/PUT/DELETE /api/monitoring/{path:path} – admin-only, intern erweitert um X-Internal-Key: $MONITOR_API_KEY
  • SSRF-Schutz: erlaubte Pfad-Prefixe sind checks, alerts, status, templates, maintenance, agent; Path-Traversal (..) wird blockiert
  • Beim Server-Delete im AdminHelper wird DELETE /servers/{id}/cleanup am Monitoring-Service gefeuert – verwaiste Checks/Alerts werden so automatisch aufgeräumt

Push-Checks vs. Pull-Checks

Es gibt zwei Klassen von Checks – entscheidend ist, wer die Daten beschafft:

ModusCheck-TypenTrigger
Push (Agent)agent_resources, service_process, docker_health, proxmox_backup, zfs_health, smart_health, system_stateBeim nächsten Agent-Push (5-Min-Timer); APScheduler ist nicht beteiligt.
Pull (Service)http, ping, tcp, agent_ping, disk_forecastAPScheduler im Monitoring-Service nach festem interval.

Push-Typen tragen push_only: True in CHECK_TYPES (apps/monitoring/app/check_types.py); der Desktop führt dieselbe Liste als PUSH_ONLY_CHECK_TYPES (apps/desktop/ui/src/lib/models/monitoring.ts), und apps/monitoring/tests/test_push_only_ui_sync.py hält beide gleich: Ein neuer Push-Typ wie system_state ändert beide Dateien im selben Commit.

Beide Pfade schreiben das Ergebnis über apply_result() (check_engine.py) in MonitorState, die Metriken über format_line() nach VictoriaMetrics und rufen ggf. process_alert(), sobald fail_count ≥ consecutive_fails. Bis dahin behält effective_status() (check_engine.py) den alten Status; ein neuer Check (pending) zeigt dabei ok, außer das Ergebnis ist unknown: dann unknown, damit ein Check ohne Daten nicht grün steht. Das kostet keine Benachrichtigung, unknown meldet nie.

In die andere Richtung hält holds_recovery() die Entwarnung, aber nur für ein gemeldetes Problem: Ist notified_status warning/critical und steht der Check auf warning, critical oder unknown, setzt apply_result() ihn bei einem ok auf notified_status, bis MonitorState.ok_count consecutive_oks erreicht (Default 2, Migration 3c66308d11a7 setzt ihn für bestehende Checks). Gehalten wird also der gemeldete Status, nie ein schlimmerer, den der Check nur stumm erreicht hat; das Halten eskaliert nicht und meldet nichts (resolve_notification → skip), auch wenn die Anzeige dabei steigt (gemeldet critical, stumm warning oder unknown, dann ok → critical „(recovery 1/m)“). Ein nie gemeldetes Problem (stumm durch Wartung oder Host-down) wird beim ersten ok sofort und still ok; gehalten würde es als neuer Alarm nachgemeldet. next_ok_count() zählt ok hoch und setzt bei jedem anderen Ergebnis auf 0; die Meldung trägt während des Haltens „(recovery n/m)“. pending → ok und ok → ok halten nie, consecutive_oks 1 hält nie. Weil der Status selbst gehalten wird, bleiben Dashboard, Glocke und die Host-down-Inhibition eines agent_ping während des Haltens beim Problem.

Der APScheduler (scheduler.py) läuft mit einem ThreadPool von 30 Workern und misfire_grace_time=30 s – verzögert startende Runs werden bis 30 s nachgeholt statt verworfen. Ein täglicher Cleanup-Job bereinigt außerdem monitor_alert_log (Retention über ALERT_LOG_RETENTION_DAYS, Default 90 Tage), alle 15 Minuten läuft der Tag-Sync (siehe unten), und alle 30 s meldet system:agent-alert-bundle die offenen Heartbeats (Sammelmeldung, siehe Alert-Pipeline).

Push-Payload (Agent → Service)

Der Go-Agent baut den Report in apps/agent/internal/monitor/report.go (BuildReport) und sendet ihn als JSON per POST {url}/agent/{server_id}/report mit den Headern Content-Type: application/json und X-API-Key (PushReport). Der Server-Handler in routers/agent.py nimmt das JSON als freies dict entgegen. Python liest dabei auch NaN, Infinity und Ganzzahlen bis 4300 Stellen (sys.get_int_max_str_digits); die Checker übernehmen Zahlen aus dem Report nur als JSON-Zahl (als endliches float darstellbar), und die to_dict-Methoden in models.py geben gespeicherte nicht endliche Zahlen und Ganzzahlen außerhalb des float-Bereichs als null aus (Check-Config, details des Zustands, channel_config einer Alert-Regel, Check- und Alert-Definitionen eines Templates), ebenso der Update-Vergleich eines Standard-Templates in current (GET /templates/{template_id}/builtin-update). Felder sind optional: docker, zfs und proxmox erscheinen, sobald docker, zpool bzw. pvesh auf dem Host liegt, auch wenn der Agent sie nicht lesen kann. Dann tragen sie available: false, error (Docker daemon_unreachable | timeout | cli_failed | parse_failed, ZFS timeout | cli_failed, Proxmox timeout | cli_failed | parse_failed | backup_index_incomplete), error_message (kurzer Text mit Aufruf und Exit-Status, nie stderr oder Pfade) und eine leere Liste, Proxmox dazu node: null (siehe Agent). Statt smart schickt der Agent ohne lesbare Platte smart_absent.reason (not_installed | scan_failed | no_devices). Diese Felder und die Container-Felder ab exit_code sind additiv: ältere Agents senden sie nicht, ältere Monitoring-Dienste ignorieren sie und werten einen Ausfall als leere Liste (ok). Auch host ist additiv: Ältere Agents senden es nicht, ältere Monitoring-Dienste ignorieren es. Ein aktueller Agent schickt es bei jedem Push (collectHostFacts() in apps/agent/internal/monitor/hostfacts.go): os ist runtime.GOOS; platform und platform_version kommen aus gopsutil host.PlatformInformation() (unter Windows der Produktname), virtualization mit system und role aus host.Virtualization() (leer, wenn nichts erkannt wird, unter Windows immer). Scheitert einer der beiden Aufrufe, fehlen nur seine Felder, nie der Block. subsystems ist immer eine Liste, in der Reihenfolge docker, zfs, proxmox mit jedem Eintrag, dessen Programm (docker, zpool bzw. pvesh) im Suchpfad liegt, unabhängig davon, ob die Plugin-Collector Daten liefern. Was der Dienst daraus macht, steht unter Vorschläge aus den Host-Fakten; dazu erkennt agent_resources an virtualization einen Container und bewertet dort die Load nicht (Checker im Überblick). VMs ohne Sensoren liefern keine temperatures. services ist ein Legacy-Key parallel zu systemd. Der Handler iteriert über resources (CPU/RAM/Load/Disk/Temp) und uptime_seconds, schreibt daraus VictoriaMetrics-Zeilen (Pseudo-Dateisysteme aus EXCLUDED_FSTYPES werden übersprungen) und wertet anschließend die fuer den Server konfigurierten Push-Checks gegen den Report aus. Die Werte liest er wie die Checker: Messwerte nur als JSON-Zahl (kein bool, kein Zahl-String, als endliches float darstellbar), fstype, mount und sensor nur als String (sonst wie ohne das Feld, mount dann ? wie im Checker, sensor unknown). Aus disks und temperatures zählen höchstens die ersten 500 Einträge, wie beim Checker; ein Eintrag, der kein Objekt ist, wird übersprungen und kostet nur sich selbst. Aus smart schreibt er keine eigenen Zeilen: Die SMART-Serien (monitor_smart_temp_<Gerät>, monitor_smart_reallocated_…, monitor_smart_pending_…) schreibt der Check smart_health mit seinen Check-Labels. Antwort: {"status":"ok","metricsWritten":N,"checksUpdated":M}; metricsWritten zählt die Zeilen, die der Handler zum Schreiben übergibt (geschrieben wird im Hintergrund, siehe VictoriaMetrics).

Report-Version 3. Der Agent setzt report_version 3; der Dienst liest die Nummer nicht, er wertet aus, was im Report steht. Alles Neue ist additiv:

  • resources.cpu_percent bleibt ein Prozentwert, ist aber der Anteil belegter CPU-Zeit seit dem letzten erfolgreich gesendeten Report statt einer 1-s-Stichprobe; ohne brauchbaren Vorwert misst der Agent weiter die Stichprobe (siehe Agent).
  • resources.cpu_count (logische CPUs), swap_total_mb, swap_used_mb und, nur mit Swap-Gerät, swap_percent: nur Linux.
  • Je Platte free_gb (der für Nicht-Root freie Platz; Linux und Windows) und inodes_percent (nur Linux und nur auf Dateisystemen, die Inodes melden).
  • system_state (nur Linux): reboot_required und time_synchronized als Bool, security_updates und oom_kills als ganze Zahl. Jedes Feld kommt nur, wenn der Agent es ermitteln konnte; ohne ein einziges fehlt der Block. oom_kills zählt seit dem letzten erfolgreich gesendeten Report und steht deshalb in genau einem Report; security_updates zählt der Agent höchstens einmal je Stunde aus den lokalen Paketlisten.
  • proxmox kommt wie docker und zfs immer, sobald pvesh im Suchpfad liegt, mit available, error und vms als Liste (auch leer); im Ausfall mit Code, error_message, node: null und leerer Liste. Ältere Agents lassen den Block bei einem Lesefehler weg.

Aus den neuen Feldern schreibt der Handler keine eigenen VictoriaMetrics-Reihen; sie gehen nur in die Bewertung und in _details. Agent und Monitoring-Dienst kommen im selben Release; gemischt gilt:

Ein älterer Desktop zeigt einen system_state-Check ohne eigene Sektion und einen Proxmox-Ausfall als „—“.

systemd.all_services ist zusätzlich gedrosselt: der Agent sendet das volle Inventar nur, wenn sich dessen Hash geändert hat oder der letzte Voll-Send über 1 h zurückliegt – fehlender Key ≠ leere Liste (leere Liste heißt: wirklich keine Services). Bei jedem Push dabei sind failed, enabled_inactive (vom Agent schon um absichtlich inaktive Units bereinigt, siehe Agent) und counts (active/total der geladenen Dienste; fehlt, wenn der Agent sie nicht auflisten konnte). Scheitert systemctl list-units bzw. sc query, trägt error einen kurzen Grund. Der Checker übernimmt ihn auf 500 Zeichen gekürzt (samt „…“) in die Meldung; ist er kein String, zählt der Fehler weiter, die Meldung nennt aber keinen Grund. Alias-Einträge im Inventar (enabled_state alias) nennen in alias_of ihre Unit. counts, error und alias_of sind additiv: ältere Agents senden sie nicht, ältere Monitoring-Dienste ignorieren sie. Der ServiceProcessChecker wertet aus:

  • auto: enabled_inactive übernimmt er unverändert vom Agent und leitet es nicht aus all_services ab; failed ist systemd.failed plus die failed-Einträge des Inventars (auf 500 gekappt, dank der Sortierung immer dieselben). Ein voller und ein gedrosselter Push desselben Zustands geben so dasselbe Ergebnis. Unter den ersten 500 Einträgen zählen aus failed und enabled_inactive nur Strings, aus all_services nur Objekte mit einem String in unit; ein anderer Eintrag wird übersprungen (für die Grenze zählt er mit), und ein systemd, das kein Objekt ist, gilt als fehlend („No service data in report“). ignore-Einträge sind Glob-Muster (fnmatch.fnmatchcase), ein Name ohne Unit-Typ passt auch auf <name>.service. Ohne Problem, aber mit error ist der Check unknown statt ok. Gültige counts (ganze Zahlen, als endliches float darstellbar, 0 ≤ active ≤ total) landen als active_count/total in _details. Die Namen in _details.failed und _details.enabled_inactive gehen über cap_agent_text auf 500 Zeichen gekürzt (samt „…“) und einzeilig dorthin; die ignore-Muster vergleichen den vollen Namen.
  • list: Je Name (ohne Unit-Typ normalisiert auf <name>.service) entscheidet die erste Quelle, die ihn kennt: report["services"] (Agent mit eigener Liste aus monitor init --services), dann all_services dieses Pushes (ein Alias über alias_of), und bei einem Push ohne Inventar der Stand der letzten Auswertung (prev_details.watched; der Push-Handler in routers/agent.py reicht service_process wie agent_resources die vorigen _details durch). Ein volles Inventar ist der aktuelle Stand und wird nicht aus prev_details ergänzt. _details.watched ist [{name, state, running}] mit state ∈ {running, down, nodata}; running (state == "running") bleibt für Desktops, die state noch nicht kennen. Status: critical bei mindestens einem down, unknown, wenn kein Name Daten hat, sonst ok; nodata zählt nicht als down.

Checker im Überblick

Jeder Checker liefert ein Tripel (status, message, metrics) mit status ∈ {ok, warning, critical, unknown}. message ist englisch und geht so in Dashboard, Glocke und Benachrichtigungen; der Desktop übersetzt, wo er aus _details rendert. Nennt die Meldung eine Liste (VMs, Pools, Container, Platten, Dienste, Mounts), geht sie über join_capped in checkers/agent.py: Der Helfer kürzt jeden Eintrag auf 500 Zeichen (samt „…“), nennt der Reihe nach höchstens 10 Einträge und höchstens 1000 Zeichen (Einträge samt Trennern), den ersten immer, und zählt die übrigen als „(+N more)“. _details trägt weiter jeden ausgewerteten Eintrag; Status und Metriken bleiben gleich. Jeder Text aus dem Report, den eine Meldung übernimmt, ein Listeneintrag ebenso wie ein Einzeltext (etwa error_message), geht über cap_agent_text, auf dem auch join_capped aufsetzt: Jedes Steuerzeichen (Unicode-Kategorie Cc, also auch Tab, Zeilenvorschub und Wagenrücklauf) und die Zeilentrenner U+2028 und U+2029 werden zu je einem Leerzeichen, die Länge und die Grenze von 500 Zeichen bleiben; eine Meldung ist damit einzeilig. cap_agent_text kürzt zuerst und ersetzt danach; weil jedes Zeichen durch genau ein Zeichen ersetzt wird, ist das Ergebnis dasselbe, und der Aufwand bleibt bei jedem noch so langen Text auf 500 Zeichen begrenzt. Die Bewertung (Ignore-Listen, Zustand) liest weiter den vollen Wert. Zusätzlich kürzt apply_result() in check_engine.py, der einzige Schreiber von MonitorState.message, jede Meldung auf 2000 Zeichen (samt „…“), auch das „Unexpected error: …“ eines Scheduler-Checks; erst danach hängt sie bei einem gedämpften Fehler „(failure n/m)“ an, bei einer gehaltenen Entwarnung „(recovery n/m)“. _details bleibt vollständig. Pull-Checker haben eine run(config)-Methode; Agent-/Push-Checker werten in evaluate(config, report, prev_details) direkt den Push-Report aus (PushChecker); prev_details ist das vorige _details des Checks oder None.

Ein Ziel, das wegen NO_PROXY nicht über den Proxy geht, verbindet wie ohne Proxy zu einer der geprüften Adressen.

agent.pyagent_ping, agent_resources, service_processAgentPingChecker prüft (scheduler-getrieben) das Alter des letzten Push gegen stale_minutes. AgentResourcesChecker wertet CPU, RAM, Swap, Load je CPU, Platten samt Inodes und Temperaturen gegen Warn-/Crit-Thresholds aus. Für Swap, Inodes, Load und den GB-Riegel gleichen seine Defaults denen in check_configs.py und im Template „Linux Server — Standard“ (Version 3), damit auch ein Check ohne diese Schlüssel (angepasst oder von Hand angelegt) sie gleich bewertet. Er liest CPU, RAM, Plattenwerte (percent) und Sensorwerte (temp_c) nur als JSON-Zahl (kein bool, als endliches float darstellbar), fstype, mount und sensor nur als String; alles andere gilt als fehlend (CPU/RAM unbewertet, Platte und Sensor 0). Auch die Zahlen, die nur in _details stehen, gehen dorthin nur als JSON-Zahl: die RAM-Summen (memory_total_mb, memory_used_mb) und Plattengrößen (total_gb, used_gb), sonst null, und die Sensorgrenzen (high, critical), sonst 0. Ausgewertet werden höchstens die ersten 500 Platten bzw. Sensoren; ein Eintrag, der kein Objekt ist, wird übersprungen, und ein resources, das kein Objekt ist, gilt als fehlend („No resource data“). Ab Report-Version 3: Swap (swap_percent, Schlüssel swap) zählt nur mit swap_total_mb > 0; die Load je CPU ist round(load_5m / cpu_count, 2) (Schlüssel load, Einheit /CPU), nur mit ganzzahligem cpu_count ≥ 1, und nicht in einem Container: Trägt der Report host.virtualization mit role guest und einem system aus _CONTAINER_SYSTEMS (lxc, docker, openvz, rkt, dieselbe Liste wie containerSystems in apps/agent/internal/monitor/system_linux.go, die test_agent_resources_checker.py gleich hält), steht load_per_cpu in _details, dazu load_rated: false, aber ohne Schlüssel load (dort ist load_5m die Load des Hosts, cpu_count womöglich die des Containers); ohne host, bei einem Host oder einer VM fehlt load_rated, und die Load zählt wie bisher; Inodes kommen je Platte aus inodes_percent (inode:<mount>). Fehlt einer dieser Werte (älterer Agent, Windows), bleibt die Metrik unbewertet, ohne unknown. Auth-Modi

Beide Modi sind in core/auth.py als FastAPI-Dependencies implementiert:

  • require_agent (Agent-Push): liest Header X-API-Key. Stimmt der Wert exakt mit dem internen Key überein, gilt er als __internal__ (Zugriff auf alle Server). Andernfalls wird der Key per MonitorAgentKey.hash_key() SHA-256-gehasht und gegen die Spalte hashed_key in monitor_agent_keys verglichen – bei Treffer liefert die Dependency die zugehörige server_id zurück. Es wird also nie ein Klartext-Key gespeichert; in der DB liegt nur der Hash.
  • require_internal (AdminHelper ↔ Service): liest Header X-Internal-Key und vergleicht ihn gegen den internen Key. Quelle ist die Env-Variable MONITOR_API_KEY; fehlt sie, wird beim Start ein zufälliger Key generiert und in $DATA_DIR/.api_key persistiert (core/config.py).

Agent-Key: Vergabe & Server-Bindung

Agent-Keys werden pro Server vergeben (routers/admin.py):

  • POST /agent-keys/{server_id} erzeugt mit secrets.token_urlsafe(48) einen Raw-Key, speichert nur dessen SHA-256-Hash und gibt den Raw-Key einmalig in der Antwort zurück. Existiert bereits ein Key für den Server, wird er vorher gelöscht (Rotation = DELETE + POST). server_id ist in der Tabelle unique, also genau ein Key pro Server.
  • Beide Endpunkte (POST/DELETE /agent-keys/{server_id}) sind selbst über require_internal geschützt – nur der AdminHelper-Server darf Keys verwalten.
  • Im Push-Handler (routers/agent.py) wird zusätzlich geprüft, dass die aus dem Key abgeleitete server_id der server_id im Pfad entspricht; sonst 403. Ein gültiger Key für Server A kann also keine Metriken für Server B einliefern (__internal__ ausgenommen).

Templates, Seeding & Tag-Sync

MonitorTemplate bündelt Check- und Alert-Definitionen als JSON mit stabiler def_id pro Definition. POST /templates/{id}/assign (Body {server_id, hostname, server_name}) rollt das Template aus; template_sync.py reconciled bei Änderungen, sodass die Server-Zuweisungen drift-frei bleiben.

Built-in-Seeding (Tombstone)

Der Lifespan seedet beim Start sechs Standard-Templates aus builtin_templates.py (markiert über builtin_slug). Der Tombstone in monitor_seed_state garantiert: pro Slug wird höchstens einmal geseedet – ein vom Nutzer gelöschtes Built-in wird von späteren Starts nie wiederhergestellt; neue Built-ins späterer Releases seeden nur sich selbst. Was ein späterer Start mit einem bestehenden Built-in macht, regelt seine Version (nächster Abschnitt). Die Definitionen passieren dieselbe Schema-Boundary wie User-Templates (Test tests/test_seed.py).

Built-in-Versionen

Jeder Eintrag in BUILTIN_TEMPLATES trägt "version"; eine geänderte Definition wird als neue Version ausgeliefert. Die Zeile merkt sich in monitor_templates.builtin_version die zuletzt ausgerollte Version und in builtin_hash den sha256 der dabei ausgerollten Definitionen (beide NULL bei Nutzer-Templates; Migration a7c9e1b3d5f7). definitions_hash() hasht das kanonische JSON (sort_keys=True, separators=(",", ":")) von canonical_definitions(check_definitions, alert_definitions): beide Listen ohne die Schlüssel, die ihren Schema-Default aus TemplateCheckDef bzw. TemplateAlertDef tragen. Grund: Der Editor speichert jede Definition vollständig (model_dump), die mitgelieferten lassen Defaults weg, und ein neues optionales Schema-Feld darf nicht den Hash jeder Installation ändern. Name und Beschreibung des Templates zählen nicht; ein umbenanntes Built-in folgt neuen Versionen weiter.

Nach dem Seeding und der Baseline (record_override_baseline(), unten) ruft der Lifespan reconcile_builtin_templates() (Best-Effort wie das Seeding, vor load_all_checks()). Eine Zeile mit builtin_slug, aber ohne Hash (vor den Versionen angelegt) bekommt Version 1 und den eingefrorenen Hash der Version 1 aus BUILTIN_V1_HASHES (ein Slug ohne Eintrag, also erst nach den Versionen ausgeliefert, den Hash der mitgelieferten Definitionen); weichen ihre Definitionen davon ab, gilt sie damit als angepasst, sonst folgt sie einer neueren Version. Die Werte in BUILTIN_V1_HASHES ändern sich nie, auch nicht mit einer neuen Version. Ist die mitgelieferte Version höher und der Hash der aktuellen Definitionen gleich builtin_hash, ersetzt _roll_out() die Definitionen (Name und Beschreibung bleiben), setzt Version und Hash und ruft sync_template(); angepasste Check-Felder bleiben. Sonst ändert sich nichts. Jede Entscheidung fällt unter der Zeilensperre (with_for_update() mit populate_existing(), wirksam auf Postgres): Ein zweiter Start oder ein gleichzeitiges „Übernehmen“ sieht danach die neue Version und synchronisiert nicht doppelt. MonitorTemplate.to_dict() liefert builtinVersion, builtinEdited (Hash der aktuellen Definitionen ≠ builtin_hash) und builtinUpdateAvailable (mitgelieferte Version > builtin_version).

Anpassungen an Template-Checks (overridden_fields)

monitor_checks.overridden_fields (Text, NOT NULL, Default '[]') hält als JSON-Liste die Felder eines Template-Checks, die der Nutzer geändert hat, mit den Spaltennamen in snake_case und in fester Reihenfolge (TEMPLATE_CHECK_FIELDS): name, description, check_type, config, enabled, interval, severity, consecutive_fails, consecutive_oks. PUT /checks/{id} und POST /checks/{id}/toggle rufen mark_overrides(): Jedes gesendete Feld wird mit dem aufgelösten Template-Wert verglichen (resolve_template_check(): Definition mit den Variablen der Zuweisung substituiert, fehlende Schlüssel mit den Defaults eines neuen Checks, bei consecutive_oks DEFAULT_CONSECUTIVE_OKS = 2 aus schemas.py), anders → aufnehmen, gleich → streichen. Steht check_type in der Liste, steht config immer mit drin. Manuelle Checks und Checks, deren Zuweisung oder Definition fehlt, bleiben unberührt. _sync_checks_for_server() schreibt beim Aktualisieren nur die Felder, die nicht in der Liste stehen; ist config angepasst, auch check_type nicht. Eine Definition, die nicht mehr im Template steht, löscht ihren Check weiterhin, angepasst oder nicht. Alert-Regeln haben kein Gegenstück: _sync_alerts_for_server() setzt sie bei jedem Sync auf die Template-Werte. MonitorCheck.to_dict() liefert dazu templateDefId und overriddenFields (Liste).

Baseline beim ersten Start (record_override_baseline)

Bestandschecks starten mit []. record_override_baseline() markiert einmal je Installation, was vorher von Hand geändert wurde: Für jeden Check mit template_id ruft sie mark_overrides() mit allen aktuellen Werten des Checks, jedes vom Template abweichende Feld gilt also als angepasst, mit der Kopplung Typ/Config. Aufgelöst wird mit server_hostname/server_name der Zuweisung, den Namen, aus denen der Check gebaut wurde; ein seither umbenannter Server ist keine Anpassung. Manuelle Checks und Checks, deren Zuweisung oder Definition fehlt, bleiben, wie sie sind. Ein Check, der sich nicht vergleichen lässt (ValueError, TypeError oder AttributeError aus unlesbarer Config oder Definition), bekommt alle Felder und eine Warnung mit seiner ID; Datenbankfehler lassen den Lauf scheitern. Die Logzeile zählt markierte und nicht vergleichbare Checks. Für das später hinzugekommene consecutive_oks läuft sie in bestehenden Installationen nicht erneut: Vor dem Update konnte niemand das Feld ändern, jeder Check trägt den Spalten-Default 2.

Erledigt ist der Lauf mit dem reservierten Schlüssel baseline:overridden-fields (OVERRIDE_BASELINE_KEY) in monitor_seed_state, im selben Commit wie die Markierungen; der Doppelpunkt hält ihn aus dem Slug-Namensraum der Built-ins. Steht der Schlüssel, vergleicht kein Lauf mehr. Die Migration a7c9e1b3d5f7 löscht ihn beim Upgrade, wenn sie overridden_fields anlegt: Ein Downgrade verwirft die Markierungen, und das nächste Upgrade nimmt die Baseline neu.

Ohne Baseline läuft kein Sync. Der Lifespan nimmt sie nach dem Seed und vor reconcile_builtin_templates(), Best-Effort wie der Seed. Jeder Weg zu einem Sync nimmt sie, bevor er etwas ändert, womit sie vergleicht: reconcile_builtin_templates() und apply_builtin_update() vor der Zeilensperre, der Namensabgleich des Tag-Syncs vor den neuen Namen, PUT /templates/{id} vor den neuen Definitionen, restore_checks(), bevor die Tombstones gehen; sync_template() und sync_assignment() rufen sie ebenfalls (danach nur noch ein Lookup). Scheitert sie dort, unterbleibt dieser Sync, der Fehler geht wie jeder Sync-Fehler an den Aufrufer, und der nächste Start oder Sync versucht es erneut. Restrisiko: Eine Template-Änderung, die vor dem Update nie auf einen Check synchronisiert wurde, erscheint dort als angepasst.

Check-Tombstones

Die Tabelle monitor_check_tombstones (template_id mit FK auf monitor_templates und ON DELETE CASCADE, server_id mit Index, def_id; eindeutig je Tripel) merkt sich Template-Checks, die der Nutzer auf einem Server gelöscht hat. DELETE /checks/{id} legt den Tombstone an, solange der Server das Template zugewiesen hat (tombstone_check()); der Sync legt für ein so markiertes Tripel keinen Check an. Weg sind die Tombstones mit der Zuweisung (remove_template(), ein erneutes Zuweisen legt also alles wieder an), mit dem Server (cleanup_server(); keine FK, der Server lebt in der Server-DB), mit dem Template (Cascade) und beim Wiederherstellen. GET /templates/assignments/{server_id} liefert je Zuweisung removedChecks: die Tombstones des Paars, deren def_id noch im Template steht (check_def_ids()).

Der Monitoring-Tab des Desktops lädt die Vorschläge beim Öffnen und nach jeder Zuweisungsänderung; scheitert der Abruf (auch mit 404 eines älteren Monitoring-Dienstes), zeigt er keinen Vorschlag und keinen Fehler. „Zuweisen“ ruft je ausgewähltem Vorschlag POST /templates/{id}/assign, „Ignorieren“ je Slug die Ablehnung, nacheinander und bis zum ersten Fehler; danach lädt der Tab Vorschläge, Zuweisungen und Checks neu.

Tag-Sync (Server ↔ Monitoring)

Tags leben in der Server-DB (Server.tags); Monitoring kennt nur server_id-Strings. tag_sync.py zieht das Inventar über GET /api/internal/servers am AdminHelper-Server (Service-to-Service, X-Internal-Key) und materialisiert für jede MonitorTemplateTagAssignment die Server-Zuweisungen mit source='tag'. Trigger: alle 15 Minuten per Scheduler und sofort als Best-Effort-Nudge – der AdminHelper-Server POSTet nach Server-Create/-Update(Tags/Name/Hostname)/-Delete auf /templates/tag-sync. Verliert ein Server den Tag, wird die Tag-Zuweisung samt materialisierter Checks entfernt; source='manual'-Zuweisungen entfernt der Sync nie. Zusätzlich gleicht er für jede verbleibende Zuweisung, manuell wie per Tag, server_hostname/server_name mit hostname/name aus dem Inventar ab: Weichen sie ab, schreibt er die neuen Werte und synchronisiert genau dieses Paar neu (sync_assignment(); angepasste Check-Felder bleiben, Alert-Regeln werden neu gesetzt), damit {{hostname}}/{{server_name}} einer Umbenennung folgen. Ein Server, der im Inventar fehlt, bleibt unverändert; scheitert der Sync, wird zurückgerollt und die alten Namen bleiben. POST /templates/tag-sync antwortet mit {"created": n, "removed": m, "refreshed": k}. Ein nicht erreichbares Server-API (None) ist strikt von einem leeren Inventar ([]) unterschieden – ein Ausfall löscht keine Zuweisungen.

Alert-Pipeline: Sent-State, Guards & Suppression

Der Alerter ist level-getrieben (docs/features/alert-sent-state.md): monitor_states.notified_status hält den zuletzt real gemeldeten Status; die Migration c1d3e5f7a9b1 backfillt ihn mit status, damit ein Deploy keinen Nachmelde-Sturm auslöst. Beide Callsites (execute_check, Agent-Push-Handler) entscheiden per resolve_notification(notified_status, eff_status): skip (nichts Neues bzw. unknown), silent_ack (ein ok ohne gemeldetes Problem – wird inline gebucht, kein Dispatch) oder notify (BG-Dispatch). Reihenfolge in process_alert() (gilt für Regel-Dispatch und Hub-Emit, da emit_to_hub hinter denselben Guards sitzt):

  1. Claim-Phase: State-Load unter FOR UPDATE (kurzes Fenster ohne I/O; serialisiert konkurrierende BG-Dispatches), current = state.status wird unter dem Lock re-gelesen (der Caller-Snapshot kann stale sein) → resolve_notification: skip/silent_ack wie oben.
  2. Aktives Maintenance-Fenster des Servers → collect-but-mute: Status/Metriken laufen weiter, Benachrichtigung unterdrückt, kein Alert-Log-Eintrag, notified_status bleibt unangetastet → der nächste Zyklus nach Fenster-Ende meldet die Diskrepanz nach. is_in_maintenance() rechnet wöchentliche Fenster in der konfigurierten IANA-Zeitzone (zoneinfo, DST-korrekt; Tages-Wrap über Mitternacht inklusive).
  3. Host-down-Inhibition (_host_is_down()): ein Check bleibt stumm, solange auf seinem Server ein eingeschalteter Signal-Check auf critical steht, nach Rangfolge: der Host Ping (check_type ping mit template_def_id HOST_PING_DEF_ID = host-ping, aus dem Built-in „Host Ping“) nie, agent_ping durch einen Host Ping, alle anderen durch einen agent_ping oder Host Ping (ANY-Semantik, eine Abfrage). So schalten sich Heartbeat und Host Ping bei einem toten Host nicht gegenseitig stumm, und ein von Hand angelegter ping hemmt nichts. notified_status bleibt unangetastet → Catch-up, sobald das Signal wieder ok steht, auch für einen Heartbeat hinter dem Host Ping, den die Sammelmeldung aber erst nach seiner nächsten Auswertung meldet (_awaits_check, unten). Punkt 2 und 3 prüft muted_reason(db, check, now) und liefert den Grund ("maintenance window"/"host down") oder None.
  4. Melden (claim-then-dispatch): notified_status = current wird VOR der Kanal-I/O committet – der Row-Lock umspannt nie Webhook-/SMTP-Timeouts (5.3-Isolation bleibt intakt) und ein späterer Commit-Fehler kann einen bereits versendeten Alert nicht erneut feuern (at-most-once). Message/Alert-Log/Hub-Emit tragen als „old“ den zuletzt gemeldeten Status (reported_old); die Log-Rows kommen mit dem Caller-Commit. „Gemeldet“ heißt: der Claim ist persistiert, unabhängig vom Erfolg einzelner Kanäle (Rule-Cooldown kann eine Eskalations-Nachmeldung dämpfen, der Glocken-Cooldown den Hub-Emit).
  5. Glocke (Hub-Emit nach dem Regel-Dispatch): hub_decision(hub_status, hub_sent_at, new_status, severity, now) auf monitor_states.hub_status (was die Glocke zuletzt zeigte) und hub_sent_at (ihre letzte Problem-Meldung). emit für die Entwarnung eines gezeigten Problems (hub_status warning/critical), für die Eskalation eines gezeigten warning auf critical (gedeckelt) und für jede andere Problem-Meldung, wenn hub_sent_at mindestens HUB_COOLDOWN (30 min) zurückliegt; sonst und für die gedeckelte Stufe info skip. Was die Glocke verwirft, wird nicht nachgeholt (der Claim steht schon). Die Entscheidung fällt in der Claim-Phase unter demselben Lock, und bei emit reserviert der Claim-Commit den Platz: hub_status = der neue Status, gedeckelt auf die severity (_capped_status), bei einer Problem-Meldung auch hub_sent_at = jetzt. Ein Dispatch desselben Checks, der während des Hub-POSTs startet, liest so die Reservierung, nicht den Stand davor. Der POST selbst (post_hub_event) läuft nach dem Regel-Dispatch. Scheitert er (HTTP ≥ 300, Ausnahme, Hub nicht konfiguriert), gibt _release_hub_slot den Platz mit dem Caller-Commit per bedingtem UPDATE zurück (WHERE hub_status = reserviert AND hub_sent_at IS NOT DISTINCT FROM reserviert): Ein gescheiterter POST ändert nichts, solange kein neuerer Dispatch dazwischen reserviert hat; dessen Reservierung bleibt. Ein Dispatch, der eine Reservierung liest, deren POST danach scheitert, entscheidet nach ihr, schickt also etwa eine Entwarnung zu einem Alarm, den der Hub nicht angenommen hat. Die Entwarnung geht mit der Stufe hub_status an den Hub, nicht mit der dann gültigen severity. Die Migration 3c66308d11a7 backfillt hub_status aus notified_status (nur warning/critical), damit ein vor dem Update gemeldetes Problem seine Entwarnung bekommt.

Sammelmeldung der Heartbeats (app/alert_bundle.py): execute_check reicht ein notify eines agent_ping nicht an den Alert-Pool, die Abweichung bleibt in monitor_states offen. Der Sent-State ist damit der Puffer: keine eigene Tabelle, kein Speicher-Puffer, ein Neustart verliert nichts. Der System-Job system:agent-alert-bundle (schedule_agent_alert_bundle(), alle FLUSH_SECONDS = 30 s, max_instances=1 am Job) ruft flush_agent_alerts() mit eigener Session über database.SessionLocal. Kandidaten sind eingeschaltete agent_ping, für die resolve_notification notify sagt und die _reportable sind, getrennt nach critical (stumm) und ok (zurück): muted_reason schaltet sie nicht stumm, und _awaits_check hält sie nicht zurück. Das tut es, solange der Status noch aus einer inzwischen beendeten Stummschaltung stammen kann: last_check (ist es leer, since) liegt in einem Wartungsfenster des Servers (is_in_maintenance zu diesem Zeitpunkt), oder ein eingeschalteter Host Ping des Servers hat ein since danach (woher er wechselte, steht nirgends, also hält jeder Wechsel für eine Auswertung zurück). Die nächste Auswertung entscheidet: weiter critical → Meldung, ok → nie gemeldet, also nicht gehalten, still entwarnt (T19, Branch-Review). Ein gelöschtes oder abgeschaltetes Fenster sieht die Prüfung nicht. Je Art ab BUNDLE_MIN (3): Claim wie in process_alert (FOR UPDATE in check_id-Reihenfolge, Entscheidung und _reportable mit der Uhrzeit des Claims neu geprüft, notified_status vor jeder Kanal-I/O committet; bleiben weniger als drei, wird nichts geclaimt), dann send_bundle() je Kanal: je Regel ab drei Treffern eine Nachricht über send_to_rule (das erste Mitglied als Check, Payload mit members) und eine Alert-Log-Zeile je Mitglied; in der Glocke je gedeckelter Stufe ab drei ein Event mit source_ids (höchstens HUB_MAX_IDS = 500 je Event; Empfänger je Nutzer, siehe Server-Doku), darunter jeweils Einzelmeldungen. hub_status/hub_sent_at setzt erst ein angenommener POST, der Claim reserviert die Glocke also nicht; deshalb laufen nie zwei Jobs gleichzeitig. Weniger als drei warten, bis ihr since _alone_wait(interval) zurückliegt, und gehen dann einzeln über dispatch_alert_bg: BUNDLE_WINDOW (5 min), höchstens aber das Intervall des Checks minus 1 min, nie unter 0 (Standard-Heartbeat 5m: 4 min, 1m: sofort; ein Intervall, das der Scheduler nicht kennt, behält BUNDLE_WINDOW). Das Fenster endet so vor der nächsten Prüfung: Fand die den Agent wieder ok, entwarnte ein nie gemeldeter Ausfall still (holds_recovery hält nur Gemeldetes), und ein Heartbeat, der eine Prüfung lang critical war, bliebe ungemeldet (Kevin 2026-10-20). Das Intervall liefert scheduler.interval_timedelta().

Maintenance-CRUD liegt in routers/maintenance.py (/maintenance, require_internal; Proxy-Prefix maintenance).

VictoriaMetrics

Externer Container (siehe docker-compose.yml), Retention -retentionPeriod=${VM_RETENTION:-90d} – unabhängig von ALERT_LOG_RETENTION_DAYS (Alert-Log in Postgres). Der Service schreibt im InfluxDB-Line-Protocol über core/victoria.py:

bash
monitor_agent_cpu_percent,server_id=srv123 value=45.2 1683000000

format_line schreibt eine Ganzzahl im int64-Bereich (−263 bis 263−1) mit dem Suffix i (value=5i), eine außerhalb davon als Gleitkommazahl (value=9.223372036854776e+18): VictoriaMetrics liest einen Wert mit i als int64 und weist bei einem Überlauf den ganzen Schreibvorgang mit HTTP 400 ab, auch dessen gültige Zeilen; gespeichert wird ohnehin float64. Eine Zahl, die als float nicht endlich ist (inf, nan, eine Ganzzahl außerhalb des float-Bereichs), weist format_line ab; in den Metriken eines Check-Ergebnisses (build_check_result_lines) fällt sie allein weg.

Der Aufrufer schreibt nicht selbst: write hängt die Zeilen an einen Puffer im Prozess und kehrt ohne Netzwerk-I/O zurück, kein Check und kein Agent-Report wartet auf VictoriaMetrics. Der Puffer fasst 100 000 Zeilen und höchstens 64 MiB (gezählt als Speicher, den die Zeilen im Prozess belegen, sys.getsizeof); passt ein Aufruf nicht mehr hinein, werden dessen Zeilen ganz verworfen, und eine WARNING nennt die Zahl der seit der letzten Meldung verworfenen Zeilen: beim Verwerfen höchstens einmal je Minute, spätestens aber, sobald der Writer den Puffer geleert hat. Ein eigener Thread (victoria-writer, startet beim ersten write) schickt den Puffer in Stapeln bis 10 000 Zeilen je POST an /write. Timeout, Verbindungsfehler und HTTP 5xx versucht er bis zu dreimal (Pausen 0,5 s und 1 s), danach ist der Stapel verloren. Eine Antwort 4xx (VictoriaMetrics lehnt den Inhalt ab, etwa eine ungültige Zeile) wiederholt er nicht: Er loggt Status, Zeilenzahl und die ersten 200 Zeichen der Antwort (dort nennt VictoriaMetrics die fehlerhafte Zeile), der ganze Stapel ist verloren. Ein Stapel trägt die Zeilen aller Checks und Agent-Reports, die seit dem letzten POST anfielen, also auch die anderer Server: Lehnt VictoriaMetrics ihn wegen einer einzigen ungültigen Zeile ab, sind bis zu 10 000 Zeilen verloren, darunter fremde. Dasselbe gilt für jede andere Antwort unter 500, die nicht 2xx ist, auch eine Weiterleitung (3xx; der Client folgt ihr nicht). Das ist ein hingenommenes Restrisiko; die WARNING-Zeile von monitor.victoria nennt Status und Zahl der verlorenen Zeilen. Beim Herunterfahren ruft der Lifespan nach dem Scheduler close(), das den Puffer höchstens 5 s lang leert; was danach oder bei einem harten Abbruch noch im Puffer liegt, fehlt.

Reads laufen über den Standard-Prometheus-Endpoint /api/v1/query bzw. /api/v1/query_range. Im Desktop-Client zeichnet uPlot daraus die Charts. Die Chart-Queries der UI sind dabei nie roh: GET /checks/{id}/metrics baut die PromQL-Query serverseitig aus einer Metrik-Allowlist pro Check-Typ (CHECK_TYPE_METRICS) und escapet Label-Werte – Freitext-Queries aus der UI erreichen VictoriaMetrics nicht (SSRF-/Injection-Schutz).

Ein Check-Ergebnis schreibt build_check_result_lines mit den Labels check_id, check_type, name und server_id: monitor_check_status (0 ok, 1 warning, 2 critical, 3 unknown; daraus liest GET /checks/{id}/metrics die Status-Zeitleiste statusHistory), monitor_check_duration_ms und je Messwert monitor_<key>. Der Push-Pfad (routers/agent.py) schreibt den Status für jeden ausgewerteten Check, auch wenn nach _details keine Messwerte übrig bleiben (etwa system_state und agent_resources immer, Docker, ZFS und Proxmox ohne lesbare Daten oder ohne Block, Proxmox ohne VMs, smart_health ohne SMART-Daten); die Dauer (dort immer 0) schreibt er nur zusammen mit Messwerten. system_state steht deshalb ohne Metriken in CHECK_TYPE_METRICS, sein Endpunkt liefert nur die Zeitleiste. agent_resources schreibt nur seinen Status: CPU, RAM, Platten und Temperaturen schreibt der Push-Handler je Server ohne check_id (monitor_agent_cpu_percent, monitor_agent_memory_percent, monitor_agent_disk_percent mit mount, monitor_agent_temp mit sensor), und GET /checks/{id}/metrics liest sie für agent_resources mit server_id="…",check_id="", jeden anderen Check-Typ (auch einen agent_resources ohne server_id) über dessen check_id, so bleiben zwei Checks desselben Typs auf einem Server getrennt. Ein leerer Label-Wert wählt nach Prometheus-Semantik die Serien ohne dieses Label: CPU- und RAM-Serien mit Check-Labels, die ältere Versionen schrieben, bleiben bis zum Ende der Retention in VictoriaMetrics, der Endpunkt liest sie aber nicht mehr.

Ingest-Validierung

Der Push-Endpunkt prüft, dass der API-Key wirklich zur angegebenen server_id gehört. Ein kompromittierter Agent-Key kann also keine fremden Server-Metriken fälschen.
