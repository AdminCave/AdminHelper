Monitoring-Stack

Monitoring ist ein Zusammenspiel aus drei Ebenen: der AdminHelper-Server agiert als Reverse-Proxy und reicht UI-Queries weiter, der separate monitoring/-Service hält Checks/Alerts/Templates und führt Scheduler-Checks aus, VictoriaMetrics speichert die Zeitreihen (Retention konfigurierbar über VM_RETENTION, Default 90 Tage).

Daten-Fluss

flow
[Agent]                                [Monitoring-Service]            [VictoriaMetrics]
   |                                          |                                |
   | POST /agent/{server_id}/report --------->|  agent_resources, service_     |
   |   (X-API-Key)                            |  process, docker_health,        |
   |                                          |  proxmox_backup, zfs_health,    |
   |                                          |  smart_health -> evaluate +     |
   |                                          |  format_line() ---------------->|
   |                                          |                                |
                                              |  APScheduler -> http / ping /  |
                                              |  tcp / agent_ping ------------>|
                                              |
[Desktop-Client] -> /api/monitoring/* (admin) -> AdminHelper-Server -> /monitor/* (X-Internal-Key) -> Monitoring-Service

AdminHelper-seitig: monitoring_proxy

Im AdminHelper-Server gibt es kein eigenes Monitoring-Modul mehr; alles läuft durch apps/server/app/modules/monitoring_proxy/router.py:

  • POST /api/monitoring/agent/{server_id}/report – öffentlich (X-API-Key), reicht 1:1 an den Service
  • GET/POST/PUT/DELETE /api/monitoring/{path:path} – admin-only, intern erweitert um X-Internal-Key: $MONITOR_API_KEY
  • SSRF-Schutz: erlaubte Pfad-Prefixe sind checks, alerts, status, templates, maintenance, agent; Path-Traversal (..) wird blockiert
  • Beim Server-Delete im AdminHelper wird DELETE /servers/{id}/cleanup am Monitoring-Service gefeuert – verwaiste Checks/Alerts werden so automatisch aufgeräumt

Push-Checks vs. Pull-Checks

Es gibt zwei Klassen von Checks – entscheidend ist, wer die Daten beschafft:

ModusCheck-TypenTrigger
Push (Agent)agent_resources, service_process, docker_health, proxmox_backup, zfs_health, smart_healthBeim nächsten Agent-Push (5-Min-Timer); APScheduler ist nicht beteiligt.
Pull (Service)http, ping, tcp, agent_ping, disk_forecastAPScheduler im Monitoring-Service nach festem interval.

Beide Pfade schreiben das Ergebnis über apply_result() (check_engine.py) in MonitorState, die Metriken über format_line() nach VictoriaMetrics und rufen ggf. process_alert(), sobald fail_count ≥ consecutive_fails. Bis dahin behält effective_status() (check_engine.py) den alten Status; ein neuer Check (pending) zeigt dabei ok, außer das Ergebnis ist unknown: dann unknown, damit ein Check ohne Daten nicht grün steht. Das kostet keine Benachrichtigung, unknown meldet nie.

In die andere Richtung hält holds_recovery() die Entwarnung, aber nur für ein gemeldetes Problem: Ist notified_status warning/critical und steht der Check auf warning, critical oder unknown, setzt apply_result() ihn bei einem ok auf notified_status, bis MonitorState.ok_count consecutive_oks erreicht (Default 2, Migration c3e5a7b9d1f2 setzt ihn für bestehende Checks). Gehalten wird also der gemeldete Status, nie ein schlimmerer, den der Check nur stumm erreicht hat; das Halten eskaliert nicht und meldet nichts (resolve_notification → skip). Ein nie gemeldetes Problem (stumm durch Wartung oder Host-down) wird beim ersten ok sofort und still ok; gehalten würde es als neuer Alarm nachgemeldet. next_ok_count() zählt ok hoch und setzt bei jedem anderen Ergebnis auf 0; die Meldung trägt während des Haltens „(recovery n/m)“. pending → ok und ok → ok halten nie, consecutive_oks 1 hält nie. Weil der Status selbst gehalten wird, bleiben Dashboard, Glocke und die Host-down-Inhibition eines agent_ping während des Haltens beim Problem.

Der APScheduler (scheduler.py) läuft mit einem ThreadPool von 30 Workern und misfire_grace_time=30 s – verzögert startende Runs werden bis 30 s nachgeholt statt verworfen. Ein täglicher Cleanup-Job bereinigt außerdem monitor_alert_log (Retention über ALERT_LOG_RETENTION_DAYS, Default 90 Tage), und alle 15 Minuten läuft der Tag-Sync (siehe unten).

Push-Payload (Agent → Service)

Der Go-Agent baut den Report in apps/agent/internal/monitor/report.go (BuildReport) und sendet ihn als JSON per POST {url}/agent/{server_id}/report mit den Headern Content-Type: application/json und X-API-Key (PushReport). Der Server-Handler in routers/agent.py nimmt das JSON als freies dict entgegen. Struktur:

Felder sind optional: docker und zfs erscheinen, sobald docker bzw. zpool auf dem Host liegt, auch wenn der Agent sie nicht lesen kann. Dann tragen sie available: false, error (Docker daemon_unreachable | timeout | cli_failed | parse_failed, ZFS timeout | cli_failed), error_message (kurzer Text mit Aufruf und Exit-Status, nie stderr oder Pfade) und eine leere Liste (siehe Agent). proxmox erscheint nur mit Daten. Statt smart schickt der Agent ohne lesbare Platte smart_absent.reason (not_installed | scan_failed | no_devices). Diese Felder und die Container-Felder ab exit_code sind additiv: ältere Agents senden sie nicht, ältere Monitoring-Dienste ignorieren sie und werten einen Ausfall als leere Liste (ok). Auch host ist additiv: Ältere Agents senden es nicht, ältere Monitoring-Dienste ignorieren es. Ein aktueller Agent schickt es bei jedem Push (collectHostFacts() in apps/agent/internal/monitor/hostfacts.go): os ist runtime.GOOS; platform und platform_version kommen aus gopsutil host.PlatformInformation() (unter Windows der Produktname), virtualization mit system und role aus host.Virtualization() (leer, wenn nichts erkannt wird, unter Windows immer). Scheitert einer der beiden Aufrufe, fehlen nur seine Felder, nie der Block. subsystems ist immer eine Liste, in der Reihenfolge docker, zfs, proxmox mit jedem Eintrag, dessen Programm (docker, zpool bzw. pvesh) im Suchpfad liegt, unabhängig davon, ob die Plugin-Collector Daten liefern. Was der Dienst daraus macht, steht unter Vorschläge aus den Host-Fakten. VMs ohne Sensoren liefern keine temperatures. services ist ein Legacy-Key parallel zu systemd. Der Handler iteriert über resources (CPU/RAM/Load/Disk/Temp), uptime_seconds und smart, schreibt daraus VictoriaMetrics-Zeilen (Pseudo-Dateisysteme aus EXCLUDED_FSTYPES werden übersprungen) und wertet anschließend die fuer den Server konfigurierten Push-Checks gegen den Report aus. Antwort: {"status":"ok","metricsWritten":N,"checksUpdated":M}.

systemd.all_services ist zusätzlich gedrosselt: der Agent sendet das volle Inventar nur, wenn sich dessen Hash geändert hat oder der letzte Voll-Send über 1 h zurückliegt – fehlender Key ≠ leere Liste (leere Liste heißt: wirklich keine Services). Bei jedem Push dabei sind failed, enabled_inactive (vom Agent schon um absichtlich inaktive Units bereinigt, siehe Agent) und counts (active/total der geladenen Dienste; fehlt, wenn der Agent sie nicht auflisten konnte). Scheitert systemctl list-units bzw. sc query, trägt error einen kurzen Grund. Der Checker übernimmt ihn auf 500 Zeichen gekürzt (samt „…“) in die Meldung; ist er kein String, zählt der Fehler weiter, die Meldung nennt aber keinen Grund. Alias-Einträge im Inventar (enabled_state alias) nennen in alias_of ihre Unit. counts, error und alias_of sind additiv: ältere Agents senden sie nicht, ältere Monitoring-Dienste ignorieren sie. Der ServiceProcessChecker wertet aus:

  • auto: enabled_inactive übernimmt er unverändert vom Agent und leitet es nicht aus all_services ab; failed ist systemd.failed plus die failed-Einträge des Inventars (auf 500 gekappt, dank der Sortierung immer dieselben). Ein voller und ein gedrosselter Push desselben Zustands geben so dasselbe Ergebnis. ignore-Einträge sind Glob-Muster (fnmatch.fnmatchcase), ein Name ohne Unit-Typ passt auch auf <name>.service. Ohne Problem, aber mit error ist der Check unknown statt ok. Gültige counts (ganze Zahlen, 0 ≤ active ≤ total) landen als active_count/total in _details.
  • list: Je Name (ohne Unit-Typ normalisiert auf <name>.service) entscheidet die erste Quelle, die ihn kennt: report["services"] (Agent mit eigener Liste aus monitor init --services), dann all_services dieses Pushes (ein Alias über alias_of), und bei einem Push ohne Inventar der Stand der letzten Auswertung (prev_details.watched; der Push-Handler in routers/agent.py reicht service_process wie agent_resources die vorigen _details durch). Ein volles Inventar ist der aktuelle Stand und wird nicht aus prev_details ergänzt. _details.watched ist [{name, state, running}] mit state ∈ {running, down, nodata}; running (state == "running") bleibt für Desktops, die state noch nicht kennen. Status: critical bei mindestens einem down, unknown, wenn kein Name Daten hat, sonst ok; nodata zählt nicht als down.

Checker im Überblick

Jeder Checker liefert ein Tripel (status, message, metrics) mit status ∈ {ok, warning, critical, unknown}. message ist englisch und geht so in Dashboard, Glocke und Benachrichtigungen; der Desktop übersetzt, wo er aus _details rendert. Nennt die Meldung eine Liste (VMs, Pools, Container, Platten, Dienste, Mounts), geht sie über join_capped in checkers/agent.py: Der Helfer kürzt jeden Eintrag auf 500 Zeichen (samt „…“), nennt der Reihe nach höchstens 10 Einträge und höchstens 1000 Zeichen (Einträge samt Trennern), den ersten immer, und zählt die übrigen als „(+N more)“. _details trägt weiter jeden ausgewerteten Eintrag; Status und Metriken bleiben gleich. Zusätzlich kürzt apply_result() in check_engine.py, der einzige Schreiber von MonitorState.message, jede Meldung auf 2000 Zeichen (samt „…“), auch das „Unexpected error: …“ eines Scheduler-Checks; erst danach hängt sie bei einem gedämpften Fehler „(failure n/m)“ an, bei einer gehaltenen Entwarnung „(recovery n/m)“. _details bleibt vollständig. Pull-Checker haben eine run(config)-Methode; Agent-/Push-Checker werten in evaluate(config, report) direkt den Push-Report aus.

CheckerTyp(en)Was er tut
http.pyhttpHTTP/HTTPS-Request via httpx (Methode konfigurierbar, folgt Redirects). Vergleicht Statuscode mit expected_status, optional Suche nach search_string im Body, misst Antwortzeit. SSRF-Schutz: URLs, die auf private/reservierte IP-Bereiche auflösen, werden abgewiesen.
ping.pypingICMP-Echo via ping -c 1 -W <timeout> als Subprozess. Ziel wird gegen ein Allowlist-Regex (Hostnamen/IPs) validiert; parst die RTT aus dem Output. Kein Private-/Reserved-Block (anders als http.py): interne Hosts zu pruefen ist der Kern-Anwendungsfall, das Signal ist reine Erreichbarkeit und Checks anlegen darf nur ein Admin.
tcp.pytcpTCP-Connect via socket.create_connection((target, port)) mit Timeout. ok bei erfolgreichem Connect (mit Connect-Zeit), critical bei Timeout/Refused. Wie ping.py ohne Private-/Reserved-Block – ein Connect liefert keinen Antwort-Inhalt.
agent.pyagent_ping, agent_resources, service_processAgentPingChecker prüft (scheduler-getrieben) das Alter des letzten Push gegen stale_minutes. AgentResourcesChecker wertet CPU/RAM/Disk/Temp gegen Warn-/Crit-Thresholds aus. Er liest CPU, RAM, Plattenwerte (percent) und Sensorwerte (temp_c) nur als JSON-Zahl (kein bool, als endliches float darstellbar), fstype, mount und sensor nur als String; alles andere gilt als fehlend (CPU/RAM unbewertet, Platte und Sensor 0). Ausgewertet werden höchstens die ersten 500 Platten bzw. Sensoren; ein Eintrag, der kein Objekt ist, wird übersprungen, und ein resources, das kein Objekt ist, gilt als fehlend („No resource data“). ServiceProcessChecker prüft Dienste – Modus auto (failed + die vom Agent gemeldeten enabled-but-inactive systemd-Units, mit Ignore-Liste aus Glob-Mustern) oder list (explizit benannte Dienste, serverseitig aus Inventar und letztem Stand ausgewertet; Details unter Push-Payload). Der Resources-Checker arbeitet pro Metrik mit Hysterese (hysteresis_pp, Release = Entry − 10 pp); die Push-Zeitpunkte persistiert der Push-Handler (routers/agent.py) in monitor_agent_liveness, der Lifespan hydratisiert sie beim Start; zusätzlich hält der Checker prozess-lokal einen monotonen Zeitstempel. Weicht die Wanduhr-Differenz um > 60 s davon ab, ist die Uhr des Monitoring-Hosts gesprungen: der Checker rechnet mit der monotonen (wahren) Alterszeit weiter und verankert den gespeicherten Wanduhr-Stempel neu — bewusst eine Korrektur, kein Abbruch mit unknown, denn das würde einen toten Agent als frisch melden und agent_ping aus der Host-down-Inhibition (die auf critical matcht) herausfallen lassen. Für hydrierte Server ohne Monoton-Wert gilt weiter die reine Wanduhr; die persistierte Row wird erst beim nächsten Push aktualisiert, ein Neustart direkt nach einem Sprung fällt also für bis zu ein Push-Intervall auf das alte Verhalten zurück – kein False-Alert-Sturm nach einem Monitoring-Restart.
forecast.pydisk_forecastPull-Checker: query_range über monitor_agent_disk_percent_value{server_id="…"} (Fenster window_hours, Step 10 m), Least-Squares-Slope pro Mount → hours_left = (100 − last) / rate. Raten ≤ 0.01 pp/h gelten als stabil (ok); zu wenig Historie → unknown. server_id wird mit escape_label_value() escapet.
smart.pysmart_healthWertet SMART-Daten aus dem Push aus (ATA-HDD/SSD und NVMe). Prüft u. a. reallocated/pending Sectors, NVMe-critical_warning-Bits und Temperaturen gegen typ-spezifische Thresholds. Fehlt der smart-Key, ist das ok, kein Fehler: Mit smart_absent nennt die Meldung den Grund (No SMART data: …), und _details ist {"absent": <reason>}; ohne (älterer Agent oder unbekannter Grund) bleibt es bei „No SMART data (VM or smartctl not available)“ ohne Details. Ausgewertet werden höchstens die ersten 500 Platten eines Reports; ein Eintrag, der kein Objekt ist, wird übersprungen, und ein smart, das keine Liste ist, gilt als leer wie ein fehlender Key. Die Zahlenfelder einer Platte (alle int-Felder von SmartDisk in apps/agent/internal/monitor/smart.go, etwa temp_c, smartctl_status, reallocated_sectors, available_spare_pct, critical_warning) zählen nur als JSON-Zahl (kein bool, als endliches float darstellbar; auch ein Zahl-String wie "16" zählt nicht), device und kind nur als String. Alles andere gilt als fehlend, mit dem Default ohne das Feld (Gerät ?, kind aus protocol, Zähler und Temperatur 0, available_spare_pct 100; in _details stehen available_spare_pct und percentage_used dann auf null). Meldung, Metriken und _details tragen die gelesenen Werte.

Die Plugin-Checker proxmox_backup, zfs_health und docker_health (in checkers/plugins.py) sind ebenfalls Push-ausgewertet. Alle drei werten höchstens die ersten 500 VMs (proxmox.vms), Pools (zfs.pools) bzw. Container (docker.containers) eines Reports aus; ein Wert dort, der keine Liste ist, gilt als leer, ein Eintrag, der kein Objekt ist, wird übersprungen (für die Grenze zählt er mit), und ein Block proxmox, zfs oder docker, der kein Objekt ist, gilt als fehlend. Die Zahlenfelder eines Eintrags (vmid und last_backup_ts einer VM, capacity_percent eines Pools, exit_code und restart_count eines Containers) zählen nur als JSON-Zahl (kein bool, als endliches float darstellbar), vmid, exit_code und restart_count nur als ganze Zahl in Ganzzahl-Schreibweise (ein JSON-3.0 gilt als fehlend); type einer VM zählt nur als String. Alles andere gilt als fehlend, mit dem Default ohne das Feld (type vm, Belegung 0 %, health zählt weiter); ein unlesbarer Backup-Zeitstempel ist „No backup“ (critical). Für zfs_health und docker_health gilt:

  • Block fehlt: unknown mit _details {"pools": []} bzw. {"containers": []} statt None – der Push-Pfad behält sonst die gespeicherten Details eines Ergebnisses ohne Details, und der Desktop zeigte die alte Liste weiter.
  • Ausfall (available: false oder error gesetzt): warning mit ZFS unavailable (<code>): <error_message> bzw. Docker unavailable (…), _details mit available: false, error und leerer Liste. Nur ein JSON-false ist ein Ausfall; null, 0 oder "false" lassen die Pools bzw. Container entscheiden. Den Code übernimmt der Checker nur aus der Liste des Agents (oben); ein anderer Wert bleibt ein Ausfall, aber ohne Code (ZFS unavailable bzw. Docker unavailable, _details.error null). error_message geht auf 500 Zeichen gekürzt (samt „…“) in die Meldung, ein Wert, der kein String ist, gar nicht. alert_on_unavailable (StrictBool in ZfsHealthConfig und DockerHealthConfig, Default true) macht daraus unknown; der Checker schaltet nur bei einem echten false ab. Lesbar, aber ohne Pools bzw. Container ist ok; sonst tragen die Details available: true und error: null.
  • docker_health bekommt wie agent_resources und service_process die vorigen _details (evaluate(config, report, prev_details), _PREV_DETAILS_TYPES in routers/agent.py) für den Neustart-Zähler je Container-ID; einen Vorwert gibt es nur für eine ID vom Typ String (der Agent schickt die 12-stellige Kurz-ID). Ohne name heißt der Container nach dieser ID, ist sie kein String, ?. name, state und der Statustext status zählen nur als String: ein anderer name gilt als fehlend, ein anderer state als leer (unknown_state), ein anderer Statustext liefert weder Exit-Code noch unhealthy. In die Meldung und in _details gehen name und state auf 500 Zeichen gekürzt (samt „…“); ignore_containers vergleicht mit dem vollen Namen, die Bewertung liest den vollen state. _details.containers ist [{id, name, image, state, category, reason, exit_code, restart_count}] mit category ∈ {ok, warning, critical, stopped} und reason ∈ unhealthy, restarted, restarting, dead, paused, created, start_failed, oom, stopped, exit:<n>, unknown_state (null bei ok); die Regeln stehen im Admin-Handbuch. Der Status ist die schlechteste Kategorie, stopped zählt als ok. Ohne exit_code bzw. health (älterer Agent) liest der Checker Exit-Code und unhealthy aus dem Statustext von docker ps; ebenso bei einem exit_code, der keine ganze Zahl ist. Einen Exit-Code mit mehr als 10 Ziffern im Statustext liest er nicht, der Container gilt dann wie ohne Exit-Code. Ein restart_count, der keine ganze JSON-Zahl ist, gilt als fehlend, der Container zählt dann nicht als neu gestartet. Die Meldungen sind englisch, der Desktop übersetzt aus den Codes.

Auth-Modi

Beide Modi sind in core/auth.py als FastAPI-Dependencies implementiert:

  • require_agent (Agent-Push): liest Header X-API-Key. Stimmt der Wert exakt mit dem internen Key überein, gilt er als __internal__ (Zugriff auf alle Server). Andernfalls wird der Key per MonitorAgentKey.hash_key() SHA-256-gehasht und gegen die Spalte hashed_key in monitor_agent_keys verglichen – bei Treffer liefert die Dependency die zugehörige server_id zurück. Es wird also nie ein Klartext-Key gespeichert; in der DB liegt nur der Hash.
  • require_internal (AdminHelper ↔ Service): liest Header X-Internal-Key und vergleicht ihn gegen den internen Key. Quelle ist die Env-Variable MONITOR_API_KEY; fehlt sie, wird beim Start ein zufälliger Key generiert und in $DATA_DIR/.api_key persistiert (core/config.py).

Agent-Key: Vergabe & Server-Bindung

Agent-Keys werden pro Server vergeben (routers/admin.py):

  • POST /agent-keys/{server_id} erzeugt mit secrets.token_urlsafe(48) einen Raw-Key, speichert nur dessen SHA-256-Hash und gibt den Raw-Key einmalig in der Antwort zurück. Existiert bereits ein Key für den Server, wird er vorher gelöscht (Rotation = DELETE + POST). server_id ist in der Tabelle unique, also genau ein Key pro Server.
  • Beide Endpunkte (POST/DELETE /agent-keys/{server_id}) sind selbst über require_internal geschützt – nur der AdminHelper-Server darf Keys verwalten.
  • Im Push-Handler (routers/agent.py) wird zusätzlich geprüft, dass die aus dem Key abgeleitete server_id der server_id im Pfad entspricht; sonst 403. Ein gültiger Key für Server A kann also keine Metriken für Server B einliefern (__internal__ ausgenommen).

Templates, Seeding & Tag-Sync

MonitorTemplate bündelt Check- und Alert-Definitionen als JSON mit stabiler def_id pro Definition. POST /templates/{id}/assign (Body {server_id, hostname, server_name}) rollt das Template aus; template_sync.py reconciled bei Änderungen, sodass die Server-Zuweisungen drift-frei bleiben.

Built-in-Seeding (Tombstone)

Der Lifespan seedet beim Start fünf Standard-Templates aus builtin_templates.py (markiert über builtin_slug). Der Tombstone in monitor_seed_state garantiert: pro Slug wird höchstens einmal geseedet – ein vom Nutzer gelöschtes Built-in wird von späteren Starts nie wiederhergestellt; neue Built-ins späterer Releases seeden nur sich selbst. Was ein späterer Start mit einem bestehenden Built-in macht, regelt seine Version (nächster Abschnitt). Die Definitionen passieren dieselbe Schema-Boundary wie User-Templates (Test tests/test_seed.py).

Built-in-Versionen

Jeder Eintrag in BUILTIN_TEMPLATES trägt "version"; eine geänderte Definition wird als neue Version ausgeliefert. Die Zeile merkt sich in monitor_templates.builtin_version die zuletzt ausgerollte Version und in builtin_hash den sha256 der dabei ausgerollten Definitionen (beide NULL bei Nutzer-Templates; Migration a7c9e1b3d5f7). definitions_hash() hasht das kanonische JSON (sort_keys=True, separators=(",", ":")) von canonical_definitions(check_definitions, alert_definitions): beide Listen ohne die Schlüssel, die ihren Schema-Default aus TemplateCheckDef bzw. TemplateAlertDef tragen. Grund: Der Editor speichert jede Definition vollständig (model_dump), die mitgelieferten lassen Defaults weg, und ein neues optionales Schema-Feld darf nicht den Hash jeder Installation ändern. Name und Beschreibung des Templates zählen nicht; ein umbenanntes Built-in folgt neuen Versionen weiter.

Nach dem Seeding und der Baseline (record_override_baseline(), unten) ruft der Lifespan reconcile_builtin_templates() (Best-Effort wie das Seeding, vor load_all_checks()). Eine Zeile mit builtin_slug, aber ohne Hash (vor den Versionen angelegt) bekommt Version 1 und den Hash der mitgelieferten Definitionen; weichen ihre Definitionen davon ab, gilt sie damit als angepasst. Ist die mitgelieferte Version höher und der Hash der aktuellen Definitionen gleich builtin_hash, ersetzt _roll_out() die Definitionen (Name und Beschreibung bleiben), setzt Version und Hash und ruft sync_template(); angepasste Check-Felder bleiben. Sonst ändert sich nichts. Jede Entscheidung fällt unter der Zeilensperre (with_for_update() mit populate_existing(), wirksam auf Postgres): Ein zweiter Start oder ein gleichzeitiges „Übernehmen“ sieht danach die neue Version und synchronisiert nicht doppelt. MonitorTemplate.to_dict() liefert builtinVersion, builtinEdited (Hash der aktuellen Definitionen ≠ builtin_hash) und builtinUpdateAvailable (mitgelieferte Version > builtin_version).

Anpassungen an Template-Checks (overridden_fields)

monitor_checks.overridden_fields (Text, NOT NULL, Default '[]') hält als JSON-Liste die Felder eines Template-Checks, die der Nutzer geändert hat, mit den Spaltennamen in snake_case und in fester Reihenfolge (TEMPLATE_CHECK_FIELDS): name, description, check_type, config, enabled, interval, severity, consecutive_fails, consecutive_oks. PUT /checks/{id} und POST /checks/{id}/toggle rufen mark_overrides(): Jedes gesendete Feld wird mit dem aufgelösten Template-Wert verglichen (resolve_template_check(): Definition mit den Variablen der Zuweisung substituiert, fehlende Schlüssel mit den Defaults eines neuen Checks, bei consecutive_oks DEFAULT_CONSECUTIVE_OKS = 2 aus schemas.py), anders → aufnehmen, gleich → streichen. Steht check_type in der Liste, steht config immer mit drin. Manuelle Checks und Checks, deren Zuweisung oder Definition fehlt, bleiben unberührt. _sync_checks_for_server() schreibt beim Aktualisieren nur die Felder, die nicht in der Liste stehen; ist config angepasst, auch check_type nicht. Eine Definition, die nicht mehr im Template steht, löscht ihren Check weiterhin, angepasst oder nicht. Alert-Regeln haben kein Gegenstück: _sync_alerts_for_server() setzt sie bei jedem Sync auf die Template-Werte. MonitorCheck.to_dict() liefert dazu templateDefId und overriddenFields (Liste).

Baseline beim ersten Start (record_override_baseline)

Bestandschecks starten mit []. record_override_baseline() markiert einmal je Installation, was vorher von Hand geändert wurde: Für jeden Check mit template_id ruft sie mark_overrides() mit allen aktuellen Werten des Checks, jedes vom Template abweichende Feld gilt also als angepasst, mit der Kopplung Typ/Config. Aufgelöst wird mit server_hostname/server_name der Zuweisung, den Namen, aus denen der Check gebaut wurde; ein seither umbenannter Server ist keine Anpassung. Manuelle Checks und Checks, deren Zuweisung oder Definition fehlt, bleiben, wie sie sind. Ein Check, der sich nicht vergleichen lässt (ValueError, TypeError oder AttributeError aus unlesbarer Config oder Definition), bekommt alle Felder und eine Warnung mit seiner ID; Datenbankfehler lassen den Lauf scheitern. Die Logzeile zählt markierte und nicht vergleichbare Checks. Für das später hinzugekommene consecutive_oks läuft sie in bestehenden Installationen nicht erneut: Vor dem Update konnte niemand das Feld ändern, jeder Check trägt den Spalten-Default 2.

Erledigt ist der Lauf mit dem reservierten Schlüssel baseline:overridden-fields (OVERRIDE_BASELINE_KEY) in monitor_seed_state, im selben Commit wie die Markierungen; der Doppelpunkt hält ihn aus dem Slug-Namensraum der Built-ins. Steht der Schlüssel, vergleicht kein Lauf mehr. Die Migration a7c9e1b3d5f7 löscht ihn beim Upgrade, wenn sie overridden_fields anlegt: Ein Downgrade verwirft die Markierungen, und das nächste Upgrade nimmt die Baseline neu.

Ohne Baseline läuft kein Sync. Der Lifespan nimmt sie nach dem Seed und vor reconcile_builtin_templates(), Best-Effort wie der Seed. Jeder Weg zu einem Sync nimmt sie, bevor er etwas ändert, womit sie vergleicht: reconcile_builtin_templates() und apply_builtin_update() vor der Zeilensperre, der Namensabgleich des Tag-Syncs vor den neuen Namen, PUT /templates/{id} vor den neuen Definitionen, restore_checks(), bevor die Tombstones gehen; sync_template() und sync_assignment() rufen sie ebenfalls (danach nur noch ein Lookup). Scheitert sie dort, unterbleibt dieser Sync, der Fehler geht wie jeder Sync-Fehler an den Aufrufer, und der nächste Start oder Sync versucht es erneut. Restrisiko: Eine Template-Änderung, die vor dem Update nie auf einen Check synchronisiert wurde, erscheint dort als angepasst.

Check-Tombstones

Die Tabelle monitor_check_tombstones (template_id mit FK auf monitor_templates und ON DELETE CASCADE, server_id mit Index, def_id; eindeutig je Tripel) merkt sich Template-Checks, die der Nutzer auf einem Server gelöscht hat. DELETE /checks/{id} legt den Tombstone an, solange der Server das Template zugewiesen hat (tombstone_check()); der Sync legt für ein so markiertes Tripel keinen Check an. Weg sind die Tombstones mit der Zuweisung (remove_template(), ein erneutes Zuweisen legt also alles wieder an), mit dem Server (cleanup_server(); keine FK, der Server lebt in der Server-DB), mit dem Template (Cascade) und beim Wiederherstellen. GET /templates/assignments/{server_id} liefert je Zuweisung removedChecks: die Tombstones des Paars, deren def_id noch im Template steht (check_def_ids()).

Vorschläge aus den Host-Fakten

Ist host im Report ein Objekt, reicht der Push-Handler es nach der NUL-Prüfung und vor der Check-Auswertung an store_host_facts() (app/template_suggestions.py). Die schreibt je Server eine Zeile in monitor_host_facts (server_id als Schlüssel, os, platform, platform_version, virt_system, virt_role, subsystems als JSON-Liste, updated_at = letzter Report; Migration b9d1f3a5c7e9) und prüft dabei: os nur aus linux, windows, darwin, sonst NULL; die übrigen Strings werden auf 64 Zeichen gekürzt, "" und Werte eines anderen Typs werden NULL; subsystems behält nur docker, zfs und proxmox, in dieser Reihenfolge, den Rest verwirft sie. Ein falscher Wert kostet nur sein Feld. Sie committet selbst und loggt einen Fehler nur (ohne Traceback): Wie die Liveness kostet das Speichern der Fakten nie den Report. Fehlt host (ein älterer Agent) oder ist es kein Objekt, bleiben gespeicherte Fakten, wie sie sind.

suggest_templates() leitet daraus die Vorschläge ab, das OS zuerst: os linux → linux-base, windows → windows-base (darwin hat kein Standard-Template), Subsystem docker → docker-host, zfs → zfs-storage, proxmox → proxmox-host. Vorgeschlagen wird ein Slug nur, wenn ein Template mit diesem builtin_slug existiert (ein gelöschtes Built-in also nicht), es dem Server nicht zugewiesen ist (gleich mit welcher source) und dort nicht ignoriert wurde. Eine Ablehnung ist eine Zeile in monitor_template_suggestion_dismissals (server_id mit Index, builtin_slug, dismissed_at; eindeutig je Paar); eine Route, die sie zurücknimmt, gibt es noch nicht. Beide Tabellen haben keine FK auf den Server; cleanup_server() löscht ihre Zeilen mit.

Tag-Sync (Server ↔ Monitoring)

Tags leben in der Server-DB (Server.tags); Monitoring kennt nur server_id-Strings. tag_sync.py zieht das Inventar über GET /api/internal/servers am AdminHelper-Server (Service-to-Service, X-Internal-Key) und materialisiert für jede MonitorTemplateTagAssignment die Server-Zuweisungen mit source='tag'. Trigger: alle 15 Minuten per Scheduler und sofort als Best-Effort-Nudge – der AdminHelper-Server POSTet nach Server-Create/-Update(Tags/Name/Hostname)/-Delete auf /templates/tag-sync. Verliert ein Server den Tag, wird die Tag-Zuweisung samt materialisierter Checks entfernt; source='manual'-Zuweisungen entfernt der Sync nie. Zusätzlich gleicht er für jede verbleibende Zuweisung, manuell wie per Tag, server_hostname/server_name mit hostname/name aus dem Inventar ab: Weichen sie ab, schreibt er die neuen Werte und synchronisiert genau dieses Paar neu (sync_assignment(); angepasste Check-Felder bleiben, Alert-Regeln werden neu gesetzt), damit {{hostname}}/{{server_name}} einer Umbenennung folgen. Ein Server, der im Inventar fehlt, bleibt unverändert; scheitert der Sync, wird zurückgerollt und die alten Namen bleiben. POST /templates/tag-sync antwortet mit {"created": n, "removed": m, "refreshed": k}. Ein nicht erreichbares Server-API (None) ist strikt von einem leeren Inventar ([]) unterschieden – ein Ausfall löscht keine Zuweisungen.

Alert-Pipeline: Sent-State, Guards & Suppression

Der Alerter ist level-getrieben (docs/features/alert-sent-state.md): monitor_states.notified_status hält den zuletzt real gemeldeten Status; die Migration c1d3e5f7a9b1 backfillt ihn mit status, damit ein Deploy keinen Nachmelde-Sturm auslöst. Beide Callsites (execute_check, Agent-Push-Handler) entscheiden per resolve_notification(notified_status, eff_status): skip (nichts Neues bzw. unknown), silent_ack (ein ok ohne gemeldetes Problem – wird inline gebucht, kein Dispatch) oder notify (BG-Dispatch). Reihenfolge in process_alert() (gilt für Regel-Dispatch und Hub-Emit, da _emit_to_hub hinter denselben Guards sitzt):

  1. Claim-Phase: State-Load unter FOR UPDATE (kurzes Fenster ohne I/O; serialisiert konkurrierende BG-Dispatches), current = state.status wird unter dem Lock re-gelesen (der Caller-Snapshot kann stale sein) → resolve_notification: skip/silent_ack wie oben.
  2. Aktives Maintenance-Fenster des Servers → collect-but-mute: Status/Metriken laufen weiter, Benachrichtigung unterdrückt, kein Alert-Log-Eintrag, notified_status bleibt unangetastet → der nächste Zyklus nach Fenster-Ende meldet die Diskrepanz nach. is_in_maintenance() rechnet wöchentliche Fenster in der konfigurierten IANA-Zeitzone (zoneinfo, DST-korrekt; Tages-Wrap über Mitternacht inklusive).
  3. Host-down-Inhibition: steht der agent_ping des Servers auf critical, bleiben alle anderen Checks des Servers stumm (notified_status unangetastet → Catch-up nach der Agent-Recovery); agent_ping selbst alertet immer.
  4. Melden (claim-then-dispatch): notified_status = current wird VOR der Kanal-I/O committet – der Row-Lock umspannt nie Webhook-/SMTP-Timeouts (5.3-Isolation bleibt intakt) und ein späterer Commit-Fehler kann einen bereits versendeten Alert nicht erneut feuern (at-most-once). Message/Alert-Log/Hub-Emit tragen als „old“ den zuletzt gemeldeten Status (reported_old); die Log-Rows kommen mit dem Caller-Commit. „Gemeldet“ heißt: der Claim ist persistiert, unabhängig vom Erfolg einzelner Kanäle (Rule-Cooldown kann eine Eskalations-Nachmeldung dämpfen; der Hub-Emit läuft immer).

Maintenance-CRUD liegt in routers/maintenance.py (/maintenance, require_internal; Proxy-Prefix maintenance).

VictoriaMetrics

Externer Container (siehe docker-compose.yml), Retention -retentionPeriod=${VM_RETENTION:-90d} – unabhängig von ALERT_LOG_RETENTION_DAYS (Alert-Log in Postgres). Der Service schreibt im InfluxDB-Line-Protocol über core/victoria.py:

bash
monitor_agent_cpu_percent,server_id=srv123 value=45.2 1683000000

Reads laufen über den Standard-Prometheus-Endpoint /api/v1/query bzw. /api/v1/query_range. Im Desktop-Client zeichnet uPlot daraus die Charts. Die Chart-Queries der UI sind dabei nie roh: GET /checks/{id}/metrics baut die PromQL-Query serverseitig aus einer Metrik-Allowlist pro Check-Typ (CHECK_TYPE_METRICS) und escapet Label-Werte – Freitext-Queries aus der UI erreichen VictoriaMetrics nicht (SSRF-/Injection-Schutz).

Ingest-Validierung

Der Push-Endpunkt prüft, dass der API-Key wirklich zur angegebenen server_id gehört. Ein kompromittierter Agent-Key kann also keine fremden Server-Metriken fälschen.
