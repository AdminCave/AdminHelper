Benutzer & Zugriff

AdminHelper unterscheidet drei Zugriffsarten: interaktive Benutzer (Web- und Desktop-Login), API-Keys (Agenten und Skripte) sowie FRP-Provision-Tokens (Einmalverwendung). Diese Seite erklärt, wie du alle drei verwaltest.

Benutzerrollen

RolleDarf
adminAlles: im Web-Panel Benutzer verwalten, API-Keys erstellen, Hooks definieren, FRP-Server-Konfiguration und globale Einstellungen; im Desktop-Client (Server-Workspace) Server registrieren, Verbindungen, Tunnel, Monitoring und Ansible pflegen.
userEigene Verbindungen pflegen, Server und Monitoring lesen. Keine Admin-Aktionen. Im Web-Panel sieht die Rolle nur einen Hinweis auf den Desktop-Client.

Benutzer anlegen

Die Benutzerverwaltung ist Teil des Web-Admin-Panels – Benutzer ist dort zugleich die Standard-Seite nach dem Login.

  1. Im Web-Panel Benutzer → Neu öffnen
  2. Username und Passwort vergeben; Passwort wird mit bcrypt gehasht
  3. Rolle wählen – Admins sehen und bearbeiten alles

Admins können jederzeit fremde Passwörter zurücksetzen. Ändert ein Admin im Web-Panel sein eigenes Passwort, beendet der Server alle Sitzungen des Kontos, und das Panel meldet ihn sofort mit einem Hinweis ab; stuft er sich selbst herab, verschwinden die Admin-Seiten sofort. Normale Benutzer können ihr eigenes Passwort in den Einstellungen ändern.

Die Zuweisung von Servern zu einem Benutzer bleibt im Web-Panel: sie wird direkt im Benutzer-Dialog gepflegt (steuert, welche Server der Nutzer sieht). Die Server-Einträge selbst werden im Desktop-Client (Server-Workspace, Infrastruktur) angelegt und bearbeitet.

Login-Flow

Der Login-Flow nutzt JWT mit Refresh-Token-Rotation:

  • Access-Token: 8h gültig, wird bei jedem Request im Authorization-Header mitgeschickt.
  • Refresh-Token: 7 Tage gültig, rotiert bei jeder Verwendung (der alte wird sofort blacklisted).
  • Reuse-Detection: Wird ein geblacklisteter Refresh-Token erneut verwendet, werden alle Sessions des Users sofort invalidiert – ein Hinweis auf einen gestohlenen Token.
  • Abmeldung nach Inaktivität: Das Web-Panel meldet in allen offenen Tabs ab, wenn in keinem davon 30 Minuten lang bedient wurde (Maus, Tastatur, Touch); ein Hinweis bleibt stehen, bis man ihn schließt. Die Dauer stellt WEB_IDLE_TIMEOUT_MINUTES ein, 0 schaltet ab (Umgebungsvariablen). Das gilt auch nach Neuladen oder Wiederöffnen im selben Browser: Liegt die letzte Bedienung dort länger als diese Dauer zurück, endet die Sitzung beim Laden sofort mit demselben Hinweis.
Login-Rate-Limit

5 fehlgeschlagene Login-Versuche pro IP innerhalb von 60 Sekunden → weitere Versuche werden mit 429 abgewiesen. Ein erfolgreicher Login setzt den Zähler zurück. Implementierung via Redis (fixed-window), mit In-Memory-Fallback für Single-Worker-Setups.

Browser-Zugriff (Client-Zertifikat)

Sobald die Datenebene auf CERT_REQUIRED scharfgeschaltet ist, braucht jeder Browser, der das Web-Panel öffnet, ein gültiges Client-Zertifikat aus der internen CA. Anders als Agent und Desktop kann sich der Browser kein Zertifikat selbst holen – du exportierst es einmalig aus dem Desktop-Client und importierst es in den Zertifikatsspeicher des Browsers.

  1. Exportieren: Desktop-Client, im Server-Workspace angemeldet → Einstellungen → Dieser Workspace → Browser-Zertifikat exportieren. Ein Passwort (mind. 12 Zeichen) vergeben und Exportieren klicken — wähle es stark, denn der .p12-Container schützt den privaten Schlüssel nur mit einem schwachen KDF, sodass bei Verlust der Datei ein kurzes Passwort offline angreifbar wäre. Der Client enrollt ein langlebiges access-Zertifikat, verpackt es als passwortgeschützte .p12 und fragt per Speichern-Dialog, wohin sie geschrieben werden soll (Default-Name adminhelper-browser.p12).
  2. Importieren – Chrome/Edge: Einstellungen → Datenschutz und Sicherheit → Zertifikate verwalten → Eigene Zertifikate → Importieren, die .p12 wählen, Passwort eingeben. (Unter Windows/macOS landet das Zertifikat im Betriebssystem-Speicher; die genaue Menüführung variiert je nach Version.)
  3. Importieren – Firefox: Einstellungen → Datenschutz & Sicherheit → Zertifikate → Zertifikate anzeigen → Ihre Zertifikate → Importieren, die .p12 wählen, Passwort eingeben.
  4. Verbinden: Web-Panel neu laden. Beim ersten Aufruf fragt der Browser, welches Client-Zertifikat er vorzeigen soll – das importierte auswählen.
Browser-Cert unter erzwungenem mTLS

Seit 0.29.0 läuft die Datenebene per Default scharf (CERT_REQUIRED) – ein Browser ohne importiertes Zertifikat wird schon am TLS-Handshake abgewiesen, das Web-Panel lädt dann nicht. Jeder Benutzer, der das Panel im Browser nutzt, exportiert dafür seine eigene .p12 aus seinem Desktop: Das Zertifikat gehört dem Benutzer, für den es ausgestellt wurde, und der Server nimmt es nur für dessen Login an. Das Browser-Zertifikat ist langlebig und erneuert sich nicht automatisch – vor Ablauf einfach neu exportieren und importieren.

Neuen Nutzer unter erzwungenem mTLS onboarden

Ist die Datenebene scharf (CERT_REQUIRED, siehe Betrieb & Konfiguration), kommt ein brandneuer Client ohne Zertifikat nicht durch den :443-Handshake – auch nicht zum Login. Das Onboarding läuft daher über die entkoppelte Enrollment-Tür (ADR 0003): erst Zertifikat per Token, dann Login.

  1. Benutzer anlegen (Admin) – wie oben unter „Benutzer anlegen". Der spätere Zertifikats-CN ist genau dieser Username. Unter mTLS gehört das Zertifikat diesem Benutzer: Login, API und Zertifikats-Ausgabe nehmen es nur für ihn an. Die Geräte-Identität gehört im Desktop einem Server-Workspace, der damit einem Benutzer zugeordnet ist; wer sich auf demselben Desktop als ein anderer Benutzer anmelden will, legt dafür einen eigenen Server-Workspace an und registriert ihn, oder setzt die Geräte-Identität des Workspace zurück und registriert ihn für sich neu.
  2. Enrollment-Token ausstellen (Admin, selbst bereits mit Cert): im Web-Panel unter Benutzer in der Zeile des neuen Benutzers Registrierungs-Token klicken, die Gültigkeit wählen (10 Minuten, 1 Stunde oder 24 Stunden; voreingestellt 10 Minuten) und Ausstellen. Der Dialog zeigt das einmalige Token genau einmal, mit Kopieren und seinem Ablauf in Ortszeit; nach dem Schließen ist es nicht mehr abrufbar. Per API: POST /api/enrollment/token/for mit { "username": "<neuer-user>", "ttl_minutes": 60 } (ttl_minutes 1 bis 1440, ohne Angabe 10); die Antwort enthält das token und seinen Ablauf expiresAt.
  3. Token out-of-band übergeben – per sicherem Kanal an den neuen Nutzer (Copy-Paste). Es ist single-use und kurzlebig.
  4. Gerät registrieren (neuer Nutzer): im Desktop-Client im Picker einen Server-Workspace mit der Server-URL anlegen und öffnen, auf dem Login-Bildschirm „Gerät mit Token registrieren" wählen, den Token eingeben → Gerät registrieren. Der Client erzeugt on-device einen Schlüssel, holt sein Zertifikat an :8444 und legt es als Geräte-Identität dieses Workspace im OS-Keyring ab. Kein Login nötig.
  5. Anmelden – danach normaler Login (Username/Passwort); der Client präsentiert jetzt sein Zertifikat am Handshake.
  6. Optional Browser – für das Web-Panel exportiert der Nutzer aus dem Desktop ein .p12 und importiert es (siehe „Browser-Zugriff" oben).

Ist mTLS nicht erzwungen und der Nutzer schon angemeldet, registriert er das Gerät ohne Abmelden: in den Einstellungen unter Dieser Workspace den Token eingeben → Gerät registrieren. Danach startet der Tunnel mit dem neuen Zertifikat.

Ist das Gerät registriert, steht in den Einstellungen unter Dieser Workspace (Server-Workspace, angemeldet), für wen und bis wann: „Registriert als admin bis 13.01.2027“. Der Name ist der CN des Geräte-Zertifikats, das Datum sein Ablauf in lokaler Zeit. Erneuert wird das Zertifikat beim Anmelden ab der Hälfte seiner Laufzeit; bleiben 14 Tage oder weniger, ist das bisher nicht gelungen, und die Zeile sagt dazu „läuft bald ab“. Ist das Zertifikat abgelaufen oder nicht lesbar, sagt die Zeile das ebenfalls: dann Geräte-Identität zurücksetzen und das Gerät mit einem neuen Token registrieren.

Ausnahme: der allererste Admin

Für den ersten Admin gibt es noch niemanden, der ein Token ausstellen könnte. Am einfachsten erledigt das scripts/install.sh (legt Admin + Erst-Token out-of-band an und schaltet scharf). Manuell ohne Script: ein einmaliges permissives Fenster (MTLS_ENFORCE=false, ersten Admin anlegen + Desktop enrollen, dann MTLS_ENFORCE=true). Ab da läuft jedes weitere Onboarding über die Token-Tür – ohne erneutes Lockern.

Geräte und Widerruf

Jedes Client-Zertifikat, das der ca-issuer ausstellt, hält ein Register fest und ordnet es einem Gerät zu: einem Desktop (jeder Server-Workspace, der sich registriert, ist ein eigenes Gerät), einer exportierten .p12 oder einem Agent. Ein erneuertes Zertifikat bleibt beim selben Gerät. Der Server nimmt ein Zertifikat nur an, solange sein Gerät nicht widerrufen ist, sonst antwortet er mit 403 und ERR_CERT_REVOKED, auch bei MTLS_ENFORCE=false.

  • Benutzer löschen sperrt alle Zertifikate, die bis dahin für diesen Benutzer ausgestellt wurden, am Server wie beim Erneuern. Legst du später einen Benutzer mit demselben Namen an, registriert er seine Geräte neu; die alten Zertifikate bleiben gesperrt. In der Geräteliste des neuen Benutzers stehen die Geräte des gelöschten als widerrufen. Ein Enrollment-Token, das bis zum Löschen ausgestellt und noch nicht eingelöst wurde, gilt danach nicht mehr.
  • Ein Gerät widerrufen (Admin): GET /api/users/{id}/devices listet die Geräte eines Benutzers mit Art, Fingerprint, Laufzeit und Widerruf; DELETE /api/users/{id}/devices/{device_id} widerruft eines. Die übrigen Geräte des Benutzers bleiben. Ein Widerruf über die API steht im Audit-Log (device.revoked).
  • „Geräte-Identität zurücksetzen“ (Desktop) widerruft das Gerät zuerst am Server und löscht dann sein Zertifikat auf dem Gerät. Widerruft der Server es dabei nicht, etwa weil er nicht erreichbar ist, sagt der Desktop, dass er nur lokal zurückgesetzt hat (siehe Fehlerbehebung).
  • Workspace löschen (Desktop, im Picker): Hat ein Server-Workspace eine Geräte-Identität, widerruft der Desktop das Gerät zuerst am Server und löscht dann den Workspace auf dem Gerät. Widerruft der Server es nicht, meldet der Picker „Nur auf diesem Gerät“; das Gerät bleibt dann am Server gültig, bis ein Admin es über die Geräte-API widerruft, denn eine spätere Registrierung, auch eines neuen Workspace, löst es nicht ab.
  • Neu registrieren: Registriert ein Server-Workspace sich neu, löst das neue Zertifikat das vorige dieses Geräts ab. Eine .p12 ist ein eigenes Gerät und löst nichts ab; eine, die nicht mehr gebraucht wird, widerrufst du über die Geräte-API.

Löschen und Widerrufen sperren die API sofort; einen Tunnel, dessen Visitor-Konfiguration der Benutzer schon hat, sperren sie nicht (siehe FRP-Tunnel: Zugang zum Tunnel entziehen).

API-Keys

API-Keys authentifizieren nicht-interaktive Clients (Go-Agent, Skripte, CI-Jobs). Unterschiede zu User-Credentials:

  • Kein Ablauf, aber widerrufbar per Klick
  • Eine von zwei Berechtigungen: read (nur lesen) oder read_write (lesen und schreiben)
  • Server speichert nur den SHA-256-Hash, der Klartext ist nach dem Anzeigen weg

API-Keys erstellen:

  1. Web-Panel → API-Keys → Neu
  2. Name vergeben und Berechtigung (read oder read_write) wählen
  3. Klartext-Key sofort kopieren – wird nie wieder angezeigt
  4. Als HTTP-Header X-API-Key: <key> senden. Der Fallback ?api_key=… (für Sync-URLs) landet im Klartext in den Access-Logs und wird serverseitig als Warnung protokolliert — bevorzuge den Header und rotiere einen so exponierten Key.

Sync-Workspace im Desktop: Ein Sync-Workspace zeigt nie ein Geräte-Zertifikat. Gegen eine Installation mit erzwungenem mTLS (der Default von scripts/install.sh) scheitert sein Abruf deshalb schon im TLS-Handshake: Für die eigene Installation nimmt man dort einen Server-Workspace, der nach dem Login dieselben Verbindungen lädt. Ein Sync-Workspace gegen die eigene Installation geht nur ohne erzwungenes mTLS (--permissive bzw. MTLS_ENFORCE=false).

IP-Restriktion

Mit ALLOWED_IPS lassen sich alle Zugriffe auf eine Whitelist begrenzen. Beispiel:

.env
ALLOWED_IPS=10.0.0.0/8,192.168.1.0/24,203.0.113.42

ALLOWED_IPS gilt für alle Anfragen an den Server, also auch für Agents und Desktop-Clients, und prüft die Client-Adresse, die das Gateway sieht: Das Gateway übermittelt sie in X-Forwarded-For, und der Server wertet diesen Header nur vom Gateway aus (TRUSTED_PROXIES, siehe Installation). Die Liste enthält also die Netze der Clients, nicht das Docker-Netz des Gateways; steht ein weiterer Proxy vor dem Gateway, zählt dessen Adresse. Ältere Versionen prüften hier die Adresse des Gateways: Wer ALLOWED_IPS darauf eingestellt hat, trägt vor dem Update die Netze der Clients ein, sonst weist der Server sie mit 403 ab. Bis der Server den Namen gateway aufgelöst hat — bei den ersten Anfragen nach seinem Start und bis zu 30 s nach einem Neustart des Gateways mit neuer Adresse —, sieht er noch die Adresse des Gateways und weist eine solche Anfrage ab, wenn die Liste das Docker-Netz nicht enthält.

Wird die Liste leer gelassen, ist der Zugriff offen (für Reverse-Proxy- oder VPN-geschützte Setups).
