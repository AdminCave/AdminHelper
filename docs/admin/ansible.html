Ansible

Die Ansible-Verwaltung trennt zentrale Pflege von lokaler Ausführung: Playbooks werden serverseitig gespeichert und versioniert; angelegt, bearbeitet, gelöscht und ausgeführt werden sie über den Desktop-Client (in einem Server-Workspace, Ansible-Seite) mit lokal installiertem ansible-playbook. Der Server führt selbst keine Playbooks aus.

Playbook-CRUD im Desktop-Client

Playbooks werden über /api/ansible/playbooks verwaltet – alle Schreib-Operationen sind Admin-only. Jedes Playbook hat Metadaten in der Datenbank (Tabelle ansible_playbooks) und eine YAML-Datei auf Disk unter DATA_DIR/ansible/playbooks/<id>/<filename>.

FeldBedeutung
nameAnzeigename im Desktop-Client
filenameDateiname der YAML-Datei – muss auf .yml oder .yaml enden, keine Pfad-Separatoren
descriptionOptionale Beschreibung
tagsListe von Tags zur Filterung/Suche
contentDer YAML-Inhalt – wird auf Disk geschrieben, nicht in der DB

Beim Erstellen (POST) und beim Bearbeiten (PUT, falls content mitgesendet wird) validiert der Server das YAML mit yaml.safe_load; ungültiges YAML liefert 422. Wird der Dateiname geändert, benennt der Server die Datei auf Disk um bzw. löscht die alte. Beim Löschen (DELETE) wird das gesamte Verzeichnis <id>/ entfernt.

HTTP
GET    /api/ansible/playbooks              # Alle Playbooks auflisten
POST   /api/ansible/playbooks              # Playbook erstellen (Admin)
GET    /api/ansible/playbooks/{id}         # Playbook-Metadaten
GET    /api/ansible/playbooks/{id}/content # YAML-Inhalt abrufen
PUT    /api/ansible/playbooks/{id}         # Playbook aktualisieren (Admin)
DELETE /api/ansible/playbooks/{id}         # Playbook löschen (Admin)

CRUD-Operationen feuern Hooks: playbook.created, playbook.updated und playbook.deleted (Payload: id + name). Details zur Hook-Konfiguration: Hooks & Events.

Playbook ausführen (Desktop)

Die Ansible-Seite zeigt links die Liste der Playbooks und rechts das gewählte Playbook. Bis ein Playbook gewählt ist, steht rechts nur ein Hinweis.

  • Liste – alle im Server gepflegten Playbooks mit Name, Beschreibung, Dateiname und Tags; der Knopf + Playbook darüber legt ein neues an.
  • Ziele – zwei Modi: Nach Servern (Einzelauswahl per Checkbox, je Server Name und Host) oder Nach Tags (Chip pro Tag wählt alle Server mit diesem Tag). Darunter steht, auf wie vielen Servern das Playbook laufen wird.
  • Ausführen – der Knopf im Kopf des Playbooks (neben Bearbeiten) wird aktiv, sobald mindestens ein Ziel-Server gewählt ist, und startet ansible-playbook: Steht Einstellungen → Terminal → Konsole für SSH auf AdminHelper-Terminal (Standard), läuft das Playbook in einem Sitzungs-Tab mit seinem Namen (ohne Neu verbinden), sonst in einem nativen Terminal. Probelauf (--check) unter den Zielen startet es auf beiden Wegen mit --check: Ansible meldet, was es ändern würde, und ändert nichts.

Beim Ausführen lädt der Desktop Dateiname und YAML-Inhalt des Playbooks selbst frisch vom angemeldeten Server (/{id} und /{id}/content), schreibt Inventory und Playbook in ein eigenes temporäres Verzeichnis je Lauf und startet den Lauf; von der Oberfläche bekommt er dafür nur die Playbook-Id und die gewählten Ziele. Im Sitzungs-Tab löscht der Desktop dieses Verzeichnis nach dem Ende des Laufs, auf jeder Plattform. Im nativen Terminal unter Linux löscht das Terminal dieses Verzeichnis samt Playbook und Inventory, sobald ansible-playbook endet, gleich mit welchem Ergebnis und auch dann, wenn das Terminal während des Laufs geschlossen wird. Scheitert der Start (kein ansible-playbook, kein Terminal) oder ein Schritt davor, löscht der Client das Verzeichnis sofort, auch mit einer halb geschriebenen Datei. Im nativen Terminal unter Windows bleibt es nach einem gestarteten Lauf im Temp-Verzeichnis liegen. Server-Inventar und Playbooks bezieht der Client direkt vom AdminHelper-Server des Workspace – lokal wird nichts gepflegt.

Inventory-Generierung

Der Desktop-Client erzeugt aus den ausgewählten Servern automatisch eine Inventory-Datei im JSON-Format (inventory.json, gelesen vom yaml-Plugin, das in Ansible standardmäßig aktiv ist) im temporären Verzeichnis des Laufs. Alle gewählten Hosts landen unter all.hosts; zusätzlich entsteht pro Server-Tag eine Gruppe unter all.children mit den zugehörigen Hosts. Ein Tag all wird keine eigene Gruppe, denn alle Hosts gehören schon zu all.

Der Name jedes Hosts bleibt sein hostname-Feld, sodass Playbooks, host_vars und Ausgaben dieselben Namen sehen wie bisher. Hat der Server eine SSH-Verbindung, schickt das Inventory Ansible dorthin, wohin Verbinden diese Verbindung öffnet: ansible_host und ansible_port (nach der Tunnel-Auflösung; Port 22 bleibt weg, wie bei Verbinden), ansible_user und ansible_ssh_private_key_file, falls gesetzt, und in ansible_ssh_common_args die übrigen Schalter der Verbindung (Sprung-Host als -o ProxyJump=…, Auth-Methode). Weiterleitungen und Agent-Forwarding nimmt Ansible nicht mit.

JSON
{
  "all": {
    "hosts": {
      "web01.example.com": {
        "ansible_host": "127.0.0.1",
        "ansible_port": 23001,
        "ansible_user": "ops",
        "ansible_ssh_private_key_file": "/home/ops/.ssh/id_ed25519",
        "ansible_ssh_common_args": "'-o' 'ProxyJump=jump@192.0.2.10'"
      },
      "db01.example.com": {}
    },
    "children": {
      "database": { "hosts": { "db01.example.com": {} } },
      "web": { "hosts": { "web01.example.com": {} } }
    }
  }
}

Die Gruppen entstehen direkt aus den Tags der Server – dieselben Tags, die am Server-Eintrag (Desktop-Client, Infrastruktur) gesetzt sind und im Tag-Modus die Auswahl steuern. Ein Tag mit [, ], { oder } lässt den Lauf mit einer Fehlermeldung abbrechen, wie schon ein Benutzer oder Schlüsselpfad mit { oder }.

Welche SSH-Verbindung Ansible nimmt

  • Genau eine SSH-Verbindung am Server: diese.
  • Keine: der Hostname wie bisher; in den Zielen steht neben dem Server die Markierung Hostname.
  • Mehrere: unter dem Server erscheint eine Auswahl, vorbelegt mit der ersten Verbindung nach Namen.

Markierung und Auswahl zeigt der Modus Nach Servern. Im Modus Nach Tags gilt je Server dieselbe Regel ohne Anzeige: die dort getroffene Wahl, sonst die erste Verbindung nach Namen, ohne Verbindung der Hostname.

Vor dem Start löst der Client jede gewählte Verbindung wie Verbinden auf, auch über einen FRP-Tunnel. Läuft der Tunnel-Visitor einer STCP-Verbindung nicht, startet der Lauf nicht und die Meldung nennt den Server; einen Rückfall auf den Hostnamen gibt es nicht. Der Desktop prüft jede Verbindung wie beim Öffnen einer SSH-Sitzung und lehnt außerdem einen lokalen Port ab, der zum Tunnel eines anderen Workspace gehört, ebenso Benutzer oder Schlüsselpfade mit { oder } (Ansible wertet Inventory-Werte als Jinja-Template aus).

Voraussetzungen

  • ansible-playbook muss auf dem Desktop-Rechner installiert und im PATH sein. Fehlt es, bricht der Lauf mit einer Fehlermeldung ab.
  • Die Ziel-Server müssen im Desktop-Client unter Infrastruktur angelegt sein – nur dort gepflegte Hosts erscheinen in den Zielen der Ansible-Seite.
  • Playbook-Pflege (Erstellen/Bearbeiten/Löschen) erfordert eine Admin-Session.
SSH-Erreichbarkeit

Die Ausführung läuft auf dem Desktop-Rechner gegen das Ziel der SSH-Verbindung jedes Servers, wie Verbinden es öffnet. Für Server ohne SSH-Verbindung (Markierung Hostname) regelst du Zugang, Keys und ggf. ansible_user wie gewohnt über deine Ansible-/SSH-Konfiguration. Nutzt eine der Verbindungen Passwort-Anmeldung, startet der Lauf mit --ask-pass: Ansible fragt das Passwort einmal im Terminal ab, wie Verbinden, und nimmt es für die Server des Laufs mit Passwort-Anmeldung; den übrigen bietet ssh es nicht an. Je nach Ansible-Version braucht das sshpass auf dem Desktop-Rechner.
