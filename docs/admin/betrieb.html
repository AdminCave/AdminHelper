Betrieb & Konfiguration

Alltagsaufgaben: Datenverzeichnis verstehen, Backups anlegen, Logs finden, Konfiguration anpassen, Server neu starten.

Datenverzeichnis & Postgres-Volume

Zustandsbehaftete Daten verteilen sich auf zwei Stellen: DATA_DIR für File-basierte Artefakte (Bootstrap-Token, PKI, Zertifikate) und das postgres-data-Volume für die eigentlichen Datenbanken.

PfadInhalt
postgres-data (Docker-Volume)PostgreSQL-Cluster mit zwei DBs: adminhelper (Benutzer, Verbindungen, Server, API-Keys, Hooks) und adminhelper_monitor (Checks, Alerts, Templates, Agent-Keys). Jeder Dienst verbindet sich mit einer eigenen Rolle ohne Superuser-Rechte; die Rollen besitzen das Schema public ihrer Datenbank, die Datenbanken selbst bleiben beim Superuser adminhelper.
data/.bootstrap_tokenEinmaliger Setup-Token-Hash für den ersten Admin (siehe Erstanmeldung in der Installations-Doku).
data/.bootstrap.lockLeer; sorgt dafür, dass bei mehreren Server-Workern nur einer das Setup-Token erzeugt. Darf bei gestopptem Server gelöscht werden.
data/.secret_keyAuto-generierter JWT-Key (sofern SECRET_KEY nicht gesetzt).
frp-config (Docker-Volume)Nur die generierte frps.toml (kein Cert-Material mehr). Die FRP-TLS-Materialien liefert der ca-issuer (Volume frps-certs, wiederherstellbar). Die alte server-eigene FRP-Master-PKI (Volume frp-pki) ist entfernt — siehe ca-pki unten.
frps-state (Docker-Volume)Statusdatei status.json des frps-Supervisors (Zustand, Grund, Herzschlag, die letzten 8 Ereignisse) und, solange frps mit Dashboard-Port läuft, je Proxy-Typ die Liste des frps-Dashboards als proxy-<typ>.json (stcp, https, tcp, udp) für die Tunnel-Statusansicht (siehe FRP-Tunnel). Der Supervisor im frps-Container schreibt sie, server und scheduler lesen sie read-only, die Proxy-Listen nur der Server. Nicht im Backup: Der Supervisor schreibt sie bei jeder Abfrage neu.
frps-active (Docker-Volume)Die geprüfte Arbeitskopie von frps.toml und TLS-Material, aus der frps startet (enthält wie frp-config und frps-certs Token und Schlüssel); nur im frps-Container gemountet. Nicht im Backup: Der Supervisor übernimmt sie aus frp-config und frps-certs neu.
ca-pki (Docker-Volume)PKI-Hierarchie des ca-issuer: Root (passphrase-verschlüsselt) + Intermediates (tunnel/access/internal). Das zentrale Backup-Ziel der internen CA — Verlust bedeutet, dass alle Clients neu enrollen müssen. Issuer-privat, nie ins Gateway/frps gemountet.
gateway-certs (Docker-Volume)TLS-Material des Gateways (access-signiertes Leaf + Key + CA-Trust-Bundle), vom ca-issuer bereitgestellt. Wiederherstellbar — der Issuer provisioniert es neu.
victoria-data (Docker-Volume)VictoriaMetrics-Speicher – Retention 90 Tage (eigenes Volume, nicht Teil dieses Datenverzeichnisses).

server, scheduler, ca-issuer und monitoring laufen unter dem Nutzer app (UID 10001) aus Programmen, die dieser Nutzer nur ausführen, nicht lesen kann. Die UID 10001 sollte auf dem Host keinem anderen Konto oder Dienst gehören, ebenso die UID 70 (Postgres im Container). install.sh und update.sh nennen ein solches Konto mit einer Warnung (sie brechen nicht ab) und schließen das Installationsverzeichnis für andere Konten (höchstens 0750, ein strengeres 0700 bleibt); der Eigentümer bleibt, wer installiert. Auch bestehende Installationen bekommen das beim nächsten Update. Ein Werkzeug, das unter einem anderen Konto ins Installationsverzeichnis schaut (etwa ein Backup-Agent), braucht danach die Gruppe des Verzeichnisses oder root. Ein Konto, das vorher schon an data/ kam, kann dort Schlüssel gelesen haben; wer eine solche Warnung sieht, entfernt das Konto oder ändert seine UID.

Backup

scripts/backup.sh sichert den kompletten Stand inklusive des CA-Kronjuwels in ein Tarball — bei laufendem Stack:

bash
./scripts/backup.sh                 # -> ./backups/adminhelper-backup-<ts>.tar.gz
./scripts/backup.sh --with-victoria # zusätzlich die (große) Metrik-Historie

Enthalten: ca-pki (Root + Intermediates), pg_dump beider DBs, monitoring-data, optional victoria-data und die .env. Nicht enthalten — und auch nicht nötig — sind gateway-certs/frps-certs: der ca-issuer regeneriert sie beim Start aus ca-pki. Ebenso wenig frps-state und frps-active, die der frps-Supervisor selbst neu anlegt. Das Archiv ist nur für den ausführenden Nutzer lesbar (0600) und trägt seinen Namen erst, wenn es vollständig geschrieben ist; einen neu angelegten Zielordner legt das Skript mit 0700 an. Das Ziel muss Unix-Eigentümer und -Modus halten können: Hält ein Mount sie nicht, wie CIFS, vfat oder NTFS in der Regel, bricht das Backup mit einem Hinweis ab. Dann lokal sichern und das Archiv danach auf das Netzlaufwerk kopieren.

CA_ROOT_PASSPHRASE getrennt aufbewahren

Die Passphrase wird bewusst nicht ins Backup geschrieben — sie verschlüsselt den mit-gesicherten Root-Key, beides zusammen wäre wertlos (ADR 0001 §5/D7). Im Passwortmanager getrennt halten. Nur der erste Start des ca-issuer braucht sie (er erzeugt die Hierarchie). Danach den Wert in .env leeren und die Zeile CA_ROOT_PASSPHRASE= behalten, sonst bricht docker compose up ab; nach dem Leeren erzeugt docker compose up -d den ca-issuer neu, ohne die Datei mit der Passphrase. Wer den Wert vor dem ersten gelungenen Start ändert, fährt docker compose up -d --force-recreate ca-issuer. Updates erzeugen keine neue: init-secrets.sh erzeugt sie nur in dem Lauf, der auch POSTGRES_PASSWORD erzeugt, also bei einer frischen Installation. Wer POSTGRES_PASSWORD vor der Installation von Hand setzt, setzt auch CA_ROOT_PASSPHRASE von Hand. Der restaurierte Stack läuft auch ohne sie (die Zeile bleibt, leer); gebraucht wird sie nur zum Rotieren der Intermediates.

Für automatische tägliche DB-Backups: den auskommentierten pg-backup-Service in docker-compose.yml einkommentieren (nur DBs, Retention 7 Tage) — ersetzt nicht das vollständige backup.sh inkl. CA. Ein Restore nur der Datenbank mit scripts/pg-restore.sh beginnt den Übergang des Zertifikats-Registers ebenso neu.

Das Backup liest als Superuser. restore.sh lässt vor dem Einspielen db-init laufen und spielt jede Datenbank als ihre Dienst-Rolle ein (ah_server, ah_monitor); die Passwörter der Rollen nimmt es aus der .env des Hosts. Fehlt eines, etwa auf einem Host, der vor den Rollen je Dienst eingerichtet wurde, bricht es vor dem Stopp des Stacks ab: dann ./scripts/init-secrets.sh und den Restore erneut starten. scripts/pg-restore.sh spielt als Superuser ein: Die zurückgespielten Tabellen gehören danach dem Superuser, und Server, Scheduler, Monitoring und ca-issuer scheitern an fehlenden Rechten, bis der Stack neu startet. Deshalb danach docker compose down && docker compose up -d: db-init übergibt die Tabellen wieder den Rollen, der Start des Servers gibt dem ca-issuer seine Rechte (grant-ca). Zurück auf einen älteren Stand: Der verbindet sich wieder als Superuser, die Daten bleiben nutzbar, die Rollen bleiben ohne Wirkung im Cluster.

Restore

bash
./scripts/restore.sh ./backups/adminhelper-backup-<ts>.tar.gz

Stoppt den Stack, stellt Volumes + DBs wieder her und fährt hoch. Die restaurierte Root ist identisch — bereits enrollte Agenten bleiben vertraut, ohne Re-Enrollment. Das Zertifikats-Register beginnt dabei seinen Übergang neu: Zertifikate, die seit dem Backup ausgestellt oder erneuert wurden, stehen nicht in der zurückgespielten Datenbank; sie werden beim ersten Kontakt übernommen, 90 Tage ab dem Restore (siehe „Zertifikats-Register und Übergang“ unten). Die .env aus dem Backup wird als .env.restored abgelegt (überschreibt eine vorhandene .env nicht). Sie trägt die Zeile CA_ROOT_PASSPHRASE nicht: Wer sie auf einem frischen Host nach .env übernimmt, lässt danach ./scripts/init-secrets.sh laufen (ein Backup von vor den Rollen je Dienst trägt deren Passwörter nicht) und ergänzt die Zeile CA_ROOT_PASSPHRASE=, leer oder mit der getrennt aufbewahrten Passphrase, sonst bricht docker compose up ab. Die restaurierte Hierarchie braucht den Wert zum Start nicht.

Logs

Die Container schreiben Plain-Text-Zeilen mit Zeitstempel auf stderr (stdout bleibt für Subprozess-IPC frei); docker compose logs -f <service> ist der schnellste Weg. Format: 2026-06-15 11:25:53 INFO adminhelper.auth … (Datum, Uhrzeit, Level, Logger, Meldung).

bash
docker compose logs -f server            # FastAPI
docker compose logs -f scheduler         # periodische Jobs (E-Mail-Versand, Aufräumen, geplante Hooks)
docker compose logs -f monitoring        # Check-Ausführungen
docker compose logs -f frps              # FRP-Server
docker compose logs -f --tail=200        # alle Services, letzte 200 Zeilen

Der Server-Container nutzt benannte Logger mit Präfix adminhelper.*; einige Module loggen unter ihrem Modulpfad app.*. Interessante Log-Namen:

  • adminhelper.auth / adminhelper.auth_router – Logins, Refresh-Rotationen, Reuse-Detection
  • adminhelper.rate_limit – Blockierte Requests
  • adminhelper.provisioning – Server-Provisionierung
  • adminhelper.servers / adminhelper.ansible – Server- und Ansible-Aktionen
  • app.modules.frp.pki / app.modules.frp.docker_manager – PKI-Aktionen und FRP-Container
  • app.core.events – gescheiterte Event-Hooks mit Namen, Event und Fehlertext, im Log des server-Dienstes
  • app.modules.hooks.scheduler – im Log des scheduler-Dienstes: gescheiterte Schedule-Hooks mit Namen und Fehlertext; eine Warnung zu einem Schedule-Hook, dessen Intervall der Scheduler nicht lesen kann (einmal je Hook und Intervall, der Hook läuft bis zur Korrektur nicht); die System-Jobs (Aufräumen von Token-Blacklist, Enrollment-Token, Zertifikats-Register, Provision-Token, Audit-Log und Benachrichtigungen, Versand der Benachrichtigungs-Outbox, Überwachung des frps-Supervisors) mit ihrem Ergebnis als INFO, sobald ein Lauf etwas getan hat, und einem Fehler mit Traceback

Der Monitoring-Container loggt unter dem Präfix monitor.* (z. B. monitor.engine, monitor.scheduler, monitor.alerter, monitor.victoria). Beide Container schreiben Plain-Text-Zeilen nach stderr, kein JSON.

Log-Level: Server und Monitoring lesen die Ausführlichkeit aus der Env-Variable LOG_LEVEL (DEBUG/INFO/WARNING/ERROR, Default INFO). Für eine tiefere Diagnose LOG_LEVEL=DEBUG in der .env setzen und docker compose up -d.

Rotation: Die Container-Logs sind über den Docker-json-file-Treiber begrenzt (max-size: 10m, max-file: 5 → max. 50 MB pro Service), damit sie nicht unbegrenzt wachsen. Konfiguriert über den x-logging-Anker in der docker-compose.yml.

Audit-Log

Sicherheits- und änderungsrelevante Aktionen werden in einem append-only Audit-Trail protokolliert — mit Actor (Benutzer oder API-Key; Aktionen der Server-CLI python -m app.cli erscheinen als system mit dem Label cli), Quell-IP und Zeitstempel. Erfasst werden u. a. das Anlegen/Ändern/Löschen und die Nutzung von Verbindungen, Änderungen an Servern/Benutzern/API-Keys/FRP/Ansible, Aktionen an Hooks (Anlegen, Ändern mit den geänderten Feldern, Löschen, Ein- und Ausschalten, Token-Rotation, manueller Lauf mit Erfolg oder Fehlschlag), das Erzeugen von Provisionierungs-Token, Schreibzugriffe über den Monitoring-Proxy (POST/PUT/DELETE mit Pfad und Antwortstatus, bei einem Abbruch nach dem Senden mit Status error, ohne den Inhalt der Anfrage) sowie Logins (Erfolg/Fehlschlag), ein Logout, der eine Sitzung beendet, und der Erst-Admin-Bootstrap; der Webhook-Trigger eines Hooks und lesende Zugriffe auf Hooks, Provisionierungs-Token und den Monitoring-Proxy bleiben ohne Eintrag. Bei einer Benutzer-Änderung nennt detail (in der Antwort von GET /api/audit) die geänderten Felder: Passwort, Admin-Recht mit dem neuen Wert, Server-Zuordnung.

Einsehbar im Web-UI unter Audit-Log (nur Admins; filterbar nach Actor, Objekt und Aktion; je Eintrag auch mit dem Detail, etwa den geänderten Feldern) oder per API: GET /api/audit (paginiert; Query-Parameter action, actor_type, object_type, object_id, status, q).

Aufbewahrung

Ein täglicher Job löscht Einträge, die älter als AUDIT_RETENTION_DAYS (Default 365) sind — der einzige Löschpfad der ansonsten append-only Tabelle. 0 behält alles dauerhaft.

Lücke: Lokal- und Sync-Workspaces

Die Nutzung einer Verbindung meldet nur ein Server-Workspace des Desktop-Clients an den Server. Was in einem Lokal- oder Sync-Workspace geöffnet wird, erreicht den Server nicht und erscheint daher nicht im Audit-Trail.

E-Mail-Benachrichtigungen (SMTP)

Der Notification-Hub kann Benachrichtigungen zusätzlich zur In-App-Glocke per E-Mail zustellen. Dafür einen externen SMTP-Relay über Environment-Variablen konfigurieren (kein lokaler Mailserver nötig):

VariableBedeutung
SMTP_HOSTHostname des Relays. Leer = E-Mail-Kanal aus (Glocke + Desktop-Hinweise bleiben aktiv).
SMTP_PORT587 (STARTTLS, Default) oder 465 (implizites TLS/SMTPS); jeder andere Port nutzt ebenfalls STARTTLS. Der Versand prüft Zertifikat und Hostnamen des Relays: Über einen Relay ohne STARTTLS oder mit einem Zertifikat, dem der Container nicht vertraut oder das nicht zu SMTP_HOST passt, geht keine Mail hinaus; nach dem letzten Zustellversuch steht der Grund im Log des scheduler-Dienstes.
SMTP_USER / SMTP_PASSWORDZugangsdaten des Relays (optional, wenn der Relay ohne Auth annimmt). Ein $ im Passwort als $$ schreiben oder den Wert in einfache Anführungszeichen setzen (siehe Umgebungsvariablen).
SMTP_FROMAbsenderadresse (Default adminhelper@localhost).
SMTP_CA_FILEOptional: Pfad im Container zu einer PEM-Datei mit der CA des Relays (selbstsigniertes Zertifikat oder Firmen-CA). Sie gilt zusätzlich zu den System-CAs und nur für SMTP, im Notification-Hub wie im E-Mail-Kanal des Monitorings; Zertifikat und Hostname werden weiter geprüft. Leer = nur die System-CAs. Einbinden: siehe Relay mit eigener CA.
NOTIFICATION_MAX_ATTEMPTSZustellversuche pro E-Mail mit linearem Backoff, danach „fehlgeschlagen" (Default 5).

Wer welche E-Mails bekommt, steuert jeder Nutzer selbst über seine Benachrichtigungs-Regeln (siehe Monitoring → Persönliche Benachrichtigungen). Der Versand läuft asynchron über eine Outbox; ein minütlicher Hintergrund-Job stellt zu.

Die SMTP_*-Variablen nutzt auch der E-Mail-Kanal der Alert-Regeln im Monitoring (siehe Monitoring → Benachrichtigungen & Alerting); eine Regel kann dort einen eigenen Relay mit eigenen Zugangsdaten setzen.

Relay mit eigener CA

Weist sich der Relay mit einem Zertifikat aus, dem die Container nicht vertrauen (selbstsigniert oder von einer Firmen-CA), die CA als PEM-Datei smtp-ca.pem neben die docker-compose.yml ins Install-Verzeichnis legen und mit einer docker-compose.override.yml daneben in die Dienste server, scheduler und monitoring einhängen, denen Compose auch die übrigen SMTP_*-Variablen gibt; eine bestehende docker-compose.override.yml (etwa mit FRPS_DASHBOARD_URL, siehe FRP-Tunnel) um diese Einträge ergänzen, nicht ersetzen:

docker-compose.override.yml
services:
  server:
    environment:
      - SMTP_CA_FILE=/run/adminhelper/smtp-ca.pem
    volumes:
      - ./smtp-ca.pem:/run/adminhelper/smtp-ca.pem:ro
  scheduler:
    environment:
      - SMTP_CA_FILE=/run/adminhelper/smtp-ca.pem
    volumes:
      - ./smtp-ca.pem:/run/adminhelper/smtp-ca.pem:ro
  monitoring:
    environment:
      - SMTP_CA_FILE=/run/adminhelper/smtp-ca.pem
    volumes:
      - ./smtp-ca.pem:/run/adminhelper/smtp-ca.pem:ro

Danach docker compose up -d. Compose liest die docker-compose.override.yml bei jedem Aufruf mit, und scripts/update.sh lässt sie stehen. Die PEM-Datei muss für den Container-Nutzer lesbar sein (chmod 644; eine CA ist kein Geheimnis). Lässt sie sich nicht laden (fehlt, nicht lesbar, kein PEM), geht keine E-Mail hinaus: Für den Hub steht der Grund nach dem letzten Zustellversuch im Log des scheduler-Dienstes, das Monitoring vermerkt im Alert-Log SMTP TLS failed. Ein Relay ohne STARTTLS bleibt auch mit SMTP_CA_FILE außen vor.

Konfiguration ändern

Alle Config-Werte kommen aus Environment-Variablen. Änderungen erfordern ein docker compose up -d, damit die Container neu erzeugt werden:

bash
# .env anpassen, danach:
docker compose up -d server

Multi-Worker-Betrieb

Standardmäßig läuft ein einzelner Uvicorn-Worker (WEB_CONCURRENCY=1). Für höhere Last skaliert man auf mehrere Worker:

  1. WEB_CONCURRENCY in der .env auf die gewünschte Worker-Zahl setzen (Faustregel (2×CPU-Kerne)+1, üblich 4–12 — nicht an die Zahl gleichzeitiger Clients koppeln). Der Entrypoint startet dann uvicorn --workers ${WEB_CONCURRENCY}.
  2. REDIS_URL muss gesetzt sein (im Standard-Compose bereits der Fall) — sonst zählt das Rate-Limit pro Worker statt global; der Server warnt beim Start.
  3. Den DB-Pool im Auge behalten: pro Worker gilt DB_POOL_SIZE+DB_MAX_OVERFLOW (Default 10+20). Bei vielen Workern diese Werte senken und Postgres max_connections prüfen.
Der Scheduler läuft als eigener Dienst

Die periodischen Jobs (E-Mail-Outbox-Versand, Aufbewahrungs-Cleanups, Scheduled Hooks) laufen im separaten scheduler-Service (genau eine Instanz, RUN_MODE=scheduler) — nicht in den Web-Workern. Würde jeder Web-Worker den Scheduler starten, liefe jeder Job pro Worker (z. B. E-Mails mehrfach versendet). Der scheduler-Dienst ist im Standard-Compose enthalten; ihn nicht auf mehrere Replicas skalieren.

Grenzen der Container

Alle Dienste des Compose-Stacks laufen mit no-new-privileges: Kein Prozess im Container erhält beim Start eines Programms zusätzliche Rechte, setuid-Bits und Datei-Capabilities bleiben wirkungslos. Dazu hat jeder Dienst eine Prozessgrenze (pids_limit, gezählt werden Prozesse und Threads). Ist sie erreicht, scheitert im betroffenen Container der Start weiterer Prozesse und Threads; der Host und die übrigen Dienste bleiben unberührt.

Außerdem hat jeder Dienst eine Speichergrenze (mem_limit), weit über seinem Bedarf im Leerlauf, damit ein Speicherleck oder eine ausufernde Abfrage nur den eigenen Container trifft. Ist sie erreicht, lagert der Kernel auf einem Host mit Swap bis zur selben Menge aus und beendet danach einen Prozess in diesem Container; endet damit dessen Hauptprozess, startet Docker den Container neu (restart: unless-stopped). Die Grenzen reservieren keinen Speicher, ihre Summe darf über dem Arbeitsspeicher des Hosts liegen. VictoriaMetrics richtet seine Caches nach dem Speicher aus, den es sieht (-memory.allowedPercent, Default 60 %): liegt die Grenze von victoria unter dem Arbeitsspeicher des Hosts, sind das 60 % der Grenze, sonst 60 % des Arbeitsspeichers; wer viele Metriken hält, hebt die Grenze von victoria an.

Der Ping-Check des Monitorings braucht dafür keine Sonderrechte: ping nutzt ICMP-Datagram-Sockets, die Compose im Container monitoring über net.ipv4.ping_group_range erlaubt.

Das Gateway behält von den Linux-Capabilities nur die vier, die sein nginx-Master zum Start braucht (CHOWN, DAC_OVERRIDE, SETGID, SETUID); alle übrigen nimmt Compose ihm, und die nginx-Worker laufen als Nutzer nginx ganz ohne.

Eine Grenze hebt man in einer docker-compose.override.yml neben der docker-compose.yml an. Compose lädt die Datei bei jedem Aufruf im Installationsverzeichnis selbst, und update.sh lässt sie stehen:

yaml
# docker-compose.override.yml
services:
  server:
    pids_limit: 8192
    mem_limit: 8g

Danach docker compose up -d server. Wer WEB_CONCURRENCY stark erhöht, prüft die Grenzen des server: Jeder Uvicorn-Worker bringt einen eigenen Thread-Pool und bis zu acht Hook-Prozesse mit und braucht eigenen Speicher.

Auf den zertifikatslosen Ebenen begrenzt das Gateway gleichzeitige Anfragen: Mehr als 16 gleichzeitige Anfragen je Client-Adresse an die Enrollment-Plane (:8444) und mehr als 64 an das Paket-Repo (:8445) beantwortet es mit 429, ebenso mehr als 128 bzw. 256 je Ebene insgesamt. Die 64 auf :8445 lassen Platz für viele Agent-Hosts hinter einer NAT-Adresse. Kommt der Kopf einer Anfrage dort nicht binnen 10 s vollständig an oder stockt ihr Body länger als 10 s, schließt das Gateway die Verbindung; eine untätige Keep-Alive-Verbindung schließt es nach 15 s. Die Daten-Plane :443 bleibt davon unberührt.

frps hängt allein im Netz frpedge, das Compose ohne IP-Masquerading anlegt: Die veröffentlichten Ports von frps bleiben erreichbar, aber Pakete, die frps selbst losschickt, verlassen den Host mit der Adresse des Containers als Absender, nicht mit der des Hosts. Antworten darauf verwirft Docker ab Version 28, weil es Pakete an die Adresse eines Containers nicht direkt durchlässt, sofern der Daemon nicht mit allow-direct-routing läuft und das Netz nicht im Gateway-Modus nat-unprotected oder routed; eine Verbindung über den Host hinaus kommt so nicht zustande. Mit älteren Versionen könnte ein Rechner antworten, der eine Route zurück in dieses Netz hat (nicht verifiziert). Was bleibt: Pakete ohne Antwort verlassen den Host weiterhin, und Dienste, die auf dem Docker-Host selbst lauschen, bleiben aus dem Netz erreichbar; sie schützt die Firewall des Hosts, nicht Docker.

Optional: Pakete aus frpedge auf dem Host verwerfen

Wer auch diese Pakete nicht aus dem Host lassen will, setzt eine Regel in die Kette DOCKER-USER, die Docker für eigene Regeln vor seinen bereitstellt (Docker-Doku: Docker with iptables). Die Regel unten verwirft alles, was aus der Bridge von frpedge in ein anderes Netz will und nicht zu einer von außen geöffneten Verbindung gehört; die veröffentlichten Ports von frps wirken weiter, Dienste des Hosts selbst deckt sie nicht ab. Sie gilt bis zum Neustart des Hosts, dauerhaft macht sie die Firewall-Verwaltung des Hosts. Legt Compose das Netz neu an (etwa nach docker compose down), hat die Bridge einen neuen Namen: dann die Regel mit dem neuen Namen setzen. Geprüft mit Docker 29 und dem iptables-Backend. Mit dem nftables-Backend (in Docker 29 experimentell) gibt es DOCKER-USER nicht, die Regel gehört dort in eine eigene Tabelle (Docker-Doku: Docker with nftables); dafür und für Hosts mit firewalld oder ufw: nicht verifiziert.

bash
# Im Installationsverzeichnis, während frps läuft: frps hängt nur im Netz frpedge
# dieses Projekts; dessen Bridge heißt br- und die ersten 12 Zeichen der Netz-ID.
ID=$(docker inspect -f '{{range .NetworkSettings.Networks}}{{println .NetworkID}}{{end}}' "$(docker compose ps -q frps)" | grep .)
BR=br-$(printf '%s' "$ID" | cut -c1-12)
if [ -n "$ID" ] && [ "$(printf '%s\n' "$ID" | wc -l)" -eq 1 ] && ip link show "$BR" >/dev/null 2>&1; then
  sudo iptables -I DOCKER-USER -i "$BR" ! -o "$BR" -m conntrack ! --ctstate ESTABLISHED,RELATED -j DROP
else
  echo "Bridge von frpedge nicht eindeutig gefunden, keine Regel gesetzt" >&2
fi
# Entfernen: dieselbe iptables-Zeile mit -D statt -I (BR wie oben)

Zeitzone

TZ wird an alle Container weitergegeben. Voreinstellung Europe/Berlin. Die API gibt Zeitstempel davon unabhängig in UTC mit Z aus (Web und Desktop zeigen sie in der Ortszeit des Browsers bzw. Rechners), und geplante Hooks rechnen in UTC.

Zertifikate erneuern

Das TLS-Zertifikat des Gateways stellt der ca-issuer aus (access-signiert, 365 Tage). Es wird beim ersten Start ins gateway-certs-Volume provisioniert; der ca-issuer stellt es beim Start bei Bedarf neu aus, das Gateway lädt es mit seinem eigenen Neustart. Agent-Zertifikate gelten 90 Tage und erneuern sich bei halber Laufzeit selbst. Ein vom ca-issuer erneuertes frps-Zertifikat übernimmt frps selbst, ohne Neustart des Containers (siehe frps-Supervisor).

Die PKI des ca-issuer (Volume ca-pki) besteht aus einer Root (10 Jahre) und den Zwischenzertifikaten tunnel, access und internal (5 Jahre), alle beim ersten Start erzeugt. Kein Zertifikat gilt länger als sein Aussteller: Client- und Server-Zertifikate, die kurz vor dem Ablauf ihres Zwischenzertifikats ausgestellt werden, fallen kürzer aus. Ein abgelaufenes Zwischenzertifikat signiert nicht mehr; Enrollment und Erneuerung in seinem Scope antworten dann mit HTTP 503. Ab 180 Tagen vor dem Ablauf der Root oder eines Zwischenzertifikats warnt der ca-issuer im Log (docker compose logs ca-issuer): bei jedem Start unter dem Logger ca-issuer.storage („intermediate 'tunnel' expires on … (N days left)“, bei der Root mit dem Hinweis, dass eine neue Root ein neues Enrollment aller Clients bedeutet), beim Signieren einmal am Tag je Scope unter ca-issuer.issuer.

Bei jedem Start prüft der ca-issuer die Hierarchie: Die Root muss selbstsigniert und gültig sein, jedes Zwischenzertifikat von ihr signiert, gültig und passend zu seinem Schlüssel (<scope>.key) und seiner Kette (<scope>-chain.pem, Zwischenzertifikat und Root). Ist ein Zertifikat abgelaufen oder passt etwas nicht zusammen, startet der ca-issuer nicht und nennt im Log Datei, Scope und Grund („PKI hierarchy invalid — …“). Das gilt auch, wenn die Uhr des Hosts vor dem Beginn der Gültigkeit (notBefore) der Root oder eines Zwischenzertifikats steht, etwa nach einem Restore auf einen Host mit falsch gestellter Uhr: Die Hierarchie ist dann noch nicht gültig, und ein fälliges Server-Zertifikat für Gateway oder frps ließe sich nicht ausstellen. Abhilfe: die Uhr des Hosts stellen (NTP), danach docker compose up -d.

Zwischenzertifikate rotieren

Wann: sobald der ca-issuer im Log vor dem Ablauf eines Zwischenzertifikats warnt (ab 180 Tagen) oder status es zeigt, spätestens wenn er wegen eines abgelaufenen Zwischenzertifikats nicht mehr startet. Vorher ein Backup ziehen (scripts/backup.sh).

docker compose run --rm --no-deps ca-issuer python -m app.cli status
docker compose run --rm --no-deps ca-issuer python -m app.cli rotate-intermediates
docker compose restart ca-issuer
docker compose ps ca-issuer        # warten, bis er healthy ist
docker compose restart gateway

Die Root-Passphrase kommt aus der Secret-Datei des Dienstes (CA_ROOT_PASSPHRASE_FILE); ist sie leer, fragt rotate-intermediates danach. Nicht mit -e CA_ROOT_PASSPHRASE=… übergeben: Die Passphrase stünde dann in der Shell-History und in docker inspect. Erst wenn der ca-issuer wieder healthy ist, das Gateway neu starten.

Was passiert: Für tunnel, access und internal entstehen neue Zwischenzertifikate unter derselben Root (Name mit Datum, etwa AdminHelper Access Intermediate 2031-05-04). Die alten bleiben bis zu ihrem Ablauf vertraut. Agenten und Desktops erneuern ihre Zertifikate bei halber Laufzeit auf die neuen; Browser-Zertifikate gelten bis zu ihrem Ablauf weiter. Gateway- und frps-Zertifikat stellt der ca-issuer beim Neustart neu aus; frps startet danach selbst neu, Tunnel sind kurz unterbrochen.

Was nicht: Die Root wird nicht erneuert, und ein gestohlenes Zertifikat wird dadurch nicht sofort ungültig. Ein --ca-fp, der auf die Root zeigt, bleibt gültig; einer, der auf das alte access-Zwischenzertifikat zeigt (der Wert in Installationsbefehlen älterer Desktop-Versionen), passt nicht mehr: provision und die Installation brechen damit ab. Ein aktueller Desktop zeigt im Provisionierungs-Tab den Fingerprint der Root; dessen Befehle bleiben über die Rotation gültig. Ein Desktop, der das Server-Zertifikat vor dem Enrollment per Vertrauensdialog gepinnt hat, fragt neu. Zwei Rotationen am selben Tag ergeben Zwischenzertifikate mit demselben Namen; unterscheiden lassen sie sich über den Schlüssel-Identifier (Subject Key Identifier des Zwischenzertifikats = Authority Key Identifier seiner Leaves, openssl x509 -noout -ext subjectKeyIdentifier,authorityKeyIdentifier).

Abgelöste Zwischenzertifikate: Sie liegen ohne Schlüssel in <scope>-retired.pem im Volume ca-pki, bis sie ablaufen. Ist ein Eintrag dort kein Zwischenzertifikat seines Scopes unter der Root (etwa nach einem Restore mit vertauschten Dateien), überspringt der ca-issuer ihn beim Start mit einer WARNING im Log, status markiert die Zeile mit SKIPPED (<Grund>) und endet mit Exit 1, und die nächste Rotation bricht mit einer Meldung ab, die Datei und Eintrag nennt. Dann den Eintrag aus der Datei entfernen (vorher Backup) und erneut rotieren.

Zertifikats-Register und Übergang

Der ca-issuer hält jedes Client-Zertifikat, das er ausstellt oder erneuert, in einem Register fest; der Server nimmt nur erfasste Zertifikate an, auch bei MTLS_ENFORCE=false (siehe Benutzer & Zugriff → Geräte und Widerruf). Zertifikate, die vor dem Update auf das Register ausgestellt wurden, kennt es noch nicht. Für sie gilt ein Übergang:

  • Sie gelten 90 Tage ab dem Update weiter und werden beim ersten Kontakt mit dem Server oder beim ersten Erneuern erfasst. Danach gelten sie wie jedes andere Zertifikat bis zu ihrem Ablauf.
  • Ein Desktop oder Agent, der in dieser Zeit den Server erreicht, ist damit erfasst; er erneuert sein Zertifikat danach wie gewohnt.
  • Eine .p12, die in den 90 Tagen nicht benutzt wurde, nimmt der Server danach nicht mehr an (ERR_CERT_REVOKED): neu exportieren und importieren.
  • Ein Restore (restore.sh, pg-restore.sh) beginnt den Übergang neu, 90 Tage ab dem Restore, für die Zertifikate, die die zurückgespielte Datenbank nicht kennt.

Nach den 90 Tagen gilt nur noch, was im Register steht.

frps-Supervisor

frps läuft aus dem Image ghcr.io/admincave/adminhelper/frps (Quelle apps/frps/) unter einem Supervisor (apps/frps/frps-supervisor.sh). Der Supervisor läuft als root mit den Capabilities DAC_OVERRIDE, SETUID, SETGID und KILL; frps startet er unter dem Nutzer frps (UID 10002) ohne Capabilities, die Proxy-Listen des frps-Dashboards fragt er unter dem eigenen Nutzer frps-fetch (UID 10003) ab, beides aus Programmen, die diese Nutzer nur ausführen, nicht lesen können. Er liest die vom Server geschriebene frps.toml (Volume frp-config, read-only) und das TLS-Material des ca-issuer (Volume frps-certs, read-only), prüft beides und startet frps nur aus einer geprüften Arbeitskopie im Volume frps-active, die frps lesen, aber nicht ändern kann; außer root und frps liest sie niemand. Seinen Zustand schreibt er nach frps-state; daraus zeigt die FRP-Seite den Block Zustand des frps (siehe FRP-Tunnel). Die UIDs 10002 (frps) und 10003 (frps-fetch) sollten auf dem Host keinem anderen Konto oder Dienst gehören.

  • Übernahme: Der Supervisor fragt die Eingabe alle 5 s ab und übernimmt eine Änderung, sobald sie zwei Abfragen lang gleich bleibt, also nach etwa 5–10 s. Gültig: frps startet aus der neuen Kopie neu. Ungültig: frps läuft mit der letzten gültigen Kopie weiter; gibt es keine, startet es nicht (waiting). Eine unveränderte Eingabe startet nichts neu. docker compose restart frps ist für Änderungen nicht nötig.
  • Prüfung vor jedem Start, auch beim Neustart nach einem Abbruch: Die Arbeitskopie muss unverändert sein und die Prüfung erneut bestehen; sonst wird sie verworfen (bei einer veränderten Kopie mit dem Ereignis copy_changed), und vor einem Neustart übernimmt der Supervisor die Eingabe neu.
  • Abbrüche: Endet frps von selbst, startet der Supervisor es nach 2, 4, 8 … höchstens 60 s neu; ab dem dritten Abbruch innerhalb von 60 s steht der Zustand auf crashloop, bis frps wieder 60 s läuft.
  • Healthcheck: docker compose ps zeigt frps in den Zuständen waiting, running und stopped als healthy, in degraded und crashloop als unhealthy.
  • Log: docker compose logs frps; die Zeilen des Supervisors beginnen mit [frps-supervisor] und nennen Codes und Pfade, nie das Token.

Zulässige Schlüssel in extra_config

Der Supervisor übernimmt nur eine frps.toml im Aufbau, den der Server erzeugt. Auf oberster Ebene schreibt der Server aus den Feldern der Maske bindPort, vhostHTTPSPort, subDomainHost, maxPortsPerClient, detailedErrorsToClient, webServer.addr, webServer.port, webServer.user, webServer.password, auth.method und auth.token. Über extra_config der FRP-Server-Konfiguration kommen dazu nur:

transport.maxPoolCount, transport.tcpMux, transport.tcpMuxKeepaliveInterval, transport.heartbeatTimeout, transport.tcpKeepalive, userConnTimeout, log.level, log.maxDays

Schlüssel werden exakt verglichen. Werte sind true, false, endliche Zahlen oder Strings ohne Anführungszeichen, Backslash, geschweifte Klammern, Steuerzeichen und einzelne Surrogate (U+D800 bis U+DFFF); dieselbe Zeichenregel gilt für die Felder Subdomain Host, Dashboard User, Dashboard Passwort und Auth Token. Andere Schlüssel und Werte lehnt der Server beim Speichern mit 422 ab (POST/PUT /api/frp/server-config); gespeicherte bereinigt er beim Start (siehe unten).

Vor dem Update

Vor dem Update in der FRP-Server-Konfiguration prüfen:

  • extra_config und die Felder Subdomain Host, Dashboard User, Dashboard Passwort und Auth Token folgen den Regeln oben.
  • Das Auth Token hat mindestens 16 Zeichen.
  • Ein gesetzter Dashboard Port ist weder 443 noch der Bind Port noch FRP_BIND_PORT.

Beim Start gleicht der Server die gespeicherte Konfiguration mit diesen Regeln ab, bevor er frps.toml schreibt:

  • extra_config-Einträge mit einem anderen Schlüssel (etwa proxyBindAddr oder log.to) oder einem unzulässigen Wert entfernt er aus der gespeicherten Konfiguration und meldet die entfernten Schlüssel den Admins in der Glocke („Zusätzliche FRP-Einstellungen entfernt“).
  • Ein Feld, das in frps.toml landet und gegen eine dieser Regeln verstößt (unzulässige Zeichen, ein Auth Token unter 16 Zeichen, ein Dashboard Port gleich 443, dem Bind Port oder FRP_BIND_PORT), ändert er nicht. Er meldet den Admins in der Glocke, welche Felder neu zu setzen sind („FRP-Server-Konfiguration: Felder neu setzen“), einmal, solange dieselben Felder betroffen sind. Die Mitteilung nennt je Feld den Namen aus der Maske und in Klammern die Regel, etwa: „Der FRP-Server übernimmt die Konfiguration so nicht. Bitte neu setzen: Auth Token (mindestens 16 Zeichen), Dashboard Port (weder 443 noch der Bind Port noch FRP_BIND_PORT).“

Log und Mitteilungen nennen Schlüssel und Felder, nie Werte. Besteht die Konfiguration die Prüfung des Supervisors nicht, läuft frps mit der letzten gültigen Kopie weiter, sofern es eine gibt. Ohne gültige Kopie, etwa direkt nach dem Update mit leerem Volume frps-active, startet frps nicht (Zustand waiting, Grund auf der FRP-Seite), bis die Konfiguration die Prüfung besteht.

mTLS scharfschalten (CERT_REQUIRED)

Die Datenebene (:443) läuft seit 0.29.0 per Default scharf (MTLS_ENFORCE=true): das Gateway verlangt am TLS-Handshake ein gültiges Client-Zertifikat (CERT_REQUIRED) und der Server weist geschützte Routen ohne gültigen Scope mit 403 ab. Ein frischer Install ist via scripts/install.sh sofort enforced nutzbar (es besorgt dem Erst-Admin sein Cert out-of-band). Permissiv (MTLS_ENFORCE=false) lässt certlose Clients durch und loggt nur — nötig nur für einen manuellen Erst-Bootstrap. Beides steuert eine Variable: MTLS_ENFORCE. Gateway und Server lesen sie gleich, ohne Rücksicht auf Groß-/Kleinschreibung: true, 1, yes und on erzwingen, false, 0, no und off schalten permissiv, ungesetzt oder leer gilt der Default (erzwungen), und jeder andere Wert erzwingt ebenfalls und schreibt eine Warnung ins Log (fail-closed).

Erst alle Clients enrollen, dann umlegen

Schalte erst scharf, wenn jeder Client – Agent, Desktop und dein eigener Browser – ein Zertifikat hat, sonst sperrst du dich selbst aus. Im Desktop gilt das je Server-Workspace, der diese Installation nutzt; ein Sync-Workspace zeigt nie ein Zertifikat, wer per Sync von dieser Installation lädt, nimmt dafür einen Server-Workspace (Benutzer & Zugriff → API-Keys). Agent und Desktop enrollen automatisch; den Browser bereitest du über den Desktop-P12-Export vor (Benutzer & Zugriff → Browser-Zugriff). Vorher auf echter Hardware testen: Windows-Desktop-Enrollment und Browser-Import. Beachte, dass ein Browser-Leaf langlebig ist (~1 Jahr) und sich nie erneuert. Ein widerrufenes nimmt der Server in beiden Modi nicht an; aussperren kann der Widerruf den Browser aber nur unter Enforcement, denn permissiv erreicht er die Anmeldung auch ohne Zertifikat.

Scharfschalten:

bash
# in der .env setzen:
MTLS_ENFORCE=true

# Gateway + Server neu starten (lesen die Variable beim Start):
docker compose up -d gateway server

Der Gateway-Log bestätigt den Modus beim Start: mTLS ENFORCED (CERT_REQUIRED) bzw. mTLS permissive.

Rollback (jederzeit, verlustfrei): MTLS_ENFORCE=false setzen und docker compose up -d gateway server – die Datenebene ist sofort wieder permissiv.

Neue Clients nach dem Scharfschalten

Die Enrollment-Plane (:8444) bleibt immer certless und token-gegated – neue Agenten und Desktops holen ihr erstes Zertifikat dort, unabhängig vom Enforcement. Neuer Nutzer: ein Admin mintet ihm ein Enrollment-Token (POST /api/enrollment/token/for) und reicht es out-of-band weiter; im Desktop-Client legt der Neue im Picker einen Server-Workspace mit der Server-URL an, wählt auf dessen Login-Bildschirm „Gerät mit Token registrieren", gibt den Token ein und registriert das Gerät – ohne vorigen Login. Danach meldet er sich normal an (jetzt mit Zertifikat). Ein permissives Fenster ist dafür nicht mehr nötig (entkoppelte Enrollment-Tür, ADR 0003).

Nur der allererste Admin (es gibt noch keinen Admin, der ein Token ausstellen könnte) ist der Sonderfall — am einfachsten über scripts/install.sh, das den Admin + einen Erst-Token out-of-band anlegt und dann scharfschaltet. Manuell ohne Script: ein einmaliges permissives Setup-Fenster (MTLS_ENFORCE=false, ersten Admin + Desktop enrollen, wieder true).
