Hooks & Events

The hook system is the primary outbound integration surface. Every relevant server event fires an event, registered scripts run in a sanitised subprocess with a hard timeout.

Architecture

tree
apps/server/app/modules/hooks/
├── router.py          /api/hooks CRUD
├── models.py          Hook
├── schemas.py         Pydantic schemas
├── scheduler.py       Schedule-hook cron + notification outbox
├── script_runner.py   Subprocess spawn (blocking)
└── script_worker.py   Child process: stdin=JSON, stdout/stderr capture

Event Catalogue

EventPayload (excerpt)
connection.created / updated / deletedConnection object
connections.importedcount, mode
server.created / updated / deletedid, name (created also hostname)
server.startup(no event_data)
user.created / deletedid, username (created also is_admin); created is fired by POST /api/users and likewise by python -m app.cli create-admin (with is_admin true)
user.promotedid, username — fires when PUT /api/users/{id} grants a user the admin right (is_admin from false to true); a demotion fires no event
frp.config.created / updated / deletedid, name
frp.tunnel.created / updated / deletedid, name (created also serverId)
playbook.created / updated / deletedid, name
alert.triggeredserver_id, severity, title, message — fires on a transition into critical (monitoring.check.transition) of a check with severity critical; checks with severity warning or info and recoveries (critical → ok) do not fire. A bundled alert covering several servers (e.g. several silent agents) fires it once per server, each time with that server's server_id; title and message are then the same for every call and name no server. The hook follows the bell and with it the bell's cooldown of 30 minutes per check (admin guide Monitoring, Cooldown): when a check goes into critical again within 30 minutes, e.g. critical → ok → critical, it fires only the first time, and a server whose heartbeat is in the bell's cooldown at a bundled alert gets no call; the escalation warning → critical fires it in the cooldown too

Hook Definition

json
{
  "name": "Slack alert",
  "hook_type": "event",
  "event_triggers": ["server.updated"],
  "script": "http_post('https://hooks.slack.com/services/T000/B000/XXX', json_data={'text': f'AdminHelper: {event_type}'})\nresult['notified'] = True"
}

The script field is Python (not shell), run by the worker via exec(). The event's context keys are available as variables (for event hooks event_type and event_data, for schedule triggered_at/last_run as RFC 3339 strings in UTC with Z, last_run None before the first run, for webhook payload/headers/params); output goes through the result dict and log(...), and every name provided is listed under Helpers in the script. For security, headers is restricted to a safe allow-list (content-type, user-agent, x-hook-source) — client-controlled headers like Authorization, Cookie and X-Forwarded-* are never exposed to the script. The whole context is passed to the worker as JSON (json.dumps with default=str), so only JSON-native types survive — non-native values in event_data (datetime, Decimal, bytes, ORM objects) reach the script as their str() form, not the original type.

Helpers in the script

Besides the context keys, the worker (apps/server/app/modules/hooks/script_worker.py) provides these names to every script:

  • load_connections() returns all connections as a list of dicts. save_connections(list) syncs the connections with the list (upsert): existing IDs are updated, new ones inserted, and connections missing from the list deleted. uuid4() returns a new UUID as a string.
  • http_get(url, headers=None, timeout=10) and http_post(url, json_data=None, headers=None, timeout=10) return a dict with status, body and json (None if the body is not JSON). They reject a target (SSRF guard) if any of its resolved addresses is private, loopback, link-local, reserved, multicast or unspecified (0.0.0.0, ::) or lies in 0.0.0.0/8 or 100.64.0.0/10; an IPv4-mapped IPv6 address counts as its IPv4 address. They also reject a URL that cannot be parsed or has no host, and a name that does not resolve within 5 s. They follow no redirect. A rejected target and a response over 1,000,000 bytes raise a ValueError. For a rejected target, its text names only the target's hostname, without port, path, query and credentials (? if the URL has no readable host). The request goes to one of the addresses resolved for the check, one after the other until one accepts the connection, and Host header and TLS name (SNI and certificate check) stay the URL's hostname; if a proxy is set for the URL's scheme (HTTP_PROXY or HTTPS_PROXY, which the hook runner passes through), the proxy connects as before and resolves the name itself, and the target is still checked first; a target that does not go through the proxy because of NO_PROXY connects, as without a proxy, to one of the checked addresses.
  • result (dict) is returned to the caller. log(msg) and print(...) write a line to logs (list), not to stdout; at most 1000 lines of 4096 characters each are kept, longer lines are truncated, further ones dropped.
  • If a context key carries the name of one of these helpers, the hook fails with an error before the script runs.

Environment Model

Hook scripts run in a dedicated Python subprocess with a reduced environment, started by run_hook_script in apps/server/app/modules/hooks/script_runner.py — this is crash/timeout isolation, not a security sandbox:

  • Reduced env: the worker gets PATH, HOME (if the server has none, DATA_DIR/hooks-home: created with mode 0700 on the first run, wider rights are taken away again; if the directory is unusable, the run fails with an error), LANG (if the server has none, C.UTF-8), PYTHONPATH (the server directory), PYTHONNOUSERSITE=1, DATABASE_URL and DATA_DIR. The worker starts with python -s and loads no Python packages from the user directory ($HOME/.local/lib/python3.X/site-packages, including usercustomize); PYTHONNOUSERSITE=1 does the same for Python processes the script starts. Packages for hooks belong in the image. The runner passes HTTP_PROXY, HTTPS_PROXY and NO_PROXY, lowercase too, through only if the server has them set, so that http_get and http_post use a configured proxy. Everything else is dropped, such as ADMIN_PASSWORD, MONITOR_API_KEY and REDIS_URL. SECRET_KEY and the DB credentials stay reachable, however (via DATA_DIR/.secret_key resp. DATABASE_URL) — no secret jail.
  • CWD is the server directory (server_dir), not a temp directory.
  • Timeout: default 30 s. The worker runs in its own process group (start_new_session=True); on expiry the runner kills the whole group. Child processes the script started die with it, except those that open a session or process group of their own. The hook then ends with success: false and error: "Timeout nach 30s". Once the worker has ended, the runner waits at most 2 s for the rest of the output; if a child process keeps stdout or stderr open longer, it kills the group and waits at most 2 s once more. It then evaluates what it has read by then: if the worker wrote its result before it ended, the result arrives even while a child process in a session of its own keeps the output open. The runner writes the payload concurrently; if the worker does not read stdin, the timeout bounds the write as well. A run thus takes at most 34 s and ends before the gateway's read timeout of 60 s.
  • Output limit: the runner reads up to 8,388,608 characters each from the worker's stdout and stderr, 8 MiB for ASCII. If it reads more, it kills the worker's whole process group; the hook then ends with success: false and error: "Hook-Ausgabe zu gross (Limit ueberschritten)". The worker writes its JSON reply including result and logs to stdout, so a very large result counts too.
  • No user switch: the worker runs as the same user as the server.
  • Concurrency: each server process lets at most 8 hook processes run at a time; the limit applies per process, not to the server as a whole. Hooks run in every Uvicorn worker (WEB_CONCURRENCY, default 1) and in the separate scheduler service (RUN_MODE=scheduler) that starts the schedule hooks; each of these processes has its own 8 slots. If all slots of a process are busy, a further call does not wait but ends at once with success: false and error: "Server ausgelastet (Hook-Limit erreicht)".
Not a full sandbox

The hook isolation is defense-in-depth, not a seccomp/namespace jail. Admins with hook-CRUD privileges can run arbitrary code on the server host. Grant hook access only to trusted roles.

Failure behaviour

If an event or schedule hook fails (success: false, for example through an exception in the script, an exit code other than 0, a timeout, the output limit or the hook limit), the server writes one line at WARNING with the hook's name, for event hooks the event, and the error text; of a text over 1,000 characters only its end is logged, the last 1,000 characters after …. Event hooks log under app.core.events in the log of the server service, schedule hooks under app.modules.hooks.scheduler in the log of the scheduler service. A webhook trigger and a run via POST /api/hooks/{id}/run report the error only in the response (success: false, error), not in the log. There is currently no automatic retry and no hook.failed meta-event; a failed hook blocks neither other hooks nor the triggering request.

If a hook stops with an error of the database layer (sqlalchemy.exc.SQLAlchemyError or psycopg.Error), error and the log line Fehler: … in logs name only the error's type, such as OperationalError, not the driver's text. Any other error of a hook appears there with its text.

Firing Custom Events

Internal code can emit events at any time:

python
from app.core.events import fire_event

fire_event("server.updated", {"id": server.id, "name": server.name})

fire_event is non-blocking: the dispatch runs in a thread pool, the call returns immediately. The HTTP response of the emitter does not wait on the hook.

Test Execution

In the web panel, "Run" starts a hook by hand via POST /api/hooks/{id}/run; the endpoint requires admin rights. The context carries no event data; it is filled as the API reference describes for this endpoint. Once the run ends, a dialog shows the result as JSON: success, result, logs and, on failure, error. There are no separate fields for stdout, stderr or exit_code; if the worker process exits with a non-zero code, its stderr is in error and logs.
