Server (Backend)

A FastAPI monolith: HTTP routers, SQLAlchemy models, APScheduler jobs, and FRP PKI are one code monolith — separation by module, not by deployment. For scaling, the web workers and the scheduler run as separate processes of the same image (see Event Bus & Scheduler).

Auth Architecture

JWT access token (HS256, 8 h) and refresh token (7 d) are returned in the JSON body; the refresh token is additionally set as an HttpOnly; Secure; SameSite=Strict cookie (path /api/auth) that browser clients use instead of localStorage (desktop/CLI keep using the body). Browser requests, recognised by the Sec-Fetch-Site header (only a browser sets it), get the refresh token only as the cookie: refresh_token in TokenResponse is then "", the schema stays the same. Token claims: uid (the account's id, users.id), sub (username, for logs only), type (access/refresh), exp, iat (issued-at), jti (UUID). The server maps a token to its account by uid; a token without uid (issued by an older server) does not hold, so everyone signs in once after the update.

  1. Login signs both tokens and returns them in TokenResponse.
  2. On POST /api/auth/refresh the server checks signature, expiry and blacklist.
  3. The old jti is added to token_blacklist (rotation); only the call that adds it gets the new pair. A second, concurrent refresh with the same token counts as reuse, just like a later one; clients coalesce their refreshes.
  4. If an already-revoked refresh is presented again → reuse detection: all sessions of the affected user chain are invalidated (WARNING log with IP); the token's uid names the account, not the name.
  5. Password reset revokes sessions: changing a password sets users.tokens_valid_after; any token whose iat predates it (or that has no iat) is rejected — without needing to know individual jtis. Creating a user sets users.tokens_valid_after to the creation time (whole second): older tokens for the same name do not hold for them.

Password hashing uses SHA-256 prehash → bcrypt, because bcrypt only consumes 72 bytes.

API keys are accepted via the X-API-Key header; the ApiKeyOrUser dependency allows JWT or API key on the same endpoint.

Rate limit & IP filter

Login limit (5 per 60 s/IP) and webhook limit (20 per 60 s/IP) are Redis-backed with in-memory fallback. IP filter via ALLOWED_IPS (CIDR list); proxy trust via TRUSTED_PROXIES (safe) instead of TRUST_PROXY_HEADERS (legacy).

Server Provisioning

New servers are onboarded via one-time tokens with a 24-hour TTL — since v0.23.2 FRP-independent inside the server module:

  1. Admin calls POST /api/servers/{server_id}/provision/token and receives {token, expiresAt, serverId, serverName}.
  2. The agent redeems it with POST /api/servers/{server_id}/provision/activate (header X-Provision-Token) and gets back: a fresh server API key (always), monitor agent key + URL (when the monitor service is reachable), frpc.toml (when FRP is configured) and a one-time enrollment token. Fields are null when the respective component is not configured — an unreachable monitor service does not block provisioning. A per-client PKI bundle is no longer shipped: the agent enrolls its own mTLS/tunnel cert at the ca-issuer (A4/A7).
  3. Tokens are one-time: used_at is set, further activations fail.
  4. At runtime the agent syncs its frpc.toml via GET /api/frp/provision/{server_id}/config + config-hash. Without an FRP config config-hash answers {"hash": null} instead of an error, there is nothing to sync; config stays 404 then. If the host has no active tunnel (active_tunnels in modules/frp/config_generator.py: enabled, STCP only with a secret, a local_port from 1 to 65535, no stored name, local_ip, custom_domains, secret_key or extra_config the API refuses today, i.e. exactly the generator's [[proxies]]; if the host itself carries a name with characters the API refuses, generate_frpc_toml writes neither user nor a tunnel, which is the same case; without_refused_server_name filters only the visitor TOML), config and config-hash serve the common part without a tunnel and without the frps credentials. An agent of this version stops and disables frpc on it; an older agent restarts frpc with it, frpc then does not log in and is restarted by systemd until the agent is updated. config-hash is the hash of exactly this text. The provisioning bundle carries the same text as config, also without an active tunnel, and an agent of this version stores its hash: its next sync has nothing to do. At provisioning an older agent writes the sync config with the new API key and this frpc.toml and starts a stopped frpc on it; a frpc that already runs takes it only at its next restart.

FRP — TOML Structure

modules/frp/config_generator.py renders the FRP configs straight from the DB models into TOML strings — no template engine, just string lists. Three generators:

FunctionTargetContent
generate_frps_toml(config)frps.toml (server)bindPort, optional vhostHTTPSPort/subDomainHost, maxPortsPerClient (always emitted, default 16 to bound a rogue agent), optional dashboard block (webServer.* on 0.0.0.0, reachable only within the compose network since the port is not published), auth.method = "token" + token, plus a [transport.tls] server block.
generate_frpc_toml(config, tunnels, frpc_user)frpc.toml (agent)serverAddr/serverPort/user, token auth, client TLS block, then one [[proxies]] block per active tunnel (active_tunnels). user is the server's ID and each proxy's name the tunnel's ID (R-1210): frps lists the proxy as {server-id}.{tunnel-id}, and no name of a server or tunnel is in the file, so a rename does not change it. A tunnel whose stored local_ip, custom_domains or secret_key has characters the API refuses (rows from before the check; only the characters, not the API's other checks such as the minimum length of a secret) is left out; the server logs the tunnel ID and the field, never the value (without_refused_fields). A user name with such characters is left out of allowUsers (name_refused). Each filter warns once per tunnel and reason, not on every sync, and names the tunnel by its ID. The [[proxies]] are sorted by tunnel ID, so the config and its config hash do not depend on the order in which the database returns the rows. Every proxy carries metadatas.ahProxyKey, the host's key (PROXY_KEY_META in modules/frp/proxy_key.py), which the frps plugin checks (see Proxy policy for frps).
generate_visitor_toml(config, tunnels, visitor_user)Visitor frpc.toml (admin PC)One [[visitors]] block per passed STCP tunnel that is enabled and has a secret and a visitor_port from 1 to 65535 (without_secretless_stcp, without_unbindable_visitor, without_refused_fields; the server logs a left-out tunnel as a warning), sorted by visitor_port, with bindAddr = "127.0.0.1" and bindPort = visitor_port. Each visitor is named {tunnel-id}-visitor and reaches the proxy by serverName = tunnel ID and serverUser = server ID. A visitor_user with characters the API refuses is refused (ValueError), the routes answer 404 for it and the bulk ZIP skips the user. The callers pass only STCP tunnels the user may see (_visible_stcp_tunnels in modules/frp/generate_router.py, in the bulk ZIP the tunnels on the user's servers; if no user has a server, the ZIP holds a single visitor.toml with all STCP tunnels instead).

Only tunnels with enabled = true are rendered. Two tunnel types get special handling:

  • STCP (type = "stcp"): gets a secretKey and allowUsers (default ["ops-admin"], otherwise the passed allow_users). allow_users are the names of all users assigned to the host and of all admins (frp/_helpers.py::get_allow_users), each once and in ascending order, so the config and its config hash stay the same after a restart and in every worker. The matching [[visitors]] block sets serverName (= tunnel ID), serverUser (= server ID, the agent's user, because FRP registers proxies as {user}.{name}) and the same secretKey. The status page (GET /api/frp/status) matches a proxy of the frps dashboard to its tunnel by exactly this name {server-id}.{tunnel-id}, also when the server or tunnel name holds dots.
  • HTTPS (type = "https"): renders customDomains from the comma-separated custom_domains field.

extra_config (JSON) is appended per tunnel preserving types: strings quoted, bools as true/false, numbers raw. A tunnel whose stored extra_config the API refuses today (a key of the plugin family, i.e. with the first segment plugin in upper or lower case, or another entry that does not pass the check of POST /api/frp/tunnels, such as a key with an empty segment or an integer beyond 64 bits, or keys that only clash together, like foo next to FOO, in which case the warning names them all; as well as text that is no JSON object) is left out by the generator (without_refused_extra_config, in active_tunnels), which logs a WARNING with the tunnel name and the keys concerned, never the values. Such a row would otherwise make a frpc.toml that does not hold for the whole host; this way the other tunnels of the host stay up. The row in the database stays as it is; the visitor TOML (no extra_config) keeps the visitor.

Proxy policy for frps

frps hands every new proxy (operation NewProxy) to the plugin frps-policy in the frps image (apps/agent/cmd/frps-policy, logic in apps/agent/internal/frpspolicy; started and watched by the supervisor, see Operations → Checking proxy registrations). It admits a proxy only if its user is a host of the policy, metadatas.ahProxyKey carries that host's key, the name {server-id}.{tunnel-id} names a tunnel of that host, and type, customDomains, subdomain, group and group key equal the tunnel's, allow_users equals the tunnel's user list as a set and sk matches its SHA-256; it never admits a remotePort. It answers an admitted registration with unchange = false and the whole content without metas.ahProxyKey (decoded generically, numbers exact), so frps neither stores the key nor hands it out through its dashboard.

The plugin already answers the operation Login, but in this version frps does not hand it logins yet (the supervisor registers NewProxy only): a host of the policy needs its key in the login metadatas (metadatas.ahProxyKey at the root of frpc.toml, which the agent already takes and the server does not write yet), other users (the desktop's STCP visitor) need none, and every admitted login gets a run_id bound to its user (BoundRunID). A later version switches this on, once the agents take the key.

  • Key (proxy_key.py): HMAC-SHA256 over frp-proxy-v1:{server-id} with a key derived from SECRET_KEY by HMAC. The server stores none; each host knows only its own, from its frpc.toml. A new SECRET_KEY changes every key; the agents fetch them with their next sync.
  • Policy (modules/frp/policy.py): build_policy reads the text of generate_frpc_toml back as TOML for each host, so policy and frpc.toml cannot drift apart, and holds per host keyHash (SHA-256 of the key) and the fields of each proxy, group key and secretKey only as SHA-256 (groupKeyHash, skHash), plus allowUsers (format version 2; the plugin reads only this one). A hostname frps would route to proxies of several servers (customDomains, subdomain + subDomainHost, wildcards as in frps getByRoute; only the same exact name in one shared non-empty group is allowed, domain_conflicts) is left out for all proxies involved with one warning per name; tunnel_router refuses new such tunnels with 409 (_reject_domain_conflict). A host without a proxy is absent; a host with an empty ID or a dot in its ID and a proxy with fields the plugin could not read are left out with a one-time warning. policy_text renders the JSON with sorted keys.
  • Writing: sync_policy writes the file through docker_manager.write_frps_policy as frps-policy.json next to frps.toml (atomically, 0644, no write when unchanged): at startup (main.py), after every change to tunnels (tunnel_router) and to the FRP configuration (config_router), after a server is deleted (servers/router.py), after a change of users' access to servers (users/router.py), and every SYNC_INTERVAL = 60 s (keep_policy_current), which also puts back a deleted or changed file and takes over a state no hook saw (after a restore, say). A failure to write aborts no request; it is logged with the exception type alone.

Names of servers, connections and tunnels

A server has one name (R-1210), ideally its FQDN. servers.hostname is NULL while the address follows the name and holds only a different address (an IP, an internal name); the API always hands out the effective address as hostname (Server.address) and says with customHostname whether an own one is stored. A hostname sent that only repeats the name stores no own address (stored_hostname). A new or changed name must not be another server's, case aside (409); names stored twice before stay.

Connections of a server and tunnels keep only their addition in name ('' = none). The API hands out the display name connections/models.py::shown_name builds as name: {server} · {addition}, without one {server} · SSH|RDP|Web, with (FRP) for tunnels and for connections a tunnel leads to; the stored value comes as label. A client from before sends name: if it only repeats the server, its address, the display name or (for tunnels) the old pattern {server}-{protocol}, the addition stays empty (own_text); sending back the display name it was shown changes nothing. Connections without a server keep their name. When a server is deleted, its connections keep the display name they showed. The migrations b1c3d5e7f9a1, c2d4e6f8a0b2 and d3e5f7a9b1c3 empty addresses and names that only copied the server or the tunnel and drop the uniqueness of tunnel names.

FRP PKI & TLS

As of A7 the frps server cert and the agent tunnel cert come from the ca-issuer's tunnel intermediate (ECDSA P-256, a single trust root): frps mounts the issuer-provisioned material (frps.crt/frps.key/ca.crt) read-only at /etc/frp-pki, and the agent uses the tunnel cert it enrolled (A4) at /etc/adminhelper/identity — one cert for server pushes and the frp tunnel, auto-renewed at ~50 % of its lifetime, or at once when /ca/trust names a new trust generation (R-1054).

The server no longer signs FRP certificates (D6, F3). The former server-run FRP CA (modules/frp/pki.py + pki_router.py with the /api/frp/pki/* endpoints + the startup CA generation in _ensure_pki()) was fully removed with the PKI migration, along with the frp-pki volume and the former master/published split. _ensure_frps_config() only writes the non-secret frps.toml at startup.

The desktop STCP visitor now presents its enrolled access identity as its frpc client cert (the desktop exports key/cert/CA from its keyring into files under identity/). For frps to accept it, the ca-issuer adds the access intermediate to frps's ca.crt (ensure_frps_cert(..., extra_trust)); the real per-tunnel authorization stays the STCP secretKey + server-side bundle filtering, not the cert scope.

The TLS wiring in frps.toml/frpc.toml is produced by the config_generator: the server block (force = true) points at the issuer-provisioned material under /etc/frp-pki; the agent block (enable = true) at the enrolled tunnel cert under /etc/adminhelper/identity; the visitor block at the desktop's exported enrolled identity ({{IDENTITY_DIR}} placeholder, replaced by the desktop with absolute paths at runtime).

SQLAlchemy Models

Tables live in their respective modules (e.g. modules/users/models.py). The schema is managed by Alembic (apps/server/alembic/): docker-entrypoint.sh runs alembic upgrade head before startup. The former SQLite approach (Base.metadata.create_all() at startup plus idempotent _migrate_add_columns() PRAGMA migrations) was dropped with the move to Postgres. The test suite, by contrast, builds the schema directly via Base.metadata.create_all(); test_alembic_builtin.py and test_migrations_smoke.py check for drift between models and migrations (see Tests).

  • Server (UUID PK, JSON tags, os_type) ↔ Connection (n:1, server_id nullable for standalone)
  • ApiKey with permission ∈ {read, read_write}
  • Hook (hook_type ∈ {webhook, event, schedule}, JSON event_triggers, Python script)

  • Playbook (Ansible) with disk-backed YAML content

Event Bus & Scheduler

APScheduler runs in a dedicated scheduler process (app.scheduler_main, RUN_MODE=scheduler), not in the web workers — otherwise uvicorn --workers N would run every job N times (duplicate outbox e-mails, duplicate hook runs). A single instance owns all system jobs (cleanups, outbox drain) and the periodic hook reconcile. Trigger types: predefined intervals (1m, 5m, 15m, 30m, 1h, 6h, 12h, 24h) or cron (5 fields). Cron expressions are in UTC, whatever TZ the scheduler process runs with; next_run is the next run in UTC (R-0756). The weekday counts as in standard cron: 0 and 7 = Sunday, 1 = Monday, 1-5 = Monday to Friday. Names (sun–sat) count as their numbers, also in ranges and with a step (mon-fri/2 = Monday, Wednesday, Friday), as in Vixie cron; a step on a single value (1/2) is invalid. As an exception, sun at the end of a range that starts after Sunday counts as 7, so sat-sun is valid. Also unlike standard cron, day of month and weekday both have to match when both are set: 0 9 1-7 * mon runs on the first Monday of the month, 0 9 15 * mon only on a Monday that falls on the 15th (R-0274). APScheduler 3.x counts from Monday in from_crontab, so _parse_trigger translates the field first (R-0249).

Since the web workers have no running scheduler, the hook CRUD routers no longer register jobs directly; they only persist the hook row. The scheduler process reconciles schedule hooks from the DB every 30 s (reconcile_scheduled_hooks() — added/changed/removed) and writes next_run back. Multi-worker is enabled via WEB_CONCURRENCY (default 1); Redis is then required for a correct global rate limit, and the DB pool applies per worker (DB_POOL_SIZE/DB_MAX_OVERFLOW).

The event bus in core/events.py distributes events through a ThreadPoolExecutor (4 workers, fire-and-forget). Active event types:

  • server.created, server.updated, server.deleted, server.startup (when each web worker starts, so N times with WEB_CONCURRENCY=N; the scheduler does not fire it)
  • connection.created, connection.updated, connection.deleted, connections.imported
  • user.created, user.deleted, user.promoted
  • alert.triggered (per server, when a monitoring check turns critical and the bell pings for it: a new incident, an escalation from warning to critical, or 30 min after the last ping; an event folded in silently does not fire)
  • frp.config.created, frp.config.updated, frp.config.deleted
  • frp.tunnel.created, frp.tunnel.updated, frp.tunnel.deleted
  • playbook.created, playbook.updated, playbook.deleted

Details in Hooks & Events. A curated subset of these events is additionally mirrored into the notification hub via modules/notifications/event_bridge.py (see below).

Data flow:

  1. Sources call service.ingest_event() — the monitoring service via POST /api/internal/events (auth X-Internal-Key = MONITOR_API_KEY, the reverse direction of the monitoring proxy), and the in-process bus via event_bridge.py (curated user.created/user.promoted/server.deleted/frp.tunnel.created).
  2. The resolver (service.resolve_recipients()) maps server_id → user_servers → users × subscriptions — least privilege: a non-admin is only notified about servers assigned to them, admins about all; an event without a server reference goes to admins only. A bundled event (source_ids instead of source_id, 1–500 server ids of 1–256 characters each, e.g. several silent agents at once) is resolved server by server under the same rules: each recipient gets one row titled <title> (<n>) with one text line per server they may see and one of their subscriptions covers (name, else id); source_id stays empty. The bundled event's title and body therefore name no server and carry no total; the alert.triggered hook fires once per server. Unknown ids reach admins only, and no user sees the name or the number of servers that are not theirs; source_id together with source_ids is rejected with 422. Tag scope matches against the server's JSON tags at runtime (deliberately no tag normalization).
  3. Folding (incidents.ingest()): an event with an incident_key folds into the active incident (open/acked) of the same key on the same server. A resolved one whose last ping lies less than REOPEN_WINDOW (30 min) back reopens silently; otherwise a new one opens, and the new keys of one bundle (incident_keys) open one bundle incident with members together. The server is part of the match: a check moved to another server starts a new incident there, so nobody reads the history of a server they do not see. Only a new incident pings, a shown warning that turns critical (an escalation; an acknowledged incident is open again afterwards), or a problem 30 min after the last ping; otherwise the event counts silently (event_count, history). A recovery (new_status ok) resolves the incident automatically, a bundle once every member has recovered, and pings only if the bell showed its problem, at the severity it showed. Events without a key (the server's own notices, an older monitoring sender) are an incident each at warning/critical, only when somebody receives them, and never resolve by themselves; info notices, keyless recoveries and keyless bundles stay rows without an incident. The ingests of one key wait on its advisory lock; a recovery then locks every incident it may write in one query ordered by id, and the team actions (acknowledging several ids) lock by id as well and only what they change: so two transactions never wait on each other in a circle.
  4. A ping writes each recipient's row of the incident anew (unread, shown again, notified_at) plus notification_outbox rows for the channels service.channels_for() picks from the person's matrix (the row of the severity, ok for the all-clear, critical for an unknown severity; without switched-off channels, none for a muted category), provided a target is set; Telegram only with TELEGRAM_BOT_TOKEN. A muted row (the incident until muted_until, or the server of the ping in notification_server_mute) takes the content only, stays read and sends nothing. A user's several matching subscriptions collapse into one feed entry. For a bundled event each outbox row gets its own title and text (notification_outbox.title/body) with the count and names of the same servers as the person's bell. Otherwise both stay NULL and delivery uses the text of the notification row.
  5. An APScheduler system job (schedule_outbox_drain, every minute, in the dedicated scheduler process — see Event Bus & Scheduler above) drains the outbox via outbox.drain_outbox() and one function per channel in sender.py (send_email via smtplib, send_ntfy, send_telegram to api.telegram.org, send_webhook) out of the request path, with linear backoff up to NOTIFICATION_MAX_ATTEMPTS (default 5), then status failed. ntfy and webhook go through ssrf.check_target(url, allow_networks=NOTIFY_PRIVATE_TARGETS) and a client pinned to the checked address, without redirects; a blocked target is failed at once. Every delivery reads the status only and runs under a hard deadline of 30 s; when a target misses it or the httpx timeout, or takes 10 s or more to answer, its further entries and the person's other HTTP entries wait for the next run without an attempt (for Telegram all Telegram entries, as it is one Bot API), and the run reads on past them, so they take none of its places. Logs and last_error name only channel, exception type and HTTP status, never URL, chat ID or token.
  6. Quiet hours and digest (quiet.py, digest.py): on a ping, incidents._queue sets next_attempt_at of anything not critical (and of critical without quiet_critical) during quiet hours to their end in the person's zone; the drain waits until then. With digest on, an e-mail below critical gets the status digest, which the drain leaves alone; the system job schedule_notification_digest (every 5 min) sends one mail per person once 08:00 in their zone (weekly: Monday) has passed after their oldest waiting entry and their last digest, to the address of the newest entry; the text carries the oldest DIGEST_MAX_LINES (200) entries and counts the rest in a closing line, all count as sent. A failed send counts an attempt on every entry, up to NOTIFICATION_MAX_ATTEMPTS, then failed. A time skipped by the spring change applies with the offset before it; an end in the repeated autumn hour takes the pass still ahead.
  7. Escalation (escalation.py, system job schedule_notification_escalation, every minute): for each row with severity critical of an open incident whose critical_since is past the person's deadline, without escalated_at, not muted (row, server or category) and for a person who still sees the incident now (the same check as incidents.access), the job writes an outbox entry on the escalation channel, regardless of the matrix but not for a switched-off channel or one without a target (a later run catches up once there is one), and sets escalated_at and the history entry escalated (text: the channel). The quiet hours apply as for critical.

Clients fetch the feed via GET /api/notifications (own feed, paginated, sorted by the last ping, hidden rows left out) plus /unread-count (without muted and hidden rows) and POST /api/notifications/read, /unread and /hide; the incident routes (detail, acknowledge, resolve, reopen, note, mute, server mute) are in the API reference. Acknowledge, resolve, reopen and notes are team actions: only someone who sees every server of the incident may take them (canAct), otherwise 403. The detail shows each person the history and the members of a bundle for their own servers only. The summarised values of a bundle (count, severity, lastAt, state, whether it escalated or notified, canAct) hold for the whole bundle and so reveal activity on servers the person does not see, but neither their names nor their number (a deliberate trade-off: the bundle stays one incident instead of being split per person). The retention (cleanup_old_notifications) deletes rows without an incident by notified_at, and an incident with its rows and history once its last event is older and it is resolved or keyless; an open check incident stays. Personal settings via GET/PUT /api/users/me/notification-prefs (replace-all).

Push (SSE): GET /api/notifications/stream is a long-lived text/event-stream. After ingest_event() commits, the server publishes a lightweight "refresh" signal (stream_hub.publish()) on the Redis channel notif:events; each web worker holds a Redis subscription and delivers it to its locally connected streams of the affected users. The stream handler is async and holds no DB connection for its whole lifetime (it reads from an asyncio.Queue); it authenticates with a short-lived session at connect and then re-validates the bearer JWT (blacklist/expiry) and the mTLS certificate (revocation, expiry and the check against its scope's trust file, as at connect) about once a minute off the event loop (a threadpool), so a logout, a revoke or an intermediate dropped from the trust file ends an already-open stream instead of pushing nudges forever. After a team action the signal goes to everyone holding a row of the incident, after hide, unread or mute only to the person. The signal carries no content — the client pulls the rows via REST (no second serialization/authorization path). Without REDIS_URL there is no push; the bell falls back to 30 s polling. The desktop tunnels the stream through the Rust client (src-tauri/src/notifications.rs) because the WebView can't open an EventSource against the self-signed cert; it emits a notification Tauri event per frame.

Persistence

State splits across two locations:

  • PostgreSQL (compose volume postgres18-data): two DBs adminhelper (server) and adminhelper_monitor (monitoring).
  • File system under DATA_DIR (default /app/data): bootstrap token, JWT secret, Ansible playbook files.
  • Shared volume frp-config (frps mounts it :ro at /etc/frp): the non-secret frps.toml (0600) and frps-policy.json (0644, the frps plugin's policy, holding of the keys only their SHA-256). The FRP TLS material is provided by the ca-issuer (volume frps-certs); the PKI crown jewel is its ca-pki volume.

The container starts as root only briefly to chown the mounted paths, then drops via gosu to a non-root user (uid 10001) — uvicorn, Alembic and hook subprocesses all run unprivileged. uvicorn listens plain-HTTP on 8080 (no host port); TLS is terminated by the upstream gateway (nginx), not the server.

Tests

Pytest suite under apps/server/tests/. Tests run against a real Postgres 18 via testcontainers (local) or services: postgres:18-alpine (CI). SAVEPOINT pattern in the db_session fixture: outer transaction + begin_nested + after_transaction_end listener — tests can call commit(), everything is rolled back at the end. No test reaches the app's engine (app.core.database.engine): an autouse fixture makes every connection attempt fail and the test fail in its teardown. Code that opens SessionLocal() itself is bound by the test to the connection of db_session; a test that needs the engine on purpose carries the marker app_engine. Plus two drift detectors between Base.metadata and the Alembic migrations: test_alembic_builtin.py runs pytest-alembic's built-in tests (exactly one head, every revision in order, models match the DDL after the full run, every revision survives a down-and-up round trip) and one data migration with data; test_migrations_smoke.py checks that upgrade head on an empty database yields the models.
