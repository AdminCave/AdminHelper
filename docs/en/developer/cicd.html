CI/CD & Release

GitHub Actions builds and tests every component, pushes the server and monitoring images to the GitHub Container Registry (ghcr.io), and creates a draft release with the desktop and agent artifacts on a version tag.

Workflows

WorkflowPurpose
ci.ymlLint & tests for every component: server pytest (Postgres service, Python 3.12/3.13), monitoring pytest (Postgres service for the migration smoke test), Go agent (gofmt/vet/test), desktop UI & web panel (svelte-check/eslint/vitest, Playwright E2E), Rust/Tauri (fmt/clippy/test). Additional PR gates against “green but broken”: cargo test --locked on Windows, the Go suite running natively on Windows (job agent-windows: go test -v ./..., a build and a version smoke of the .exe), a cargo tauri build smoke on Linux (debug, deb only), Docker builds of both images without push, and an FRP pin consistency check (FRP_VERSION + SHA-256 across ci.yml/release.yml/docker-compose.yml/crabbox_bootstrap.sh). Coverage runs report-only in the test jobs (no gate). On main pushes + manual dispatch (deliberately not a per-PR gate yet, since it builds the server image and boots a five-container stack): a from-outside integration test (scripts/tests/integration_stack_test.sh) that boots the real stack with mTLS enforced and drives the full path through the nginx gateway only – enrollment token, CSR → enroll plane (:8444) → client cert, certless → rejected, cert+JWT → 200. The desktop E2E (WebdriverIO + tauri-driver under xvfb, apps/desktop/e2e/) deliberately does not run in CI; it runs locally/manually (cd apps/desktop/e2e && xvfb-run -a npm test): the headless WebKit chain (tauri-driver → WebKitWebDriver → WebKit) drifts with the runner image + ungated upstream tools and reddened main without signalling a real defect. The heavy tier (multi-host stack, mTLS over a real network hop, desktop GUI) instead runs on crabbox (ephemeral Proxmox VMs) – see DEVELOPMENT.md and the /test skill
docker.ymlBuild & push the server + monitoring images to ghcr.io/admincave/adminhelper/{server,monitoring}; sign each digest keylessly with cosign (+ SLSA provenance/SBOM)
release.ymlDesktop DEB/RPM/binary, Go-agent DEB/RPM + Linux/Windows binaries, Windows MSI (best-effort), SHA256SUMS (+ minisign signature), draft release. Jobs: desktop-linux, agent, agent-windows-smoke (hard – runs the built .exe once), desktop-windows (best-effort, installs and uninstalls the MSI), release. The assertions are listed below under “Release assertions”.
audit.ymlWeekly dependency audit (Monday morning, also manually via workflow_dispatch): pip-audit (server + monitoring locks), cargo audit (desktop), govulncheck (agent), npm audit (web + desktop UI)

Test aggregator (scripts/tests/run.sh)

One entry point for every suite – locally, on a crabbox VM and in the CI job ops-scripts. The call is bash scripts/tests/run.sh [layer] [flags]; layers are lint, unit, quick (default), integration, e2e, all. The heavy layers refuse to run without AH_ALLOW_REAL=1.

Flag / envEffect
--strictA SKIP of a required step is a failure, not a pass. So is a strict run in which no step executed at all.
--only <keys…>Restricts lint/unit to components (server monitoring ca-issuer agent desktop desktop-rs desktop-ui desktop-e2e web scripts). Under --strict a step asked for this way counts as required. Env form: AH_ONLY.
--step <name>Exactly one step (a substring of its name). An unknown or ambiguous name is rejected in a dry pass, before any suite starts.
AH_REQUIREDThis machine’s required set (step ids, space-separated); overrides AH_REQUIRED_DEFAULT and belongs in the gitignored .devenv.sh. Under --strict the effective set is printed with the summary. When the variable is unset and the layer is integration, e2e or all, every step of that layer is required (the box rule; heavy.sh clears the dev box’s set before a box run).
AH_ARGSExtra arguments for the suite itself – how verify.sh <component> -- <args> forwards them.

Exit 75 means SKIP. A script whose precondition is missing exits 75 (EX_TEMPFAIL) and is counted as a SKIP. A bare exit 0 would be a green PASS although nothing ran – which is how the seven desktop GUI suites and agent_install_test.sh stayed invisible for months. The minisign branches in install_test.sh / update_test.sh were the sharper case: they reported PASS after neutralising the signature path. SKIP does not mean verified.

test-skips. Even inside a green pytest suite a single test can be skipped silently. Under --strict the Python suites run with -rs and run.sh reads the skip lines: if a required test’s precondition is met and it skips anyway, the run ends with strict-failed: <test> (test-skip). Each precondition mirrors what the test itself checks – DATABASE_URL for test_migrations_smoke, a reachable Redis for test_stream_redis, a Postgres in AH_TEST_DB for test_db_token_store, a reachable database (or Docker) for test_auth_token_lifecycle. On a box that genuinely cannot run a test it stays a visible SKIP.

The summary line is therefore N passed, M failed, K skipped, J test-skips, R reruns. reruns stays 0 on purpose: the weekly run re-runs a red step itself and classifies it, rather than letting the suites retry quietly (see “Weekly run”).

Go under -race. The Go step runs go test -race -cover when the box has a C compiler with cgo enabled – the agent is concurrent (monitor, frpc, config), and a data race is the bug class neither review nor a single-threaded test can see. Without a compiler the suite runs unchanged and the run says so (race: off (no gcc)): a green run that checked less must stay distinguishable. The CI job agent always has cgo and runs -race unconditionally.

Upgrade path. The integration layer includes scripts/tests/upgrade_path_test.sh – the one suite that does not start from scratch: it brings the stack up from the last published release's images, seeds it through the admin API, switches to the images built from this checkout (both services migrate on startup) and asserts that the seeds are still readable and a fresh agent report still lands (UPGRADE_OK). Then scripts/update.sh --ref <tag> runs for real against a second install directory (UPDATE_SH_OK, or UPDATE_SH_SKIP when that release ships no runtime bundle). Without Docker or network it exits 75.

Evidence. Every run writes $AH_OUT_DIR/last-<layer>.json (default .crabbox-out/, gitignored) holding the layer, the flags, the required set, timestamps, every step with its result and duration, the test-skips – plus head and tree_hash. The tree hash comes from scripts/dev/tree-hash.sh: it is built in a throwaway index, so it sees untracked files while tasks/ and the output directories stay out. Ticking a ledger box therefore does not invalidate a run’s evidence; a new, uncommitted source file does.

Weekly run (scripts/tests/heavy.sh)

The heavy tier used to run whenever someone remembered, and its results were recorded nowhere. heavy.sh is a wrapper around the existing crabbox scripts that adds exactly that: a report, a history, and a mechanical classification of the all layer's red steps. (Retries, quarantine and the second VM belong to that layer; the capstone layer reports its red assertions directly as fail.) It never starts by itself – Kevin starts it, usually in tmux, and reads the report afterwards.

tmux new -d -s ah-weekly 'bash scripts/tests/heavy.sh weekly'

bash scripts/tests/heavy.sh all|capstone|weekly [--base <sha>] [--no-second-vm] [--notify]

all = warm box → run.sh all --strict; capstone = crabbox_multibox.sh --capstone --strict; weekly = both, serially. The capstone is skipped only when the all layer ended UNVERIFIED (seven VMs must not burn into a broken environment) – a plain FAIL does not stop it. Beforehand it checks crabbox doctor and crabbox list: a foreign box means the capacity is not there, and the run stops before spending a single VM.

The report lands in .crabbox-out/weekly/<yyyy-mm-dd-hhmm>/report.md. Its first line is the verdict and is quoted verbatim, never paraphrased; then come the wrappers' summary lines verbatim, the step table, the “Kevin sichtet” section, the notes, the audit.yml verdict and the VM list. Facts, never a judgement. The history is tasks/private/history.csv (datum,commit,tree_hash,ebene,schritt,ergebnis,sekunden,vm), committed in the private repo and never pushed.

ResultHow it is reachedWhat it means
infrathe box could not be had, or the step could not run: no warm box, warm pond not ready, a failed server lease, strict-failed: no step ran, strict-failed: … (SKIP), wrapper exit 74Never a regression; the report header reads UNVERIFIED.
flakygreen within three retries on the same box (AH_NO_SYNC=1, desktop suites spec-exact)Quarantine line in tasks/private/seen.md; the run does not fail because of it.
unbestaetigt3× red but green on a fresh second VM – or the counter-check was not possible: no PASS commit in history.csv, --no-second-vm, the worktree could not be created, the second box could not be leased, the base commit could not be checked outKevin looks at it; never a REG row.
externred on the second VM and on the last PASS commitEnvironment, dependency, network – not the code since the last PASS.
regred on the second VM, green on the last PASS commitRoadmap row (class REG, status neu) plus a short ledger tasks/reg-<date>-<step>.md. Releasing it stays Kevin's tick.
failred on all three retries but failing differently each time; every red capstone assertion; the layer row when steps stay red after the retriesReproducibly broken without the stable signature a regression claim needs – no second VM.

The second VM is a worktree .crabbox-worktrees/w2 with its own lane (AH_LANE=w2, pond ah-warm-w2); heavy.sh reaps that pond and removes the worktree itself. Kevin's own warm box (ah-warm) is never touched. --base <sha> sets the comparison commit (default: the newest history.csv layer row with ebene=all,schritt=-,ergebnis=pass, not a single step's), --no-second-vm skips the counter-check, and --notify posts the verdict line and the report path to AH_NOTIFY_URL (off by default).

Exit codes: 0 = PASS, 1 = FAIL, 74 = UNVERIFIED, 2 = usage. UNVERIFIED means the infrastructure did not let the run happen, so nothing is known about the code. That distinction is the whole point: “SKIP is not verified” applies to a whole run too.

Verify convention (scripts/dev/verify.sh)

A task’s Verify: line always calls a component suite in this form:

bash
bash scripts/dev/verify.sh <component> [--strict] [--tree <path>] [-- <args>]

The script sources .devenv.sh (or $AH_DEVENV), resolves AH_TEST_DB, delegates to run.sh quick --only <component> (its lint and unit steps), runs against another checkout with --tree and writes last-verify.json – the run artifact plus component, args, tree. The wrapper exists because of the allowlist: a Bash allow rule never matches across an env prefix, so source .devenv.sh && DATABASE_URL=… pytest cannot be allowlisted. The script resolves what the environment needs; the caller writes flags only.

Container Images (ghcr.io)

Tagging is driven by docker/metadata-action. :latest is produced only on a (non-prerelease) semver tag – not on every main push:

text
ghcr.io/admincave/adminhelper/server:0.24.0      # release tag
ghcr.io/admincave/adminhelper/server:latest      # latest semver release
ghcr.io/admincave/adminhelper/server:main        # latest main build
ghcr.io/admincave/adminhelper/server:sha-abc1234 # per commit
# likewise: ghcr.io/admincave/adminhelper/monitoring:…
Package visibility

Freshly created ghcr packages are private. After the first successful docker.yml run, server and monitoring must be switched to public once in the GitHub package settings – otherwise docker compose pull fails for external users with unauthorized/manifest-unknown.

Release Artifacts

release.yml runs on a v* tag and attaches the built artifacts to a draft release (not published until a human clicks “Publish”):

  • Desktop client: .deb + .rpm (Tauri) + ELF binary
  • Go agent: .deb + .rpm + linux/windows binaries
  • Agent package repo: adminhelper-agent-repo-<tag>.tar.gz (GPG-signed apt+rpm repo, once REPO_GPG_PRIVATE_KEY is set) — plus the archive keyring adminhelper-archive-keyring.gpg as a standalone asset (a second channel to fingerprint-verify it against SHA256SUMS + minisign)
  • Desktop client Windows .msi (best-effort – does not block the release if the Windows build fails)
  • SHA256SUMS over all assets – plus SHA256SUMS.minisig (minisign signature) once armed

The agent version is derived from the tag (${GITHUB_REF_NAME#v}) and injected into the binaries via -ldflags "-X main.version=$VERSION". The tauri-cli is pinned to an exact version in CI and release (cargo install tauri-cli --locked --version …) so a new CLI release cannot break a tag build.

Release assertions

All six release-blocking defects of the 0.43.x/0.44.0 series came out of execution, none out of static review. release.yml therefore checks the result, not the recipe:

  • Static agent. After the build, file must report the binary as statically linked and objdump -T must import no GLIBC_ symbol. The Makefile pins CGO_ENABLED=0, but the result was never checked: an inlined go build produced a binary dynamically linked against glibc 2.39 that would not start on older distributions – while the crabbox tests, which use make, stayed green.
  • The shipped .deb. ar t on the artifact that is actually uploaded: no .zst member. build-deb.sh guards its own output; this guards what ends up in the release.
  • Signature against the pinned key. Right after minisign -S, the fresh signature is verified against the MINISIGN_PUBKEY pinned in scripts/update.sh. A rotated or wrong MINISIGN_SECRET_KEY produces a perfectly valid signature that install.sh/update.sh reject – which otherwise only shows up on user machines, after publishing.
  • The Windows binary runs. The hard job agent-windows-smoke (windows-latest, tags only) downloads the agent artifact and runs adminhelper-agent-windows-x86_64.exe version; the output must name the tag version. The draft job gates on it.
  • MSI installed and uninstalled. desktop-windows installs the MSI silently (msiexec /i … /qn /norestart /l*v), asserts the success line in the log and the installed adminhelper.exe (whose install path is still unverified – the job therefore searches ProgramFiles, ProgramFiles(x86) and LOCALAPPDATA\Programs), and uninstalls again; msi.log is uploaded as its own artifact (never as a release asset). The job stays continue-on-error until the Windows VM arrives – a red MSI is visible but does not block.
  • Version locations. bash scripts/release/check-versions.sh ${GITHUB_REF_NAME#v} checks all six hand-maintained locations instead of only tauri.conf.json, printing ok/MISSING per location. That same call belongs before the tag – what is red there aborts the draft here.

Release Signing (supply chain)

The curl|bash install/update flow should prove authenticity, not just transport integrity (otherwise the bundle and SHA256SUMS come from the same origin). Two mechanisms:

  • Container images: docker.yml signs each pushed image digest keylessly with cosign (GitHub OIDC, no private key) and attaches SLSA provenance (mode=max) + an SBOM. Verify: 
    cosign verify ghcr.io/admincave/adminhelper/server \
  --certificate-identity-regexp 'https://github.com/AdminCave/AdminHelper/.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
  • Release assets: release.yml signs SHA256SUMS with minisign into SHA256SUMS.minisig – and immediately verifies the fresh signature against the same public key scripts/update.sh pins, so a wrong secret aborts the draft instead of the users. install.sh/update.sh verify that signature against a public key pinned in the script before trusting the checksums (fail closed).
Arming (maintainer, one-time)

This repo is armed: the key is pinned, so verification fails closed – a missing/invalid signature aborts install.sh/update.sh, and the release workflow fails if MINISIGN_SECRET_KEY is absent. A fork that has not set its own key falls back to checksum-only verification (with a warning) until armed. To arm a fork:

minisign -G -W                 # generate a passwordless keypair
# 1) store the secret-key file base64-encoded as the GitHub Actions secret
#    (single line, paste-safe — a raw multi-line key gets mangled otherwise):
#    base64 -w0 minisign.key | gh secret set MINISIGN_SECRET_KEY
# 2) pin the public key (the "RW…" line from minisign.pub) into
#    MINISIGN_PUBKEY in scripts/install.sh AND scripts/update.sh

Repo signing (agent package repo)

release.yml also builds a GPG-signed apt/rpm repo (apps/agent/build-repo.sh: InRelease/Release.gpg, rpm --addsign + repomd.xml.asc) and attaches it as one asset adminhelper-agent-repo-<tag>.tar.gz – covered by SHA256SUMS + minisign. The server serves it over the gateway's certless repo plane (:8445); install.sh/update.sh pull the asset into ./repo. Agent hosts trust the GPG fingerprint (trust root), not the transport (see Agent deployment).

Arming (maintainer, one-time)

Without a configured key, release.yml skips the repo asset (with a warning) and /repo returns 404 – no breakage. To arm, generate a passphrase-less GPG key:

# 1) Generate a passphrase-less signing key
gpg --batch --passphrase '' \
    --quick-generate-key "AdminHelper Repo <repo@admincave.com>" rsa3072 sign 0

# 2) Store the secret key base64-encoded as the GitHub Actions secret
#    (single line, paste-safe):
gpg --export-secret-keys --armor <KEYID> | base64 -w0 | gh secret set REPO_GPG_PRIVATE_KEY

# 3) Pin the fingerprint: replace the <REPO-GPG-FINGERPRINT> placeholder in
#    agent-deployment.html (DE+EN) with this value:
gpg --fingerprint <KEYID>
Key rotation (overlap window)

When the signing key expires or is compromised the clients must not break fleet-wide: they pin the old key via Signed-By= (apt) or the imported RPM key, and the only way to fetch the new keyring is the very repo they no longer trust without an overlap. So rotate in two steps:

  1. Overlap: generate the new key (as in arming). Keep signing with the old one (REPO_GPG_KEY_ID=<OLD>) but ship both public keys: REPO_GPG_EXPORT_IDS="<OLD> <NEW>". Cut a release – every host gets the new key into its keyring and trusts both from then on.
  2. Switch (once the fleet has pulled the overlap release): sign with the new key (REPO_GPG_KEY_ID=<NEW>), ship only the new one (REPO_GPG_EXPORT_IDS=<NEW>) and update the fingerprint in agent-deployment.html (DE+EN). The old key can then be revoked.

Version Locations

A release needs the new version set in multiple places at once – the tag alone isn't enough:

  • apps/desktop/src-tauri/tauri.conf.json + Cargo.toml + Cargo.lock – Tauri bundle
  • apps/desktop/ui/package.json + apps/web/package.json (+ each package-lock.json) – Vite builds
  • apps/desktop/ui/src/components/AppShell.svelte – sidebar badge
  • apps/agent/build-deb.sh + build-rpm.sh – default VERSION (CI overrides it from the tag)
  • docs/**/*.html – footer <span>v0.24.0</span> + landing “What's new” + code samples
  • README.md – agent DEB install command
  • CHANGELOG.md – new section at the top + link ref

The server itself does not carry its own version – the backend is identified by Docker image tag.

Release Checklist

  1. Bump the versions in the files listed above to the target value.
  2. Update the footer versions in docs/**/*.html (footer span + landing “What's new” + code samples). Filter on the class (grep -rl 'class="sidebar-footer"'), not on the one-line markup: the two landing pages write the footer across two lines and therefore hung from 0.43.2 through 0.45.0.
  3. Update CHANGELOG.md (Keep a Changelog: new section + link ref).
  4. bash scripts/release/check-versions.sh X.Y.Z – must report 0 missing. The same call runs in the release workflow on the tag.
  5. Commit & tag: git commit -am "release: v0.24.0" && git tag v0.24.0.
  6. git push --follow-tags.
  7. Watch docker.yml + release.yml; after the first image push, switch the ghcr packages to public (once).
  8. In the GitHub draft release, review the notes, verify the mandatory assets, and click “Publish”.
Draft instead of auto-publish

The release is deliberately created as a draft, and the release job is success-gated on the mandatory Linux builds. This lets you verify before publishing that all mandatory artifacts (Linux desktop + agent) are actually attached – the Windows MSI build is best-effort and may be missing.
