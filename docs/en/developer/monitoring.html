Monitoring Stack

Monitoring is three layers cooperating: the AdminHelper server acts as a reverse proxy and forwards UI queries, the separate monitoring/ service holds checks/alerts/templates and runs scheduler-based pull checks, VictoriaMetrics stores the time-series data (retention configurable via VM_RETENTION, default 90 days).

Data Flow

flow
[Agent]                                [Monitoring service]            [VictoriaMetrics]
   |                                          |                                |
   | POST /agent/{server_id}/report --------->|  agent_resources, service_     |
   |   (X-API-Key)                            |  process, docker_health,        |
   |                                          |  proxmox_backup, zfs_health,    |
   |                                          |  smart_health -> evaluate +     |
   |                                          |  format_line() ---------------->|
   |                                          |                                |
                                              |  APScheduler -> http / ping /  |
                                              |  tcp / agent_ping ------------>|
                                              |
[Desktop client] -> /api/monitoring/* (admin) -> AdminHelper server -> /monitor/* (X-Internal-Key) -> Monitoring service

AdminHelper side: monitoring_proxy

There is no dedicated monitoring module on the AdminHelper server anymore; everything goes through apps/server/app/modules/monitoring_proxy/router.py:

  • POST /api/monitoring/agent/{server_id}/report – public (X-API-Key), forwarded 1:1 to the service
  • GET/POST/PUT/DELETE /api/monitoring/{path:path} – admin-only, internally augmented with X-Internal-Key: $MONITOR_API_KEY
  • SSRF guard: allowed path prefixes are checks, alerts, status, templates, maintenance, agent; path traversal (..) is blocked
  • Deleting a server in AdminHelper fires DELETE /servers/{id}/cleanup at the monitoring service – orphaned checks/alerts are pruned automatically

Push checks vs. pull checks

There are two classes of checks – what matters is who gathers the data:

ModeCheck typesTrigger
Push (agent)agent_resources, service_process, docker_health, proxmox_backup, zfs_health, smart_healthOn the next agent push (5-minute timer); APScheduler is not involved.
Pull (service)http, ping, tcp, agent_ping, disk_forecastAPScheduler inside the monitoring service, by a fixed interval.

Both paths write the result into MonitorState through apply_result() (check_engine.py), the metrics to VictoriaMetrics through format_line(), and call process_alert() when fail_count ≥ consecutive_fails. Until then effective_status() (check_engine.py) keeps the old status; a new check (pending) shows ok meanwhile, unless the result is unknown: then it shows unknown, so a check without data does not stand green. That costs no notification, unknown never notifies.

In the other direction holds_recovery() holds the recovery, but only for a reported problem: when notified_status is warning/critical and the check stands at warning, critical or unknown, apply_result() sets it to notified_status on an ok until MonitorState.ok_count reaches consecutive_oks (default 2; migration c3e5a7b9d1f2 sets it for existing checks). So the hold keeps the reported status, never a worse one the check only reached while muted; holding neither escalates nor reports anything (resolve_notification → skip). A problem never reported (muted by maintenance or host-down) turns ok on the first ok, at once and silently; held, it would be caught up as a fresh alert. next_ok_count() counts an ok up and resets to 0 on any other result; while the hold lasts the message carries “(recovery n/m)”. pending → ok and ok → ok never hold, nor does consecutive_oks 1. Because the status itself is held, the dashboard, the bell and an agent_ping's host-down inhibition stay with the problem during the hold.

APScheduler (scheduler.py) runs with a thread pool of 30 workers and misfire_grace_time=30 s – runs that start late are caught up within 30 s instead of being dropped. A daily cleanup job additionally prunes monitor_alert_log (retention via ALERT_LOG_RETENTION_DAYS, default 90 days), and the tag sync runs every 15 minutes (see below).

Push payload (agent → service)

The Go agent assembles the report in apps/agent/internal/monitor/report.go (BuildReport) and sends it as JSON via POST {url}/agent/{server_id}/report with the headers Content-Type: application/json and X-API-Key (PushReport). The server handler in routers/agent.py accepts the JSON as a free-form dict. Python also reads NaN, Infinity and integers of up to 4300 digits there (sys.get_int_max_str_digits); the checkers take numbers from the report only as a JSON number (representable as a finite float), and the to_dict methods in models.py return stored non-finite numbers and integers beyond float range as null (check config, details of the state, channel_config of an alert rule, check and alert definitions of a template), and so does the update comparison of a standard template in current (GET /templates/{template_id}/builtin-update). The stored value stays as it is. Structure:

Fields are optional: docker and zfs appear as soon as docker or zpool is on the host, even when the agent cannot read them. They then carry available: false, error (Docker daemon_unreachable | timeout | cli_failed | parse_failed, ZFS timeout | cli_failed), error_message (a short text with the call and the exit status, never stderr or paths) and an empty list (see Agent). proxmox appears only with data. Instead of smart, the agent sends smart_absent.reason (not_installed | scan_failed | no_devices) when no disk is readable. These fields and the container fields from exit_code on are additive: older agents do not send them, older monitoring services ignore them and read an outage as an empty list (ok). host is additive as well: older agents do not send it, older monitoring services ignore it. A current agent sends it with every push (collectHostFacts() in apps/agent/internal/monitor/hostfacts.go): os is runtime.GOOS; platform and platform_version come from gopsutil host.PlatformInformation() (the product name on Windows), virtualization with system and role from host.Virtualization() (empty when nothing is detected, always on Windows). If either call fails, only its fields are missing, never the block. subsystems is always a list, in the order docker, zfs, proxmox, with every entry whose program (docker, zpool or pvesh) is on the search path, whether or not the plugin collectors return data. What the service makes of it is described under Suggestions from the host facts. VMs without sensors send no temperatures. services is a legacy key alongside systemd. The handler iterates over resources (CPU/RAM/load/disk/temp), uptime_seconds and smart, writes VictoriaMetrics lines from them (pseudo filesystems in EXCLUDED_FSTYPES are skipped), then evaluates the push checks configured for the server against the report. Response: {"status":"ok","metricsWritten":N,"checksUpdated":M}.

systemd.all_services is additionally throttled: the agent sends the full inventory only when its hash has changed or the last full send is more than 1 h ago – a missing key ≠ an empty list (an empty list means: genuinely no services). Every push carries failed, enabled_inactive (the agent has already removed the units inactive by design, see Agent) and counts (active/total of the loaded services; missing when the agent could not list them). If systemctl list-units or sc query fails, error carries a short reason. The checker copies it into the message cut to 500 characters (including the “…”); if it is not a string, the failure still counts, but the message names no reason. Alias entries in the inventory (enabled_state alias) name their unit in alias_of. counts, error and alias_of are additive: older agents do not send them, older monitoring services ignore them. The ServiceProcessChecker evaluates:

  • auto: it takes enabled_inactive from the agent as sent and does not derive it from all_services; failed is systemd.failed plus the failed entries of the inventory (capped at 500, always the same ones thanks to the sort order). A full and a throttled push of the same state thus give the same result. ignore entries are glob patterns (fnmatch.fnmatchcase); a name without a unit type also matches <name>.service. Without a problem but with error, the check is unknown instead of ok. Valid counts (integers representable as a finite float, 0 ≤ active ≤ total) end up in _details as active_count/total. The names in _details.failed and _details.enabled_inactive go there through cap_agent_text, cut to 500 characters (including the “…”) and on one line; the ignore patterns compare the full name.
  • list: per name (without a unit type normalized to <name>.service) the first source that knows it decides: report["services"] (an agent with its own list from monitor init --services), then all_services of this push (an alias through alias_of), and on a push without the inventory the state of the last evaluation (prev_details.watched; the push handler in routers/agent.py passes the previous _details to service_process as it does for agent_resources). A full inventory is the current state and is not filled up from prev_details. _details.watched is [{name, state, running}] with state ∈ {running, down, nodata}; running (state == "running") stays for desktops that do not know state yet. Status: critical if at least one name is down, unknown if no name has data, otherwise ok; nodata does not count as down.

Checkers at a glance

Each checker returns a triple (status, message, metrics) with status ∈ {ok, warning, critical, unknown}. message is English and goes as it is into the dashboard, the bell and the notifications; the desktop translates where it renders from _details. A list in the message (VMs, pools, containers, disks, services, mounts) goes through join_capped in checkers/agent.py: the helper cuts each entry to 500 characters (the “…” included), names in order at most 10 entries and at most 1000 characters (entries and separators), the first always, and counts the rest as “(+N more)”. _details still carries every entry the checker rated; status and metrics stay the same. Every text from the report that a message takes over, a list entry as well as a single text (such as error_message), goes through cap_agent_text, which join_capped builds on: every control character (Unicode category Cc, tab, line feed and carriage return included) and the separators U+2028 and U+2029 become one space each, the length and the limit of 500 characters stay; a message is thus a single line. cap_agent_text cuts first and replaces after; since each character is replaced by exactly one, the result is the same, and the work stays bounded to 500 characters however long the text is. The rating (ignore lists, state) still reads the full value. On top of that, apply_result() in check_engine.py, the one writer of MonitorState.message, cuts every message to 2000 characters (the “…” included), a scheduler check's “Unexpected error: …” too; only then does it append “(failure n/m)” to a damped failure, or “(recovery n/m)” to a held recovery. _details stays complete. Pull checkers expose a run(config) method; agent/push checkers evaluate the push report directly in evaluate(config, report).

The numbers that only go into _details go there only as a JSON number as well: the RAM sums (memory_total_mb, memory_used_mb) and disk sizes (total_gb, used_gb), otherwise null, and the sensor limits (high, critical), otherwise 0. At most the first 500 disks or sensors are rated; an entry that is not an object is skipped, and a resources that is not an object counts as missing (“No resource data”). ServiceProcessChecker checks services – mode auto (failed + the enabled-but-inactive systemd units the agent reports, with an ignore list of glob patterns) or list (explicitly named services, evaluated server-side from the inventory and the last state; details under push payload). The resources checker applies per-metric hysteresis (hysteresis_pp, release = entry − 10 pp); push timestamps are persisted by the push handler (routers/agent.py) in monitor_agent_liveness and hydrated by the lifespan at startup; the checker additionally keeps a process-local monotonic stamp. A wall-clock divergence of > 60 s means the monitoring host's clock jumped: the checker grades on the monotonic (true) age and re-anchors the stored wall stamp — deliberately a correction, not an unknown bail-out, which would declare a dead agent fresh and drop agent_ping out of the host-down inhibition (that matches critical). A hydrated server without a monotonic stamp keeps plain wall-clock behavior; the persisted row is only rewritten on the next push, so a restart right after a jump falls back to the old behavior for up to one push interval – no false-alert storm after a monitoring restart.
forecast.pydisk_forecastPull checker: query_range over monitor_agent_disk_percent_value{server_id="…"} (window window_hours, step 10 m), least-squares slope per mount → hours_left = (100 − last) / rate. Rates ≤ 0.01 pp/h count as stable (ok); too little history → unknown. server_id is escaped with escape_label_value().
smart.pysmart_healthEvaluates SMART data from the push (ATA HDD/SSD and NVMe). Checks reallocated/pending sectors, NVMe critical_warning bits and temperatures against type-specific thresholds, among others. A missing smart key is ok, not an error: with smart_absent the message names the reason (No SMART data: …) and _details is {"absent": <reason>}; without it (an older agent or an unknown reason) the message stays “No SMART data (VM or smartctl not available)” without details. At most the first 500 disks of a report are rated; an entry that is not an object is skipped, and a smart that is not a list counts as empty, like a missing key. The number fields of a disk (every int field of SmartDisk in apps/agent/internal/monitor/smart.go, e.g. temp_c, smartctl_status, reallocated_sectors, available_spare_pct, critical_warning) only count as a JSON number (no bool, representable as a finite float; a numeric string such as "16" does not count either), device, kind and model only as a string (message and _details show an empty device or model as ?). Anything else counts as missing, with the default for a missing field (device and model ?, kind from protocol, counters and temperature 0, available_spare_pct 100; _details then has available_spare_pct and percentage_used as null). Message, metrics and _details carry the values read. device and model go through cap_agent_text into the message and _details, cut to 500 characters (including the “…”) and on one line, and so does kind into _details; ignore_devices and the metric names read the full device, the temperature thresholds the full kind. protocol picks the checks by its raw value (only ATA and NVMe have checks of their own; without the field it is ATA); _details has it only as a string and capped the same way, otherwise ATA. smart_passed is in _details as a bool, as the rating reads it: false, null, 0, "", [] and {} are “SMART FAILED” (critical), any other value and a missing field count as passed.

The plugin checkers proxmox_backup, zfs_health and docker_health (in checkers/plugins.py) are likewise push-evaluated. All three rate at most the first 500 VMs (proxmox.vms), pools (zfs.pools) or containers (docker.containers) of a report; a value there that is not a list counts as empty, an entry that is not an object is skipped (it still counts toward the limit), and a proxmox, zfs or docker block that is not an object counts as missing. The number fields of an entry (vmid and last_backup_ts of a VM, capacity_percent of a pool, exit_code and restart_count of a container) only count as a JSON number (no bool, representable as a finite float), vmid, exit_code and restart_count only as a whole number in integer notation (a JSON 3.0 counts as missing); a VM's name and type and a pool's name and health only count as a string (an empty one counts as missing). Anything else counts as missing, with the default for a missing field (name ?, type vm, health UNKNOWN; capacity 0 %, health then still counts); an unreadable backup timestamp is “No backup” (critical). These texts go through cap_agent_text into the message and _details, cut to 500 characters (including the “…”) and on one line; the rating reads the full health, the metric name zfs_capacity_<name> the full pool name. For zfs_health and docker_health:

  • Block missing: unknown with _details {"pools": []} or {"containers": []} instead of None – otherwise the push path keeps the stored details of a result without any, and the desktop would go on showing the old list.
  • Outage (available: false or error set): warning with ZFS unavailable (<code>): <error_message> or Docker unavailable (…), _details with available: false, error and an empty list. Only a JSON false is an outage; null, 0 or "false" let the pools or containers decide. The checker takes the code only from the agent's list (above); any other value is still an outage, but without a code (ZFS unavailable or Docker unavailable, _details.error null). error_message goes into the message cut to 500 characters (including the “…”); a value that is not a string stays out. alert_on_unavailable (StrictBool in ZfsHealthConfig and DockerHealthConfig, default true) turns that into unknown; the checker only switches off on a real false. Readable but without pools or containers is ok; otherwise the details carry available: true and error: null.
  • docker_health gets the previous _details like agent_resources and service_process (evaluate(config, report, prev_details), _PREV_DETAILS_TYPES in routers/agent.py) for the restart counter per container ID; only an ID of type string has a previous value (the agent sends the 12-character short ID). Without name the container is named after that ID, or ? if it is not a string. name, state and the status text status only count as strings: any other name counts as missing, any other state as empty (unknown_state), any other status text yields neither an exit code nor unhealthy. name and state go into the message and into _details cut to 500 characters (including the trailing “…”), and so do image and id into _details; these only count as a string (an empty one counts as missing), otherwise _details has "" or null. ignore_containers compares against the full name, the rating reads the full state; the checker looks up the previous restart count under the capped ID, as _details stores it. _details.containers is [{id, name, image, state, category, reason, exit_code, restart_count}] with category ∈ {ok, warning, critical, stopped} and reason ∈ unhealthy, restarted, restarting, dead, paused, created, start_failed, oom, stopped, exit:<n>, unknown_state (null for ok); the rules are in the admin guide. The status is the worst category, stopped counts as ok. Without exit_code or health (an older agent) the checker reads the exit code and unhealthy from the docker ps status text; likewise for an exit_code that is not a whole number. An exit code of more than 10 digits in the status text is not read; the container then counts as without an exit code. A restart_count that is not a whole JSON number counts as missing, and the container then does not count as restarted. The messages are in English; the desktop translates from the codes.

Auth modes

Both modes are implemented in core/auth.py as FastAPI dependencies:

  • require_agent (agent push): reads header X-API-Key. If the value matches the internal key exactly, it counts as __internal__ (access to all servers). Otherwise the key is SHA-256-hashed via MonitorAgentKey.hash_key() and compared against the hashed_key column in monitor_agent_keys – on a hit the dependency returns the associated server_id. A clear-text key is never stored; only the hash lives in the DB.
  • require_internal (AdminHelper ↔ service): reads header X-Internal-Key and compares it against the internal key. Its source is the env var MONITOR_API_KEY; if absent, a random key is generated at startup and persisted to $DATA_DIR/.api_key (core/config.py).

Agent key: issuance & server binding

Agent keys are issued per server (routers/admin.py):

  • POST /agent-keys/{server_id} creates a raw key with secrets.token_urlsafe(48), stores only its SHA-256 hash, and returns the raw key once in the response. If a key already exists for the server, it is deleted first (rotation = DELETE + POST). server_id is unique in the table, so exactly one key per server.
  • Both endpoints (POST/DELETE /agent-keys/{server_id}) are themselves guarded by require_internal – only the AdminHelper server may manage keys.
  • The push handler (routers/agent.py) additionally checks that the server_id derived from the key matches the server_id in the path; otherwise 403. A valid key for server A therefore cannot submit metrics for server B (__internal__ excepted).

Templates, seeding & tag sync

MonitorTemplate bundles check and alert definitions as JSON with a stable def_id per definition. POST /templates/{id}/assign (body {server_id, hostname, server_name}) rolls out the template; template_sync.py reconciles changes so server assignments stay drift-free.

Built-in seeding (tombstone)

At startup the lifespan seeds five standard templates from builtin_templates.py (marked via builtin_slug). The tombstone in monitor_seed_state guarantees: each slug is seeded at most once – a user-deleted built-in is never restored by later startups; new built-ins of later releases seed only themselves. What a later startup does with an existing built-in is governed by its version (next section). The definitions pass the same schema boundary as user templates (test tests/test_seed.py).

Built-in versions

Every entry in BUILTIN_TEMPLATES carries "version"; a changed definition ships as a new version. The row keeps the version last rolled out in monitor_templates.builtin_version and the sha256 of the definitions rolled out with it in builtin_hash (both NULL on user templates; migration a7c9e1b3d5f7). definitions_hash() hashes the canonical JSON (sort_keys=True, separators=(",", ":")) of canonical_definitions(check_definitions, alert_definitions): both lists without the keys that hold their schema default from TemplateCheckDef or TemplateAlertDef. Reason: the editor stores every definition in full (model_dump), the shipped ones leave defaults out, and a new optional schema field must not change the hash of every install. The template's name and description do not count; a renamed built-in keeps following new versions.

After seeding and the baseline (record_override_baseline(), below), the lifespan calls reconcile_builtin_templates() (best effort like the seeding, before load_all_checks()). A row with builtin_slug but no hash (created before versions) gets version 1 and the hash of the shipped definitions; if its definitions differ from those, it counts as edited from then on. If the shipped version is higher and the hash of the current definitions equals builtin_hash, _roll_out() replaces the definitions (name and description stay), sets version and hash and calls sync_template(); customized check fields stay. Otherwise nothing changes. Every decision is taken under the row lock (with_for_update() with populate_existing(), effective on Postgres): a second startup or a concurrent "Apply" then sees the new version and does not sync twice. MonitorTemplate.to_dict() returns builtinVersion, builtinEdited (hash of the current definitions ≠ builtin_hash) and builtinUpdateAvailable (shipped version > builtin_version).

Customized template checks (overridden_fields)

monitor_checks.overridden_fields (text, NOT NULL, default '[]') holds, as a JSON list, the fields of a template check the user changed, by their snake_case column names and in a fixed order (TEMPLATE_CHECK_FIELDS): name, description, check_type, config, enabled, interval, severity, consecutive_fails, consecutive_oks. PUT /checks/{id} and POST /checks/{id}/toggle call mark_overrides(): every field sent is compared with the resolved template value (resolve_template_check(): the definition with the assignment's variables substituted, missing keys filled with the defaults of a new check, for consecutive_oks DEFAULT_CONSECUTIVE_OKS = 2 from schemas.py); different → added, equal → removed. When check_type is in the list, config always is too. Manual checks and checks whose assignment or definition is gone are left alone. On update, _sync_checks_for_server() writes only the fields not in the list; with config customized it does not write check_type either. A definition no longer in the template still deletes its check, customized or not. Alert rules have no counterpart: _sync_alerts_for_server() sets them to the template's values on every sync. MonitorCheck.to_dict() returns templateDefId and overriddenFields (list).

Baseline at the first start (record_override_baseline)

Existing checks start with []. record_override_baseline() marks once per install what was changed by hand before: for every check with a template_id it calls mark_overrides() with all of the check's current values, so every field that differs from the template counts as customized, with the type/config coupling. It resolves with the assignment's server_hostname/server_name, the names the check was built from; a server renamed since is no customization. Manual checks and checks whose assignment or definition is gone stay as they are. A check that cannot be compared (ValueError, TypeError or AttributeError from an unreadable config or definition) gets every field and a warning with its ID; database errors fail the run. The log line counts the marked and the not comparable checks. For consecutive_oks, added later, it does not run again in existing installs: nobody could change the field before the update, every check holds the column default 2.

The run is done with the reserved key baseline:overridden-fields (OVERRIDE_BASELINE_KEY) in monitor_seed_state, committed together with the marks; the colon keeps it out of the built-ins' slug namespace. Once the key is there, no run compares again. Migration a7c9e1b3d5f7 deletes it on upgrade when it adds overridden_fields: a downgrade drops the marks, and the next upgrade takes the baseline again.

No sync runs without the baseline. The lifespan takes it after the seed and before reconcile_builtin_templates(), best effort like the seed. Every path to a sync takes it before it changes anything the baseline compares with: reconcile_builtin_templates() and apply_builtin_update() before the row lock, the tag sync's name refresh before the new names, PUT /templates/{id} before the new definitions, restore_checks() before the tombstones go; sync_template() and sync_assignment() call it as well (only a lookup by then). If it fails there, that sync does not happen, the error goes to the caller as for any sync error, and the next start or sync tries again. Residual risk: a template change that was never synced to a check before the update shows there as customized.

Check tombstones

The table monitor_check_tombstones (template_id with an FK to monitor_templates and ON DELETE CASCADE, server_id with an index, def_id; unique per triple) records template checks a user deleted on one server. DELETE /checks/{id} creates the tombstone while the server has the template assigned (tombstone_check()); the sync creates no check for a triple marked this way. The tombstones go with the assignment (remove_template(), so assigning again creates everything again), with the server (cleanup_server(); no FK, the server lives in the server DB), with the template (cascade) and on restore. GET /templates/assignments/{server_id} returns removedChecks per assignment: the pair's tombstones whose def_id is still in the template (check_def_ids()).

Suggestions from the host facts

If host in the report is an object, the push handler passes it to store_host_facts() (app/template_suggestions.py) after the NUL check and before evaluating the checks. It writes one row per server to monitor_host_facts (server_id as the key, os, platform, platform_version, virt_system, virt_role, subsystems as a JSON list, updated_at = last report; migration b9d1f3a5c7e9) and checks on the way: os only from linux, windows, darwin, otherwise NULL; the other strings are cut to 64 characters, "" and values of another type become NULL; subsystems keeps only docker, zfs and proxmox, in that order, and drops the rest. A wrong value costs only its own field. It commits on its own and only logs a failure (without a traceback): like the liveness, storing the facts never costs the report. If host is missing (an older agent) or not an object, stored facts stay as they are.

suggest_templates() derives the suggestions from them, the OS first: os linux → linux-base, windows → windows-base (darwin has no standard template), subsystem docker → docker-host, zfs → zfs-storage, proxmox → proxmox-host. A slug is suggested only if a template with that builtin_slug exists (so not a deleted built-in), it is not assigned to the server (whatever the source) and it was not dismissed there. A dismissal is a row in monitor_template_suggestion_dismissals (server_id with an index, builtin_slug, dismissed_at; unique per pair); there is no route to take one back yet. Neither table has an FK to the server; cleanup_server() deletes their rows too.

Tag sync (server ↔ monitoring)

Tags live in the server DB (Server.tags); monitoring only knows server_id strings. tag_sync.py pulls the inventory via GET /api/internal/servers on the AdminHelper server (service-to-service, X-Internal-Key) and materializes the server assignments for every MonitorTemplateTagAssignment with source='tag'. Triggers: every 15 minutes via the scheduler and immediately as a best-effort nudge – the AdminHelper server POSTs to /templates/tag-sync after server create/update(tags/name/hostname)/delete. When a server loses the tag, the tag assignment and its materialized checks are removed; source='manual' assignments are never removed by the sync. In addition, for every remaining assignment, manual and tag alike, it compares server_hostname/server_name with hostname/name from the inventory: if they differ, it writes the new values and syncs exactly this pair again (sync_assignment(); customized check fields stay, alert rules are set again), so {{hostname}}/{{server_name}} follow a rename. A server missing from the inventory stays unchanged; if the sync fails, it is rolled back and the old names stay. POST /templates/tag-sync responds with {"created": n, "removed": m, "refreshed": k}. An unreachable server API (None) is strictly distinguished from an empty inventory ([]) – an outage deletes no assignments.

Alert pipeline: sent-state, guards & suppression

The alerter is level-driven (docs/features/alert-sent-state.md): monitor_states.notified_status holds the status last actually reported; migration c1d3e5f7a9b1 backfills it with status so a deploy triggers no catch-up storm. Both call sites (execute_check, the agent push handler) decide via resolve_notification(notified_status, eff_status): skip (nothing new, or unknown), silent_ack (an ok without a reported problem – booked inline, no dispatch) or notify (BG dispatch). Order in process_alert() (applies to rule dispatch and the hub emit, since _emit_to_hub sits behind the same guards):

  1. Claim phase: state load under FOR UPDATE (a short window with no I/O; serializes concurrent BG dispatches), current = state.status is re-read under the lock (the caller snapshot may be stale) → resolve_notification: skip/silent_ack as above.
  2. Active maintenance window of the server → collect-but-mute: status/metrics keep flowing, the notification is suppressed, no alert-log row, notified_status stays untouched → the first cycle after the window reports the discrepancy. is_in_maintenance() evaluates weekly windows in the configured IANA time zone (zoneinfo, DST-correct; including day wrap across midnight).
  3. Host-down inhibition: while the server's agent_ping stands at critical, all other checks of that server stay silent (notified_status untouched → catch-up after the agent recovery); agent_ping itself always alerts.
  4. Report (claim-then-dispatch): notified_status = current is committed BEFORE the channel I/O – the row lock never spans webhook/SMTP timeouts (the 5.3 isolation stays intact) and a later commit failure cannot re-fire an already-sent alert (at-most-once). Message/alert log/hub emit carry the last reported status as "old" (reported_old); the log rows land with the caller's commit. "Reported" means the claim persisted, independent of per-channel success (the rule cooldown may damp an escalation catch-up; the hub emit always runs).

Maintenance CRUD lives in routers/maintenance.py (/maintenance, require_internal; proxy prefix maintenance).

VictoriaMetrics

External container (see docker-compose.yml), retention -retentionPeriod=${VM_RETENTION:-90d} – independent of ALERT_LOG_RETENTION_DAYS (alert log in Postgres). The service writes in InfluxDB line protocol via core/victoria.py:

bash
monitor_agent_cpu_percent,server_id=srv123 value=45.2 1683000000

format_line writes an integer within the int64 range (−263 to 263−1) with the suffix i (value=5i), one outside it as a float (value=9.223372036854776e+18): VictoriaMetrics reads a value with i as int64 and answers an overflow with HTTP 400 for the whole write, its valid lines included; it stores float64 anyway. A number that is not finite as a float (inf, nan, an integer beyond the float range) is rejected by format_line; in the metrics of a check result (build_check_result_lines) it alone is dropped.

Reads use the standard Prometheus endpoints /api/v1/query and /api/v1/query_range. uPlot in the desktop client renders the charts. The UI chart queries are never raw: GET /checks/{id}/metrics builds the PromQL query server-side from a per-check-type metric allowlist (CHECK_TYPE_METRICS) and escapes label values – free-text queries from the UI never reach VictoriaMetrics (SSRF/injection guard).

Ingest validation

The push endpoint enforces that the API key really belongs to the supplied server_id. A compromised agent key cannot forge metrics for other servers.
