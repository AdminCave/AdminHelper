Developer Guide

Monitoring Stack

Monitoring is three layers cooperating: the AdminHelper server acts as a reverse proxy and forwards UI queries, the separate monitoring/ service holds checks/alerts/templates and runs scheduler-based pull checks, VictoriaMetrics stores the time-series data (retention configurable via VM_RETENTION, default 90 days).

Data Flow

flow
[Agent]                                [Monitoring service]            [VictoriaMetrics]
   |                                          |                                |
   | POST /agent/{server_id}/report --------->|  agent_resources, service_     |
   |   (X-API-Key)                            |  process, docker_health,        |
   |                                          |  proxmox_backup, zfs_health,    |
   |                                          |  smart_health -> evaluate +     |
   |                                          |  format_line() ---------------->|
   |                                          |                                |
                                              |  APScheduler -> http / ping /  |
                                              |  tcp / agent_ping ------------>|
                                              |
[Desktop client] -> /api/monitoring/* (admin) -> AdminHelper server -> {MONITOR_SERVICE_URL}/{path} (X-Internal-Key) -> Monitoring service

The server forwards without a prefix: /api/monitoring/{path} becomes {MONITOR_SERVICE_URL}/{path} (default http://monitoring:8080), because the monitoring service mounts its routers without a prefix (apps/monitoring/app/main.py).

AdminHelper side: monitoring_proxy

There is no dedicated monitoring module on the AdminHelper server anymore; everything goes through apps/server/app/modules/monitoring_proxy/router.py:

  • POST /api/monitoring/agent/{server_id}/report – public (X-API-Key), forwarded 1:1 to the service
  • GET/POST/PUT/DELETE /api/monitoring/{path:path} – admin-only, internally augmented with X-Internal-Key: $MONITOR_API_KEY
  • SSRF guard: allowed path prefixes are checks, alerts, status, templates, maintenance, agent; path traversal (..) is blocked
  • Deleting a server in AdminHelper fires DELETE /servers/{id}/cleanup at the monitoring service – orphaned checks/alerts are pruned automatically

Push checks vs. pull checks

There are two classes of checks – what matters is who gathers the data:

ModeCheck typesTrigger
Push (agent)agent_resources, service_process, docker_health, proxmox_backup, zfs_health, smart_health, system_stateOn the next agent push (5-minute timer); APScheduler is not involved.
Pull (service)http, ping, tcp, agent_ping, disk_forecastAPScheduler inside the monitoring service, by a fixed interval.

Push types carry push_only: True in CHECK_TYPES (apps/monitoring/app/check_types.py); the desktop keeps the same list as PUSH_ONLY_CHECK_TYPES (apps/desktop/ui/src/lib/models/monitoring.ts), and apps/monitoring/tests/test_push_only_ui_sync.py keeps the two equal: a new push type such as system_state changes both files in the same commit.

Both paths write the result into MonitorState through apply_result() (check_engine.py), the metrics to VictoriaMetrics through format_line(), and call process_alert() when fail_count ≥ consecutive_fails. Until then effective_status() (check_engine.py) keeps the old status; a new check (pending) shows ok meanwhile, unless the result is unknown: then it shows unknown, so a check without data does not stand green. That costs no notification, unknown never notifies.

In the other direction holds_recovery() holds the recovery, but only for a reported problem: when notified_status is warning/critical and the check stands at warning, critical or unknown, apply_result() sets it to notified_status on an ok until MonitorState.ok_count reaches consecutive_oks (default 2; migration 3c66308d11a7 sets it for existing checks). So the hold keeps the reported status, never a worse one the check only reached while muted; holding neither escalates nor reports anything (resolve_notification → skip), also when the display rises meanwhile (reported critical, muted warning or unknown, then ok → critical “(recovery 1/m)”). A problem never reported (muted by maintenance or host-down) turns ok on the first ok, at once and silently; held, it would be caught up as a fresh alert. next_ok_count() counts an ok up and resets to 0 on any other result; while the hold lasts the message carries “(recovery n/m)”. pending → ok and ok → ok never hold, nor does consecutive_oks 1. Because the status itself is held, the dashboard, the bell and an agent_ping's host-down inhibition stay with the problem during the hold.

APScheduler (scheduler.py) runs with a thread pool of 30 workers and misfire_grace_time=30 s – runs that start late are caught up within 30 s instead of being dropped. A daily cleanup job additionally prunes monitor_alert_log (retention via ALERT_LOG_RETENTION_DAYS, default 90 days), the tag sync runs every 15 minutes (see below), and every 30 s system:agent-alert-bundle reports the open heartbeats (bundled alert, see the alert pipeline).

Push payload (agent → service)

The Go agent assembles the report in apps/agent/internal/monitor/report.go (BuildReport) and sends it as JSON via POST {url}/agent/{server_id}/report with the headers Content-Type: application/json and X-API-Key (PushReport). The server handler in routers/agent.py accepts the JSON as a free-form dict. Python also reads NaN, Infinity and integers of up to 4300 digits there (sys.get_int_max_str_digits); the checkers take numbers from the report only as a JSON number (representable as a finite float), and the to_dict methods in models.py return stored non-finite numbers and integers beyond float range as null (check config, details of the state, channel_config of an alert rule, check and alert definitions of a template), and so does the update comparison of a standard template in current (GET /templates/{template_id}/builtin-update). The stored value stays as it is. Structure:

Fields are optional: docker, zfs and proxmox appear as soon as docker, zpool or pvesh is on the host, even when the agent cannot read them. They then carry available: false, error (Docker daemon_unreachable | timeout | cli_failed | parse_failed, ZFS timeout | cli_failed, Proxmox timeout | cli_failed | parse_failed | backup_index_incomplete), error_message (a short text with the call and the exit status, never stderr or paths) and an empty list, Proxmox also node: null (see Agent). Instead of smart, the agent sends smart_absent.reason (not_installed | scan_failed | no_devices) when no disk is readable. These fields and the container fields from exit_code on are additive: older agents do not send them, older monitoring services ignore them and read an outage as an empty list (ok). host is additive as well: older agents do not send it, older monitoring services ignore it. A current agent sends it with every push (collectHostFacts() in apps/agent/internal/monitor/hostfacts.go): os is runtime.GOOS; platform and platform_version come from gopsutil host.PlatformInformation() (the product name on Windows), virtualization with system and role from host.Virtualization() (empty when nothing is detected, always on Windows). If either call fails, only its fields are missing, never the block. subsystems is always a list, in the order docker, zfs, proxmox, with every entry whose program (docker, zpool or pvesh) is on the search path, whether or not the plugin collectors return data. What the service makes of it is described under Suggestions from the host facts; in addition, agent_resources tells a container from virtualization and does not rate the load there (Checkers at a glance). VMs without sensors send no temperatures. services is a legacy key alongside systemd. The handler iterates over resources (CPU/RAM/load/disk/temp) and uptime_seconds, writes VictoriaMetrics lines from them (pseudo filesystems in EXCLUDED_FSTYPES are skipped), then evaluates the push checks configured for the server against the report. It reads the values as the checkers do: measured values only as a JSON number (no bool, no numeric string, representable as a finite float), fstype, mount and sensor only as a string (otherwise as without the field, mount then ? as in the checker, sensor unknown). Of disks and temperatures, at most the first 500 entries count, as in the checker; an entry that is not an object is skipped and costs only itself. It writes no lines of its own from smart: the SMART series (monitor_smart_temp_<device>, monitor_smart_reallocated_…, monitor_smart_pending_…) come from the smart_health check with its check labels. Response: {"status":"ok","metricsWritten":N,"checksUpdated":M}; metricsWritten counts the lines the handler hands over for writing (the write happens in the background, see VictoriaMetrics).

Report version 3. The agent sets report_version 3; the service does not read the number, it rates what the report carries. Everything new is additive:

  • resources.cpu_percent stays a percentage, but is the share of busy CPU time since the last report sent successfully instead of a 1-second sample; without a usable previous sample the agent still takes the sample (see Agent).
  • resources.cpu_count (logical CPUs), swap_total_mb, swap_used_mb and, only with a swap device, swap_percent: Linux only.
  • Per disk free_gb (the space left to non-root users; Linux and Windows) and inodes_percent (Linux only, and only on filesystems that report inodes).
  • system_state (Linux only): reboot_required and time_synchronized as a bool, security_updates and oom_kills as an integer. Each field comes only when the agent could determine it; without a single one the block is missing. oom_kills counts since the last report sent successfully and is therefore in exactly one report; the agent counts security_updates at most once an hour from the local package lists.
  • proxmox, like docker and zfs, is always sent as soon as pvesh is on the search path, with available, error and vms as a list (empty too); on an outage with the code, error_message, node: null and an empty list. Older agents leave the block out on a read error.

The handler writes no VictoriaMetrics series of its own from the new fields; they only go into the rating and into _details. Agent and monitoring service ship in the same release; mixed versions behave as follows:

AgentMonitoring serviceResult
before report version 3currentSwap, inodes, load per CPU and the system state stay unrated (system_state is ok with “Not evaluated: no system state in report”); without free_gb only the percentage counts for disks, as before; a Proxmox outage leaves the block out and stays unknown (“No Proxmox data in report”), now with an empty VM list.

An older desktop shows a system_state check without a section of its own and a Proxmox outage as “—”.

systemd.all_services is additionally throttled: the agent sends the full inventory only when its hash has changed or the last full send is more than 1 h ago – a missing key ≠ an empty list (an empty list means: genuinely no services). Every push carries failed, enabled_inactive (the agent has already removed the units inactive by design, see Agent) and counts (active/total of the loaded services; missing when the agent could not list them). If systemctl list-units or sc query fails, error carries a short reason. The checker copies it into the message cut to 500 characters (including the “…”); if it is not a string, the failure still counts, but the message names no reason. Alias entries in the inventory (enabled_state alias) name their unit in alias_of. counts, error and alias_of are additive: older agents do not send them, older monitoring services ignore them. The ServiceProcessChecker evaluates:

  • auto: it takes enabled_inactive from the agent as sent and does not derive it from all_services; failed is systemd.failed plus the failed entries of the inventory (capped at 500, always the same ones thanks to the sort order). A full and a throttled push of the same state thus give the same result. Among the first 500 entries, only strings count from failed and enabled_inactive, and only objects with a string in unit from all_services; any other entry is skipped (it still counts toward the limit), and a systemd that is not an object counts as missing (“No service data in report”). ignore entries are glob patterns (fnmatch.fnmatchcase); a name without a unit type also matches <name>.service. Without a problem but with error, the check is unknown instead of ok. Valid counts (integers representable as a finite float, 0 ≤ active ≤ total) end up in _details as active_count/total. The names in _details.failed and _details.enabled_inactive go there through cap_agent_text, cut to 500 characters (including the “…”) and on one line; the ignore patterns compare the full name.
  • list: per name (without a unit type normalized to <name>.service) the first source that knows it decides: report["services"] (an agent with its own list from monitor init --services), then all_services of this push (an alias through alias_of), and on a push without the inventory the state of the last evaluation (prev_details.watched; the push handler in routers/agent.py passes the previous _details to service_process as it does for agent_resources). A full inventory is the current state and is not filled up from prev_details. _details.watched is [{name, state, running}] with state ∈ {running, down, nodata}; running (state == "running") stays for desktops that do not know state yet. Status: critical if at least one name is down, unknown if no name has data, otherwise ok; nodata does not count as down.

Checkers at a glance

Each checker returns a triple (status, message, metrics) with status ∈ {ok, warning, critical, unknown}. message is English and goes as it is into the dashboard, the bell and the notifications; the desktop translates where it renders from _details. A list in the message (VMs, pools, containers, disks, services, mounts) goes through join_capped in checkers/agent.py: the helper cuts each entry to 500 characters (the “…” included), names in order at most 10 entries and at most 1000 characters (entries and separators), the first always, and counts the rest as “(+N more)”. _details still carries every entry the checker rated; status and metrics stay the same. Every text from the report that a message takes over, a list entry as well as a single text (such as error_message), goes through cap_agent_text, which join_capped builds on: every control character (Unicode category Cc, tab, line feed and carriage return included) and the separators U+2028 and U+2029 become one space each, the length and the limit of 500 characters stay; a message is thus a single line. cap_agent_text cuts first and replaces after; since each character is replaced by exactly one, the result is the same, and the work stays bounded to 500 characters however long the text is. The rating (ignore lists, state) still reads the full value. On top of that, apply_result() in check_engine.py, the one writer of MonitorState.message, cuts every message to 2000 characters (the “…” included), a scheduler check's “Unexpected error: …” too; only then does it append “(failure n/m)” to a damped failure, or “(recovery n/m)” to a held recovery. _details stays complete. Pull checkers expose a run(config) method; agent/push checkers evaluate the push report directly in evaluate(config, report, prev_details) (PushChecker); prev_details is the check's previous _details or None.

CheckerType(s)What it does
http.pyhttpHTTP/HTTPS request via httpx (method configurable, follows redirects itself, at most 5; at most 5 content-encoding layers). Compares the status code against expected_status, optionally searches for search_string in the first 1 MiB of the decoded body (the check inflates gzip and deflate step by step itself, other encodings stay raw), measures response time. SSRF guard: URLs that resolve to private/reserved IP ranges are rejected, the first URL as well as every redirect hop. Each request connects to one of the addresses checked there (check_target + pinned_client), one after the other until one accepts the connection; Host header and TLS name (SNI and certificate check) stay the hostname. If the environment sets a proxy for the URL's scheme (HTTP_PROXY, HTTPS_PROXY or ALL_PROXY), the proxy connects as before and resolves the name itself; the URL is still checked first. A target that does not go through the proxy because of NO_PROXY connects, as without a proxy, to one of the checked addresses.
ping.pypingICMP echo via ping -c 1 -W <timeout> as a subprocess. The target is validated against an allowlist regex (hostnames/IPs); parses the RTT from the output. No private/reserved block (unlike http.py): probing internal hosts is the core use case, the signal is reachability only, and check creation is admin-only.
tcp.pytcpTCP connect via socket.create_connection((target, port)) with timeout. ok on a successful connect (with connect time), critical on timeout/refused. Like ping.py, no private/reserved block – a connect returns no response content.
agent.pyagent_ping, agent_resources, service_processAgentPingChecker checks (scheduler-driven) the age of the last push against stale_minutes. AgentResourcesChecker evaluates CPU, RAM, swap, load per CPU, disks with their inodes and temperatures against warn/crit thresholds. For swap, inodes, load and the free-GB gate its defaults equal those in check_configs.py and in the “Linux Server — Standard” template (version 3), so a check without these keys (customised or built by hand) rates them alike. It reads CPU, RAM, disk values (percent) and sensor values (temp_c) only as a JSON number (no bool, representable as a finite float) and fstype, mount and sensor only as a string; anything else counts as missing (CPU/RAM not graded, disk and sensor 0). The numbers that only go into _details go there only as a JSON number as well: the RAM sums (memory_total_mb, memory_used_mb) and disk sizes (total_gb, used_gb), otherwise null, and the sensor limits (high, critical), otherwise 0. At most the first 500 disks or sensors are rated; an entry that is not an object is skipped, and a resources that is not an object counts as missing (“No resource data”). From report version 3 on: swap (swap_percent, key swap) counts only with swap_total_mb > 0; the load per CPU is round(load_5m / cpu_count, 2) (key load, unit /CPU), only with an integer cpu_count ≥ 1, and not in a container: if the report carries host.virtualization with role guest and a system from _CONTAINER_SYSTEMS (lxc, docker, openvz, rkt, the same list as containerSystems in apps/agent/internal/monitor/system_linux.go, which test_agent_resources_checker.py keeps equal), load_per_cpu is in _details, along with load_rated: false, but without the key load (there load_5m is the host's load, cpu_count possibly the container's); without host, on a host or a VM load_rated is missing and the load counts as before; inodes come per disk from inodes_percent (inode:<mount>). If one of these values is missing (older agent, Windows), the metric stays unrated, without unknown. A disk's percentage alarm (disk:<mount>) counts only when free_gb is missing (older agent), min_free_gb is 0 or free_gb < min_free_gb; the label then names the free GB (Disk / 85%, 15 GB free). warn, crit and min_free_gb come per mount from disk_overrides (a null there counts as unset), otherwise from disk_warn, disk_crit and disk_min_free_gb. A mount in ignore_mounts is rated neither for usage nor for inodes and is listed in _details with ignored: true; both lists take exact mount paths. A disk without mount is named ? alike in the rating, in the ignore_mounts match and in _details (NO_MOUNT). _details also carries swap, swap_total_mb, swap_used_mb, cpu_count, load_per_cpu and per disk free_gb, inodes_percent and ignored (numbers only as a JSON number, otherwise null), plus problems, the level per rated metric ({<key>: "warning" | "critical"} with cpu, memory, swap, load, disk:<mount>, inode:<mount>, temp:<sensor>). The desktop colours its live section from it, since only the checker knows the free-GB gate, the thresholds per mount and the hysteresis; details without problems it computes from the configuration as before. ServiceProcessChecker checks services – mode auto (failed + the enabled-but-inactive systemd units the agent reports, with an ignore list of glob patterns; after the ignore list a failed service, i.e. .service or a name without a unit suffix from _UNIT_TYPES such as a Windows service, is critical, any other failed unit such as .mount, .timer or .socket and any enabled-but-inactive unit warning; the message separates Failed: …; Failed units: …; Inactive (autostart): …, _details.failed still lists all; the desktop's services line colours with a copy of the suffixes, UNIT_TYPES in apps/desktop/ui/src/components/monitoring/section/SecServices.svelte, which apps/monitoring/tests/test_unit_types_ui_sync.py keeps equal) or list (explicitly named services, evaluated server-side from the inventory and the last state; details under push payload). The resources checker applies per-metric hysteresis (hysteresis_pp, release = entry − 10 pp; not for the load, which is no percentage and arrives already averaged as load_5m); push timestamps are persisted by the push handler (routers/agent.py) in monitor_agent_liveness and hydrated by the lifespan at startup; the checker additionally keeps a process-local monotonic stamp. A wall-clock divergence of > 60 s means the monitoring host's clock jumped: the checker grades on the monotonic (true) age and re-anchors the stored wall stamp — deliberately a correction, not an unknown bail-out, which would declare a dead agent fresh and drop agent_ping out of the host-down inhibition (that matches critical). A hydrated server without a monotonic stamp keeps plain wall-clock behavior; the persisted row is only rewritten on the next push, so a restart right after a jump falls back to the old behavior for up to one push interval – no false-alert storm after a monitoring restart.
system.pysystem_stateSystemStateChecker rates the system_state block (push, evaluate(config, report, prev_details); run() returns unknown “Waiting for agent data”). reboot_required and time_synchronized count only as a JSON bool, security_updates and oom_kills only as an integer (agent_number); anything else counts as missing. A problem is reboot_required true, time_synchronized false at uptime_seconds ≥ 900 or without an uptime (_TIME_SYNC_GRACE_SECONDS: the NTP client needs a while after boot), security_updates > 0 and oom_kills > 0; check_reboot, check_time_sync, check_security_updates and check_oom (SystemStateConfig, each a StrictBool, default true) switch a point off only with a real false. With a problem warning, the messages joined with ; (Reboot required, Clock not synchronized, 3 security updates pending, 2 OOM kills since last report), otherwise ok “System state OK”; never critical. If the block is missing, is no object or carries not a single usable field, the check is ok with “Not evaluated: no system state in report”. _details is always {reboot_required, time_synchronized, security_updates, oom_kills, problems} with null for not determined and problems ⊆ reboot, time_sync, security_updates, oom, without a block too: the push path otherwise keeps the stored details, and the desktop would show old values. The check has no measured values (see VictoriaMetrics). Since oom_kills is in one report only, an OOM kill only notifies with consecutive_fails 1, as in the template.
forecast.pydisk_forecastPull checker: query_range over monitor_agent_disk_percent_value{server_id="…"} (window window_hours, step 10 m), least-squares slope per mount → hours_left = (100 − last) / rate. Rates ≤ 0.01 pp/h count as stable (ok); too little history → unknown. server_id is escaped with escape_label_value().
smart.pysmart_healthEvaluates SMART data from the push (ATA HDD/SSD and NVMe). Checks reallocated/pending sectors, NVMe critical_warning bits and temperatures against type-specific thresholds, among others. A missing smart key is ok, not an error: with smart_absent the message names the reason (No SMART data: …) and _details is {"absent": <reason>}; without it (an older agent or an unknown reason) the message stays “No SMART data (VM or smartctl not available)” without details. At most the first 500 disks of a report are rated; an entry that is not an object is skipped, and a smart that is not a list counts as empty, like a missing key. The number fields of a disk (every int field of SmartDisk in apps/agent/internal/monitor/smart.go, e.g. temp_c, smartctl_status, reallocated_sectors, available_spare_pct, critical_warning) only count as a JSON number (no bool, representable as a finite float; a numeric string such as "16" does not count either), device, kind and model only as a string (message and _details show an empty device or model as ?). Anything else counts as missing, with the default for a missing field (device and model ?, kind from protocol, counters and temperature 0, available_spare_pct 100; _details then has available_spare_pct and percentage_used as null). Message, metrics and _details carry the values read. device and model go through cap_agent_text into the message and _details, cut to 500 characters (including the “…”) and on one line, and so does kind into _details; ignore_devices and the metric names read the full device, the temperature thresholds the full kind. protocol picks the checks by its raw value (only ATA and NVMe have checks of their own; without the field it is ATA); _details has it only as a string and capped the same way, otherwise ATA. smart_passed is in _details as a bool, as the rating reads it: false, null, 0, "", [] and {} are “SMART FAILED” (critical), any other value and a missing field count as passed.

The plugin checkers proxmox_backup, zfs_health and docker_health (in checkers/plugins.py) are likewise push-evaluated. All three rate at most the first 500 VMs (proxmox.vms), pools (zfs.pools) or containers (docker.containers) of a report; a value there that is not a list counts as empty, an entry that is not an object is skipped (it still counts toward the limit), and a proxmox, zfs or docker block that is not an object counts as missing. The number fields of an entry (vmid and last_backup_ts of a VM, capacity_percent of a pool, exit_code and restart_count of a container) only count as a JSON number (no bool, representable as a finite float), vmid, exit_code and restart_count only as a whole number in integer notation (a JSON 3.0 counts as missing); a VM's name and type and a pool's name and health only count as a string (an empty one counts as missing). Anything else counts as missing, with the default for a missing field (name ?, type vm, health UNKNOWN; capacity 0 %, health then still counts); an unreadable backup timestamp is “No backup” (critical). These texts go through cap_agent_text into the message and _details, cut to 500 characters (including the “…”) and on one line; the rating reads the full health, the metric name zfs_capacity_<name> the full pool name. For zfs_health, docker_health and proxmox_backup:

  • Block missing: unknown with _details {"pools": []}, {"containers": []} or {"vms": []} instead of None – otherwise the push path keeps the stored details of a result without any, and the desktop would go on showing the old list.
  • Outage (available: false or error set): warning with ZFS unavailable (<code>): <error_message>, Docker unavailable (…) or Proxmox unavailable (…), _details with available: false, error and an empty list. Only a JSON false is an outage; null, 0 or "false" let the pools, containers or VMs decide. The checker takes the code only from the agent's list (above; _ZFS_ERRORS, _DOCKER_ERRORS, _PROXMOX_ERRORS); any other value is still an outage, but without a code (ZFS unavailable, Docker unavailable or Proxmox unavailable, _details.error null). error_message goes into the message cut to 500 characters (including the “…”); a value that is not a string stays out. alert_on_unavailable (StrictBool in ZfsHealthConfig, DockerHealthConfig and ProxmoxBackupConfig, default true) turns that into unknown; the checker only switches off on a real false. Readable but without pools, containers or VMs/CTs is ok (Proxmox “No VMs/CTs found”); otherwise the details carry available: true and error: null.
  • docker_health gets the previous _details like agent_resources and service_process (every push checker takes evaluate(config, report, prev_details), PushChecker in checkers/__init__.py; agent_resources, service_process and docker_health read the previous value) for the restart counter per container ID; only an ID of type string has a previous value (the agent sends the 12-character short ID). Without name the container is named after that ID, or ? if it is not a string. name, state and the status text status only count as strings: any other name counts as missing, any other state as empty (unknown_state), any other status text yields neither an exit code nor unhealthy. name and state go into the message and into _details cut to 500 characters (including the trailing “…”), and so do image and id into _details; these only count as a string (an empty one counts as missing), otherwise _details has "" or null. ignore_containers compares against the full name, the rating reads the full state; the checker looks up the previous restart count under the capped ID, as _details stores it. _details.containers is [{id, name, image, state, category, reason, exit_code, restart_count}] with category ∈ {ok, warning, critical, stopped} and reason ∈ unhealthy, restarted, restarting, dead, paused, created, start_failed, oom, stopped, exit:<n>, unknown_state (null for ok); the rules are in the admin guide. The status is the worst category, stopped counts as ok. Without exit_code or health (an older agent) the checker reads the exit code and unhealthy from the docker ps status text; likewise for an exit_code that is not a whole number. An exit code of more than 10 digits in the status text is not read; the container then counts as without an exit code. A restart_count that is not a whole JSON number counts as missing, and the container then does not count as restarted. The messages are in English; the desktop translates from the codes.

Auth modes

Both modes are implemented in core/auth.py as FastAPI dependencies:

  • require_agent (agent push): reads header X-API-Key. If the value matches the internal key exactly, it counts as __internal__ (access to all servers). Otherwise the key is SHA-256-hashed via MonitorAgentKey.hash_key() and compared against the hashed_key column in monitor_agent_keys – on a hit the dependency returns the associated server_id. A clear-text key is never stored; only the hash lives in the DB.
  • require_internal (AdminHelper ↔ service): reads header X-Internal-Key and compares it against the internal key. Its source is the env var MONITOR_API_KEY; if absent, a random key is generated at startup and persisted to $DATA_DIR/.api_key (core/config.py).

Agent key: issuance & server binding

Agent keys are issued per server (routers/admin.py):

  • POST /agent-keys/{server_id} creates a raw key with secrets.token_urlsafe(48), stores only its SHA-256 hash, and returns the raw key once in the response. If a key already exists for the server, it is deleted first (rotation = DELETE + POST). server_id is unique in the table, so exactly one key per server.
  • Both endpoints (POST/DELETE /agent-keys/{server_id}) are themselves guarded by require_internal – only the AdminHelper server may manage keys.
  • The push handler (routers/agent.py) additionally checks that the server_id derived from the key matches the server_id in the path; otherwise 403. A valid key for server A therefore cannot submit metrics for server B (__internal__ excepted).

Templates, seeding & tag sync

MonitorTemplate bundles check and alert definitions as JSON with a stable def_id per definition. POST /templates/{id}/assign (body {server_id, hostname, server_name}) rolls out the template; template_sync.py reconciles changes so server assignments stay drift-free.

Built-in seeding (tombstone)

At startup the lifespan seeds six standard templates from builtin_templates.py (marked via builtin_slug). The tombstone in monitor_seed_state guarantees: each slug is seeded at most once – a user-deleted built-in is never restored by later startups; new built-ins of later releases seed only themselves. What a later startup does with an existing built-in is governed by its version (next section). The definitions pass the same schema boundary as user templates (test tests/test_seed.py).

Built-in versions

Every entry in BUILTIN_TEMPLATES carries "version"; a changed definition ships as a new version. The row keeps the version last rolled out in monitor_templates.builtin_version and the sha256 of the definitions rolled out with it in builtin_hash (both NULL on user templates; migration a7c9e1b3d5f7). definitions_hash() hashes the canonical JSON (sort_keys=True, separators=(",", ":")) of canonical_definitions(check_definitions, alert_definitions): both lists without the keys that hold their schema default from TemplateCheckDef or TemplateAlertDef. Reason: the editor stores every definition in full (model_dump), the shipped ones leave defaults out, and a new optional schema field must not change the hash of every install. The template's name and description do not count; a renamed built-in keeps following new versions.

After seeding and the baseline (record_override_baseline(), below), the lifespan calls reconcile_builtin_templates() (best effort like the seeding, before load_all_checks()). A row with builtin_slug but no hash (created before versions) gets version 1 and the frozen hash of version 1 from BUILTIN_V1_HASHES (a slug without an entry, that is one shipped only after the versions, the hash of the shipped definitions); if its definitions differ from those, it counts as edited from then on, otherwise it follows a newer version. The values in BUILTIN_V1_HASHES never change, not even with a new version. If the shipped version is higher and the hash of the current definitions equals builtin_hash, _roll_out() replaces the definitions (name and description stay), sets version and hash and calls sync_template(); customized check fields stay. Otherwise nothing changes. Every decision is taken under the row lock (with_for_update() with populate_existing(), effective on Postgres): a second startup or a concurrent "Apply" then sees the new version and does not sync twice. MonitorTemplate.to_dict() returns builtinVersion, builtinEdited (hash of the current definitions ≠ builtin_hash) and builtinUpdateAvailable (shipped version > builtin_version).

Customized template checks (overridden_fields)

monitor_checks.overridden_fields (text, NOT NULL, default '[]') holds, as a JSON list, the fields of a template check the user changed, by their snake_case column names and in a fixed order (TEMPLATE_CHECK_FIELDS): name, description, check_type, config, enabled, interval, severity, consecutive_fails, consecutive_oks. PUT /checks/{id} and POST /checks/{id}/toggle call mark_overrides(): every field sent is compared with the resolved template value (resolve_template_check(): the definition with the assignment's variables substituted, missing keys filled with the defaults of a new check, for consecutive_oks DEFAULT_CONSECUTIVE_OKS = 2 from schemas.py); different → added, equal → removed. When check_type is in the list, config always is too. Manual checks and checks whose assignment or definition is gone are left alone. On update, _sync_checks_for_server() writes only the fields not in the list; with config customized it does not write check_type either. A definition no longer in the template still deletes its check, customized or not. Alert rules have no counterpart: _sync_alerts_for_server() sets them to the template's values on every sync. MonitorCheck.to_dict() returns templateDefId and overriddenFields (list).

Baseline at the first start (record_override_baseline)

Existing checks start with []. record_override_baseline() marks once per install what was changed by hand before: for every check with a template_id it calls mark_overrides() with all of the check's current values, so every field that differs from the template counts as customized, with the type/config coupling. It resolves with the assignment's server_hostname/server_name, the names the check was built from; a server renamed since is no customization. Manual checks and checks whose assignment or definition is gone stay as they are. A check that cannot be compared (ValueError, TypeError or AttributeError from an unreadable config or definition) gets every field and a warning with its ID; database errors fail the run. The log line counts the marked and the not comparable checks. For consecutive_oks, added later, it does not run again in existing installs: nobody could change the field before the update, every check holds the column default 2.

The run is done with the reserved key baseline:overridden-fields (OVERRIDE_BASELINE_KEY) in monitor_seed_state, committed together with the marks; the colon keeps it out of the built-ins' slug namespace. Once the key is there, no run compares again. Migration a7c9e1b3d5f7 deletes it on upgrade when it adds overridden_fields: a downgrade drops the marks, and the next upgrade takes the baseline again.

No sync runs without the baseline. The lifespan takes it after the seed and before reconcile_builtin_templates(), best effort like the seed. Every path to a sync takes it before it changes anything the baseline compares with: reconcile_builtin_templates() and apply_builtin_update() before the row lock, the tag sync's name refresh before the new names, PUT /templates/{id} before the new definitions, restore_checks() before the tombstones go; sync_template() and sync_assignment() call it as well (only a lookup by then). If it fails there, that sync does not happen, the error goes to the caller as for any sync error, and the next start or sync tries again. Residual risk: a template change that was never synced to a check before the update shows there as customized.

Check tombstones

The table monitor_check_tombstones (template_id with an FK to monitor_templates and ON DELETE CASCADE, server_id with an index, def_id; unique per triple) records template checks a user deleted on one server. DELETE /checks/{id} creates the tombstone while the server has the template assigned (tombstone_check()); the sync creates no check for a triple marked this way. The tombstones go with the assignment (remove_template(), so assigning again creates everything again), with the server (cleanup_server(); no FK, the server lives in the server DB), with the template (cascade) and on restore. GET /templates/assignments/{server_id} returns removedChecks per assignment: the pair's tombstones whose def_id is still in the template (check_def_ids()).

Suggestions from the host facts

If host in the report is an object, the push handler passes it to store_host_facts() (app/template_suggestions.py) after the check for NUL bytes and lone surrogates and before evaluating the checks. It writes one row per server to monitor_host_facts (server_id as the key, os, platform, platform_version, virt_system, virt_role, subsystems as a JSON list, updated_at = last report; migration b9d1f3a5c7e9) and checks on the way: os only from linux, windows, darwin, otherwise NULL; the other strings are cut to 64 characters, "" and values of another type become NULL; subsystems keeps only docker, zfs and proxmox, in that order, and drops the rest. A wrong value costs only its own field. It commits on its own and only logs a failure (without a traceback): like the liveness, storing the facts never costs the report. If host is missing (an older agent) or not an object, stored facts stay as they are.

suggest_templates() derives the suggestions from them, the OS first: os linux → linux-base, windows → windows-base (darwin has no standard template), subsystem docker → docker-host, zfs → zfs-storage, proxmox → proxmox-host. A slug is suggested only if a template with that builtin_slug exists (so not a deleted built-in), it is not assigned to the server (whatever the source) and it was not dismissed there. A dismissal is a row in monitor_template_suggestion_dismissals (server_id with an index, builtin_slug, dismissed_at; unique per pair); there is no route to take one back yet. Neither table has an FK to the server; cleanup_server() deletes their rows too.

Tag sync (server ↔ monitoring)

Tags live in the server DB (Server.tags); monitoring only knows server_id strings. tag_sync.py pulls the inventory via GET /api/internal/servers on the AdminHelper server (service-to-service, X-Internal-Key) and materializes the server assignments for every MonitorTemplateTagAssignment with source='tag'. Triggers: every 15 minutes via the scheduler and immediately as a best-effort nudge – the AdminHelper server POSTs to /templates/tag-sync after server create/update(tags/name/hostname)/delete. When a server loses the tag, the tag assignment and its materialized checks are removed; source='manual' assignments are never removed by the sync. In addition, for every remaining assignment, manual and tag alike, it compares server_hostname/server_name with hostname/name from the inventory: if they differ, it writes the new values and syncs exactly this pair again (sync_assignment(); customized check fields stay, alert rules are set again), so {{hostname}}/{{server_name}} follow a rename. A server missing from the inventory stays unchanged; if the sync fails, it is rolled back and the old names stay. POST /templates/tag-sync responds with {"created": n, "removed": m, "refreshed": k}. An unreachable server API (None) is strictly distinguished from an empty inventory ([]) – an outage deletes no assignments.

Alert pipeline: sent-state, guards & suppression

The alerter is level-driven (docs/features/alert-sent-state.md): monitor_states.notified_status holds the status last actually reported; migration c1d3e5f7a9b1 backfills it with status so a deploy triggers no catch-up storm. Both call sites (execute_check, the agent push handler) decide via resolve_notification(notified_status, eff_status): skip (nothing new, or unknown), silent_ack (an ok without a reported problem – booked inline, no dispatch) or notify (BG dispatch). Order in process_alert() (applies to rule dispatch and the hub emit, since emit_to_hub sits behind the same guards):

  1. Claim phase: state load under FOR UPDATE (a short window with no I/O; serializes concurrent BG dispatches), current = state.status is re-read under the lock (the caller snapshot may be stale) → resolve_notification: skip/silent_ack as above.
  2. Active maintenance window of the server → collect-but-mute: status/metrics keep flowing, the notification is suppressed, no alert-log row, notified_status stays untouched → the first cycle after the window reports the discrepancy. is_in_maintenance() evaluates weekly windows in the configured IANA time zone (zoneinfo, DST-correct; including day wrap across midnight).
  3. Host-down inhibition (_host_is_down()): a check stays silent while an enabled signal check of its server stands at critical, by rank: the Host Ping (check_type ping with template_def_id HOST_PING_DEF_ID = host-ping, from the built-in “Host Ping”) never, agent_ping by a Host Ping, all others by an agent_ping or a Host Ping (ANY-semantics, one query). So heartbeat and Host Ping never silence each other when the host is gone, and a ping set up by hand inhibits nothing. notified_status stays untouched → catch-up once the signal is back at ok, also for a heartbeat behind the Host Ping, which the bundled alert reports only after its next evaluation, though (_awaits_check, below). Steps 2 and 3 are checked by muted_reason(db, check, now), which returns the reason ("maintenance window"/"host down") or None.
  4. Report (claim-then-dispatch): notified_status = current is committed BEFORE the channel I/O – the row lock never spans webhook/SMTP timeouts (the 5.3 isolation stays intact) and a later commit failure cannot re-fire an already-sent alert (at-most-once). Message/alert log/hub emit carry the last reported status as "old" (reported_old); the log rows land with the caller's commit. "Reported" means the claim persisted, independent of per-channel success (the rule cooldown may damp an escalation catch-up, the bell cooldown the hub emit).
  5. Bell (hub emit after the rule dispatch): hub_decision(hub_status, hub_sent_at, new_status, severity, now) on monitor_states.hub_status (what the bell last showed) and hub_sent_at (its last problem report). emit for the recovery of a shown problem (hub_status warning/critical), for the escalation of a shown warning to critical (capped) and for any other problem report once hub_sent_at lies at least HUB_COOLDOWN (30 min) back; otherwise, and for the capped level info, skip. What the bell drops is not caught up (the claim already stands). The decision is made in the claim phase under the same lock, and on emit the claim commit reserves the slot: hub_status = the new status, capped at the severity (_capped_status), and for a problem report hub_sent_at = now. A dispatch of the same check that starts during the hub POST thus reads the reservation, not the record from before. The POST itself (post_hub_event) runs after the rule dispatch. If it fails (HTTP ≥ 300, an exception, hub not configured), _release_hub_slot hands the slot back with the caller's commit through a conditional UPDATE (WHERE hub_status = reserved AND hub_sent_at IS NOT DISTINCT FROM reserved): a failed POST changes nothing as long as no newer dispatch reserved in between; that one's reservation stays. A dispatch that reads a reservation whose POST fails afterwards decides by it, so it may send an all-clear for an alert the hub did not accept. The recovery goes to the hub at the level hub_status, not at the severity valid by then. Migration 3c66308d11a7 backfills hub_status from notified_status (warning/critical only), so a problem reported before the update gets its recovery.

Bundled alert of the heartbeats (app/alert_bundle.py): execute_check does not hand a notify of an agent_ping to the alert pool; the discrepancy stays open in monitor_states. The sent-state is thus the buffer: no table of its own, no in-memory buffer, a restart loses nothing. The system job system:agent-alert-bundle (schedule_agent_alert_bundle(), every FLUSH_SECONDS = 30 s, max_instances=1 on the job) calls flush_agent_alerts() with a session of its own via database.SessionLocal. Candidates are enabled agent_ping checks for which resolve_notification says notify and that are _reportable, split into critical (silent) and ok (back): muted_reason does not mute them, and _awaits_check does not hold them back. It does so while the status may still date from a muting that is over: last_check (if empty, since) lies in a maintenance window of the server (is_in_maintenance at that time), or an enabled Host Ping of the server has a since after it (what it changed from is stored nowhere, so any change holds back for one evaluation). The next evaluation decides: still critical → reported, ok → never reported, so not held, recovered in silence (T19, branch review). A window deleted or disabled is not seen by the check. Per kind from BUNDLE_MIN (3) on: a claim as in process_alert (FOR UPDATE in check_id order, the decision and _reportable checked again at the time of the claim, notified_status committed before any channel I/O; if fewer than three are left, nothing is claimed), then send_bundle() per channel: per rule with three or more matches one message via send_to_rule (the first member as the check, payload with members) and an alert-log row per member; in the bell, per capped level with three or more, one event with source_ids (at most HUB_MAX_IDS = 500 per event; recipients per user, see the server docs); below that single messages each. hub_status/hub_sent_at are set only by an accepted POST, so the claim does not reserve the bell; that is why two jobs never run at once. Fewer than three wait until their since lies _alone_wait(interval) back and then go out one by one via dispatch_alert_bg: BUNDLE_WINDOW (5 min), but at most the check's interval minus 1 min, never below 0 (standard heartbeat 5m: 4 min, 1m: at once; an interval the scheduler does not know keeps BUNDLE_WINDOW). The window thus ends before the next check: had that one found the agent ok again, an outage never reported would recover in silence (holds_recovery holds only what was reported), and a heartbeat that was critical for one check would go unreported (Kevin 2026-10-20). The interval comes from scheduler.interval_timedelta().

Maintenance CRUD lives in routers/maintenance.py (/maintenance, require_internal; proxy prefix maintenance).

VictoriaMetrics

External container (see docker-compose.yml), retention -retentionPeriod=${VM_RETENTION:-90d} – independent of ALERT_LOG_RETENTION_DAYS (alert log in Postgres). The service writes in InfluxDB line protocol via core/victoria.py:

bash
monitor_agent_cpu_percent,server_id=srv123 value=45.2 1683000000

format_line writes an integer within the int64 range (−263 to 263−1) with the suffix i (value=5i), one outside it as a float (value=9.223372036854776e+18): VictoriaMetrics reads a value with i as int64 and answers an overflow with HTTP 400 for the whole write, its valid lines included; it stores float64 anyway. A number that is not finite as a float (inf, nan, an integer beyond the float range) is rejected by format_line; in the metrics of a check result (build_check_result_lines) it alone is dropped.

Callers do not write themselves: write appends the lines to an in-process buffer and returns without network I/O, so no check and no agent report waits on VictoriaMetrics. The buffer holds 100,000 lines and at most 64 MiB (counted as the memory the lines take up in the process, sys.getsizeof); a call that no longer fits is dropped as a whole, and a WARNING names the number of lines dropped since the last one: on a drop at most once a minute, and at the latest once the writer has emptied the buffer. A thread of its own (victoria-writer, started by the first write) sends the buffer to /write in batches of up to 10,000 lines per POST. It tries a timeout, a connection error and HTTP 5xx up to three times (pauses of 0.5 s and 1 s); after that the batch is lost. A 4xx answer (VictoriaMetrics rejects the content, such as a malformed line) is not retried: it logs the status, the line count and the first 200 characters of the answer (where VictoriaMetrics names the bad line), and the whole batch is lost. A batch carries the lines of every check and agent report that came in since the last POST, those of other servers included: if VictoriaMetrics rejects it over a single malformed line, up to 10,000 lines are lost, other servers' among them. The same holds for any other answer below 500 that is not 2xx, a redirect (3xx) included; the client does not follow it. This is an accepted residual risk; the WARNING line of monitor.victoria names the status and the number of lost lines. On shutdown the lifespan calls close() after stopping the scheduler, which flushes the buffer for at most 5 s; whatever is still buffered after that, or on a hard kill, is lost.

Reads use the standard Prometheus endpoints /api/v1/query and /api/v1/query_range. uPlot in the desktop client renders the charts. The UI chart queries are never raw: GET /checks/{id}/metrics builds the PromQL query server-side from a per-check-type metric allowlist (CHECK_TYPE_METRICS) and escapes label values – free-text queries from the UI never reach VictoriaMetrics (SSRF/injection guard).

build_check_result_lines writes a check result with the labels check_id, check_type, name and server_id: monitor_check_status (0 ok, 1 warning, 2 critical, 3 unknown; GET /checks/{id}/metrics reads the status timeline statusHistory from it), monitor_check_duration_ms and monitor_<key> per measured value. The push path (routers/agent.py) writes the status for every evaluated check, also when no measured values remain after _details (for example system_state and agent_resources always, Docker, ZFS and Proxmox without readable data or without a block, Proxmox without VMs, smart_health without SMART data); the duration (always 0 there) only comes with measured values. That is why system_state is in CHECK_TYPE_METRICS without metrics, and its endpoint returns only the timeline. agent_resources writes only its status: the push handler writes CPU, RAM, disks and temperatures per server without a check_id (monitor_agent_cpu_percent, monitor_agent_memory_percent, monitor_agent_disk_percent with mount, monitor_agent_temp with sensor), and GET /checks/{id}/metrics reads them for agent_resources with server_id="…",check_id="", every other check type (also an agent_resources without server_id) by its check_id, so two checks of one type on one server stay apart. An empty label value selects the series without that label (Prometheus semantics): CPU and RAM series with check labels written by older versions stay in VictoriaMetrics until the retention ends, but the endpoint no longer reads them.

Ingest validation

The push endpoint enforces that the API key really belongs to the supplied server_id. A compromised agent key cannot forge metrics for other servers.
