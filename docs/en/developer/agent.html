Go Agent

Unified Go agent under apps/agent/. Replaces the legacy shell + Python agents and merges monitoring, FRP-client setup, and service installer into a single binary that runs on Linux (systemd), Windows (service manager) and FreeBSD (cron and rc.d).

Cobra Subcommands

Seven top-level commands, three of them with sub-subcommands:

CommandPurpose
versionEmit version + git commit (set via -ldflags).
runStandalone mode: run one full cycle (monitor push + FRP sync).
provisionInitial setup: redeem token against /api/servers/{id}/provision/activate, install server API key + optional monitor key + optional FRP bundle in a single call.
frpc syncPeriodic config sync via hash compare; only writes when the server-side hash changed or frpc does not run despite a tunnel (flow under FRP sync).
monitor initCreate the monitor config (URL, API key, services list).
monitor pushOne metric collection + push run.
monitor credential set / delete / listStore a credential for probes on this host (from stdin, without echo on a terminal), delete it or list the names (see Probes).
service install / uninstallInstall/remove the systemd unit (Linux) or Windows service (SCM).
diagnosticsWrite a redacted diagnostics report for a bug report (version, host, config with masked secrets, log tail).

Configuration

Two config files in key=value format (quotes allowed). OS paths:

  • Linux: /etc/frp/adminhelper.conf and /etc/adminhelper/monitor.conf
  • Windows: under %ProgramData%\AdminHelper\
  • FreeBSD: /usr/local/etc/adminhelper/frp/adminhelper.conf and /usr/local/etc/adminhelper/monitor.conf (log under /var/log/adminhelper); modes and protection as on Linux (securedir_unix.go)

The agent creates the secret-bearing directories protected before their first use, so that the API key and mTLS private key are not readable by other local users: config.EnsureSecureDir secures a directory, config.EnsureDataDir one of the agent's data. On Linux this is 0700 as before, also for an existing directory; EnsureDataDir is EnsureSecureDir there. On Windows, where mode bits have no effect, EnsureDataDir first secures the data root %ProgramData%\AdminHelper and then the directory below it (frp, logs, identity). A new directory is created there in one step with a fixed security descriptor: owner Administrators, full control for SYSTEM and the Administrators only, inherited by everything below, nothing inherited from %ProgramData%.

On Windows the agent handles an existing directory only through handles that are opened relative to the parent directory and follow no reparse point; for this it enables SeTakeOwnershipPrivilege, SeBackupPrivilege and SeRestorePrivilege, which LocalSystem holds, in the thread token. If the directory belongs to SYSTEM or the Administrators and is not a reparse point, it keeps the directory with its contents and sets the protected ACL again; kept entries then only inherit the directory's ACL. It replaces foreign content: a directory with another owner is removed with its contents, a reparse point only as the link, its target stays untouched; then it creates the directory anew. In a kept directory it removes reparse points (again only the link), files with more than one name and entries that belong neither to SYSTEM nor to the Administrators. If the directory was already closed before the run (owner SYSTEM or Administrators, rights to write and create only for them, in the inheritable form the agent sets), it takes over an entry with another owner instead, with its contents, owned by the Administrators afterwards; this keeps what an earlier provisioning left there. If a step fails, EnsureSecureDir returns the error instead of discarding it; only an entry that disappears while cleaning counts as removed. provision secures the data root first, before it redeems the one-time token, also without monitoring and on Linux as well (/etc/adminhelper); if it cannot be secured, provision stops with the directory in the error, and the token stays valid. If frp cannot be secured, provision stops after redeeming the token; if the data root cannot be secured, monitor init stops as well. If identity cannot be secured, provision skips the enrollment and goes on with the API key, and a due certificate renewal in the service run is skipped with a warning. The FRP sync (run, frpc sync) changes files in frp only after it has secured the directory with EnsureDataDir in the same run, for writing as for deleting (on Windows the data root first, on Linux 0700 for /etc/frp); if it cannot be secured, the sync stops with the directory in the error and writes, deletes, starts and stops nothing. A run without a change secures nothing.

Files the agent creates in these directories belong to the Administrators on Windows, also when a signed-in administrator runs the agent: config.WriteFile calls config.OwnByAdministrators after writing, the identity files go through OwnByAdministrators directly, and the lock files of the identity and of frpc are created with this owner. If that fails, the write ends with an error. On Linux OwnByAdministrators has no effect. logging.Init secures the log directory through config.EnsureLogDir before it opens the log file; if it cannot be secured, the agent logs to stdout only. When it runs as a Windows service (svc.IsWindowsService), whose stdout no one sees, logging.Init reports this once as a warning in the event log (Application, source logging.EventSource, that is AdminHelper-Agent, event ID 1) with the directory, the reason and the consequences; if that fails as well, stdout is all there is. An interactive run, for example without administrator rights, stays without a notice. On Linux the logger creates the directory itself, as before.

FrpcConfig fields: ADMINHELPER_URL, API_KEY, SERVER_ID, CACERT, INSECURE. MonitorConfig additionally carries MONITOR_URL and SERVICES (comma-separated). The agent reads INSECURE only from configurations of earlier versions; provision and monitor init do not write it.

FRP sync

On every run (run or frpc sync) the agent fetches config-hash and compares it with /etc/frp/.config-hash. Only on a mismatch, or when frpc does not run although frpc.toml is in place, does it fetch the server's frpc.toml, which must match the advertised hash. It stores the hash of the server's text, and only once frpc has taken the config; a failed step is retried on the next run. Provisioning (frpc.Apply) takes the same path with the text from the bundle. After an agent update the first run fetches the text once, even with the same hash, and runs it through the new version's check: if it passes, frpc is left alone (no reload, no restart), otherwise the row “Server text fails the check” applies. /etc/frp/.checked-by holds the agent version that last checked the stored text, with that text's hash; without the file (every agent before it), or naming another version or hash, the text counts as unchecked. Without a stored hash, and for a text without [[proxies]], there is nothing to check again.

Situation (Linux)Flow
{"hash": null} (no FRP config)Stop and disable frpc, delete frpc.toml and the hash.
Server text without [[proxies]]Stop and disable frpc, delete frpc.toml, store the hash.
Server text fails the check (sync and provisioning)Error naming line and key, never a value; stop and disable frpc, delete frpc.toml and the hash, so frpc does not keep running on the old file. The next run fetches and checks again; with nothing left, systemctl is not touched.
frpc not runningWrite, systemctl enable --now frpc.service.
frpc running, common part as at its startWrite, reload over the local admin API (/usr/bin/frpc reload -c /etc/frp/frpc.toml, 15 s timeout). If the agent's own frpc does not listen there or the reload fails, restart.
frpc running, common part changed (frps address, token, user, TLS)Write, systemctl restart frpc.service.
frpc.toml in place, but frpc not running (same or new hash)Fetch the config; with [[proxies]] renew the admin API (new port, new password), write, start frpc. Without [[proxies]] stop as above, the admin API stays.

Every systemctl call of the sync has a cap of 15 s and ends when the run ends (signal or service stop in continuous mode). If systemctl is-active does not answer (cap, end of the run, systemctl does not start), frpc does not count as stopped. If the server's config is unchanged or nothing listens on the admin port, the sync stops without writing, starting frpc or storing the hash. If the server changed the config and frpc listens on its admin port, the sync writes frpc.toml and loads it over the admin API, provided the common part is the one frpc started on and the socket belongs to the agent's own frpc (“Reload instead of restart” below); then it stores the hash. If the common part differs or the reload fails, the new frpc.toml is already in place, the hash stays the old one, and the sync ends with an error. Provisioning never reloads and warns as after a failed start. The next run tries again. An exit status other than 0 still means that frpc does not run.

Stop without systemd: when the sync is to stop frpc (the first three table rows) and systemctl fails, the agent drops the tunnels anyway: it writes frpc.toml as the common part without [[proxies]] and loads it over the local admin API, only into its own frpc (“Reload instead of restart” below). frpc then keeps running without tunnels. The sync still ends with the systemctl error, the hash stays the old one, and the next run stops frpc over systemd again and reloads the file without tunnels once more.

Lock: when the sync or provisioning changes frpc's files or service (frpc.toml, the hashes, admin.conf, adminhelper.conf, starting and stopping frpc.service), it holds the lock /etc/frp/frpc.lock (Windows %ProgramData%\AdminHelper\frp\frpc.lock), from securing the directory to after its last step. A second call waits at most 60 s, a run also only until it ends (signal or service stop in continuous mode); then it stops with an error that names the lock file and changes nothing. Provisioning then ends with this error after redeeming the token, as on a write error; a run catches up on the sync next time. A run without a change locks nothing. The lock file is created only in the directory the same call secured before, and stays behind empty.

Reload instead of restart: the common part is the text before the first [[proxies]]. frp takes it only at start; a reload swaps only the proxies, and unchanged tunnels and their connections stay up. The agent compares with the common part frpc last started on (its hash in /etc/frp/.started-hash). Before every start it deletes that record and writes it again only on success, so after a failed start the next run restarts instead of reloading. If the run has already ended (signal, service stop), it starts nothing and leaves the record in place. The agent sends the reload only to its own frpc: /proc/net/tcp must show a socket of root listening on 127.0.0.1 at the admin port (frpc.service runs as root) and none of another user, otherwise it restarts frpc. Provisioning always restarts a running frpc: it may have set up a new identity, and a reload does not connect to frps anew, only a restart does.

Local admin API: the agent puts a local head in front of the server's text: loginFailExit = false (frpc keeps trying while frps is unreachable), then webServer.addr = "127.0.0.1", webServer.port, webServer.user = "adminhelper" and webServer.password. The API listens on 127.0.0.1 only and never without a password: without one, every local process would get the frps token through GET /api/config. Port and password (32 random bytes, hex) live in /etc/frp/admin.conf with 0600, protected like frpc.toml: the agent runs as a oneshot, and a reload has to reach the frpc that started with these values. An admin.conf that is not as the agent writes it gets new values. The kernel assigns the port (127.0.0.1:0). If another process holds it after a reboot, frpc does not start; the next run then picks a new port and a new password (last table row). The server does not set the local head. The agent takes a server text only in the form generate_frpc_toml writes: every line is blank, one of the table heads [transport.tls] (at most once, before the first proxy) and [[proxies]], or key = value with a bare or dotted key without quotes (at most 32 segments; at most 4096 key paths per table and 131072 in the whole text, counting every table a dotted key opens) and a value on one line (a string without " and \, a list of such strings, a number, true or false). The root holds only the generator's keys: serverAddr, serverPort, user, auth.method (only "token"), auth.token, and under transport.tls all four keys with the generator's values: enable = true, and trustedCaFile, certFile and keyFile set to /etc/adminhelper/identity/ca.crt, agent.crt and agent.key (if one is missing, the agent refuses the text), so no key of the local head either; a proxy may carry further keys (a tunnel's extra_config), but none whose first segment is plugin, in upper or lower case (such as plugin.type or Plugin.localPath): the server sets up no proxy plugins. No key stands twice in a table, in upper or lower case, and the text holds no {{ and no control character but the line break. The agent refuses any other text with an error that names line and key (the key cut after 64 bytes), never the value; what follows is the row “Server text fails the check” above: frpc stops, and the next run checks again. To a text that passes, the agent adds serverName = "frps.adminhelper.invalid" under transport.tls: right after [transport.tls] or, if the text sets its TLS keys in the root, as a first line transport.tls.serverName. Only the frps certificate carries the name (FRP tunnel, tunnel PKI). The agent sets it itself instead of taking it from the server: an older agent refuses the unknown key and stops frpc, and the agent is never newer than the server, whose ca-issuer mints the name. The stored hash stays the one of the server's text. After an agent update the first run checks the text again even with the same hash; if the frpc.toml in place differs from the one this agent writes (such as without the name), it writes it anew and restarts frpc, since the name is in the common part.

On Windows the agent manages no frpc service: start, stop and reload are no-ops there.

FreeBSD: frpc runs as the rc.d service adminhelper_frpc under daemon(8) (apps/agent/freebsd/adminhelper_frpc, frpc at /usr/local/libexec/adminhelper/frpc, outside the search path, so the package does not clash with the frpc of the net/frp port). Instead of systemctl the sync calls /usr/sbin/service adminhelper_frpc with the same 15 s cap (internal/frpc/platform_freebsd.go): enabling is enable (sets the rcvar for boot) and onestart, restart is onerestart, stop is faststop and disable. The one forms because rc.subr skips a start or restart while the rcvar is off and still returns 0. frpc runs when status returns 0 and daemon(8)'s child pidfile (/var/run/adminhelper_frpc.child.pid) holds a PID; it is empty while daemon waits to start frpc again. Only the agent's own frpc gets the reload: according to sockstat -4 -l -q -n -P tcp -p <port> a socket of uid 0 with the PID from that file must listen on 127.0.0.1 at the admin port, and no other process on that port, not on * either; the PID decides, not the process name, which whoever starts the file chooses. The stop without a service manager and the lock apply as above; the files live under /usr/local/etc/adminhelper/frp instead of /etc/frp.

Monitor Collector

Central collection in internal/monitor/collector.go. Every collector returns map[string]any, which is JSON-serialised on push:

  • collectCPUSince(prev, now) – cpu_percent as the share of busy CPU time since the last report sent successfully, on all platforms. The agent reads cpu.Times(false) and computes as gopsutil does internally for cpu.Percent (getAllBusy/calculateBusy, not exported, hence rebuilt in cpuBusyTimes/cpuPercentSince): the total without Guest/GuestNice on Linux, busy = total − Idle − Iowait, the ratio of the two increases limited to 0–100. The previous sample (cpu: unix, total, busy) comes from the report state (below). Without a usable one, collectCPU() takes the 1-second sample as before (cpu.Percent): in the first run, with a missing or corrupt state, with a sample older than 15 min (cpuStateMaxAge) or from the future, with a total that did not grow (host rebooted) and when cpu.Times fails. BuildReport (the test push of monitor init) always takes the sample.
  • collectMemory() – memory_percent, memory_total_mb, memory_used_mb
  • collectLoad() – load_1m, load_5m, load_15m
  • collectSwapAndCPUCount() – Linux and FreeBSD, like the load the monitoring service puts into proportion with it: cpu_count (logical CPUs, cpu.Counts(true); a 0 counts as failed and is left out), swap_total_mb, swap_used_mb and, only with a swap device (Total > 0), swap_percent (mem.SwapMemory()). A failed call drops only its own fields.
  • collectNetwork() – Linux, Windows and FreeBSD: net_rx_bytes_total and net_tx_bytes_total, the byte counters since boot (net.IOCounters(true)), summed over the counted interfaces. On Linux every interface with /sys/class/net/<name>/device counts (physical or virtio), and if there is none (container, veth), every one except loopback; on Windows and FreeBSD every one except loopback. A Proxmox host so counts eno1 but not again vmbr0 and the guests' tap devices. A failed read drops both fields (a partial sum would read as a traffic drop). The fields are additive; the report version stays.
  • collectDisks() – per mountpoint mount, fstype, percent, total_gb, used_gb and free_gb (gopsutil Free, the space left to non-root users, Bavail; it can be less than total minus used; all platforms), plus inodes_percent on Linux only and only when the filesystem reports inodes (InodesTotal > 0; btrfs and vfat do not). The pure function diskInfo does the mapping.
  • collectUptime()
  • collectTemperatures() – lm-sensors / Windows WMI / FreeBSD sysctls
  • collectServiceHealth(ctx) + collectWatchedServices(ctx, names)
  • collectDocker(ctx) – via the docker CLI: docker info, docker ps -a --format '{{json .}}' (of it only ID, Names, Image, State, Status) and one batched docker inspect --type container <ids> with the standard JSON output, decoded into a struct (Id, RestartCount, State.Status, State.ExitCode, State.OOMKilled, State.Health.Status, HostConfig.RestartPolicy.Name, Config.Labels, NetworkSettings.Ports, State.StartedAt; every other field is ignored). A Go template on .State.Health.Status fails for containers without a health check, hence JSON. Per container the report carries id, name, image, state (from inspect), status (text from ps), restart_policy, exit_code, oom_killed, restart_count and health (empty without a health check); a container that vanishes between ps and inspect drops out. Without a docker binary the block is missing (silently). Otherwise it is always sent, on failure as {"available": false, "error": …, "error_message": …, "containers": []} with error ∈ daemon_unreachable (docker info fails), timeout, cli_failed, parse_failed (no readable line from ps, or unreadable inspect output). error_message names the call and the exit status, never stderr or paths; every abort is also logged as a warning. putDockerDetails sets the details for the desktop client, each only when inspect has it: compose_project and compose_service from the labels com.docker.compose.project and com.docker.compose.service (composeLabel: only up to 255 characters without control characters, otherwise left out, since a cut name would group the container under another project), ports (publishedPorts: only ports with a host binding, as host_ip:host_port->port/protocol like the docker CLI, sorted, at most 64) and started_at (epoch seconds; the zero time of a container that never started is left out)
  • collectZFS(ctx) – zpool list -H -o name,size,alloc,free,cap,health,frag (frag as fragmentation_percent, - → no field), plus zpool status -x (as errors) when a pool is not ONLINE. Without a zpool binary the block is missing (silently). If zpool list fails or hangs, the block is {"available": false, "error": …, "error_message": …, "pools": []} with error ∈ cli_failed, timeout; otherwise available: true, error: null and the pools, an empty list without pools. The parser skips lines with too few columns. Plus one zpool status -j --json-int --json-flat-vdevs (zpoolDetails, parseZpoolStatus; OpenZFS 2.3 and newer): per pool scrub (state SCANNING, PAUSED – a paused scrub shows in the output as SCANNING with scrub_pause –, FINISHED or CANCELED, errors, end once it no longer runs) and vdev_errors (the vdevs with a read, write or checksum error, at most 32). Without -v, so never the names of damaged files. A zpool without -j, a call that fails or hangs, or output it cannot read gives no details and no error
  • collectProxmox(ctx) – pvesh get (node status, VMs/CTs, backups per storage; PVE hosts only). The agent builds the backup index (the newest ctime per VM) from the node's backup storages (/cluster/resources --type storage, the storages of this node with content backup; pvestatd's cache, which activates no storage) and their content (/nodes/<node>/storage/<storage>/content --content backup). It reads the content at most every 30 min (proxmoxBackupsEvery); in between the index from the report state holds (backupIndexCheck, saved after a successful push, with the details: newest, jobs, error_task, errors), read again at once for another node or other backup storages. Without a pvesh binary the block is missing (silently). Otherwise it is always sent: when read, with available: true, error: null, node (name, cpu, memory_percent) and vms, an empty list without VMs, never null; on an outage (proxmoxUnavailable) as {"available": false, "error": …, "error_message": …, "node": null, "vms": []}. An outage is any failure at the local hostname, the node status (/nodes/<node>/status), the storage list (/cluster/resources --type storage), the content of a storage and the VM list (/cluster/resources --type vm), with error ∈ timeout (a pvesh call ran into the timeout), cli_failed (exit status, pvesh does not start, hostname unreadable), parse_failed (no JSON answer of the expected form, null included), backup_index_incomplete (the status of a backup storage is not available; /cluster/resources does not list a disabled storage, and the agent skips it). An incomplete index would report every VM with backups on the missing storage as having none, and a VM list that was not read would look like no VMs: hence an outage instead of a list. error_message names the call and its exit status, or backup storage <id> not active, never stderr; the same text goes to the log as a warning with the code (such as pvesh get /cluster/resources timed out after 15s, proxmox reported as unavailable (timeout)). With the index the agent reads the details for the desktop client, read-only: per guest storage, size and verification of the newest backup (backupDetailOf; the size 1 PBS reports for an unknown size counts as unknown; the verification only in the form [a-z][a-z0-9_-]{0,31}), the enabled vzdump jobs (readBackupJobs, /cluster/backup, at most 64; kept are only ID, schedule, storage and what selects the guests, never mail addresses, comments or note templates) and the last failed vzdump task of the node (readBackupErrors: /nodes/<node>/tasks --typefilter vzdump --statusfilter error --limit 1, then its log with --limit 10000; the log of a task already read is not read again). From the log only the line ERROR: Backup of VM <id> failed - <text> counts, the text cut to 200 characters, control characters as spaces (capBackupError). putBackupDetails sets backup_storage, backup_size, backup_verify, backup_jobs (the jobs that cover the guest, by vzdump's rule in backupJob.covers: pool before VMID list before “all” minus the exclusions, a job bound to a node only for its guests; [] when the jobs were read and none covers it) and backup_error with backup_error_ts (the task's start), the latter only while the guest has no newer backup. If one of these calls fails, only its details are missing; it is no outage of the block
  • collectSystemState(ctx, st) (internal/monitor/system_linux.go, updates_linux.go; FreeBSD system_freebsd.go, pkgaudit.go; otherwise system_other.go without a block) – the system_state block. Each field comes only when the agent could determine it; without a single one the block is missing. Why a field is missing goes to the log as a warning, short and without stderr (commandFailure); a host without a tool for a point (neither apt-get nor needs-restarting, or dnf) misses the field without a warning. Every tool runs as root with fixed arguments; nothing from the report or the server goes into a call.
    • reboot_required: with apt-get on the search path (Debian family), /var/run/reboot-required decides (present → true, missing → false, not checkable → no field); otherwise, with needs-restarting on the search path (RPM family), needs-restarting -r: exit 0 → false, exit 1 → true, any other outcome (other exit, timeout, does not start) → no field. With true, reboot_packages names the packages behind it: Debian from /var/run/reboot-required.pkgs (debianRebootPackages; without the file no names and no error), RPM from the * <name> lines of needs-restarting -r (parseNeedsRestarting).
    • time_synchronized: timedatectl show, the line NTPSynchronized=yes|no. Without -p, which timedatectl(1) describes for show-timesync only; the line is searched for. If the program is missing, the call fails, the line is missing or carries another value: no field.
    • security_updates: with apt-get on the search path, apt-get -s dist-upgrade with LC_ALL=C; it counts the Inst lines whose origin in the parenthesis after the new version contains security, case-insensitively (Debian Debian-Security:12/stable-security, Ubuntu Ubuntu:24.04/noble-security). Otherwise, with dnf on the search path, dnf -C -q updateinfo list --security; it counts the distinct package names (third column, without version, release and architecture), and a line of another form makes the output unreadable. No network (-s or -C; the agent does not refresh the package lists), timeout updatesTimeout 30 s. At most once an hour (updatesCheckEvery): the result is kept with its time in the report state (updates), and within the hour the agent sends it without a call. A failed attempt counts as the attempt (security: null), so the field stays out until the next count; a time in the future (clock set back) counts as due. Neither the form of the origin after Inst nor the output of dnf updateinfo is documented; both parsers are tested against fixtures, the RPM path not on a real host (not verified). The same count names the packages as security_packages.
    • oom_kills: the increase of the oom_kill counter in /proc/vmstat against the counter in the report state (oom_kill), i.e. since the last report sent successfully. The first run (no previous counter) has no field, only the counter for the next one; a counter smaller than the saved one (host rebooted) counts in full. If the agent cannot read the counter, the saved one stays. proc_vmstat(5) describes the name value lines but does not list the counter (Linux 4.13 and later by the kernel source); without the line there is no field. In a container, /proc/vmstat counts the kills of the whole host; there the agent reads oom_kill from /sys/fs/cgroup/memory.events instead (memoryEventsPath, the same name value lines), under cgroup v2 the counter of its own cgroup including sub-cgroups (checked in Docker, also with a kill in a sub-cgroup; not verified in an LXC on Proxmox VE). A container means: hostFactsCalls.virtualization, the same call as in collectHostFacts(), reports the role guest and a system from containerSystems (lxc, docker, openvz, rkt: the container systems of gopsutil v4.26.5, internal/common/common_linux.go; gopsutil does not detect Podman; plus jail on FreeBSD, hostfacts.go); a failed detection counts as no container. gopsutil keeps the detection per process, so the second question in the same report reads no file. If memory.events is missing in a container (cgroup v1) or unreadable, the field is missing with a warning, without falling back to /proc/vmstat. The report state keeps the source (oom_kill_source); a run that reads another source than the saved one sends no field, only the new counter for the next run. After a kill (source /proc/vmstat, not in a container: the kernel log there is the host's), oom_processes names the ended processes as {pid, name} (oomProcesses): journalctl --no-pager --quiet --dmesg --output=cat --priority=3 --since=-<n>s, the window since the CPU sample of the last successful push, at most one hour (oomWindow); only the kernel line Killed process <pid> (<comm>) total-vm: is read (parseOOMProcesses, the newest ten). The form of that line is no documented interface. Without journalctl, or when it fails, the names are missing with a warning in the log; oom_kills stays.
    • FreeBSD (freebsdSystemState): no time_synchronized and no oom_kills (FreeBSD counts no OOM kills the way /proc/vmstat does). /bin/freebsd-version runs once, on the host with -kru, in a jail (security.jail.jailed) with -u only, since the kernel is the host's. Outside a jail reboot_required compares the installed kernel (-k) with the running one (-r); in a jail the field is missing. security_updates counts hourly as on Linux (the same report state updates, updatesTimeout 30 s) the vulnerable installed packages with /usr/local/sbin/pkg audit -q, on a RELEASE plus the base system's names as periodic does in 405.pkg-base-audit: FreeBSD-<userland> and, outside a jail, FreeBSD-kernel-<kernel> (freebsdBaseNames); STABLE, CURRENT, BETA and RC have no entries in the VuXML and count the packages only. pkg audit reads the local vuln.xml that periodic's daily security run fetches; the agent never fetches it (no -F). Without pkg the field is missing without a warning. security_packages names the affected packages and base system names.
  • collectSmart(ctx) – smartctl --scan --json=c, then smartctl --all --json=c -d <type> per device in parallel, with the type from the scan (such as megaraid,N for a disk behind a MegaRAID controller on /dev/bus/N, which smartctl cannot detect without -d); no -d for scsi: the scan reports every disk on /dev/sdX without a USB bridge as scsi, a SATA disk too, and -d scsi switches off the SAT detection, so the disk would come without its ATA attributes. ATA and NVMe paths parsed separately. The device field is the device name from the scan; for a scan type megaraid,… or sssraid,… it is the scan's info_name (smartDiskID, such as /dev/bus/0 [megaraid_disk_00]): all disks behind the controller share the device name, and the monitoring service builds the metric names from device and matches it against ignore_devices. Not the query's info_name: smartctl appends [SAT] to it on open when it finds a SATA disk behind the controller. A query that ends with exit bit 0 or 1 (smartctl(8), EXIT STATUS: command line did not parse, device open failed) drops the device from the list: its JSON has no smart_status and would look like a failed SMART check. With bits 2 to 7 it stays, and smartctl_status carries the full exit code. Without a single readable disk it returns the reason instead of the list, and BuildReport sets smart_absent: {"reason": …} instead of smart: not_installed (no smartctl), scan_failed (the scan fails, hangs or prints no JSON, or no device it found gives readable data; a query with exit bit 0 or 1 does not count as readable), no_devices (the scan finds none)
  • collectHostFacts() (internal/monitor/hostfacts.go) – os from runtime.GOOS, platform and platform_version from gopsutil host.PlatformInformation() (the product name on Windows), virtualization (system, role) from host.Virtualization(), where "not implemented" (Windows) counts as empty; on FreeBSD, where gopsutil cannot, from the sysctls security.jail.jailed and kern.vm_guest without starting a process (virt_freebsd.go, freebsdVirtualization): a jail is jail/guest and wins over the VM it may run in, otherwise the hypervisor from kern.vm_guest unless it is none, and subsystems: docker, zfs, proxmox in a fixed order, depending on whether docker, zpool or pvesh is on the search path (exec.LookPath, independent of the plugin collectors), an empty list when none is found. Deliberately two calls instead of host.Info(), which fails as a whole on any part it cannot read: a failed call costs only its own fields and a warning in the log, never the block. The monitoring service suggests standard templates from it

CPU, RAM, swap, CPU count, load, disks and temperatures are shipped under the resources JSON key, the system state under system_state, the services under systemd, the plugins under docker, proxmox, zfs and smart or smart_absent, the host facts under host, the probe results under probes, the names of the stored credentials under credentials, the discovery inventory under discovery, the self-measurement under self.collectors and the load gate under self.load_shed (see Probes); everything goes to the monitoring service with report_version 4 via POST /agent/{server_id}/report (format see Monitoring Stack).

Push Behaviour

  • Retry: When the metrics push fails, PushReport (internal/monitor/report.go) does exactly one retry after 10 s – a lost push otherwise wastes a full 5-minute slot.
  • Inventory throttling: The all_services inventory (100–300 mostly static units) is only sent when its SHA-256 hash changes or the last full send is >1 h ago; otherwise the key is omitted from the report. The throttle state lives in .inventory-state.json next to monitor.conf (Linux /etc/adminhelper/, Windows %ProgramData%\AdminHelper\) and is only persisted after a successful push. The hash covers unit, active_state, enabled_state and alias_of of every entry, so any state change of a service forces a full send; the list mode of service_process relies on that. Watched services plus failed, enabled_inactive, counts and, if set, error go with every push.
  • Report state: What the next report is measured against lives in .report-state.json next to .inventory-state.json (0600, internal/monitor/reportstate.go, path config.MonitorReportStateFile()): {"cpu": {"unix", "total", "busy", "iowait"}, "oom_kill": n, "oom_kill_source": "vmstat" | "cgroup", "updates": {"checked_unix", "security": n | null, "packages"}} (packages the names of the count; a state of an older agent has them only after the next one), oom_kill and oom_kill_source on Linux only, updates on Linux and FreeBSD; a state without oom_kill_source (written before it existed) counts as vmstat. Push loads it before collecting (if it is missing or corrupt, the empty state applies: CPU sample, no oom_kills, a new update count) and writes the new one only after a successful push; a write failure is only logged, the push still counts. A lost push thus widens the next CPU window (if the previous sample is more than 15 min old, the agent takes the sample), and its OOM kills count in the next report. The hourly throttle of the update count, however, only holds while pushes go through: if the monitoring service is unreachable, the saved time stays as it is, and once it is more than an hour old, apt-get -s, dnf -C or pkg audit run on every run. monitor init (test push via BuildReport) neither reads nor writes the state. On top come probes (the last result per probe), throttle (factor and counters of the self-throttle per collector), brake (per credential name the refused credential), bindings (per credential name the id and the target it went to first), cursors (where the last run of every counting probe stopped) and load_shed (the load gate's state: active, since in Unix seconds, hits and clean; missing while the gate is idle: no run over the limits and no shedding); Push writes these six after a failed push too, so probes that ran are not repeated before their interval and a host under load is not measured in full while the service is away. An older agent leaves the file in place and ignores it.
  • Plugin timeouts: Every docker call has a 10-second timeout, zpool, pvesh, systemctl, sc, timedatectl and needs-restarting 15 s each, on FreeBSD service and freebsd-version 15 s each, apt-get, dnf and pkg audit (security updates, hourly) 30 s each, smartctl 15 s for the scan and 30 s per device – a hanging daemon or pool does not stall the push, and a hanging system state tool costs only its field. A docker, zpool or pvesh call the timeout kills is reported in the block as timeout (runTimed), not as a failed call. systemctl, sc, timedatectl and needs-restarting also run through runTimed (runWithTimeout), apt-get and dnf through runTimedEnv: for a call the timeout kills, the reason reads timed out after 15s (or 30s), not signal: killed (Linux) or exit status 1 (Windows). Every run (run --once, the long-running loop and the Windows service) has a budget of 240 s: renewal at most 60 s, the FRP sync at most 60 s, the report's collection ends 45 s before the end, and the push has those 45 s. A tool call the budget ends reports like a timeout; a signal or a service stop ends the run at once. On Linux the unit still ends a run after TimeoutStartSec=270, on FreeBSD timeout(1) in the cron entry after 270 s (cronentry.go).
  • Command allowlist: Every external command the agent starts from monitor, probe and discovery goes through allowlist.RunEnv (package internal/allowlist): the collectors through runTimedEnv (internal/monitor/allowlist.go; runTimed, runWithTimeout and the …CLI indirections lead there), the sensors and discovery through runTool. It starts only calls from the list commands: the command and its fixed arguments, the variable parts (node, storage ID, device, unit, container ID or name, Windows service, journal priority, cursor and match, package, on FreeBSD rc.d script and base system name for pkg audit, the UPID of a vzdump task) against a pattern that never begins with -; the sensors' MariaDB and PostgreSQL queries and the six configd calls of the opnsense sensor (configctl service list, interface gateways status, firmware product, filter diag state_size, interface show carp, interface list ifconfig) are in it verbatim. Any other call does not start; the collector reports it like a failed call (<command> call not on the command allowlist), with a warning in the log. Left off the list on purpose is whatever writes, repairs or activates storages, such as apt-get check, zpool scrub, postfix check, docker exec, pvesh get /nodes/<node>/storage and pkg audit -F (fetches the vuln.xml). A new command needs an entry. The tests check every current call and these traps; the stubs of the collector, sensor and discovery tests check every call they record against the list. internal/monitor/allowlist_test.go makes sure through the AST that no other file of the packages monitor, probe and discovery calls exec.Command, exec.CommandContext, os.StartProcess, execx.Run or execx.RunEnv. runTimedEnv itself starts through execx.RunEnv, so the self-throttle counts every time-limit hit.

Probes, plan and self-throttle

Operation and security model are described in the admin guide, catalog and plan on the service side in the monitoring stack.

  • Plan (internal/monitor/plan.go): before collecting, currentPlan fetches GET {MONITOR_URL}/agent/{server_id}/plan over the push's client (15 s) and saves it in .plan.json next to monitor.conf (config.MonitorPlanFile(), 0600). If the service cannot be reached, an older one answers 404 or the agent does not understand the plan, the saved one applies, without a scan; without a saved plan no probe runs. parsePlan takes plan version 1 only and holds it to bounds of its own: at most 256 probes, ID matching ^[A-Za-z0-9._:-]{1,128}$, interval at least 300 s, timeout 1–30 s (10 if none is given).
  • Flow: runDueProbes runs the due probes after the collectors one after the other, oldest result first, in what is left of the run. A probe only starts while its whole timeout still fits; the others stay due for the next run. A probe is due when its last result is at least its interval times the throttle factor minus 60 s old. Every probe's last result goes along with its own time in every report (probes) and is kept in the report state.
  • Sensors (internal/probe/): unit, process, socket, container, certfile, file_age (sensor_local*.go), http, tls, proto, unixsocket, dns, sql, opnsense (sensor_opnsense.go: no target, parameter view, reads through internal/opnsense with runTool) and the counting log, which counts on from the stored journal cursor of its last run. A sensor only returns the fields the probe asks for; error texts never name a credential. An unknown sensor or invalid parameters yield invalid without running anything; a sensor that cannot run on this host (no systemd, no Docker, no configctl) yields unsupported. On FreeBSD a unit is an rc.d service: measureUnit and unitOwner lead to measureRC and rcOwner (unit_rcd.go, service <name> onestatus, the name after rcNamePattern). As on Linux, dialUnix checks a unix socket first at its path (socketToDial, see Guard), then at its peer process (checkPeer, peerPID via LOCAL_PEERCRED): a process the guard also refuses over TCP, or inetd, yields not_allowed. refuseKernelFile refuses files in file systems of the kernel (procfs, linprocfs, linsysfs, fdescfs, devfs). Only a target given as a container stays ErrUnsupported there (containerEndpoint in target_freebsd.go).
  • Guard (guard.go, target*.go): a sensor only connects to loopback, an address of this host or one of its own containers, checked at the address the connection is actually made to. Never to ports 22, 3306 and 9100–9107, to listeners of sshd, mysqld and mariadbd, or to the host's control daemons (container and VM management including the processes of the VMs, API and console daemons of Proxmox, Kubernetes node daemons, system bus, key agents; hostDaemons, hostDaemonPrefixes), not over a unix socket either. Unix sockets in the runtime directories of these daemons and the control socket of OPNsense's configd, which runs actions as root (controlSockets, /var/run counts as /run), are refused, checked at the given and at the resolved path (socketToDial, on Linux and FreeBSD); the connection goes to the resolved one. Before that, controlSocketFile compares the file's device and inode with the single sockets of controlSockets, so a hard link or second name yields not_allowed; after connecting, checkPeer checks the name the server bound (getpeername, not RemoteAddr; checkPeerName: relative, abstract or refused yields not_allowed), then the peer process. A daemon that renames its socket after binding stays a limit. If a forwarder whose target port the guard cannot see listens on a port (forwarders as a prefix, forwarderNames whole, matched on the process name and on argv[0], also after a re-exec through /proc/self/exe), the guard refuses that port. On Linux the guard checks every address and port against the published ports of the running Docker containers (docker inspect, cached with a TTL like the listener list) and refuses a host port that forwards to a refused container port; if a Docker daemon answers whose containers it cannot read, it refuses. If a dockerd runs while the standard socket does not answer (dockerSocketServes, dockerdRuns), Docker counts as present and unreadable: every TCP probe at an address of its own is refused (fail-closed). A listener that systemd alone holds (socket activation) is refused, because the service behind it is not known; since gopsutil reports the first process of each socket, this holds for practically every socket-activated service. The guard reads the listening sockets through gopsutil, on FreeBSD from sockstat -46 -l -n -q -w -P tcp (listen_freebsd.go, sockstat.go; gopsutil asks lsof there, which the base system lacks): a socket without a process (? or ??) has an unknown owner (PID 0), a line of any other form rejects the whole output, and then no probe passes. A process belongs to a container only if every cgroup hierarchy both name matches. Refused means not_allowed, an ambiguous target ambiguous_target.
  • Credentials (internal/credentials/): credentials.json next to monitor.conf (config.MonitorCredentialsFile()), kept with monitor credential. On Linux and FreeBSD the agent only reads it when the file belongs to it and is open to no one else; on Windows only when SYSTEM or the Administrators own it and only they have access. If a target refuses a credential (401/403), the probes with that name rest until it is set anew (brake in the report state, status denied). At its first use Access.credential binds the id of the credential to the target as the plan names it (bindingOf: sensor, use, kind, name, port hint, scheme, for unixsocket the path); another target gets not_allowed, without the sensor seeing the secret, until the credential is set anew (new id; bindings in the report state).
  • Discovery (internal/discovery/): runs only when the plan asks for scan, in a frame of its own of 60 s with a limit per part, and reports names, ports and states only (contents in the admin guide). It reads units and containers on Linux only (linuxHost); on FreeBSD these lists stay empty. It checks markers on Linux and FreeBSD (markerHost), installed packages through dpkg or rpm only (installedPackages).
  • Self-throttle (internal/monitor/selfmeasure.go): every collector runs in a measuring frame (duration, CPU time, time-limit hits, block self.collectors). The core collectors (resources, system_state, services) always run. For the optional ones (docker, proxmox, zfs, smart, the discovery) two runs in a row with a hit double the factor, three without halve it, at most 8; with factor n the collector runs every n-th run, otherwise its block is missing and the service leaves the checks on it as they are. For the probes (probes) a hit is a due probe the run's time no longer left room for; their factor stretches the intervals. A probe that runs into its timeout is its own result, not a hit.
  • Load gate (internal/monitor/loadgate.go): after the core collectors, loadReadingOf reads three values: the load per CPU (load_1m divided by cpu_count; not in a container, where the load is the host's, and not on Windows, which reports neither load nor CPU count), the I/O wait since the CPU sample of the last run (iowaitPercentSince, Linux only; a counter of 0 means "not read") and the available memory (100 minus memory_percent). Over the limit is a load per CPU from 2.0, an I/O wait from 25 % or available memory below 10 % (shedLoadPerCPU, shedIowaitPercent, shedMemAvailPercent); a value that cannot be read counts as under it. From the second run in a row over a limit the agent sheds (shedEnter), from the third run in a row without one it measures everything again (shedLeave); the state is kept as load_shed in the report state. While shedding, the optional collectors, the probes and a requested discovery do not run; the core collectors always run. A collector held back reports throttled: true with reason: "load" and its unchanged factor in self.collectors: its throttle stays, and what it costs is measured by its next real run. The probes send their stored last results and are due once the shedding is over; a discovery held back stays requested until one is sent. Every report carries self.load_shed: active, over (the values over their limit out of load, iowait, memory), values (load_per_cpu, iowait_percent, mem_available_percent, only those read) and, while shedding, since (UTC, 2006-01-02T15:04:05Z). What the service makes of it is described in the monitoring stack.

systemd Timer with Jitter

Instead of cron, the agent uses systemd with OnBootSec=60, OnUnitActiveSec=300 (5 min interval) and RandomizedDelaySec=30. The jitter spreads load across the 5-minute window and avoids thundering-herd requests at the server.

The unit runs capped: Nice=19, IOSchedulingClass=idle, CPUQuota=50%, MemoryMax=256M and OOMPolicy=continue, so a tool over the memory limit ends only itself, not the run and its push. The packaged unit (systemd/adminhelper-agent.service) and the one service install writes (serviceUnitText) must stay the same; TestServiceUnitMatchesPackagedUnit checks that. The Windows service sets IDLE_PRIORITY_CLASS in agentService.Execute. Operation and override: Agent deployment → Resource limits.

On FreeBSD cron starts the run on every fifth full minute, without jitter, with nice -n 19 and the runtime cap of timeout(1); memory and CPU caps such as MemoryMax and CPUQuota do not exist there.

The DEB and RPM packages install /usr/bin/adminhelper-agent plus /usr/bin/frpc (downloaded in CI) and register the systemd unit + timer. Both recommend smartmontools (Recommends, not a hard dependency: without smartctl the agent keeps running and reports smart_absent with not_installed); apps/agent/cmd/adminhelper-agent/packaging_test.go pins that.

build-pkg.sh packs the same static binary per ABI (FreeBSD:14:amd64, FreeBSD:15:amd64) with pkg-create(8) into freebsd/<ABI>/All/adminhelper-agent-<version>.pkg under OUT_DIR (default build-pkg): /usr/local/bin/adminhelper-agent, frpc of the frp release freebsd_amd64 (FRPC_BINARY, default frpc-freebsd at the repo root) as /usr/local/libexec/adminhelper/frpc the rc.d script /usr/local/etc/rc.d/adminhelper_frpc and the newsyslog entry for its log file /var/log/adminhelper/frpc.log as /usr/local/etc/newsyslog.conf.d/adminhelper.conf (0644), all root:wheel. With PKG_REPO_KEY (PEM file of the RSA key) pkg-repo(8) signs the repository of each ABI (meta.conf, packagesite.pkg, data.pkg); without it only the packages are built. pkg must be on the PATH, FreeBSD's or one built from the sources on Linux.

The package scripts live in apps/agent/freebsd/. +POST_INSTALL starts nothing on a fresh install (the sync enables the tunnel, the setup writes the cron entry) and on an upgrade (PKG_UPGRADE) restarts an enabled tunnel, so the new frpc runs. +PRE_DEINSTALL stops the tunnel on removal and deletes its rcvar and the cron entry; configuration and identity stay. Under pkg -r or pkg -c (PKG_ROOTDIR, PKG_CHROOTED) both leave the host's services alone. packaging_pkg_test.go and internal/frpc/rcscript_test.go pin that; the box scripts/tests/freebsd_box.sh checks package, signed repository, cron entry and rc.d service with FreeBSD's own pkg.

Next to it build-pkg.sh builds the OPNsense plugin freebsd/<ABI>/All/os-adminhelper-<version>.pkg per ABI: the tree apps/agent/opnsense/src below /usr/local with the modes of the checkout, as OPNsense's plugins.mk packs it, the version file /usr/local/opnsense/version/adminhelper (product_id os-adminhelper, product_abi 26.1 on FreeBSD 14 and 26.7 on FreeBSD 15, product_tier 4), which also makes up the package's annotations, and the dependency on adminhelper-agent of the same version. With PKG_REPO_KEY it adds the key's public part as /usr/local/etc/pkg/keys/AdminHelper.pub (openssl rsa -pubout; openssl must then be on the PATH); without it the file is missing, and the plugin's repository script (apps/agent/opnsense/src/opnsense/scripts/firmware/repos/AdminHelper.sh) writes no repo file. +POST_INSTALL and +POST_DEINSTALL from apps/agent/opnsense/ do what plugins.mk generates; on top, the install writes the repo file and the removal deletes it. apps/agent/opnsense/plugin_test.go (XML, form, ACL, configd actions, status, switch, repository script, package scripts) and packaging_pkg_test.go hold this; the box scripts/tests/opnsense_box.sh checks plugin and agent on a real OPNsense.

DEB/RPM Replaces

The DEB/RPM packages carry Replaces + Conflicts entries for the legacy packages srm-frpc-client, srm-monitor-agent and srm-agent. A single apt install adminhelper-agent migrates clean installs automatically.
