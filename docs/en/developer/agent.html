Go Agent

Unified Go agent under apps/agent/. Replaces the legacy shell + Python agents and merges monitoring, FRP-client setup, and service installer into a single binary that runs on Linux (systemd) and Windows (service manager) alike.

Cobra Subcommands

Six top-level commands, three of them with sub-subcommands:

CommandPurpose
versionEmit version + git commit (set via -ldflags).
runStandalone mode: run one full cycle (monitor push + FRP sync).
provisionInitial setup: redeem token against /api/servers/{id}/provision/activate, install server API key + optional monitor key + optional FRP bundle in a single call.
frpc syncPeriodic config sync via hash compare; only writes when the server-side hash changed or frpc does not run despite a tunnel (flow under FRP sync).
monitor initCreate the monitor config (URL, API key, services list).
monitor pushOne metric collection + push run.
service install / uninstallInstall/remove the systemd unit (Linux) or Windows service (SCM).

Configuration

Two config files in key=value format (quotes allowed). OS paths:

  • Linux: /etc/frp/adminhelper.conf and /etc/adminhelper/monitor.conf
  • Windows: under %ProgramData%\AdminHelper\

The secret-bearing directories are hardened on creation: 0700 on Linux, and on Windows an ACL reset to SYSTEM + Administrators only (SID-based via icacls, since mode bits are ignored there) — so the API key and mTLS private key are not readable by other local users.

FrpcConfig fields: ADMINHELPER_URL, API_KEY, SERVER_ID, CACERT, INSECURE. MonitorConfig additionally carries MONITOR_URL and SERVICES (comma-separated).

FRP sync

On every run (run or frpc sync) the agent fetches config-hash and compares it with /etc/frp/.config-hash. Only on a mismatch, or when frpc does not run although frpc.toml is in place, does it fetch the server's frpc.toml, which must match the advertised hash. It stores the hash of the server's text, and only once frpc has taken the config; a failed step is retried on the next run. Provisioning (frpc.Apply) takes the same path with the text from the bundle.

Situation (Linux)Flow
{"hash": null} (no FRP config)Stop and disable frpc, delete frpc.toml and the hash.
Server text without [[proxies]]Stop and disable frpc, delete frpc.toml, store the hash.
frpc not runningWrite, systemctl enable --now frpc.service.
frpc running, common part as at its startWrite, reload over the local admin API (/usr/bin/frpc reload -c /etc/frp/frpc.toml, 15 s timeout). If the agent's own frpc does not listen there or the reload fails, restart.
frpc running, common part changed (frps address, token, user, TLS)Write, systemctl restart frpc.service.
frpc.toml in place, but frpc not running (same or new hash)Fetch the config; with [[proxies]] renew the admin API (new port, new password), write, start frpc. Without [[proxies]] stop as above, the admin API stays.

Reload instead of restart: the common part is the text before the first [[proxies]]. frp takes it only at start; a reload swaps only the proxies, and unchanged tunnels and their connections stay up. The agent compares with the common part frpc last started on (its hash in /etc/frp/.started-hash). Before every start it deletes that record and writes it again only on success, so after a failed start the next run restarts instead of reloading. The agent sends the reload only to its own frpc: /proc/net/tcp must show a socket of root listening on 127.0.0.1 at the admin port (frpc.service runs as root) and none of another user, otherwise it restarts frpc. Provisioning always restarts a running frpc: it may have set up a new identity, and a reload does not connect to frps anew, only a restart does.

Local admin API: the agent puts a local head in front of the server's text: loginFailExit = false (frpc keeps trying while frps is unreachable), then webServer.addr = "127.0.0.1", webServer.port, webServer.user = "adminhelper" and webServer.password. The API listens on 127.0.0.1 only and never without a password: without one, every local process would get the frps token through GET /api/config. Port and password (32 random bytes, hex) live in /etc/frp/admin.conf with 0600, protected like frpc.toml: the agent runs as a oneshot, and a reload has to reach the frpc that started with these values. An admin.conf that is not as the agent writes it gets new values. The kernel assigns the port (127.0.0.1:0). If another process holds it after a reboot, frpc does not start; the next run then picks a new port and a new password (last table row). The server does not set the local head: the agent refuses a server text with a webServer or loginFailExit key or table, in upper or lower case, with an error; it then writes nothing and starts nothing, and the next run tries again.

On Windows the agent manages no frpc service: start, stop and reload are no-ops there.

Monitor Collector

Central collection in internal/monitor/collector.go. Every collector returns map[string]any, which is JSON-serialised on push:

  • collectCPU() – load and per-core utilization
  • collectMemory() – total / used / free / swap
  • collectLoad() – load_1m, load_5m, load_15m
  • collectDisks() – per mountpoint with FS type, usage, inodes
  • collectUptime()
  • collectTemperatures() – lm-sensors / Windows WMI
  • collectServiceHealth() + collectWatchedServices(names)
  • collectDocker() – via the docker CLI: docker info, docker ps -a --format '{{json .}}' (of it only ID, Names, Image, State, Status) and one batched docker inspect --type container <ids> with the standard JSON output, decoded into a struct (Id, RestartCount, State.Status, State.ExitCode, State.OOMKilled, State.Health.Status, HostConfig.RestartPolicy.Name; every other field is ignored). A Go template on .State.Health.Status fails for containers without a health check, hence JSON. Per container the report carries id, name, image, state (from inspect), status (text from ps), restart_policy, exit_code, oom_killed, restart_count and health (empty without a health check); a container that vanishes between ps and inspect drops out. Without a docker binary the block is missing (silently). Otherwise it is always sent, on failure as {"available": false, "error": …, "error_message": …, "containers": []} with error ∈ daemon_unreachable (docker info fails), timeout, cli_failed, parse_failed (no readable line from ps, or unreadable inspect output). error_message names the call and the exit status, never stderr or paths; every abort is also logged as a warning
  • collectZFS() – zpool list -H -o name,size,alloc,free,cap,health, plus zpool status -x (as errors) when a pool is not ONLINE. Without a zpool binary the block is missing (silently). If zpool list fails or hangs, the block is {"available": false, "error": …, "error_message": …, "pools": []} with error ∈ cli_failed, timeout; otherwise available: true, error: null and the pools, an empty list without pools. The parser skips lines with too few columns
  • collectProxmox() – pvesh get (node status, VMs/CTs, backups per storage; PVE hosts only)
  • collectSmart() – smartctl --scan --json=c, then smartctl --all --json=c per device in parallel; ATA and NVMe paths parsed separately. Without a single readable disk it returns the reason instead of the list, and BuildReport sets smart_absent: {"reason": …} instead of smart: not_installed (no smartctl), scan_failed (the scan fails, hangs or prints no JSON, or no device it found gives readable data), no_devices (the scan finds none)

CPU, RAM, load, disks and temperatures are shipped under the resources JSON key, the services under systemd, the plugins under docker, proxmox, zfs and smart or smart_absent; everything goes to the monitoring service via POST /agent/{server_id}/report (format see Monitoring Stack).

Push Behaviour

  • Retry: When the metrics push fails, PushReport (internal/monitor/report.go) does exactly one retry after 10 s – a lost push otherwise wastes a full 5-minute slot.
  • Inventory throttling: The all_services inventory (100–300 mostly static units) is only sent when its SHA-256 hash changes or the last full send is >1 h ago; otherwise the key is omitted from the report. The throttle state lives in .inventory-state.json next to monitor.conf (Linux /etc/adminhelper/, Windows %ProgramData%\AdminHelper\) and is only persisted after a successful push. The hash covers unit, active_state, enabled_state and alias_of of every entry, so any state change of a service forces a full send; the list mode of service_process relies on that. Watched services plus failed, enabled_inactive, counts and, if set, error go with every push.
  • Plugin timeouts: Every docker call has a 10-second timeout, zpool and pvesh 15 s each, smartctl 15 s for the scan and 30 s per device – a hanging daemon or pool does not stall the push. A docker or zpool call the timeout kills is reported in the block as timeout (runTimed), not as a failed call.

Platform Splits: Linux vs. Windows

Collector, service activation, and paths are separated via Go build tags (//go:build linux / //go:build windows). The table below lists the concrete per-function behaviour on each platform.

FunctionLinuxWindows
collectServiceHealth()
services_*.go		 systemctl list-units --all + list-unit-files + list-units --state=failed; populates failed, enabled_inactive, all_services and counts.
all_services is sorted by unit (with active_state / enabled_state). Units that list-units only lists as not-found inactive (not installed, merely referenced by another unit) are left out; a not-found unit that is running or failed stays. Aliases (enabled_state alias, without template names *@.service) get alias_of from one batched systemctl show -p Id,Names; if that call fails, there is no alias_of.
enabled_inactive: one batched systemctl show -p Id,Names,Type,Result,ConditionResult,TriggeredBy,ConditionTimestampMonotonic re-checks the candidates (inactive and enabled). A unit is dropped if TriggeredBy is not empty (timer, socket, path), or, if its start was attempted (ConditionTimestampMonotonic ≠ 0), if it has Type=oneshot with Result=success or ConditionResult=no; a missing or empty property drops nothing. If the batch fails with exit > 0, the agent asks at most 50 candidates one by one; a call killed by the timeout or one that does not start ends the re-check, and the unchecked units stay candidates.
counts ({"active": n, "total": m}) counts the loaded units: listed by list-units, without not-found and masked. If list-units fails, counts is missing and error carries the reason (systemctl list-units failed: exit status N, never stderr).		 sc query state= all; Windows state is mapped to the systemd format (RUNNING→active, STOPPED/PAUSED→inactive, *_PENDING→activating). failed and enabled_inactive stay empty, enabled_state is always unknown. counts counts every listed service. If sc query fails, the inventory stays empty, counts is missing and error carries the reason (sc query failed: …).
collectWatchedServices(names)
services_*.go		 One batched systemctl show -p Id,Names,ActiveState,MainPID for all names; matching on Id and Names also finds aliases (sshd → ssh.service) and names without .service. If the batch fails with exit > 0 (a template name, say), the agent asks name by name with the same limits as for enabled_inactive; a name without an answer counts as not running. sc query (search for RUNNING); PID via sc queryex.
collectTemperatures()
temperatures.go (shared)		 A single shared file with no build tag: reads gopsutil/v4/sensors.SensorsTemperatures(). Identical code on both platforms; gopsutil reads hwmon/lm-sensors on Linux and WMI on Windows. Sensors with temperature ≤ 0 are dropped; with no sensors it returns nil (not an error).
collectLoad()
collector.go (shared)		 load.Avg() yields load_1m/load_5m/load_15m. Returns nil (no load average) — guarded by runtime.GOOS == "windows".
collectDisks()
collector.go (shared)		 Shared code via gopsutil/disk. The filter lists skipFSTypes (squashfs, tmpfs, overlay, proc…) and skipMountPrefixes (/sys, /proc, /dev/, /snap…) are Linux-specific; on Windows they never match and filter nothing.
enableMonitorService()
platform_*.go		 systemctl enable --now adminhelper-agent.timer. No-op: prints a hint to run adminhelper-agent service install (SCM integration left as a TODO).
service.Install()
service_*.go		 Copies the binary to /usr/local/bin/adminhelper-agent (root-owned, so the root unit does not point at a user-writable path), writes .service (Type=oneshot, ExecStart=/usr/local/bin/adminhelper-agent run --once) + .timer (OnBootSec=60, OnUnitActiveSec=300, Persistent=true) to /etc/systemd/system, then daemon-reload + enable --now on the timer. Unit name adminhelper-agent. Copies the binary to %ProgramFiles%\AdminHelper\, registers via sc create (binPath=<exe> run, start= auto, obj= LocalSystem), sets recovery via sc failure (restart after 60 s) and starts with sc start. Service name AdminHelper-Agent — a long-running service, not a timer.

systemd Timer with Jitter

Instead of cron, the agent uses systemd with OnBootSec=60, OnUnitActiveSec=300 (5 min interval) and RandomizedDelaySec=30. The jitter spreads load across the 5-minute window and avoids thundering-herd requests at the server.

Build

bash
cd apps/agent
make build-linux       # bin/adminhelper-agent       (ELF amd64)
make build-windows     # bin/adminhelper-agent.exe   (PE amd64)

VERSION=0.26.0 bash build-deb.sh
VERSION=0.26.0 bash build-rpm.sh

The DEB and RPM packages install /usr/bin/adminhelper-agent plus /usr/bin/frpc (downloaded in CI) and register the systemd unit + timer. Both recommend smartmontools (Recommends, not a hard dependency: without smartctl the agent keeps running and reports smart_absent with not_installed); apps/agent/cmd/adminhelper-agent/packaging_test.go pins that.

DEB/RPM Replaces

The DEB/RPM packages carry Replaces + Conflicts entries for the legacy packages srm-frpc-client, srm-monitor-agent and srm-agent. A single apt install adminhelper-agent migrates clean installs automatically.
