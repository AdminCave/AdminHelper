Go Agent

Unified Go agent under apps/agent/. Replaces the legacy shell + Python agents and merges monitoring, FRP-client setup, and service installer into a single binary that runs on Linux (systemd) and Windows (service manager) alike.

Cobra Subcommands

Six top-level commands, three of them with sub-subcommands:

CommandPurpose
versionEmit version + git commit (set via -ldflags).
runStandalone mode: run one full cycle (monitor push + FRP sync).
provisionInitial setup: redeem token against /api/servers/{id}/provision/activate, install server API key + optional monitor key + optional FRP bundle in a single call.
frpc syncPeriodic config sync via hash compare; only writes when the server-side hash changed or frpc does not run despite a tunnel (flow under FRP sync).
monitor initCreate the monitor config (URL, API key, services list).
monitor pushOne metric collection + push run.
service install / uninstallInstall/remove the systemd unit (Linux) or Windows service (SCM).

Configuration

Two config files in key=value format (quotes allowed). OS paths:

  • Linux: /etc/frp/adminhelper.conf and /etc/adminhelper/monitor.conf
  • Windows: under %ProgramData%\AdminHelper\

The agent creates the secret-bearing directories protected before their first use, so that the API key and mTLS private key are not readable by other local users: config.EnsureSecureDir secures a directory, config.EnsureDataDir one of the agent's data. On Linux this is 0700 as before, also for an existing directory; EnsureDataDir is EnsureSecureDir there. On Windows, where mode bits have no effect, EnsureDataDir first secures the data root %ProgramData%\AdminHelper and then the directory below it (frp, logs, identity). A new directory is created there in one step with a fixed security descriptor: owner Administrators, full control for SYSTEM and the Administrators only, inherited by everything below, nothing inherited from %ProgramData%.

On Windows the agent handles an existing directory only through handles that are opened relative to the parent directory and follow no reparse point; for this it enables SeTakeOwnershipPrivilege, SeBackupPrivilege and SeRestorePrivilege, which LocalSystem holds, in the thread token. If the directory belongs to SYSTEM or the Administrators and is not a reparse point, it keeps the directory with its contents and sets the protected ACL again; kept entries then only inherit the directory's ACL. It replaces foreign content: a directory with another owner is removed with its contents, a reparse point only as the link, its target stays untouched; then it creates the directory anew. In a kept directory it removes reparse points (again only the link), files with more than one name and entries that belong neither to SYSTEM nor to the Administrators. If the directory was already closed before the run (owner SYSTEM or Administrators, rights to write and create only for them, in the inheritable form the agent sets), it takes over an entry with another owner instead, with its contents, owned by the Administrators afterwards; this keeps what an earlier provisioning left there. If a step fails, EnsureSecureDir returns the error instead of discarding it; only an entry that disappears while cleaning counts as removed. provision secures the data root first, before it redeems the one-time token, also without monitoring and on Linux as well (/etc/adminhelper); if it cannot be secured, provision stops with the directory in the error, and the token stays valid. If frp cannot be secured, provision stops after redeeming the token; if the data root cannot be secured, monitor init stops as well. If identity cannot be secured, provision skips the enrollment and goes on with the API key, and a due certificate renewal in the service run is skipped with a warning. The FRP sync (run, frpc sync) changes files in frp only after it has secured the directory with EnsureDataDir in the same run, for writing as for deleting (on Windows the data root first, on Linux 0700 for /etc/frp); if it cannot be secured, the sync stops with the directory in the error and writes, deletes, starts and stops nothing. A run without a change secures nothing.

Files the agent creates in these directories belong to the Administrators on Windows, also when a signed-in administrator runs the agent: config.WriteFile calls config.OwnByAdministrators after writing, the identity files go through OwnByAdministrators directly, and the lock files of the identity and of frpc are created with this owner. If that fails, the write ends with an error. On Linux OwnByAdministrators has no effect. logging.Init secures the log directory through config.EnsureLogDir before it opens the log file; if it cannot be secured, the agent logs to stdout only. When it runs as a Windows service (svc.IsWindowsService), whose stdout no one sees, logging.Init reports this once as a warning in the event log (Application, source logging.EventSource, that is AdminHelper-Agent, event ID 1) with the directory, the reason and the consequences; if that fails as well, stdout is all there is. An interactive run, for example without administrator rights, stays without a notice. On Linux the logger creates the directory itself, as before.

FrpcConfig fields: ADMINHELPER_URL, API_KEY, SERVER_ID, CACERT, INSECURE. MonitorConfig additionally carries MONITOR_URL and SERVICES (comma-separated). The agent reads INSECURE only from configurations of earlier versions; provision and monitor init do not write it.

FRP sync

On every run (run or frpc sync) the agent fetches config-hash and compares it with /etc/frp/.config-hash. Only on a mismatch, or when frpc does not run although frpc.toml is in place, does it fetch the server's frpc.toml, which must match the advertised hash. It stores the hash of the server's text, and only once frpc has taken the config; a failed step is retried on the next run. Provisioning (frpc.Apply) takes the same path with the text from the bundle. After an agent update the first run fetches the text once, even with the same hash, and runs it through the new version's check: if it passes, frpc is left alone (no reload, no restart), otherwise the row “Server text fails the check” applies. /etc/frp/.checked-by holds the agent version that last checked the stored text, with that text's hash; without the file (every agent before it), or naming another version or hash, the text counts as unchecked. Without a stored hash, and for a text without [[proxies]], there is nothing to check again.

Situation (Linux)Flow
{"hash": null} (no FRP config)Stop and disable frpc, delete frpc.toml and the hash.
Server text without [[proxies]]Stop and disable frpc, delete frpc.toml, store the hash.
Server text fails the check (sync and provisioning)Error naming line and key, never a value; stop and disable frpc, delete frpc.toml and the hash, so frpc does not keep running on the old file. The next run fetches and checks again; with nothing left, systemctl is not touched.
frpc not runningWrite, systemctl enable --now frpc.service.
frpc running, common part as at its startWrite, reload over the local admin API (/usr/bin/frpc reload -c /etc/frp/frpc.toml, 15 s timeout). If the agent's own frpc does not listen there or the reload fails, restart.
frpc running, common part changed (frps address, token, user, TLS)Write, systemctl restart frpc.service.
frpc.toml in place, but frpc not running (same or new hash)Fetch the config; with [[proxies]] renew the admin API (new port, new password), write, start frpc. Without [[proxies]] stop as above, the admin API stays.

Every systemctl call of the sync has a cap of 15 s and ends when the run ends (signal or service stop in continuous mode). If systemctl is-active does not answer (cap, end of the run, systemctl does not start), frpc does not count as stopped. If the server's config is unchanged or nothing listens on the admin port, the sync stops without writing, starting frpc or storing the hash. If the server changed the config and frpc listens on its admin port, the sync writes frpc.toml and loads it over the admin API, provided the common part is the one frpc started on and the socket belongs to the agent's own frpc (“Reload instead of restart” below); then it stores the hash. If the common part differs or the reload fails, the new frpc.toml is already in place, the hash stays the old one, and the sync ends with an error. Provisioning never reloads and warns as after a failed start. The next run tries again. An exit status other than 0 still means that frpc does not run.

Lock: when the sync or provisioning changes frpc's files or service (frpc.toml, the hashes, admin.conf, adminhelper.conf, starting and stopping frpc.service), it holds the lock /etc/frp/frpc.lock (Windows %ProgramData%\AdminHelper\frp\frpc.lock), from securing the directory to after its last step. A second call waits at most 60 s, a run also only until it ends (signal or service stop in continuous mode); then it stops with an error that names the lock file and changes nothing. Provisioning then ends with this error after redeeming the token, as on a write error; a run catches up on the sync next time. A run without a change locks nothing. The lock file is created only in the directory the same call secured before, and stays behind empty.

Reload instead of restart: the common part is the text before the first [[proxies]]. frp takes it only at start; a reload swaps only the proxies, and unchanged tunnels and their connections stay up. The agent compares with the common part frpc last started on (its hash in /etc/frp/.started-hash). Before every start it deletes that record and writes it again only on success, so after a failed start the next run restarts instead of reloading. If the run has already ended (signal, service stop), it starts nothing and leaves the record in place. The agent sends the reload only to its own frpc: /proc/net/tcp must show a socket of root listening on 127.0.0.1 at the admin port (frpc.service runs as root) and none of another user, otherwise it restarts frpc. Provisioning always restarts a running frpc: it may have set up a new identity, and a reload does not connect to frps anew, only a restart does.

Local admin API: the agent puts a local head in front of the server's text: loginFailExit = false (frpc keeps trying while frps is unreachable), then webServer.addr = "127.0.0.1", webServer.port, webServer.user = "adminhelper" and webServer.password. The API listens on 127.0.0.1 only and never without a password: without one, every local process would get the frps token through GET /api/config. Port and password (32 random bytes, hex) live in /etc/frp/admin.conf with 0600, protected like frpc.toml: the agent runs as a oneshot, and a reload has to reach the frpc that started with these values. An admin.conf that is not as the agent writes it gets new values. The kernel assigns the port (127.0.0.1:0). If another process holds it after a reboot, frpc does not start; the next run then picks a new port and a new password (last table row). The server does not set the local head. The agent takes a server text only in the form generate_frpc_toml writes: every line is blank, one of the table heads [transport.tls] (at most once, before the first proxy) and [[proxies]], or key = value with a bare or dotted key without quotes (at most 32 segments) and a value on one line (a string without " and \, a list of such strings, a number, true or false). The root holds only the generator's keys: serverAddr, serverPort, user, auth.method (only "token"), auth.token, and under transport.tls enable, trustedCaFile, certFile and keyFile, so no key of the local head either; a proxy may carry further keys (a tunnel's extra_config), but none whose first segment is plugin, in upper or lower case (such as plugin.type or Plugin.localPath): the server sets up no proxy plugins. No key stands twice in a table, in upper or lower case, and the text holds no {{ and no control character but the line break. The agent refuses any other text with an error that names line and key, never the value; what follows is the row “Server text fails the check” above: frpc stops, and the next run checks again.

On Windows the agent manages no frpc service: start, stop and reload are no-ops there.

Monitor Collector

Central collection in internal/monitor/collector.go. Every collector returns map[string]any, which is JSON-serialised on push:

  • collectCPUSince(prev, now) – cpu_percent as the share of busy CPU time since the last report sent successfully, on both platforms. The agent reads cpu.Times(false) and computes as gopsutil does internally for cpu.Percent (getAllBusy/calculateBusy, not exported, hence rebuilt in cpuBusyTimes/cpuPercentSince): the total without Guest/GuestNice on Linux, busy = total − Idle − Iowait, the ratio of the two increases limited to 0–100. The previous sample (cpu: unix, total, busy) comes from the report state (below). Without a usable one, collectCPU() takes the 1-second sample as before (cpu.Percent): in the first run, with a missing or corrupt state, with a sample older than 15 min (cpuStateMaxAge) or from the future, with a total that did not grow (host rebooted) and when cpu.Times fails. BuildReport (the test push of monitor init) always takes the sample.
  • collectMemory() – memory_percent, memory_total_mb, memory_used_mb
  • collectLoad() – load_1m, load_5m, load_15m
  • collectSwapAndCPUCount() – Linux only, like the load the monitoring service puts into proportion with it: cpu_count (logical CPUs, cpu.Counts(true); a 0 counts as failed and is left out), swap_total_mb, swap_used_mb and, only with a swap device (Total > 0), swap_percent (mem.SwapMemory()). A failed call drops only its own fields.
  • collectDisks() – per mountpoint mount, fstype, percent, total_gb, used_gb and free_gb (gopsutil Free, the space left to non-root users, Bavail; it can be less than total minus used; both platforms), plus inodes_percent on Linux only and only when the filesystem reports inodes (InodesTotal > 0; btrfs and vfat do not). The pure function diskInfo does the mapping.
  • collectUptime()
  • collectTemperatures() – lm-sensors / Windows WMI
  • collectServiceHealth() + collectWatchedServices(names)
  • collectDocker() – via the docker CLI: docker info, docker ps -a --format '{{json .}}' (of it only ID, Names, Image, State, Status) and one batched docker inspect --type container <ids> with the standard JSON output, decoded into a struct (Id, RestartCount, State.Status, State.ExitCode, State.OOMKilled, State.Health.Status, HostConfig.RestartPolicy.Name; every other field is ignored). A Go template on .State.Health.Status fails for containers without a health check, hence JSON. Per container the report carries id, name, image, state (from inspect), status (text from ps), restart_policy, exit_code, oom_killed, restart_count and health (empty without a health check); a container that vanishes between ps and inspect drops out. Without a docker binary the block is missing (silently). Otherwise it is always sent, on failure as {"available": false, "error": …, "error_message": …, "containers": []} with error ∈ daemon_unreachable (docker info fails), timeout, cli_failed, parse_failed (no readable line from ps, or unreadable inspect output). error_message names the call and the exit status, never stderr or paths; every abort is also logged as a warning
  • collectZFS() – zpool list -H -o name,size,alloc,free,cap,health, plus zpool status -x (as errors) when a pool is not ONLINE. Without a zpool binary the block is missing (silently). If zpool list fails or hangs, the block is {"available": false, "error": …, "error_message": …, "pools": []} with error ∈ cli_failed, timeout; otherwise available: true, error: null and the pools, an empty list without pools. The parser skips lines with too few columns
  • collectProxmox() – pvesh get (node status, VMs/CTs, backups per storage; PVE hosts only). The agent builds the backup index (the newest ctime per VM) from the node's backup storages (/nodes/<node>/storage --content backup) and their content (/nodes/<node>/storage/<storage>/content --content backup). Without a pvesh binary the block is missing (silently). Otherwise it is always sent: when read, with available: true, error: null, node (name, cpu, memory_percent) and vms, an empty list without VMs, never null; on an outage (proxmoxUnavailable) as {"available": false, "error": …, "error_message": …, "node": null, "vms": []}. An outage is any failure at the local hostname, the node status (/nodes/<node>/status), the storage list, the content of a storage and the VM list (/cluster/resources --type vm), with error ∈ timeout (a pvesh call ran into the timeout), cli_failed (exit status, pvesh does not start, hostname unreadable), parse_failed (no JSON answer of the expected form, null included), backup_index_incomplete (a backup storage is not active; active counts as a bool or as 0/1). An incomplete index would report every VM with backups on the missing storage as having none, and a VM list that was not read would look like no VMs: hence an outage instead of a list. error_message names the call and its exit status, or backup storage <id> not active, never stderr; the same text goes to the log as a warning with the code (such as pvesh get /cluster/resources timed out after 15s, proxmox reported as unavailable (timeout))
  • collectSystemState(st) (internal/monitor/system_linux.go, updates_linux.go; outside Linux system_other.go without a block) – the system_state block. Each field comes only when the agent could determine it; without a single one the block is missing. Why a field is missing goes to the log as a warning, short and without stderr (commandFailure); a host without a tool for a point (neither apt-get nor needs-restarting, or dnf) misses the field without a warning. Every tool runs as root with fixed arguments; nothing from the report or the server goes into a call.
    • reboot_required: with apt-get on the search path (Debian family), /var/run/reboot-required decides (present → true, missing → false, not checkable → no field); otherwise, with needs-restarting on the search path (RPM family), needs-restarting -r: exit 0 → false, exit 1 → true, any other outcome (other exit, timeout, does not start) → no field.
    • time_synchronized: timedatectl show, the line NTPSynchronized=yes|no. Without -p, which timedatectl(1) describes for show-timesync only; the line is searched for. If the program is missing, the call fails, the line is missing or carries another value: no field.
    • security_updates: with apt-get on the search path, apt-get -s dist-upgrade with LC_ALL=C; it counts the Inst lines whose origin in the parenthesis after the new version contains security, case-insensitively (Debian Debian-Security:12/stable-security, Ubuntu Ubuntu:24.04/noble-security). Otherwise, with dnf on the search path, dnf -C -q updateinfo list --security; it counts the distinct package names (third column, without version, release and architecture), and a line of another form makes the output unreadable. No network (-s or -C; the agent does not refresh the package lists), timeout updatesTimeout 30 s. At most once an hour (updatesCheckEvery): the result is kept with its time in the report state (updates), and within the hour the agent sends it without a call. A failed attempt counts as the attempt (security: null), so the field stays out until the next count; a time in the future (clock set back) counts as due. Neither the form of the origin after Inst nor the output of dnf updateinfo is documented; both parsers are tested against fixtures, the RPM path not on a real host (not verified).
    • oom_kills: the increase of the oom_kill counter in /proc/vmstat against the counter in the report state (oom_kill), i.e. since the last report sent successfully. The first run (no previous counter) has no field, only the counter for the next one; a counter smaller than the saved one (host rebooted) counts in full. If the agent cannot read the counter, the saved one stays. proc_vmstat(5) describes the name value lines but does not list the counter (Linux 4.13 and later by the kernel source); without the line there is no field. In a container, /proc/vmstat counts the kills of the whole host; there the agent reads oom_kill from /sys/fs/cgroup/memory.events instead (memoryEventsPath, the same name value lines), under cgroup v2 the counter of its own cgroup including sub-cgroups (checked in Docker, also with a kill in a sub-cgroup; not verified in an LXC on Proxmox VE). A container means: hostFactsCalls.virtualization, the same call as in collectHostFacts(), reports the role guest and a system from containerSystems (lxc, docker, openvz, rkt: the container systems of gopsutil v4.26.5, internal/common/common_linux.go; gopsutil does not detect Podman); a failed detection counts as no container. gopsutil keeps the detection per process, so the second question in the same report reads no file. If memory.events is missing in a container (cgroup v1) or unreadable, the field is missing with a warning, without falling back to /proc/vmstat. The report state keeps the source (oom_kill_source); a run that reads another source than the saved one sends no field, only the new counter for the next run.
  • collectSmart() – smartctl --scan --json=c, then smartctl --all --json=c -d <type> per device in parallel, with the type from the scan (such as megaraid,N for a disk behind a MegaRAID controller on /dev/bus/N, which smartctl cannot detect without -d); no -d for scsi: the scan reports every disk on /dev/sdX without a USB bridge as scsi, a SATA disk too, and -d scsi switches off the SAT detection, so the disk would come without its ATA attributes. ATA and NVMe paths parsed separately. The device field is the device name from the scan; for a scan type megaraid,… or sssraid,… it is the scan's info_name (smartDiskID, such as /dev/bus/0 [megaraid_disk_00]): all disks behind the controller share the device name, and the monitoring service builds the metric names from device and matches it against ignore_devices. Not the query's info_name: smartctl appends [SAT] to it on open when it finds a SATA disk behind the controller. A query that ends with exit bit 0 or 1 (smartctl(8), EXIT STATUS: command line did not parse, device open failed) drops the device from the list: its JSON has no smart_status and would look like a failed SMART check. With bits 2 to 7 it stays, and smartctl_status carries the full exit code. Without a single readable disk it returns the reason instead of the list, and BuildReport sets smart_absent: {"reason": …} instead of smart: not_installed (no smartctl), scan_failed (the scan fails, hangs or prints no JSON, or no device it found gives readable data; a query with exit bit 0 or 1 does not count as readable), no_devices (the scan finds none)
  • collectHostFacts() (internal/monitor/hostfacts.go) – os from runtime.GOOS, platform and platform_version from gopsutil host.PlatformInformation() (the product name on Windows), virtualization (system, role) from host.Virtualization(), where "not implemented" (Windows) counts as empty, and subsystems: docker, zfs, proxmox in a fixed order, depending on whether docker, zpool or pvesh is on the search path (exec.LookPath, independent of the plugin collectors), an empty list when none is found. Deliberately two calls instead of host.Info(), which fails as a whole on any part it cannot read: a failed call costs only its own fields and a warning in the log, never the block. The monitoring service suggests standard templates from it

CPU, RAM, swap, CPU count, load, disks and temperatures are shipped under the resources JSON key, the system state under system_state, the services under systemd, the plugins under docker, proxmox, zfs and smart or smart_absent, the host facts under host; everything goes to the monitoring service with report_version 3 via POST /agent/{server_id}/report (format see Monitoring Stack).

Push Behaviour

  • Retry: When the metrics push fails, PushReport (internal/monitor/report.go) does exactly one retry after 10 s – a lost push otherwise wastes a full 5-minute slot.
  • Inventory throttling: The all_services inventory (100–300 mostly static units) is only sent when its SHA-256 hash changes or the last full send is >1 h ago; otherwise the key is omitted from the report. The throttle state lives in .inventory-state.json next to monitor.conf (Linux /etc/adminhelper/, Windows %ProgramData%\AdminHelper\) and is only persisted after a successful push. The hash covers unit, active_state, enabled_state and alias_of of every entry, so any state change of a service forces a full send; the list mode of service_process relies on that. Watched services plus failed, enabled_inactive, counts and, if set, error go with every push.
  • Report state: What the next report is measured against lives in .report-state.json next to .inventory-state.json (0600, internal/monitor/reportstate.go, path config.MonitorReportStateFile()): {"cpu": {"unix", "total", "busy"}, "oom_kill": n, "oom_kill_source": "vmstat" | "cgroup", "updates": {"checked_unix", "security": n | null}}, oom_kill, oom_kill_source and updates on Linux only; a state without oom_kill_source (written before it existed) counts as vmstat. Push loads it before collecting (if it is missing or corrupt, the empty state applies: CPU sample, no oom_kills, a new update count) and writes the new one only after a successful push; a write failure is only logged, the push still counts. A lost push thus widens the next CPU window (if the previous sample is more than 15 min old, the agent takes the sample), and its OOM kills count in the next report. The hourly throttle of the update count, however, only holds while pushes go through: if the monitoring service is unreachable, the saved time stays as it is, and once it is more than an hour old, apt-get -s or dnf -C run on every run. monitor init (test push via BuildReport) neither reads nor writes the state. An older agent leaves the file in place and ignores it.
  • Plugin timeouts: Every docker call has a 10-second timeout, zpool, pvesh, systemctl, sc, timedatectl and needs-restarting 15 s each, apt-get and dnf (security updates, hourly) 30 s each, smartctl 15 s for the scan and 30 s per device – a hanging daemon or pool does not stall the push, and a hanging system state tool costs only its field. A docker, zpool or pvesh call the timeout kills is reported in the block as timeout (runTimed), not as a failed call. systemctl, sc, timedatectl and needs-restarting also run through runTimed (runWithTimeout), apt-get and dnf through runTimedEnv: for a call the timeout kills, the reason reads timed out after 15s (or 30s), not signal: killed (Linux) or exit status 1 (Windows). Every run (run --once, the long-running loop and the Windows service) has a budget of 240 s: renewal at most 60 s, the FRP sync at most 60 s, the report's collection ends 45 s before the end, and the push has those 45 s. A tool call the budget ends reports like a timeout; a signal or a service stop ends the run at once. On Linux the unit still ends a run after TimeoutStartSec=270.

Collector, service activation, and paths are separated via Go build tags (//go:build linux / //go:build windows). The table below lists the concrete per-function behaviour on each platform.

temperatures.go (shared)		 A single shared file with no build tag: reads gopsutil/v4/sensors.SensorsTemperatures(). Identical code on both platforms; gopsutil reads hwmon/lm-sensors on Linux and WMI on Windows. Sensors with temperature ≤ 0 are dropped; with no sensors it returns nil (not an error).

collectSwapAndCPUCount()

collectSystemState(st)

collectDisks()
collector.go (shared)		 Shared code via gopsutil/disk. The filter lists skipFSTypes (squashfs, tmpfs, overlay, proc…) and skipMountPrefixes (/sys, /proc, /dev/, /snap…) are Linux-specific; on Windows they never match and filter nothing. free_gb comes on both platforms, inodes_percent on Linux only.
service.EnableTimer()
service_*.go		 systemctl enable --now adminhelper-agent.timer (capped at 30 s). Called by provision (always, at the end, also without monitor and tunnel), monitor init (after the setup) and service install, never by a run: the FRP sync enables only frpc.service, so run without --once does not run beside the timer. If the call fails, provision and monitor init report it and still succeed; service install stops. No timer: logs a hint to run adminhelper-agent service install.
service.Install()
service_*.go		 Copies the binary to /usr/local/bin/adminhelper-agent (root-owned, so the root unit does not point at a user-writable path), writes .service (Type=oneshot, ExecStart=/usr/local/bin/adminhelper-agent run --once) + .timer (OnBootSec=60, OnUnitActiveSec=300, Persistent=true) to /etc/systemd/system, then daemon-reload + enable --now on the timer. Unit name adminhelper-agent. Copies the binary to %ProgramFiles%\AdminHelper\, registers via sc create (binPath=<exe> run, start= auto, obj= LocalSystem), sets recovery via sc failure (restart after 60 s) and starts with sc start. Service name AdminHelper-Agent — a long-running service, not a timer.

service_*.go		 systemctl stop/disable for timer and service, removes the unit files, daemon-reload. sc stop + sc delete on AdminHelper-Agent.

systemd Timer with Jitter

Instead of cron, the agent uses systemd with OnBootSec=60, OnUnitActiveSec=300 (5 min interval) and RandomizedDelaySec=30. The jitter spreads load across the 5-minute window and avoids thundering-herd requests at the server.

Build

bash
cd apps/agent
make build-linux       # bin/adminhelper-agent       (ELF amd64)
make build-windows     # bin/adminhelper-agent.exe   (PE amd64)

VERSION=0.26.0 bash build-deb.sh
VERSION=0.26.0 bash build-rpm.sh

The DEB and RPM packages install /usr/bin/adminhelper-agent plus /usr/bin/frpc (downloaded in CI) and register the systemd unit + timer. Both recommend smartmontools (Recommends, not a hard dependency: without smartctl the agent keeps running and reports smart_absent with not_installed); apps/agent/cmd/adminhelper-agent/packaging_test.go pins that.

DEB/RPM Replaces

The DEB/RPM packages carry Replaces + Conflicts entries for the legacy packages srm-frpc-client, srm-monitor-agent and srm-agent. A single apt install adminhelper-agent migrates clean installs automatically.
