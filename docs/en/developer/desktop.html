Developer Guide

Desktop Client

The Desktop Client is a Tauri 2 wrapper around a Svelte 5 SPA. The Rust backend (apps/desktop/src-tauri/) exposes typed commands; the frontend (apps/desktop/ui/) consumes them through a 1:1 bridge. Since v0.32.0, in server mode the client is also the operational cockpit: the Infrastructure hub manages the server inventory and, per server, connections, FRP tunnels, monitoring checks, and provisioning; plus the fleet-wide Monitoring and Ansible pages. Operational writes go through the api_proxy to the AdminHelper server's REST API.

Only one instance runs at a time: a second launch only brings the window of the running app to the front and then exits (tauri-plugin-single-instance, registered as the first plugin in main.rs, on Linux through the D-Bus session bus). For this, enableGTKAppId in tauri.conf.json stays false: with a GTK app id, GApplication itself forwards the second launch to the running instance, which then runs its setup again and crashes.

Pages & Infrastructure hub (server mode)

In server mode the client is the operational cockpit. Five pages:

PageContent
DashboardOverview/status after login.
InfrastructureServer inventory (create/edit/delete) and, per server, tabs: Overview, Connections (ssh/rdp/web, server-side CRUD), Tunnel (FRP tunnels per server; the FRP server config is picked but stays a web-admin concern), Monitoring (this server's checks), Provisioning (one-time token + agent command).
ConnectionsQuick launcher for starting sessions; in server mode also server-side editing.
MonitoringFleet-wide: checks overview, alert rules (CRUD), templates (CRUD), alert log.
AnsibleCreate/edit/delete AND run playbooks (3-step wizard).

These operational pages exist only in server mode; in standalone/local mode the client stays a pure connection launcher. Writes go through api_proxy against the server's REST API (admin session required).

Tauri Commands

The commands are registered in src/main.rs via invoke_handler and cover auth, connection persistence, connect flow, FRP tunnel, keyring, API proxy, Ansible, diagnostics and notifications. Each command is typed – the bridge in apps/desktop/ui/src/lib/bridge/ mirrors them 1:1. The commands that talk to the server as the signed-in user (api_proxy, fetch_connections_jwt, fetch_tunnels, start_tunnel, refresh_tunnel, start_notification_stream, export_browser_p12) take neither a server URL nor a token: they act for the session in the Rust process (see Server Mode Flow) and fail with “Keine aktive Sitzung” without one.

RDP Race Guard

Clicking Connect several times in quick succession leaves multiple RDP attempts in flight – and a late rdp-error event from an abandoned one would mark the attempt that is actually running as failed. The Desktop Client therefore assigns a correlation ID per attempt (crypto.randomUUID()) and matches every error event back to its attempt; an event with no matching open attempt is discarded. The ID goes to open_connection or open_connection_stored as correlation_id. Implementation in apps/desktop/ui/src/lib/stores/connectFlow.ts, tests in apps/desktop/ui/src/lib/stores/connectFlow.test.ts.

Keyring Secrets

Passwords are stored in the OS keyring, never in the local connection file:

  • Linux: secret-service (GNOME Keyring / KWallet)
  • macOS: Keychain
  • Windows: Credential Manager

Service com.admincave.adminhelper; an RDP password sits under the account rdp|<host>|<port>|<user>|<domain> (lower-cased). On Windows it sits in the Credential Manager under TERMSRV/<address> instead, where mstsc reads it.

TLS certificate pinning (TOFU)

When the user enables “Allow self-signed certificates”, TLS verification is not turned off (the old danger_accept_invalid_certs(true) disabled chain and hostname checks with no pinning – open to MITM). Instead tofu.rs pins the server certificate using the trust-on-first-use model (like SSH known_hosts):

  • Single choke point: on the self-signed path http_client::build_client builds a reqwest client with a custom rustls ServerCertVerifier (use_preconfigured_tls, ring provider). This covers every credential-carrying path – login, refresh, api_proxy, the tunnel/connection fetches and sync.
  • The session's choice: login records whether “Allow self-signed certificates” was on at sign-in. Every request of the session (renewal, api_proxy, connections, tunnel, notification stream and the browser export) builds its client with that value, not with one from the UI. A change of the setting therefore takes effect at the next sign-in. An enrolled device uses its pinned CA regardless (see Enrolled state).
  • First contact without the opt-in (ERR_TLS_UNKNOWN_ISSUER): while “Allow self-signed certificates” is (still) off, build_client validates against the public roots (webpki). Against the standard install's internal PKI leaf that fails with UnknownIssuer by design; error.rs detects exactly this case by downcasting through the reqwest source chain (the rustls error hangs off io::Error::get_ref(), not the source() chain) and replaces the raw rustls message with the stable code ERR_TLS_UNKNOWN_ISSUER plus an actionable hint. The login screen then opens a trust dialog: Trust & continue persists allowSelfSignedCerts=true and retries the sign-in or token enrollment via the TOFU path; cancelling shows the message (without the code) inline. The pin verifiers are unaffected – they never emit a raw UnknownIssuer but their own ERR_* messages.
  • Other network errors reach the UI with their cause chain (the TOFU verifier's pin-mismatch message or Connection refused, say), but without the request URL: reqwest names it in full in its message, path and query included, and the sync calls a user-entered URL. From<reqwest::Error> in error.rs strips it (without_url) before the error becomes AppError::Network; every reqwest error goes through that conversion. The same holds for the log lines that write an AppError.
  • Pin = SHA-256 of the leaf DER. Captured on first connect and stored in the OS keyring (key tofu|cert|<host:port>, service com.admincave.adminhelper) with an in-memory cache so the enforcement path does not hit the keyring per request. Afterwards: accept only on an exact fingerprint match, otherwise reject (possible MITM). Hostname/expiry are intentionally irrelevant – the pin is the identity.
  • The handshake signature is still verified against the presented public key (delegated to the ring provider), so a captured certificate cannot be replayed without its private key.
  • Recovery after a legitimate certificate rotation: reset_server_cert_pin clears the pin (keyring + cache) – UI button “Reset pinned certificate” in settings.
  • Enrolled state (mTLS): once the device is enrolled (A5), every request goes through enrolled_client – the CA pin in enrollment.rs (hostname-agnostic), not the leaf pin. The exception is the sync fetch (sync.rs): it uses the device identity only when the sync URL has the same origin (scheme, host, port) as the stored serverUrl; any other sync URL it fetches through http_client::build_client_without_identity like a device that isn't enrolled (TOFU pin when self-signed certificates are allowed, public CA otherwise). A second hostname of your own server counts as another origin here. If the server certificate no longer chains to the CA pinned at enrollment (server reinstall / re-created PKI → BadSignature or UnknownIssuer), the CaPinVerifier returns an explicit danger message instead of the raw rustls error. Recovery: reset_device_identity first revokes the device at the server with this very certificate: POST /api/enrollment/self/revoke through the mTLS client (enrolled_client), without a JWT. Only then does it clear the mTLS identity (enroll|key/enroll|cert/enroll|ca) and the TOFU pin. The result is a ResetOutcome: revoked (the server revoked the device or had already refused the certificate as revoked), localOnly (the server did not revoke it, e.g. because it was unreachable) or notEnrolled (no identity). On localOnly the client keeps the fingerprint of the old certificate in the keyring (enroll|replaces) and names it as replaces at the next enrollment; the UI adds the hint “on this device only”. The UI button “Reset device identity” sits in two places: in the settings (server mode, only shown when enrolled and signed in; with a danger confirmation) and on the login screen on ERR_CA_PIN_MISMATCH (also with a danger confirmation), ERR_CERT_USER_MISMATCH and ERR_CERT_REVOKED (with a confirmation). Afterwards the device enrolls again with a new one-time token; without an identity the settings show the token field for it.
  • Verification: a real-handshake test in tofu.rs (tokio-rustls server, two distinct certificates) proves first-use pinning, reconnect with the same cert, and rejection on a cert change.
  • Accompanying hardening: the session's token only goes to the session's origin (token-destination pin in session::authed_send, checked on the request as built); launch_ansible only accepts paths under the app temp dir (adminhelper_ansible prefix, canonicalized – blocks ../symlink escape); the webview CSP connect-src is narrowed to 'self' ipc: http://ipc.localhost (no https: exfiltration channel, since all server traffic goes through api_proxy).

FRP Sidecar

Tauri capabilities are scoped: frpc can only be spawned from the app binaries directory. At build time the matching target binary (frpc-x86_64-unknown-linux-gnu, frpc-aarch64-apple-darwin, …) must be dropped into apps/desktop/src-tauri/binaries/.

Server Mode Flow

In Server mode (setting mode = 'server') the client loads connections from the AdminHelper server via JWT and brings up the FRP tunnel itself. The steps wire together across auth.rs, session.rs, sync.rs, frpc.rs and tunnel.rs:

  1. Login – login posts to /api/auth/login, then fetches /api/auth/me and keeps the session only in the memory of the Rust process (session.rs): server URL, user, access and refresh token and the certificate choice of the sign-in. The UI gets only serverUrl, username and isAdmin, never a token. Earlier versions kept the tokens in the OS keyring (auth|jwt, auth|refresh, auth|server_url); the start removes those entries once (best effort). Implemented in auth.rs and session.rs.
  2. Login on every start – For security the client no longer restores a stored session on startup: server mode always requires a fresh password login (server URL and username are pre-filled, persisted in settings.json as serverUrl/lastUsername – never the password). The session ends with the process. While it runs, every authenticated request (api_proxy, connections, tunnel mappings, visitor bundle, the token for the browser export, notification stream) goes through session::authed_send: on a 401 it renews the session at /api/auth/refresh and repeats the request once. Only one renewal runs at a time; a request that meets a 401 meanwhile waits and repeats with the new token instead of sending the already rotated refresh token a second time (the server would end the whole session for that). If the renewal fails or takes longer than 30 s, the session ends and Rust sends the Tauri event session-expired. The UI then signs out like the logout button (logoutAndReload: stop the tunnel, sign out, reload the window), and the login screen shows the notice “Session expired — please sign in again.” The opportunistic mTLS cert renewal (maybe_renew) now hangs off a successful login (previously off the removed check_session).
  3. Load connections – fetch_connections_jwt retrieves the list via authenticated_get (through session::authed_send, see above) from /api/connections and writes it to the server/sync cache (connections.json). Local mode uses a separate store (connections.local.json) that a server/sync fetch never overwrites – so local connections survive switching into server mode and back. Passwords are never part of the sync data.
  4. Start & reconcile tunnel – refresh_tunnel fetches the visitor bundle (TOML) from /api/frp/generate/visitor-bundle and brings frpc in line with it; start_tunnel is the same reconciliation and returns only the status. A lock in the backend runs the reconciliations one after another. It compares the parsed server TOML, checked and rewritten to local ports (see Local ports below), with the one the running frpc applied, not the text: if no frpc runs, it starts one (started). If the root table without visitors changes (serverAddr, serverPort, user, auth.*, transport.*, so a token rotation too), frpc restarts (restarted), because frp reads these values only at start. If only the visitors change, frpc hot-reloads them (reloaded); unchanged visitors and their connections stay up. Otherwise everything stays as it is (unchanged). If the server answers 404 (no visible STCP tunnels), the reconciliation stops frpc without an error message (stopped); any other failure (network, 5xx, 401 after a failed refresh, a TOML the allow-list rejects) leaves the running frpc untouched. The allow-list admits only what the server's generator emits: STCP visitors with unique names that listen on 127.0.0.1 only (bindAddr with that value alone, bindPort a port from 1 to 65535 that no other visitor has), under auth only method (with the value token alone) and token, under transport only tls.enable, tls.trustedCaFile, tls.certFile and tls.keyFile; any further key is rejected. If the TOML does not parse, the error message names only line and column, not the content of the line. Local ports: after the check the desktop rewrites every visitor to bindAddr = "127.0.0.1" and, as bindPort, the local port from the port map (port_registry.rs): port-registry.json (0600) in the app data directory, which all AdminHelper processes of the user share under a file lock, keyed by visitor name. The server's bindPort is the preferred port: if no other entry of the map holds it and it binds on 127.0.0.1, the visitor gets it, otherwise the first free port from 23000–23999; a server port below 1024 goes straight to this fallback range. The assigned port stays as long as the visitor is in the bundle, without a new bind test, since the desktop's own frpc holds it. Only a reconciliation while no frpc runs (at start and after it ended) tests the assigned ports too and gives one that someone else has taken meanwhile a new port. Into the root of the checked server TOML the desktop puts a local head: loginFailExit = false, so frpc keeps trying while frps is unreachable, and frpc's local admin API (webServer on 127.0.0.1, a free port, user adminhelper, a password of 32 random bytes). Every start and restart gets a new port and a new password; a reload keeps both. GET /api/reload with Basic auth triggers the reload (no proxy, 5 s timeout); if it fails, frpc restarts. The final visitor.toml (0600) lives in the app data directory next to the exported device identity (identity/; the {{IDENTITY_DIR}} placeholder in tls.trustedCaFile, tls.certFile and tls.keyFile is rewritten to the absolute path, the key with 0600) whenever the checked table holds transport.tls, be it as a header, in dotted keys or inline; frpc runs as a sidecar with frpc -c <config>. frpc gets exactly what was checked: the desktop does not write the server's text but generates visitor.toml from the checked and rewritten table, head included, every string on one line; it rejects a value with a line break. frp renders the config file as a Go template before it reads the TOML, so the desktop rejects a server TOML (with the identity path filled in) or a generated config that contains {{.
  5. Status & events – tunnel_status returns running, visitor_name, connected_since, visitors (names of the visitors the running frpc applied) and bindings (name, server port and local port of each visitor); without a running frpc both lists are empty. The sidecar process emits the Tauri events frpc-terminated and frpc-error; the tunnel store (stores/tunnel.ts) listens for them and feeds the status indicator (TunnelIndicator.svelte) with the UI states connecting / connected / disconnected. Only the running frpc process announces frpc-terminated and frpc-error: if after a restart (stop → start) the old process ends or still reports an error only once the new one runs, no event reaches the UI, and the indicator does not show the running tunnel as disconnected. A stop silences the stopped process the same way: neither its late end nor a late error switches the indicator back to disconnected. While a server session is active, the tunnel store reconciles right away and then every 60 s (refresh_tunnel, then fetch_tunnels; if that fails, the old mappings stay). Only one reconciliation runs at a time: a tick that meets a running one is skipped; refreshNow() (from the tunnel dialog after create, update and delete) queues exactly one follow-up behind it. stopped sets the indicator to idle without a message, and the store loads the mappings all the same; a failed reconciliation leaves the indicator as it is (only a failed first start becomes disconnected) and reports once per series of failures. If frpc ends unexpectedly (frpc-terminated or frpc-error while the tick is active), the indicator becomes disconnected, and a reconciliation restarts frpc after 5 s, each further one after 10, 20, 40 and at most 60 s. The series ends only once a restarted frpc has held for a whole tick, and brings at most one message. A reconciliation while a restart is due does not change the indicator: its status may predate the end of frpc. stop() ends the tick and any planned restart and clears the mappings. On disconnected, TunnelIndicator.svelte shows the Reconnect button: reconnectNow() brings a planned restart forward (as a follow-up behind a running reconciliation), lets the pauses begin at 5 s again and does nothing without an active tick; until its reconciliation is through, the button is disabled.
  6. Tunnel resolution – fetch_tunnels retrieves the mappings from /api/frp/tunnels, without STCP tunnels too (after stopped), as HTTPS tunnels need no frpc; only admins may read them. resolve_connection resolves in Rust (tunnel.rs), with these mappings and the bindings of the running frpc, by two rules: (1) if the connection has a mapping (connection_id), it decides: stcp → host = 127.0.0.1, port = the local port of the visitor whose server port is the mapping's visitor_port (web also url = http://127.0.0.1:<port>); https → url = https://<custom-domain>. (2) Without a mapping, literally: host 127.0.0.1 or localhost and the server port of a visitor as port → 127.0.0.1 and that visitor's local port (web likewise with url). That is how the server's automatic connections point at their tunnel, so they resolve for non-admins too. Rule 2 applies to every connection: while frpc runs, a connection of your own to 127.0.0.1 or localhost and the server port of a visitor goes through the tunnel too, not to a local service on that port. While no frpc runs, every STCP connection stays as it is: a linked one opens its stored target. A connection whose port no visitor of the running frpc has as server port stays as it is as well.

Sidecar auto-start happens only in Server mode: startIfServerMode() in the tunnel store bails out when there is no session or settings.mode !== 'server'. On app exit, RunEvent::Exit in main.rs tears down the frpc process via stop_frpc.

Connect Flow

  1. User clicks Connect → initiateConnect in the connectFlow store resolves the connection with resolve_connection, without mappings too (getMappings(), empty for non-admins; see Tunnel resolution above); if that fails, it stays unchanged. Only then does it check the resolved connection (validateConnection), as the server's automatic web connections have no url until the resolution gives them one. An invalid one is reported in the status bar and not connected.
  2. For RDP the password comes next: if storePasswords is on, password_state asks the keyring; a stored password is used, otherwise the PasswordPrompt modal asks (optionally storing it via save_password). Without the password store the modal asks on Linux only. After the modal the store resolves the connection again, with user and domain from there. A stored RDP password is kept under the connection before the tunnel resolution, i.e. under the host and port from the list, not under 127.0.0.1:<local port>; open_connection_stored therefore receives that connection as credentialConnection next to the resolved one. Rust opens a stored password only for exactly the target it computes itself from the tunnel mappings the session holds (the last result of fetch_tunnels) and the running visitors; any other target ends with an error before the password is loaded. On Windows mstsc reads the password itself (TERMSRV/<address>); for tunnelled targets it finds none there yet, because it looks under 127.0.0.1:<local port>.
  3. For RDP the store assigns a correlation ID (RDP race guard) and calls open_connection, or open_connection_stored for a stored password; SSH and web go to open_connection without a correlation ID.
  4. The backend launches the RDP, SSH or web client.
  5. Then the store records the use (lastUsed) and reports the start in the status bar. The connect flow neither brings up nor tears down the tunnel: the tunnel store runs frpc.

Theming & design system

The UI follows the AdminCave design system (monochrome, True-Black dark-first, Geist font bundled via @fontsource-variable – offline/CSP-safe, no CDN, pill radii). Colours/radii/shadows are CSS custom properties in src/styles/app.css – a :root block (dark) plus a :root[data-theme="light"] block (light), value-equal to the web panel. The theme switcher (icon button in the sidebar footer next to “Settings”) flips between dark and light via the theme store; the choice lives in localStorage.ah-theme – deliberately not in the persisted Settings contract (no Rust/migration change). An inline script in the <head> sets data-theme FOUC-free before the first paint. The uPlot monitoring charts read axis/grid colours from the tokens and re-render on theme change. Default = dark.
