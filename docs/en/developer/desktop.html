Developer Guide

Desktop Client

The Desktop Client is a Tauri 2 wrapper around a Svelte 5 SPA. The Rust backend (apps/desktop/src-tauri/) exposes typed commands; the frontend (apps/desktop/ui/) consumes them through a 1:1 bridge. Since v0.32.0, in a server workspace the client is also the operational cockpit: the Infrastructure hub manages the server inventory and, per server, connections, FRP tunnels, monitoring checks, and provisioning; plus the fleet-wide Monitoring and Ansible pages. Operational writes go through the api_proxy to the AdminHelper server's REST API. Several workspaces (each a server, a sync source or local connections) run side by side, each in a window and process of its own (see Workspaces).

The desktop runs as the launcher and, per open workspace, as a workspace process of its own (see Workspaces). Only the launcher runs once: a second launch without arguments hands over to a running launcher, which brings its window to the front, and exits; if none runs, it is the launcher itself. For this, tauri-plugin-single-instance is registered in the launcher only, there as the first plugin in main.rs (on Linux through the D-Bus session bus). Workspace processes run side by side; only one at a time holds the lock of a workspace. enableGTKAppId in tauri.conf.json stays false: with a GTK app id, GApplication itself forwards a second launch to the running instance, which then runs its setup again and crashes.

Workspaces

A workspace is a working area with a fixed kind (server, sync or local; it replaces the former mode switch), a name (1–40 characters without control characters), a colour from a fixed palette and, for server and sync, a URL; several workspaces of one kind are allowed. One window is one workspace and one OS process: workspaces share neither session nor tunnel, device identity, RDP passwords, connection files or log file, and there are no views across workspaces. workspace.rs holds the workspace of the process, set once at start; whatever hangs on a workspace (data paths, keyring prefix, tunnel) fails without one (in the launcher) with an error instead of landing in the app data directory.

Launcher and workspace process

StartProcess
adminhelperLauncher: the picker (Picker.svelte) with all workspaces (colour, name, kind, host, “open”), the one used last preselected, arrow keys select, Enter opens; create and edit through WorkspaceEditor.svelte, delete. Window “AdminHelper”, smaller than a workspace window.

Ids are standard, lokal, sync and server from the migration, otherwise w-<8 hex>; every boundary (arguments, IPC, files) checks them against ^[a-z0-9-]{1,32}$ with the character class spelled out. Other arguments end with the usage line on stderr, never in the launcher. The pure function workspace::startup decides the start: first the migration, then, for a workspace process, the registry entry with its directory, then the lock, only then workspace.json. setup builds the window last (WebviewWindowBuilder; app.windows in tauri.conf.json is empty), with its title from the first frame; a process that does not start never shows one. Exit codes of a start that does not come about, each with a line a workspace process writes to stderr only (the log file of the workspace may be another process's):

CodeMeaning
1The migration failed, workspaces.json or workspace.json does not load, or the lock could not be taken. The line names file and position, never a value from it.
2Unknown workspace, or the arguments name none.
3The workspace is open in another process.

Lock: workspaces/<id>/instance.lock, a lock file of its own (File::try_lock; on Windows that is LockFileEx, which can be mandatory, hence never on a data file). A start keeps trying for up to 2 s so that the picker's short probe (is_open, gives the lock back at once) does not turn it away; the process holds the lock until it ends. The picker shows a workspace whose lock is held as “open”; it lets you open, edit and delete it only once its window is closed. The picker does not bring an open window to the front.

Opening: open_workspace sets lastUsed, starts adminhelper --workspace <id> detached (Unix a process group of its own, Windows DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP, stdio to null) and waits at most 10 s until the new process holds the lock; if it ends before or the time runs out, the picker shows the error. Then the launcher exits. Workspaces… in the workspace window (chip at the top of the sidebar, login screen) calls open_launcher: it starts the launcher, which hands over to a running one.

Marking: window title “<name> — AdminHelper”; at the top of the sidebar a chip with colour dot and name instead of the former mode badge (collapsed, only the colour dot with the name as tooltip); a 4 px colour stripe at the window edge; the confirmation dialog names colour dot and name above the question; OS notifications begin with “[<name>] ” (osNotify.ts), the title of the xfreerdp window likewise (if nothing of the name is left after sanitizing, the id stands there). The pages Infrastructure, Monitoring and Ansible show the dashboard in a sync or local workspace.

Files other processes read while one writes them (prefs.json, workspaces.json, workspace.json, secrets.json) the desktop replaces at once on every platform (temp file with the pid, sync_all, rename). If a process ends between the temp file and the rename, the next write of the same file deletes the temp file (<file name>.<pid>.tmp) once it is at least ten minutes old; a younger one, one with a future or unreadable modification time and one that cannot be deleted stay. The log files lie in the app's OS log directory: adminhelper.log for the launcher, adminhelper-<id>.log for a workspace process and its purge. A process that does not get its workspace writes to stderr only, since the log file may be another process's. The diagnostics report reads the log of its own process, names the workspace id and is called <log name>-diagnostics-<time>.txt. Inventory and playbook for Ansible are written by ansible_run, after it has loaded the playbook from the signed-in server, per run into a directory of their own, adminhelper_ansible_<pid>_<n>_<time> in the temp dir, which it creates exclusively and which on Linux and macOS only the own user can access (mode 0700); so two workspaces with the same playbook name do not overwrite each other either. Ansible reads variable and plugin directories (group_vars/, host_vars/, modules) next to the inventory and the playbook; only what the run writes lies there. On Linux the script in the terminal (linux_run_script) deletes the directory once ansible-playbook ends, whatever its exit code; if the shell ends first because the terminal is closed (SIGHUP, likewise SIGTERM), an EXIT trap deletes it once ansible-playbook has ended. If a step before the start fails (the inventory or the playbook cannot be written, or only in part, the path check of launch_ansible fails, no ansible-playbook, no terminal), ansible_run deletes the whole directory; if the fetch itself fails, it creates none. On Windows nobody deletes the directory after a started run.

Migration

migration::migrate runs at every process start under migrate.lock, simultaneous starts one after the other; if workspaces.json is there already, it does nothing. Otherwise it builds from settings.json (file missing: defaults, i.e. local; if it does not load, see below):

  • Standard (standard) of the kind of the previous mode, with its URL, interval, “Allow self-signed certificates”, for server the remembered user, and the connections of that kind.
  • Lokal (lokal) if the mode was not local and connections.local.json holds connections.
  • Sync (sync) if the mode was not sync and a sync URL is stored.
  • Server (server) if the mode was not server and a server URL is stored (with the remembered user and the certificate choice).

Every migrated workspace carries legacyKeys: true: it keeps using the keyring keys without a prefix, and stored RDP passwords and an existing device identity stay usable. Then the migration writes prefs.json (language, store passwords, RDP options, OS notifications), hands the port map entries from before workspaces (owner default) to the migrated server workspace (standard or server; at most 500 entries and 250 fallback ports, the rest goes) or drops them if there is none, and writes workspaces.json last, at once, as the commit marker (lastUsed: standard, migratedNotice: true; the picker shows the note once). Each workspace is built in <id>.partial/ and then renamed; an abort at any point is rebuilt at the next start from the old files, which stay unchanged (an older version reads them again after a downgrade and does not see changes from the workspace era). If workspaces/ is a symlink or a junction, it stops instead of cleaning up. A first start without old data makes “Standard” (local) only.

Unreadable settings.json: if it does not read or parse, the migration renames it, as it is, to settings.json.unreadable-<UTC time> (%Y%m%dT%H%M%SZ, with -2, -3 … if the name is taken; nothing is deleted) and builds on as if there were none: “Standard” only, local. The other old data goes as always: connections.local.json to “Standard”, the cache connections.json only if there is no local file (migrate_between), else it stays as an old file; the port map entries from before workspaces lapse for want of a server workspace, and prefs.json gets the defaults. The registry keeps the file name without a path in unreadableSettings; list_workspaces gives it once as WorkspaceList.unreadableSettings and clears it as it does migratedNotice, and the picker shows a note of its own on it (data-msg="unreadable-settings"). If a run stops after the rename, the next one finds no settings.json but the file set aside, and takes its name (the latest if there are more). If the rename fails (on Windows, while another process holds the file open), the migration stops as on any other error (exit 1); the check of workspaces/ runs before, so a stop there changes nothing. The warning in the log names the file, where it breaks and the new name, never a value from it. A workspace process (--workspace) does not log the migration: its logger comes only after workspace::startup, so the line is in adminhelper.log only if the launcher migrated. Renaming the file back does not migrate again while workspaces.json exists. If that is deleted too, the next run removes the directories of all migrated ids with everything made in them since and builds them anew; workspaces with a w-… id are missing from the new registry, their directories stay, and the launcher drops their port map entries. The troubleshooting in the Admin Guide therefore advises against it.

Settings: global and per workspace

Settings keeps its shape and field names (bridge, types.ts): load_settings puts it together from prefs.json and the process's workspace.json, mode being the kind; the launcher gets the prefs and defaults. Global, for all workspaces of the device: language, store passwords, RDP options, OS notifications, console for SSH and terminal options (sshConsole, terminal; the theme stays in the webview's localStorage as before). Per workspace: kind, name, colour, URL, sync interval, “Allow self-signed certificates”, remembered user; in the keyring device identity and RDP passwords; at the server the notification rules. TOFU pins (tofu|cert|<host:port>) stay global, like SSH known_hosts. The settings dialog (components/settings/: SettingsModal.svelte mounts SettingsDialog.svelte on every opening, which reads the settings once, R-0715) shows six sections on the left as a vertical tab list (arrow keys, Home/End): General (language, theme, passwords, self-signed certificates), Workspace & sync (name, colour and URL as display, interval, sign-out), RDP, Terminal (console for SSH, terminal options), Notifications (OS notifications, notification rules) and Device (device identity, token, browser certificate, pinned certificate, diagnostics). All sections stay mounted and only the active one shows; what is typed survives a switch and saving takes all of them. What belongs to the workspace carries data-scope="workspace" and the mark “This workspace”, the rest data-scope="device"; saving ends neither session nor tunnel.

save_settings never writes mode, and writes the URL only while the workspace has none (checked as in the picker; for server not while it holds a device identity); another one is an error (server URL: another origin; sync source: any other spelling). Only the picker changes name, colour and URL, while the workspace is closed; never the kind, and not to the URL of another server while the workspace holds a device identity. Every process writes the global fields under prefs.lock in a three-way merge: read anew and take over only the fields this process changed against the state it loaded last, so the change of a second window stays.

Sign-in per workspace

A server workspace asks for a sign-in when it opens (no session is restored); sync and local workspaces open without one. The login screen reads “Sign in to ● <name>”; if the workspace has a URL, it is shown as display, and a URL field (login and token enrollment) exists only while it has none. Workspaces… replaces “Continue without a server”. login and enroll_with_token take only the workspace's URL (another spelling of the same origin counts as the same); without a URL the one sent counts, which the workspace keeps after the sign-in, and at once after a successful enrollment. If it cannot keep it then, say because it got another server meanwhile, the desktop revokes the new identity at once at the issuing server and the enrollment fails. reset_device_identity, check_server_cert and reset_server_cert_pin (this one to the sync source too) bind to the workspace's URL as well; the revocation of the device identity goes over HTTPS only, otherwise it stays localOnly. Sync and local workspaces sign in nowhere and enroll no device; a sync never loads with the device certificate. Whoever syncs against their own installation under mTLS takes a server workspace.

The same sign-in only once: login refuses if another workspace carries the same normalized origin (scheme, host regardless of case, port with the default port) with the same remembered user (regardless of case); the message names the other workspace. The check is not atomic: two simultaneous sign-ins of the same user in two workspaces can both pass it (accepted).

Keyring prefix

Every workspace has a prefix of its own in front of its keyring keys (Workspace::keyring_prefix): ws:<id>| on Linux and macOS (service com.admincave.adminhelper), on Windows com.admincave.adminhelper/ws:<id>| as the target name, since a Windows credential has no service field and shares its namespace with every program of the user. This applies to the device identity (enroll|key, enroll|cert, enroll|ca, enroll|replaces) and the RDP passwords (rdp|…, see Keyring Secrets); tofu|cert|* stays global. The migrated workspaces (legacyKeys) use the keys without a prefix as before workspaces and share them. The launcher has no workspace and so neither identity nor RDP keys; writing there is an error.

Deleting

Deleting happens only in the picker and only for a closed workspace; the confirmation names it, for local with a note on the data loss. delete_workspace starts adminhelper --workspace <id> --purge and waits up to 120 s. The purge child takes the workspace's lock and context, since self-revoke, identity and keyring prefix hang on them, and so the launcher never gets a foreign prefix. Its exit code is the outcome (10 revoked, 11 localOnly, 12 notEnrolled); any other is an error, and the registry entry stays to delete again. A workspace whose workspace.json does not load or whose directory is gone can be deleted by its id. The purge

  1. first reads what it will delete or hand over: the names in secrets.json (RDP keys with its own prefix only; another name stops it rather than delete a foreign key), for a migrated workspace also the old keys derived from its connections and legacy-secrets.json. One of these files that does not load stops it before the revocation, the message naming the file; so a broken connections file refuses the deletion of a migrated workspace.
  2. for a server workspace with a URL revokes the device at the server (POST /api/enrollment/self/revoke, over HTTPS only) and deletes the identity including enroll|replaces; without a server URL an existing identity is localOnly. For a migrated workspace the identity without a prefix counts as shared if another migrated server workspace has the same origin; likewise if its own origin is unknown and another migrated server workspace exists, or if the workspace.json of another migrated workspace does not load. Then it revokes nothing, leaves the identity in place and reports notEnrolled (no identity of its own).
  3. deletes the RDP keys. A migrated workspace hands its keys without a prefix, while another migrated workspace exists, over to legacy-secrets.json in the app data directory; the purge of the last migrated workspace deletes those handed over with its own and then the file. Old keys never loaded (rdp|<conn-id>|… from before workspaces and rdp|<host>|… without an id) it derives from the workspace's connections, as reading derives them; a key without a matching connection it leaves in place. An old key that was loaded is in secrets.json anyway.
  4. releases the workspace's port map entries, deletes secrets.json and last the directory; only then does the launcher take the registry entry out.

After localOnly the picker shows the note “on this device only”. What the purge cannot derive stays in the keyring: old keys of connections that left the list or changed their address before the deletion (accepted). On Windows not even the purge of the last migrated workspace deletes generic TERMSRV/<address> entries without the marker from before workspaces: they cannot be told from entries of one's own made with cmdkey. So an entry stays that neither the takeover at a start nor deleting the password of a connection has removed (see Windows RDP passwords; accepted).

Port map per workspace and foreign ports

The port map (port-registry.json, see Local ports in the Server Workspace Flow) stays in the app data directory and applies to all processes; every entry has an owner, the id of the workspace whose frpc runs the visitor. Two workspaces with the same visitor name and server port get different local ports: if an entry of one holds the server port, the other gets a fallback port. Per owner at most 500 visitors and at most 250 ports from the fallback range 23000–23999 apply; beyond that the reconciliation refuses and the map stays as it was. So the fallback range lasts for at least four workspaces, even if a server sends many visitors. The entries of a workspace without a running tunnel stay, so its local ports are the same at the next open (SSH known_hosts, FreeRDP's certificate cache and browser cookies hang on [127.0.0.1]:<port>); they go with the deletion of the workspace and as orphans (owner without a workspace) at the launcher's start.

Foreign ports: the bindings of a process come from its own frpc. Without a tunnel of its own, though, 127.0.0.1:<port> would land at the frpc of another workspace and through it at a machine of another server. So resolve_connection, open_connection, open_connection_stored and terminal_open_ssh refuse a target on this machine whose port the port map gives another workspace and no visitor of the own frpc holds, before anything starts or a password is loaded; the message says to start the tunnel of this workspace. Targets on this machine are 127.0.0.0/8 (also in short forms like 127.1), ::1, localhost and names under it, 0.0.0.0, :: and IPv4 mapped into IPv6, for web also the host of the URL. The port that counts is the one the starter takes: for SSH the host after the last @ or an ssh:// destination, for RDP with a port in the host field (host:port, [IPv6]:port) both ports, since it is not verified which one FreeRDP and mstsc take. A host the check cannot read (an IPv6 address with a zone, host:port:port, a user in the RDP host, say) it refuses while another workspace holds ports: user and port belong in their own fields.

Accepted residual risks: a name that points at this machine only through DNS, /etc/hosts or an ssh_config alias, and a web URL that redirects to a foreign loopback port, the check does not detect. Through the visitors it sends its workspace, a server can also block local ports of another workspace; that fails safe (a refusal, never a connection elsewhere).

Tunnel runtime files

visitor.toml and the exported device identity (identity/) lie in workspaces/<id>/run/ (Unix 0700) and only while the tunnel runs: stop_frpc empties run/ (at sign-out, at a change of sign-in and at RunEvent::Exit too), and so does a reconciliation after which no frpc runs. Before the first write of a process, the reconciliation clears what an aborted run left. Before that it stops a frpc that still runs on the visitor.toml there (frpc does not end with the process that started it): through POST /api/stop of its admin API with the credentials from webServer, only if that head is exactly the desktop's (127.0.0.1, user adminhelper, a hex password), then it waits at most 2 s for the admin port to close. If no frpc answers there, it refuses, or there is no such head, the reconciliation goes on as without. Both assume one process per workspace, which the lock ensures. On Windows frpc ends with the desktop process already, on any path, after “End task” or a crash too: right after the start the desktop puts frpc into a job object with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE whose only handle the process holds until it ends. If that fails, a warning goes to the log, and the reconciliation of the next start stops frpc as above. If run/ is a symlink or a junction, the desktop does not empty it but reports an error. Two exceptions: the runtime files of earlier versions in the app data directory go only at the first reconciliation of a workspace process. And if frpc ends by itself (a crash, say), the files stay until the next reconciliation, stop or exit of the app.

When a command fails, invoke rejects with the object {code, message} (AppError in src/error.rs): message is the text for the human, code the stable code the UI branches on – ERR_VALIDATION, ERR_IO, ERR_CONNECTION, ERR_KEYRING, ERR_JSON and ERR_SESSION_EXPIRED by variant, ERR_MTLS_CERT_REQUIRED when the gateway refuses the login without a device certificate (enforced mTLS); a network error carries ERR_TLS_UNKNOWN_ISSUER (certificate without a trusted CA), ERR_TOFU_PIN_MISMATCH or ERR_CA_PIN_MISMATCH (pinned certificate changed), or else ERR_NETWORK. When the server answers api_proxy or login with a non-2xx, the refusal also carries status; code is then the server's code or ERR_HTTP, message the text of its detail (for a 422 the msg texts, without the prefix <code>: , redacted), without a readable text HTTP <status>. Codes only the client gives (TLS, pins, ERR_MTLS_CERT_REQUIRED) are not taken from the server. Transition for servers without code: when detail starts with ERR_CERT_REVOKED: , ERR_CERT_USER_MISMATCH: or ERR_CERT_SERVER_MISMATCH: , that prefix counts as the code. The bridge turns it into an IpcError with code; the UI reads the code only through errCode, never from the text. A refusal of Tauri itself (a missing argument, say) arrives as text without a code and becomes a plain Error.

RDP Race Guard

Clicking Connect several times in quick succession leaves multiple RDP attempts in flight – and a late rdp-error event from an abandoned one would mark the attempt that is actually running as failed. The Desktop Client therefore assigns a correlation ID per attempt (crypto.randomUUID()) and matches every error event back to its attempt: it marks only that attempt as failed (markRdpError). An event whose correlation ID matches no open attempt marks no other attempt; the status bar shows its message all the same. An event without a correlation ID marks every open attempt. The ID goes to open_connection or open_connection_stored as correlation_id. Implementation in apps/desktop/ui/src/lib/stores/connectFlow.ts, tests in apps/desktop/ui/src/lib/stores/connectFlow.test.ts.

Keyring Secrets

Passwords are stored in the OS keyring, never in the local connection file:

  • Linux: secret-service (GNOME Keyring / KWallet)
  • macOS: Keychain
  • Windows: Credential Manager

Service com.admincave.adminhelper; an RDP password sits under the account <prefix>rdp|<id>|<host>|<port>|<user>|<domain> (<prefix> is the workspace's keyring prefix, see Workspaces, empty in migrated workspaces; <id> is the connection's id; host, user and domain lower-cased), so it belongs to exactly one connection of one workspace; a connection without an id or with | in it stores none. On Windows it sits in the app's namespace too, as a generic entry in the Credential Manager with this key as its target name; only a start of mstsc writes TERMSRV/<address> (see Windows RDP passwords). The keyring cannot list its entries, so every workspace keeps the names of its RDP keys (never the passwords) in secrets.json: saving enters the name before the key, deleting takes it out after, and deleting the workspace deletes the keys named there. On Linux and macOS the app reaches the keyring through keyring-core with the platform's store crate (Secret Service through zbus-secret-service-keyring-store, Keychain through apple-native-keyring-store), with a store per call (keyring_store::os_entry): a Secret Service connection kept by the process would stay broken after the service restarts. A Secret Service that cannot be reached is a read error, not a missing entry.

Only a migrated workspace reads keys without a prefix. A password an earlier version stored under rdp|<host>|<port>|<user>|<domain> counts as stored there for every connection to that target until the first one opens it: that connection takes it over under its own account and the old entry is deleted. This does not apply to targets on this machine (localhost and names under .localhost, loopback and unspecified addresses) such as the server's automatic connections over 127.0.0.1: connections of different servers can name the same such target, so no connection reads or takes over an old entry for it, and its password is entered once more per connection. When a migrated workspace loads a key without a prefix, it enters its name in its secrets.json, so the purge of the last migrated workspace finds it (see Deleting); if secrets.json does not load, a migrated workspace therefore fails the RDP start with a stored password too, not only saving and deleting. Deleting removes the connection's entry and an old entry of the same target.

Windows RDP passwords

mstsc takes no password on its command line; it looks for stored credentials in the Credential Manager under TERMSRV/<address> (not verified for generic entries, see below), a namespace every program of the user shares. So that a stored password neither lies there for good nor applies to every connection to that address (from another workspace or started by hand too), the desktop writes it there for the start only (password.rs: termsrv_plan, start_mstsc):

  • Saving puts the password in the app's namespace under the workspace's RDP key (see Keyring Secrets), never under TERMSRV/…. password_state reports that entry; in a migrated workspace a generic TERMSRV/<listed address> from before workspaces counts as stored as well, but only without the app's marker and not for an address on this machine. Deleting removes the app's entry, in a migrated workspace TERMSRV/<listed address> too.
  • Start with a stored password (open_connection_stored, after check_credential_connection): Rust writes TERMSRV/<address> for the address in the .rdp file (without the port for 3389, so for a tunnel 127.0.0.1:<local port>) as a generic entry with CRED_PERSIST_SESSION and the app's fixed marker in the Comment field, starts mstsc and deletes the entry 60 s after the start; at once if the start fails; at RunEvent::Exit if the process ends before; otherwise at the latest with the sign-out of the logon session. It deletes only an entry with the marker and the same user. On Windows Rust drops a typed password and mstsc asks itself; so if you tick “Remember password” in the password dialog and saving succeeds, the desktop starts through the stored password.
  • An existing entry without the marker (an own cmdkey entry, or an old entry from before workspaces) for a target off this machine: the app writes and deletes nothing, mstsc takes the existing one, and a log line says so at every start. A rest of its own with the marker (after a crash) a start with a password overwrites, and a start without one removes it first.
  • Targets on this machine (loopback, so every tunnel target): before every start, with or without a stored password, Rust deletes both types (generic and the domain password mstsc saves itself), with or without the marker, under both name forms of the address (TERMSRV/<host>:<port> and TERMSRV/<host>), for a port in the host field also under those of the host part with either port and without one. Such an entry would otherwise go to the server now behind that port. Entries for other targets stay.
  • Holds: every start holds the names its mstsc may look up, in termsrv-holds.json in the app data directory, across all workspace processes (check and hold under one file lock): a start with a password until its entry is deleted, one without until it expires (60 s plus a 10 s margin). If another connection (in the same or another workspace) would, meanwhile, write a name the hold may look up, or look up or delete one it wrote, the app refuses the start (“another RDP connection holds the Windows credential … try again in N s”). The same connection may start again and extends the time; an expired hold counts as free. Two tunnel starts on different local ports do not block each other.
  • Taking over old entries: when a migrated workspace starts a connection without a tunnel for which the app's namespace holds no password yet, but a generic TERMSRV/<listed address> without the marker exists for the same user (DOMAIN\user or user) and not for this machine, Rust moves the password into the app's namespace (key and secrets.json as when saving) and then deletes the old entry; only then does the start run as above. If saving fails, the start fails and the old entry stays. An old entry of another user stays (mstsc takes it), and so does one for a connection with a tunnel (mstsc then asks at the start as before workspaces). After a takeover, an mstsc started by hand for that address asks for the password.

Accepted residual risks: once a password is in the app's namespace (taken over or saved), it goes through a tunnel at the next start if the workspace's server later creates a tunnel mapping for that connection; the server decides the route of its connections. In migrated workspaces the keys on Windows carry no app prefix: their target name rdp|… lies in the namespace every program of the user shares, and Windows compares it regardless of case. Saving, and the purge of the last migrated workspace, which derives old keys from the connections the server delivered, can therefore hit an entry of the same name that does not come from the app. Other programs of the user can read a generic entry anyway, in the app's namespace too.

Not verified on Windows (mstsc): the CI job rust-windows checks the credential calls; no Microsoft source documents that mstsc reads such an entry. Open are: (1) whether mstsc uses a generic TERMSRV/… entry, also with Credential Guard and on a domain device against a target that identifies only through NTLM; (2) whether it finds entries with CRED_PERSIST_SESSION; (3) when it reads the entry and whether 60 s suffice; (4) which name it looks up at a port other than 3389, IPv6 too, and which port it takes for a port in the host field; (5) which entry counts if a generic and a domain entry of the same name exist; (6) whether a reconnection after the time ran out succeeds without asking.

Embedded RDP (backend)

Besides the operating system's RDP client (Connect Flow), the desktop carries an embedded RDP client: IronRDP (MIT or Apache-2.0) as a Git dependency at a fixed revision, the code in src/rdp_embedded/. So far there is only the backend. No UI calls the commands, the operating system's client remains the only way to open an RDP connection; tab, picture and certificate dialog follow in a later stage.

  • Session (session.rs): a thread of its own per session with IronRDP and the frame WebSocket. TLS with CredSSP only (no standard RDP security), graphics pipeline (GFX) on, bulk compression off, no clipboard, no drives, no audio, a fixed desktop of 1280×720 (no adjustment to the window size). H.264 is there on Windows only (Media Foundation through ironrdp-egfx-native).
  • License gates (license_gate.rs, a test in the plain cargo test): aws-lc-rs, aws-lc-sys and openh264-sys2 are absent from the built dependency graph (cargo tree), ring is present. IronRDP offers all three behind features; one flipped feature in Cargo.toml turns the test red.
  • Password: from the app keyring only (load_password_keyring), never through the TERMSRV path of the Windows client; without a stored password the start refuses. The backend holds it in Zeroizing, IronRDP however as a plain String, and every reconnect gets a fresh copy.

Frame WebSocket

frame_ws.rs opens one server per session on 127.0.0.1, the system picks the port (ws_port); the CSP allows ws://127.0.0.1:* for it.

  1. Login: as its first text message the client sends the session's token (32 bytes from ring's random generator, hex), compared in constant time, within 5 s. Up to eight logins run at once; a wrong token or none closes only that connection. The first valid one wins, after that the port no longer listens. There is no Origin check: the token reaches the webview only over Tauri IPC, and a local process sets the header freely anyway.
  2. Picture: one binary message per picture. The header is seven u16 little-endian (version 1, x, y, width, height, desktop width, desktop height), followed by the RGBA pixels of the rectangle row by row. The first picture and every size change send the whole desktop.
  3. Back pressure: the next picture goes only after the receipt {"t":"ack"}. Whatever changes until then the server merges into the enclosing rectangle instead of buffering pictures.
  4. Input as text JSON: {"t":"key","code":<scancode>,"ext":<E0 prefix>,"down":bool}, {"t":"mouse","x":…,"y":…,"buttons":<bit mask>,"wheel":…} (bit 1 left, 2 right, 4 middle; coordinates in the desktop; the wheel with the sign of the RDP convention, clamped to -256 to 255) and {"t":"close"}. The server drops unknown or malformed messages without ending the session. When IronRDP's input queue is full, the message is dropped.

When the client closes the WebSocket or sends a message over 4 KiB, the session ends with disconnected/closed. A failure of the WebSocket server ends it with failed/connect, the same code as a failed RDP connect. A session no client ever logs in to runs until rdp_session_stop.

Watchdog

watchdog.rs detects a stalled picture. The pure state machine waits after every login for the first picture, and after an input the desktop answers with a picture, for the answer. Such an input is a key press other than modifiers and locks, or a mouse button press; movement and wheel do not count, because a quiet desktop often answers them without a picture. If no picture comes within 10 s, the session reconnects (reconnecting), and only an answered input resets the counter. The fourth stall in a row ends the session with failed/watchdog.

False alarm: a key press or click can also stay without a picture (a password prompt without echo, a click into nothing); the session then reconnects needlessly after 10 s. During IronRDP's own reconnect the watchdog does not wait. If that hangs, the session stays in reconnecting until IronRDP gives up or it is stopped.

TLS certificate pinning (TOFU)

When the user enables “Allow self-signed certificates”, TLS verification is not turned off (the old danger_accept_invalid_certs(true) disabled chain and hostname checks with no pinning – open to MITM). Instead tofu.rs pins the server certificate using the trust-on-first-use model (like SSH known_hosts):

  • Single choke point: on the self-signed path http_client::build_client builds a reqwest client with a custom rustls ServerCertVerifier (tls_backend_preconfigured, ring provider). This covers every credential-carrying path – login, refresh, api_proxy and the tunnel/connection fetches. The sync fetch builds its client through http_client::build_client_without_identity, without the device identity: with the same TOFU verifier on the self-signed path, against the public roots otherwise.
  • No crypto provider in reqwest: reqwest runs with rustls-no-provider, without aws-lc. Every client therefore gets a preconfigured rustls config in http_client::with_timeouts (ring provider, roots from webpki-roots, TLS 1.2 and 1.3); the TOFU and mTLS paths then replace it with their own. A client not built through with_timeouts (reqwest::Client::new(), say) panics when it is built.
  • The session's choice: login records whether “Allow self-signed certificates” was on at sign-in. Every request of the session (renewal, api_proxy, connections, tunnel, notification stream and the browser export) builds its client with that value, not with one from the UI. A change of the setting therefore takes effect at the next sign-in. An enrolled device uses its pinned CA regardless (see Enrolled state).
  • First contact without the opt-in (ERR_TLS_UNKNOWN_ISSUER): while “Allow self-signed certificates” is (still) off, build_client validates against the public roots (webpki). Against the standard install's internal PKI leaf that fails with UnknownIssuer by design; error.rs detects exactly this case by downcasting through the reqwest source chain (the rustls error hangs off io::Error::get_ref(), not the source() chain) and replaces the raw rustls message with the stable code ERR_TLS_UNKNOWN_ISSUER plus an actionable hint. The login screen then opens a trust dialog: Trust & continue persists allowSelfSignedCerts=true and retries the sign-in or token enrollment via the TOFU path; cancelling shows the message (without the code) inline. The pin verifiers are unaffected – they never emit a raw UnknownIssuer: a changed pin reports ERR_TOFU_PIN_MISMATCH (TOFU) or ERR_CA_PIN_MISMATCH (the CA pin of device enrollment), and a keyring the TOFU pin cannot be read from or stored in reports a message without a code.
  • Other network errors reach the UI with their cause chain (the TOFU verifier's pin-mismatch message or Connection refused, say), but without the request URL: reqwest names it in full in its message, path and query included, and the sync calls a user-entered URL. From<reqwest::Error> in error.rs strips it (without_url) before the error becomes AppError::Network; every reqwest error goes through that conversion. The same holds for the log lines that write an AppError.
  • Pin = SHA-256 of the leaf DER. Captured on first connect and stored in the OS keyring (key tofu|cert|<host:port>, service com.admincave.adminhelper) with an in-memory cache so the enforcement path does not hit the keyring per request. The pin only counts once it is stored in the keyring; the cache only holds stored pins. If the pin cannot be read from or stored in the keyring (a locked keyring, say), the client refuses the connection without pinning, with a message that names the keyring rather than a certificate change (no ERR_TOFU_PIN_MISMATCH, so the login screen offers no pin reset). Afterwards: accept only on an exact fingerprint match, otherwise reject (possible MITM). Hostname/expiry are intentionally irrelevant – the pin is the identity.
  • The handshake signature is still verified against the presented public key (delegated to the ring provider), so a captured certificate cannot be replayed without its private key.
  • Recovery after a legitimate certificate rotation: reset_server_cert_pin clears the pin (keyring + cache) – UI button “Reset pinned certificate” in settings; it asks first with the same warning as the login screen (login.resetPin.confirmMitm).
  • Enrolled state (mTLS): once the device is enrolled (A5), every request goes through enrolled_client – the CA pin in enrollment.rs (hostname-agnostic), not the leaf pin. The exception is the sync fetch (sync.rs): it loads only in a sync workspace and only that workspace's stored sync URL (workspace::sync_url); if the UI names another one, even of the same origin with another path or query, sync_connections refuses, and the error names no URL. It always loads without the device identity, through http_client::build_client_without_identity, like a device that isn't enrolled (TOFU pin when self-signed certificates are allowed, public CA otherwise). If the server certificate no longer chains to the CA pinned at enrollment (server reinstall / re-created PKI → BadSignature or UnknownIssuer), the CaPinVerifier returns an explicit danger message instead of the raw rustls error. After a successful chain check it accepts only a server certificate issued by the access intermediate (issuer CN AdminHelper Access Intermediate, like isAccessIntermediate in the agent); a leaf of another intermediate under the same root is an error without ERR_CA_PIN_MISMATCH. Recovery: reset_device_identity first revokes the device at the workspace's server (over HTTPS only) with this very certificate: POST /api/enrollment/self/revoke through the mTLS client (enrolled_client), without a JWT. Only then does it clear the workspace's mTLS identity (enroll|key/enroll|cert/enroll|ca behind its keyring prefix) and the TOFU pin. The result is a ResetOutcome: revoked (the server revoked the device or had already refused the certificate as revoked), localOnly (the server did not revoke it, e.g. because it was unreachable) or notEnrolled (no identity). On localOnly the client keeps the fingerprint of the old certificate in the keyring (enroll|replaces) and names it as replaces at the next enrollment; the UI adds the hint “on this device only”. The UI button “Reset device identity” sits in two places: in the settings (server workspace, only shown when enrolled and signed in; with a danger confirmation) and on the login screen on ERR_CA_PIN_MISMATCH (also with a danger confirmation), ERR_CERT_USER_MISMATCH and ERR_CERT_REVOKED (with a confirmation). Afterwards the device enrolls again with a new one-time token; without an identity the settings show the token field for it.
  • Verification: a real-handshake test in tofu.rs (tokio-rustls server, two distinct certificates) proves first-use pinning, reconnect with the same cert, rejection on a cert change, and refusal of a first connection whose pin cannot be stored.
  • RDP pins (embedded RDP): rdp_embedded/tofu.rs uses the same keyring store (key tofu|cert|<identity>) with an identity of its own: rdp/<workspace id>/<host>:<port>, through a tunnel rdp/<workspace id>/<tunnel>/<host>:<port>. Host and port are those of the stored connection, not of the local tunnel endpoint, because private addresses repeat between sites; the host is lowercased, IPv6 in brackets, % and / escaped, and without a port 3389 applies. Unlike the server pin, a first contact pins nothing: the session ends with certificate and reports the fingerprint, and only rdp_trust_certificate stores the confirmed one. rdp_session_start reads the pin before connecting; if it cannot be read, the call refuses with ERR_KEYRING.
    • IronRDP takes no rustls verifier of ours, it calls a callback only after its strict check (platform roots and server name) has failed. Self-signed RDP certificates, the normal case, always reach the callback; a certificate a platform CA issued for the host name passes without a pin. If the platform roots cannot be loaded, the session ends beforehand with failed/tls. The callback only compares values and only for the session's endpoint.
    • The connection's trust_cert (“Trust certificate”) accepts any certificate without a dialog, like /cert:ignore when starting xfreerdp, and leaves the pins alone.
    • Outside the callback: IronRDP accepts the certificate a redirecting server reports for the redirection target without asking; the session follows no redirection and ends with failed/redirect. When SSLKEYLOGFILE is set, IronRDP's rustls configuration writes the TLS session keys to that file.
  • Accompanying hardening: the session's token only goes to the session's origin (token-destination pin in session::authed_send, checked on the request as built); launch_ansible only accepts inventory and playbook in one and the same directory that lies directly in the temp dir, starts with adminhelper_ansible_ and on Linux and macOS grants group and others nothing (after resolving .. and symlinks), so that ansible-playbook only runs files of a run directory of our own and a failed start only deletes such a directory – this does not check the playbook's content, which ansible_run loads itself from the signed-in server; the webview CSP connect-src is narrowed to 'self' ipc: http://ipc.localhost ws://127.0.0.1:* (ws://127.0.0.1:* reaches only services of the own machine and is there for the frame WebSocket of the embedded RDP, which demands a token; no https: exfiltration channel: server traffic goes through api_proxy and the other commands in the Rust process; a workspace without a stored URL takes one from its window once, at the first save of the settings or the first sign-in (storage::meta_with) or enrollment (storage::keep_enrolled_url); after that only that one counts, and the sync loads only from it).

FRP Sidecar

Tauri capabilities are scoped: frpc can only be spawned from the app binaries directory. At build time the matching target binary (frpc-x86_64-unknown-linux-gnu, frpc-aarch64-apple-darwin, …) must be dropped into apps/desktop/src-tauri/binaries/.

Server Workspace Flow

In a server workspace (kind server, in Settings as mode = 'server') the client loads connections from the AdminHelper server via JWT and brings up the FRP tunnel itself. The steps wire together across auth.rs, session.rs, sync.rs, frpc.rs and tunnel.rs:

  1. Login – login posts to /api/auth/login, then fetches /api/auth/me and keeps the session only in the memory of the Rust process (session.rs): server URL, user, access and refresh token and the certificate choice of the sign-in. The UI gets only serverUrl, username and isAdmin, never a token. Earlier versions kept the tokens in the OS keyring (auth|jwt, auth|refresh, auth|server_url); the start removes those entries once (best effort). Implemented in auth.rs and session.rs.
  2. Login on every start – For security the client no longer restores a stored session on startup: opening a server workspace always requires a fresh password login (the workspace's URL is fixed, the username pre-filled, persisted in its workspace.json as url/lastUsername – never the password; see Sign-in per workspace). The session ends with the process. While it runs, every authenticated request (api_proxy, connections, tunnel mappings, visitor bundle, the token for the browser export, notification stream) goes through session::authed_send: on a 401 it renews the session at /api/auth/refresh and repeats the request once. Only one renewal runs at a time; a request that meets a 401 meanwhile waits and repeats with the new token instead of sending the already rotated refresh token a second time (the server would end the whole session for that). If the renewal fails or takes longer than 30 s, the session ends and Rust sends the Tauri event session-expired. The UI then signs out like the logout button (logoutAndReload: stop the tunnel, sign out, reload the window), and the login screen shows the notice “Session expired — please sign in again.” Rust ends frpc itself already: every sign-in, every sign-out and the end of the session by a failed renewal stop it in the backend (the listener SessionState::on_sign_in_change, set to stop_frpc in main.rs); a renewal that succeeds leaves it running. A reconciliation under way at that moment starts nothing afterwards. The UI still stops the tunnel as well. The opportunistic mTLS cert renewal (maybe_renew) now hangs off a successful login (previously off the removed check_session).
  3. Load connections – fetch_connections_jwt retrieves the list via authenticated_get (through session::authed_send, see above) from /api/connections and writes it to the workspace's server/sync cache (connections.json in its data directory). A local workspace uses a separate store (connections.local.json) that no server or sync fetch overwrites; every workspace has files of its own. Passwords are never part of the sync data.
  4. Start & reconcile tunnel – refresh_tunnel fetches the visitor bundle (TOML) from /api/frp/generate/visitor-bundle and brings frpc in line with it; start_tunnel is the same reconciliation and returns only the status. A lock in the backend runs the reconciliations one after another. It compares the parsed server TOML, checked and rewritten to local ports (see Local ports below), with the one the running frpc applied, not the text: if no frpc runs, it starts one (started). If it runs for another sign-in (server URL or user) than the one the bundle was fetched for, it restarts (restarted), whatever changed. If the root table without visitors changes (serverAddr, serverPort, user, auth.*, transport.*, so a token rotation too), frpc restarts (restarted), because frp reads these values only at start. If only the visitors change, frpc hot-reloads them (reloaded); unchanged visitors and their connections stay up. Otherwise everything stays as it is (unchanged). If the server answers 404 (no visible STCP tunnels), the reconciliation stops frpc without an error message (stopped). If it answers 403 (it refuses the device or user access, say after a revocation), the reconciliation stops frpc just the same (stopped) and returns refused = 403 with it; the UI reports the refusal once, with the code, in the status bar, and again only after a reconciliation without a refusal or a new activation. If renewing the session fails, the session ends and frpc with it. Any other failure (network, 5xx, a 401 despite a renewed session, a TOML the allow-list rejects) leaves the running frpc untouched. The allow-list admits only what the server's generator emits: STCP visitors with unique names that listen on 127.0.0.1 only (bindAddr with that value alone, bindPort a port from 1 to 65535 that no other visitor has), under auth only method (with the value token alone) and token, under transport only tls.enable, tls.trustedCaFile, tls.certFile and tls.keyFile; any further key is rejected. If the TOML does not parse, the error message names only line and column, not the content of the line. Local ports: after the check the desktop rewrites every visitor to bindAddr = "127.0.0.1" and, as bindPort, the local port from the port map (port_registry.rs): port-registry.json (0600) in the app data directory, which all AdminHelper processes of the user share under a file lock, keyed by owner (the workspace's id) and visitor name (see Port map per workspace and foreign ports). The server's bindPort is the preferred port: if no other entry of the map holds it and it binds on 127.0.0.1, the visitor gets it, otherwise the first free port from 23000–23999; a server port below 1024 goes straight to this fallback range. The assigned port stays as long as the visitor is in the bundle, without a new bind test, since the desktop's own frpc holds it. Only a reconciliation while no frpc runs (at start and after it ended) tests the assigned ports too and gives one that someone else has taken meanwhile a new port. Into the root of the checked server TOML the desktop puts a local head: loginFailExit = false, so frpc keeps trying while frps is unreachable, and frpc's local admin API (webServer on 127.0.0.1, a free port, user adminhelper, a password of 32 random bytes). Every start and restart gets a new port and a new password; a reload keeps both. GET /api/reload with Basic auth triggers the reload (no proxy, 5 s timeout); if it fails, frpc restarts. The final visitor.toml (0600) lives in workspaces/<id>/run/ while frpc runs (see Tunnel runtime files), next to the exported device identity (identity/; the {{IDENTITY_DIR}} placeholder in tls.trustedCaFile, tls.certFile and tls.keyFile is rewritten to the absolute path, the key with 0600) whenever the checked table holds transport.tls, be it as a header, in dotted keys or inline; frpc runs as a sidecar with frpc -c <config>. frpc gets exactly what was checked: the desktop does not write the server's text but generates visitor.toml from the checked and rewritten table, head included, every string on one line; it rejects a value with a line break. frp renders the config file as a Go template before it reads the TOML, so the desktop rejects a server TOML (with the identity path filled in) or a generated config that contains {{.
  5. Status & events – tunnel_status returns running, visitor_name, connected_since, visitors (names of the visitors the running frpc applied) and bindings (name, server port and local port of each visitor); without a running frpc both lists are empty. The sidecar process emits the Tauri events frpc-terminated and frpc-error; the tunnel store (stores/tunnel.ts) listens for them and feeds the status indicator (TunnelIndicator.svelte) with the UI states connecting / connected / disconnected. Only the running frpc process announces frpc-terminated and frpc-error: if after a restart (stop → start) the old process ends or still reports an error only once the new one runs, no event reaches the UI, and the indicator does not show the running tunnel as disconnected. A stop silences the stopped process the same way: neither its late end nor a late error switches the indicator back to disconnected. While a server session is active, the tunnel store reconciles right away and then every 60 s (refresh_tunnel, then fetch_tunnels; if that fails, the old mappings stay). Only one reconciliation runs at a time: a tick that meets a running one is skipped; refreshNow() (from the tunnel dialog after create, update and delete) queues exactly one follow-up behind it. stopped sets the indicator to idle without a message, and the store loads the mappings all the same; a failed reconciliation leaves the indicator as it is (only a failed first start becomes disconnected) and reports once per series of failures. If frpc ends unexpectedly (frpc-terminated or frpc-error while the tick is active), the indicator becomes disconnected, and a reconciliation restarts frpc after 5 s, each further one after 10, 20, 40 and at most 60 s. The series ends only once a restarted frpc has held for a whole tick, and brings at most one message. A reconciliation while a restart is due does not change the indicator: its status may predate the end of frpc. stop() ends the tick and any planned restart and clears the mappings. On disconnected, TunnelIndicator.svelte shows the Reconnect button: reconnectNow() brings a planned restart forward (as a follow-up behind a running reconciliation), lets the pauses begin at 5 s again and does nothing without an active tick; until its reconciliation is through, the button is disabled.
  6. Tunnel resolution – fetch_tunnels retrieves the mappings from /api/frp/tunnels, without STCP tunnels too (after stopped), as HTTPS tunnels need no frpc; admins read all of them, other users the enabled tunnels of the servers assigned to them. resolve_connection resolves in Rust (tunnel.rs), with these mappings and the bindings of the frpc that runs for the current sign-in (server URL and user), by two rules: (1) if the connection has a mapping (connection_id), it decides: stcp → host = 127.0.0.1, port = the local port of the visitor whose server port is the mapping's visitor_port (web also url = http://127.0.0.1:<port>); https → url = https://<custom-domain>. (2) Without a mapping, literally: host 127.0.0.1 or localhost and the server port of a visitor as port → 127.0.0.1 and that visitor's local port (web likewise with url). That is how the server's automatic connections point at their tunnel, so they resolve for non-admins too. Rule 2 applies to every connection: while frpc runs for the current sign-in, a connection of your own to 127.0.0.1 or localhost and the server port of a visitor goes through the tunnel too, not to a local service on that port. While no frpc runs for the current sign-in, without a session too, every STCP connection stays as it is: a linked one opens its stored target. A connection whose port no visitor of the frpc of the current sign-in has as server port stays as it is as well. A target on this machine at a port the port map gives another workspace and no own visitor holds, resolve_connection refuses (see Port map per workspace and foreign ports).

Sidecar auto-start happens only in a server workspace: startIfServerMode() in the tunnel store bails out when there is no session or settings.mode (the workspace's kind) is not 'server'. On app exit, RunEvent::Exit in main.rs tears down the frpc process via stop_frpc.

Connect Flow

  1. User clicks Connect → initiateConnect in the connectFlow store resolves the connection with resolve_connection, without mappings too (getMappings(), empty for a user without an assigned server with an enabled tunnel; see Tunnel resolution above). If Rust refuses the connection there (a port of another workspace, say), the status bar reports the reason and nothing goes on: no password dialog, no URL check, no start; open_connection would refuse the same target anyway. Only then does it check the resolved connection (validateConnection), as the server's automatic web connections have no url until the resolution gives them one. An invalid one is reported in the status bar and not connected.
  2. For SSH, sshConsoleFor picks the console: the one chosen for this start (the arrow on the Connect button), else sshConsole of the settings, and while they have not loaded the default embedded. In the AdminHelper terminal, openTerminal in the terminals store opens a tab and starts ssh through terminal_open_ssh; the tab shows how the start goes, the status bar reports only a failure, and only a start that worked records the use (lastUsed). The steps below apply to SSH in the OS terminal, RDP and web.
  3. For RDP the password comes next: if storePasswords is on, password_state asks the keyring; a stored password is used, otherwise the PasswordPrompt modal asks (optionally storing it via save_password). In a server workspace the modal offers “Remember password” only for a connection the server already keeps (its id is in the list): one not saved yet (“Connect” before “Save” in the editor) has a client id that the server replaces with its own on save, and a password under it would belong to no connection. The typed password then holds for this start only. Without the password store the modal asks on Linux only. After the modal the store resolves the connection again, with user and domain from there; if Rust refuses it now, the status bar says so and nothing starts. If “Remember password” is ticked in the modal and save_password succeeds, the store starts through the stored password (open_connection_stored), otherwise with the typed one. A stored RDP password is kept under the connection before the tunnel resolution, i.e. under the host and port from the list, not under 127.0.0.1:<local port>; open_connection_stored therefore receives that connection as credentialConnection next to the resolved one. Rust opens a stored password only for exactly the target it computes itself from the tunnel mappings the session holds (the last result of fetch_tunnels) and the visitors that run for the current sign-in, all from one state of the session; any other target ends with an error before the password is loaded. On Windows only this path gives mstsc a password: Rust writes it for the start under TERMSRV/<address> of the resolved address, so for tunnelled targets 127.0.0.1:<local port> (see Windows RDP passwords); a typed one Rust drops there, and mstsc asks itself. A typed password reaches the Rust process as text over the IPC, a stored one Rust reads from the keyring; from there it goes to xfreerdp via stdin on Linux and macOS, and into the Credential Manager on Windows. Rust zeroes the copy it builds for that (the line for stdin or the UTF-16 value for the Credential Manager) afterwards with zeroize; the desktop does not overwrite the string from the IPC, the command arguments, the strings from the keyring or the session's tokens in memory.
  4. For RDP the store assigns a correlation ID (RDP race guard) and calls open_connection, or open_connection_stored for a stored password; SSH and web go to open_connection without a correlation ID.
  5. The backend launches the RDP, SSH or web client.
  6. Then the store records the use (lastUsed) and reports the start in the status bar. The connect flow neither brings up nor tears down the tunnel: the tunnel store runs frpc.

Theming & design system

The UI follows the AdminCave design system (monochrome, dark-first with a soft black #17181b instead of true black, Geist font bundled via @fontsource-variable – offline/CSP-safe, no CDN, pill radii). Colours/radii/shadows are CSS custom properties in src/styles/app.css – a :root block (dark) plus a :root[data-theme="light"] block (light), using the design system names (--bg, --surface, --surface-raised, --surface-inset, --text-muted, the status pairs --success/--success-bg/--success-border and so on, --radius-*, --space-*, --dur-*, --ring). The older names (--bg-surface, --bg-panel, --text-faint, --sp-* …) stay as aliases of these tokens until no page uses them; src/styles/tokens.test.ts pins both sets and checks that every var(--x) under src/ names a property declared somewhere there. Under prefers-reduced-motion every duration is 0. Icons come from Lucide (@lucide/svelte, one import per icon); only the brand logo stays inline SVG. src/components/ui/ is the component library of the design system: Badge, Button, Callout, Checkbox, CodeBlock, ConfirmDialog, Dot, EmptyState, FormField, IconButton, Input, Kbd, Menu, MetaList, Modal, Panel, Pill, RadioGroup, SearchField, Segmented, Select, Skeleton, Slider, Spinner, Switch, Tabs, Tag, Toast, Tooltip. New pages build on it instead of drawing their own buttons, fields or dialogs; existing pages move over when they are touched anyway. The theme switcher (icon button in the sidebar footer next to “Settings”) flips between dark and light via the theme store; the choice lives in localStorage.ah-theme – deliberately not in the persisted Settings contract (no Rust/migration change). An inline script in the <head> sets data-theme FOUC-free before the first paint. The uPlot monitoring charts read axis/grid colours from the tokens and re-render on theme change. Default = dark.
