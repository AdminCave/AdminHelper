Admin Guide

Overview

This guide is aimed at operators who install, configure, and maintain AdminHelper. It covers the server, reverse proxy, agents, monitoring stack, FRP tunnel, and day-to-day operations.

Stack at a Glance

Server

FastAPI monolith with PostgreSQL 17 + Redis, per-module routers, Alembic migrations, APScheduler, hook system.

Web Panel

Svelte 5 SPA served by the server, hash router, i18n DE/EN.

Desktop Client

Tauri 2 + Rust + Svelte 5, OS keyring, RDP/SSH/web launcher. In a server workspace it is also the operational cockpit: server inventory, connections, tunnels, monitoring, and Ansible are managed here.

Agents

Go-Agent (apps/agent/) for Linux & Windows – monitoring, FRP, provisioning.

Monitoring

Dedicated FastAPI service, VictoriaMetrics storage, agent push + scheduler pull.

FRP

Managed mTLS PKI (10 y CA / 1 y client certs), TCP/HTTP/STCP tunnels.

Reading Order

  1. Installation – Docker Compose setup, reverse proxy, first login.
  2. Operations & Config – Environment variables, data directories, backups, logging.
  3. Users & Access – Roles, API keys, rate limits, audit log.
  4. Agent Deployment – Install Linux/Windows agents, provision flow.
  5. Monitoring – Check types, alerts, charts (managed in the desktop client, server workspace).
  6. FRP Tunnel – PKI, visitor ports, certificate rotation (tunnels in the desktop client; frps server config in the web panel).
  7. Ansible – Playbook management and local execution (in the desktop client).
  8. Troubleshooting – Structured error diagnosis.
Web admin panel vs. desktop client (since v0.32.0)

Operational management has moved into the desktop client: server inventory, connections, FRP tunnels, monitoring checks, and Ansible playbooks are maintained in the server-centric "Infrastructure" hub (in a server workspace only). The web admin panel is now pure instance management: users (the default page after login), API keys, hooks, the FRP server configuration, and login. The user↔server assignment stays in the web panel (in the user dialog).

Desktop client: workspaces

The desktop client works in workspaces. A workspace has a fixed kind – Server (sign-in at an AdminHelper installation), Sync (a connection list from an HTTPS URL) or Local (connections on this device only) –, a name, a colour and, for Server and Sync, a URL; several per kind are allowed. Whoever looks after several installations, say those of two customers, creates a server workspace per installation and has them open side by side, without signing out or enrolling the device again. Each workspace runs in a window and process of its own, with its own sign-in, tunnel, device identity, stored RDP passwords, connections and log file (the workspaces taken over from the previous version share the keyring entries from before, see below).

  • Picker: adminhelper opens the launcher with the list of all workspaces (colour, name, kind, host, “open”); the one used last is preselected, Enter opens it. There you create workspaces (New workspace) and edit or delete closed ones; only the picker changes name, colour and URL. Once the opened workspace runs, the launcher closes, and Workspaces… in the window brings it back. One workspace never runs twice.
  • Recognisable: the window title “<name> — AdminHelper”, a chip with a colour dot and the name at the top of the sidebar and a colour stripe at the edge of the window; confirmations, OS notifications (“[<name>] …”) and, on Linux, the title of the RDP window name the workspace.
  • Sign-in per workspace: a server workspace asks for a sign-in every time it opens. The server URL is the workspace's and is fixed; the login screen shows a URL field only while the workspace has none. A user of one installation signs in in one workspace only: if another workspace has already signed in as this user at the same installation, the sign-in is refused and names that workspace. Sync and local workspaces open without a sign-in and enroll no device; for your own installation under enforced mTLS you therefore need a server workspace (see Users & Access → API keys).
  • Settings: the dialog separates This workspace (sign-out, certificates, device identity and token, browser certificate, notification rules, sync interval) from All workspaces on this device (language, passwords, RDP, OS notifications, diagnostics).
  • Deleting works only in the picker and only while the workspace is closed; the confirmation names it. If a server workspace has a device identity, the desktop first revokes it at the server; then it deletes the data of the workspace on this device, stored RDP passwords included, for workspaces taken over (see below) only with the last of them, as they share the keys. If the server does not revoke it, for example because it cannot be reached, the picker reports “On this device only”, and the device stays valid at the server until an administrator revokes it (see Users & Access → Devices and revocation). Deleting a local workspace loses its connections for good.

The first start after the update creates the workspace “Standard” in the previous mode from the data so far; local connections, a sync URL or a server URL the previous mode left unused become “Lokal”, “Sync” and “Server” beside it. These workspaces taken over share the entries in the system keyring from before, so stored RDP passwords and a device identity stay usable. Without data from before there is just “Standard” (local) at first. If the previous settings.json could not be read, “Standard” starts as a local workspace and the file is set aside; how to carry on is in Troubleshooting → Unreadable settings. Technical details are in the Developer Guide → Desktop client.

Prerequisites

Linux host, Docker & Docker Compose v2.6+, a public port for reverse-proxy TLS termination, and optionally a wildcard DNS entry for FRP HTTP tunnels.
