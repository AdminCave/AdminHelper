Admin Guide

Overview

This guide is aimed at operators who install, configure, and maintain AdminHelper. It covers the server, reverse proxy, agents, monitoring stack, FRP tunnel, and day-to-day operations.

Components at a Glance

Server

Docker containers with FastAPI + PostgreSQL. Provides the REST API, the web admin panel (instance management), the monitoring scheduler, and the FRP backend. Typically runs behind a reverse proxy with TLS.

Desktop Client

Tauri app for Linux, Windows, and macOS. Opens RDP, SSH, or HTTP sessions including the FRP tunnel and, in a server workspace, is also the operational cockpit: server inventory, connections, tunnels, monitoring, and Ansible are managed here.

Go Agent

One binary for Linux (systemd) and Windows. Runs the monitoring collector and the FRP client auto-provisioning. Shipped as DEB, RPM, or a single .exe (Windows).

Typical admin tasks

  • Install the server with Docker Compose and run the first initialization
  • Set environment variables, data directories, backups, and logging
  • Create admin users, distribute API keys, maintain server assignments (web admin panel)
  • Roll out the agent to new servers via apt/dnf or .exe
  • Define monitoring checks and review alerts (desktop client, server workspace)
  • Set up an FRP tunnel for a server (desktop client; frps server config in the web panel)
  • Manage and run Ansible playbooks (desktop client)
  • Diagnose problems and read logs
Web admin panel vs. desktop client (since v0.32.0)

Operational management has moved into the desktop client: server inventory, connections, FRP tunnels, monitoring checks, and Ansible playbooks are maintained in the server-centric "Infrastructure" hub (in a server workspace only). The web admin panel is now pure instance management: users (the default page after login), API keys, hooks, the FRP server configuration, and login. The user↔server assignment stays in the web panel (in the user dialog).

Desktop client: workspaces

The desktop client works in workspaces. A workspace has a fixed kind – Server (sign-in at an AdminHelper installation), Sync (a connection list from an HTTPS URL) or Local (connections on this device only) –, a name, a colour and, for Server and Sync, a URL; several per kind are allowed. Whoever looks after several installations, say those of two customers, creates a server workspace per installation and has them open side by side, without signing out or enrolling the device again. Each workspace runs in a window and process of its own, with its own sign-in, tunnel, device identity, stored RDP passwords, connections and log file (the workspaces taken over from the previous version share the keyring entries from before, see below).

  • Picker: adminhelper opens the launcher with the list of all workspaces (colour, name, kind, host, “open”); the one used last is preselected, Enter opens it. There you create workspaces (New workspace) and edit or delete closed ones; only the picker changes name, colour and URL. Once the opened workspace runs, the launcher closes, and Workspaces… in the window brings it back. One workspace never runs twice.
  • Recognisable: the window title “<name> — AdminHelper”, a chip with a colour dot and the name at the top of the sidebar and a colour stripe at the edge of the window; confirmations, OS notifications (“[<name>] …”) and, on Linux, the title of the RDP window name the workspace.
  • Sign-in per workspace: a server workspace asks for a sign-in every time it opens. The server URL is the workspace's and is fixed; the login screen shows a URL field only while the workspace has none. A user of one installation signs in in one workspace only: if another workspace has already signed in as this user at the same installation, the sign-in is refused and names that workspace. Sync and local workspaces open without a sign-in and enroll no device; for your own installation under enforced mTLS you therefore need a server workspace (see Users & Access → API keys).
  • Settings: the dialog has five sections on the left: General (language, theme, passwords, self-signed server certificates), Workspace & sync (kind and URL, sync interval, sign-out), RDP, Notifications (OS notifications, notification rules) and Device (device registration and token, browser certificate, pinned certificate, diagnostics). What applies to this workspace only carries the mark This workspace; everything else applies to all workspaces on this device.
  • Getting around: Ctrl+K (macOS ⌘+K) or the search button in the header opens the command palette: connections, pages and actions (new connection, settings, theme, switch workspace) by search and Enter. The status bar at the foot of the window shows kind and host, the tunnel, monitoring problems (server), the last sync (sync) and the device registration; messages appear as a stack of at most three, each one closable.
  • Notifications (server workspace only): the bell in the header counts the unread entries; its badge turns red while an unread critical one is among them. The panel shows the tabs All, Unread and Open (unread with severity warning or critical), grouped by today, yesterday and older. Opening the panel marks nothing read: the tick on an entry does, a click on it (it then opens it on the Notifications page) and Mark all as read. New entries also appear as a notice with Open; a critical one stays until closed, more than three are summed up as “+N more”. Do not disturb in the panel (1 hour, 4 hours, until 07:00 tomorrow) holds back notices and OS notifications of this workspace window, critical ones still come through; bell and page stay as they are, the status bar shows the end, and the choice survives a restart. The Notifications page (via Show all or the command palette) has mailboxes (Inbox = unread or open, Open, All), filters by severity and category, a search in title and text, multi-select to mark read, and on the right the detail with source and time; it loads 500 entries, Load more fetches the next ones.
  • Connections: The Connections page shows a sidebar on the left with the library (All, Favorites, Last 24 h, Via tunnel), type and folders (tags), the list in the middle as a table or cards, grouped by server, folder or type, and on the right the inspector of the selected connection (fields, a command preview to copy, notes, connect, edit, favorite). The sidebar and the inspector only appear once the window is wide enough; in a narrow window the table turns compact. Above the list sits Quick access: the favorites first, then the recently used connections, at most four. The desktop keeps favorites (the star) on this device only, per workspace; they do not go to the server or the sync source. Keyboard: ↑/↓ select the next row, Enter or a double-click connects, Space selects the focused row, Esc clears the selection. The row check boxes mark several connections; the Bulk actions bar adds a tag to them or removes it, exports them as CSV (columns name,type,host,port,user,url,tags, without passwords and notes) or deletes them after a confirmation, together with their stored RDP passwords. In a sync workspace changes only last until the next sync. The Ping column measures reachability from the device: a TCP connect to host and port of every visible connection (web: host and port of the URL), every 60 s while the window is visible, with a 1.5 s timeout; it shows the time in ms or “unreachable”. Connections through a tunnel show “Tunnel” and are not probed. The probe only opens and closes a TCP connection; targets with strict connection logging or lockouts after repeated connections see it every 60 s.
  • Connection editor: At the top you choose the type (SSH, RDP, Web); switching it goes back to General. SSH and RDP split their fields over two tabs: General (name, host, port, username, the domain for RDP, tags, notes, last used) and Sign-in (SSH: key path; RDP: trust certificate). Web has only General with the URL. In a server workspace Assign server links the connection to a server of the inventory, and with it to that server's monitoring status and tunnels. Only admins see the field, as only they may read the server list and save connections. No server removes the link; deleting a server removes the link from its connections. If the server list does not know the assigned server, for example because it could not be loaded, the field reads “Unknown server”, and saving keeps the link until you choose another.
  • Deleting works only in the picker and only while the workspace is closed; the confirmation names it. If a server workspace has a device identity, the desktop first revokes it at the server; then it deletes the data of the workspace on this device, stored RDP passwords included, for workspaces taken over (see below) only with the last of them, as they share the keys. If the server does not revoke it, for example because it cannot be reached, the picker reports “On this device only”, and the device stays valid at the server until an administrator revokes it (see Users & Access → Devices and revocation). Deleting a local workspace loses its connections for good.

The first start after the update creates the workspace “Standard” in the previous mode from the data so far; local connections, a sync URL or a server URL the previous mode left unused become “Lokal”, “Sync” and “Server” beside it. These workspaces taken over share the entries in the system keyring from before, so stored RDP passwords and a device identity stay usable. Without data from before there is just “Standard” (local) at first. If the previous settings.json could not be read, “Standard” starts as a local workspace and the file is set aside; how to carry on is in Troubleshooting → Unreadable settings. Technical details are in the Developer Guide → Desktop client.

Architecture in a paragraph

Modular monolith

AdminHelper is a modular monolith: one FastAPI process serves the web panel, the REST API, and the APScheduler that runs monitoring jobs. Metrics are streamed to an external VictoriaMetrics, and FRP runs in a container of its own. Persistence is PostgreSQL 18 (its own Compose service); the server and the monitoring service share one Postgres cluster with two databases (adminhelper, adminhelper_monitor). The mTLS PKI is run by the separate ca-issuer service; certificate lifetimes are in Operations & Config.

Versions

This guide describes the current release series; what changed in each version is in CHANGELOG.md in the repository.

Prerequisites

Linux host, Docker & Docker Compose v2.6+, a public port for reverse-proxy TLS termination, and optionally a wildcard DNS entry for FRP HTTP tunnels.
