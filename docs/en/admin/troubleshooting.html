Troubleshooting

Quick diagnostic paths for the five most common failure classes: login, TLS, agents, monitoring, and FRP.

Install aborts

  • compose project '…' is already installed here: before the start the installer finds containers or a postgres-data or ca-pki volume of the compose project and stops without changing the stack or its data. For a running installation: ./scripts/update.sh in the install directory. For the remains of an aborted attempt, its stale postgres-data volume does not match the new .env (Postgres only sets the password on the volume's first init, else the start ends in password authentication failed). Then start over — this deletes the data of the volumes: 
    cd adminhelper
./scripts/install.sh … --reset
    --reset names the volumes of the project and deletes them only after the project name is typed on a terminal, --yes included; without a terminal it stops, and so it does when the containers of the project belong to another directory. Gotcha: the compose project name is the directory name (unless COMPOSE_PROJECT_NAME in the .env sets it), so two installs in different paths sharing the basename adminhelper reuse the same adminhelper_postgres-data volume — a "fresh" folder can still hit an old one.

Login fails

  1. Rate-limited? Check docker compose logs server | grep ratelimit – 5 bad attempts / 15 min blocks the IP.
  2. Password forgotten? Changing ADMIN_PASSWORD and restarting does NOT help — startup only creates an admin when none exists (idempotent). Reset it directly, no login needed: docker compose exec server python -m app.cli reset-admin --username admin --password NEW-PASSWORD (or --password-stdin to keep it out of the process argv). The password must be 8–128 characters, as at login; the command refuses a longer one with exit 1. The reset also signs out all of the user's existing sessions; log in again with the new password.
  3. Refresh cookie rejected? Check the clock skew between the browser and server (TOTP also relies on this).

TLS / reverse proxy

bash
# Cert valid?
openssl s_client -connect srm.example.com:443 -servername srm.example.com < /dev/null 2>/dev/null | openssl x509 -noout -dates

# Does the server ignore certificate headers from a peer that is not the gateway?
docker compose logs server | grep 'does not come from the gateway'

# Did the server fail to resolve the gateway (its forwarded headers are then ignored)?
docker compose logs server | grep 'cannot resolve'

Agent doesn't check in

bash
sudo adminhelper-agent run --once --log-level debug   # one run by hand, with debug output
systemctl status adminhelper-agent.timer
journalctl -u adminhelper-agent.service -n 100 --no-pager
openssl x509 -in /etc/adminhelper/identity/agent.crt -noout -enddate   # client cert expired?

Common causes: clock skew > 5 min, expired client cert, DNS failure, firewall blocking 443/tcp (the agent's pushes and its cert renewal go through the gateway).

Timer red vs. green: A permanent failure — a revoked/rotated API key (401/403) or a deleted server (404) — makes the adminhelper-agent.service oneshot exit non-zero (shows as failed in systemctl status, and a configured OnFailure= fires). Transient failures (server 5xx, network/DNS) stay green and are retried on the next run.

Desktop client, first contact: “Server certificate is not publicly trusted”: with a standard installation the gateway presents a leaf of the internal CA on all ports (443, 8444), so the very first sign-in or enrollment attempt with default settings opens a dialog asking whether to trust the server anyway. Trust & continue permanently enables “Allow self-signed certificates” for this workspace (TOFU pin, see the next paragraph) and automatically retries the interrupted action. After Cancel the message Das Server-Zertifikat stammt nicht von einer öffentlich vertrauenswürdigen CA … is shown — remedy: repeat the action and confirm the dialog, tick the checkbox in the desktop settings under This workspace (visible in sync and server workspaces), or install a publicly trusted certificate on the gateway.

Desktop client, “Allow self-signed certificates”: the first connection pins the server certificate's SHA-256 fingerprint (trust-on-first-use, like SSH known_hosts) in the OS keyring; afterwards only that exact certificate is accepted and any change is rejected as a possible MITM. If a legitimate certificate rotation triggers ERR_TOFU_PIN_MISMATCH: AdminHelper TOFU: Das Server-Zertifikat für … hat sich seit dem ersten Verbinden geändert … (the message is in German), click Reset pinned certificate in the desktop settings under This workspace, confirm the question and reconnect (re-pins on next connect). If the client instead reports that the pin could not be read from or stored in the keyring (AdminHelper TOFU: The certificate pin for … could not be read from or stored in the system keyring …), unlock the system keyring and reconnect; Reset pinned certificate does not help here. If the reset itself reports … the pinned certificate could not be removed from the keyring: … (from Reset pinned certificate as from Reset device identity), the old pin stayed in the keyring: unlock the system keyring and repeat the same reset.

Desktop client, already-enrolled device (mTLS): once the device is enrolled, the client verifies the server certificate against the CA pinned at enrollment (no longer the leaf pin). After a server reinstall or re-created PKI the old CA no longer matches and the connection fails with AdminHelper: Das Server-Zertifikat wird nicht mehr von der … gepinnten CA gedeckt (mögliche MITM-Attacke). If the change is expected, click the Reset device identity button below the error message on the login screen (when signed in, it is also in the desktop settings under This workspace) — this clears the mTLS device certificate of this workspace and the certificate pin — then enroll the device again with a new one-time token from your administrator, on the login screen via "Enroll this device with a token" or, when signed in, in the settings.

Desktop client, login: “The server requires a device certificate”: the gateway enforces mTLS (MTLS_ENFORCE=true) and turns a device without a certificate away with 400 before the login. Signing in does not help here: the button “Enroll this device with a token” below leads the way, with a one-time token from your administrator (see Users & Access). Then the login works.

Desktop client, login: “This device is registered for another user”: under mTLS the device certificate belongs to the user the device was registered for; the server accepts it for that user only (403, ERR_CERT_USER_MISMATCH). Sign in as that user, use the button “Reset device identity” below to reset the identity of the workspace and register it for yourself with a one-time token, or create a server workspace of your own and register it (see Users & Access). In the browser the same holds for a .p12: each user uses their own.

Desktop client, login: “The certificate of this device is no longer valid”: the server no longer accepts the device certificate (403, ERR_CERT_REVOKED). The device was revoked, its user deleted, the certificate replaced by a newer one of this device, or it dates from before the certificate register and was not used during the transition (see Operations & Config). Use the button “Reset device identity” below to reset the identity, then register the device again with a one-time token from your administrator. In the browser: export a new .p12, import it and remove the old one from the certificate store. An agent gets a new certificate by being provisioned again (see Agent Deployment).

Desktop client, “On this device only: the server did not revoke the old certificate”: while resetting the device identity or deleting a server workspace in the picker the server did not revoke the certificate, for example because it could not be reached or does not know the function yet; the certificate is deleted on this device only. After a reset: registering the workspace again for the same user replaces the old certificate. After deleting a workspace no registration replaces the old certificate, not even one of a new workspace. Then, and if the workspace is not registered again or is registered for another user, the administrator revokes the old device through the device API (see Users & Access).

Desktop client: workspaces

  • Login: the workspace "<name>" signs in to this server as this user; one workspace per server and user: the other workspace it names has already signed in as this user at the same server address (scheme, host and port); there is one workspace per server and user. The desktop checks this before the sign-in, so the password does not go to the server, and the refusal holds while that workspace is closed too. Remedy: sign in as another user, or open the named workspace through Workspaces… and work there.
  • Picker: the workspace <id> is open already: the workspace already runs in a window of its own, for example because it was started after the picker had loaded the list. The message names the id (standard, lokal, sync, server or w-…); the picker then loads the list anew and shows the workspace as “open”. The picker does not bring an open window to the front: switch to that window. The workspace can be opened, edited and deleted again once its window is closed.
  • Picker: “The previous settings could not be read …”: at the first start after the update to workspaces the previous settings.json could not be read or was no valid JSON, say cut short or edited wrongly by hand. The desktop renamed it, as it was, to settings.json.unreadable-<time> (UTC, for example settings.json.unreadable-20261021T080000Z) and went on without it, as if there were no settings. The note comes once and names the file. What follows:
    • “Standard” is a local workspace with the local connections of this device (connections.local.json). If there was no local file, the connections from the previous cache (connections.json, the list from the server or sync source) are now local connections of “Standard”; if there was one, the cache stays as a file in the data folder and is not taken over. The workspaces “Lokal”, “Sync” and “Server” are not made.
    • The settings for all workspaces (language, passwords, RDP, desktop notifications) are at their defaults; set them again in the settings under All workspaces on this device. Once storing passwords in the system keyring is on again, “Standard” finds the RDP passwords stored so far for its connections again.
    • The local tunnel ports from before are released; a new server workspace hands them out anew, and a visitor may get another local port.
    Carrying on:
    • Server before: in the picker, make a server workspace with the server URL through New workspace, open it and sign in. It has keys of its own and sees neither the previous device identity nor the RDP passwords stored so far: register the device there again with a one-time token from your administrator (tunnels always need this, the sign-in if the server requires a device certificate), on the login screen via “Enroll this device with a token” or, when signed in, in the settings; enter stored RDP passwords again. The old device stays valid at the server until the administrator revokes it through the device API (see Users & Access).
    • Sync before: make a sync workspace with the sync URL; it needs no registration.
    • URL no longer at hand: the file set aside is text; the server URL is mostly still readable in it under serverUrl, the sync URL under url. It holds no passwords, but maybe a sync URL with credentials: delete it once it is no longer needed.
    Repairing the file set aside and renaming it back to settings.json does nothing by itself: the data from before is taken over only while there is no workspaces.json in the data folder. If that is deleted too, the next start builds the workspaces taken over (standard, lokal, sync, server) anew from the old files and drops everything made in them since the update; workspaces made by hand are then missing from the picker and can no longer be deleted there, and the device of such a server workspace stays registered at the server. Hence not recommended. Where the files are:
    • Data folder: Linux ~/.local/share/com.admincave.adminhelper (or under $XDG_DATA_HOME), macOS ~/Library/Application Support/com.admincave.adminhelper, Windows %APPDATA%\com.admincave.adminhelper.
    • Log of the launcher (adminhelper.log): Linux logs/ in the data folder, macOS ~/Library/Logs/com.admincave.adminhelper, Windows %LOCALAPPDATA%\com.admincave.adminhelper\logs. It names the error as a warning settings.json does not parse (…) or settings.json does not read (…) with the new file name, never any content of the file. If a workspace was started directly first after the update (adminhelper --workspace <id>), the line is missing: a workspace process opens its log only after the takeover.
    If the file could not be renamed (on Windows, while another program holds it open), the desktop does not start, and adminhelper.log reports the data was not moved into workspaces with was not set aside as: close the other program and start the desktop again.

Monitoring ingest dropping samples

bash
# Check auth
docker compose logs monitoring | grep 'invalid api key'

# Check VictoriaMetrics health
docker compose exec monitoring curl -s http://victoria:8428/health

# Disk full?
docker compose exec monitoring df -h /data/victoria

# Agent side, on the target host: one run by hand, with debug output
sudo adminhelper-agent run --once --log-level debug

FRP visitor connect hangs

  • Visitor-port pool exhausted? Scale VISITOR_PORT_END.
  • Client cert of the agent expired? Check it on the agent host: openssl x509 -in /etc/adminhelper/identity/agent.crt -noout -enddate. The agent renews it itself on every run once half of its lifetime is over; if that fails, Cert-Renew Fehler shows in the journal of adminhelper-agent.service.
  • Wrong sk on STCP tunnels – both sides must match.

Diagnostics bundle

Collect a redacted diagnostics bundle for a bug report, on the server host:

bash
./scripts/diagnostics.sh               # writes adminhelper-diagnostics-<ts>.tar.gz
./scripts/diagnostics.sh --tail 1000   # more log lines per service
./scripts/diagnostics.sh --mask-hosts  # also mask IP addresses, the .env host names and the machine name

The bundle contains report.txt (versions, OS, docker, service status), compose.yml, an env.sanitized (secret values masked) and the last log lines per service. Only the user who runs the script can read it (0600); started with sudo, it belongs to root. Then attach it to a GitHub issue.

Masked are the secrets of the .env, API keys and tokens (in the access logs too: api_key, token and access_token as query parameters, the token in /hooks/trigger/<token>, provisioning tokens adminhelper_prov_…) as well as JWT and Bearer tokens. Without a switch, host names and IP addresses stay: the domain and the SANs, the client addresses in the access logs and the machine name in report.txt, so domain and certificate errors show in the bundle. With --mask-hosts, IPv4 and IPv6 addresses become <ip> by their form, and the names and addresses from DOMAIN, EXTRA_SANS, CA_FRPS_EXTRA_SANS, ALLOWED_IPS, FRP_SERVER_ADDR, TRUSTED_PROXIES, SMTP_HOST and SMTP_FROM (of SMTP_FROM with a display name only the address in angle brackets, not the name) as well as the machine name become <host>, in report.txt, the logs and env.sanitized, which shows those keys as <masked>. compose.yml stays an unchanged copy.

For the desktop client: in the window of the workspace concerned, Settings → All workspaces on this device → Diagnostics → "Create diagnostics report". Each workspace writes a log of its own (adminhelper-<id>.log, the launcher adminhelper.log); the report carries the last lines from the log of its workspace and names its id. For an agent on a managed server: adminhelper-agent diagnostics.

Skim before sending

The secrets of the .env (SECRET_KEY, passwords, SMTP user), API keys and tokens (in the access logs too), JWT and Bearer tokens are masked automatically. --mask-hosts adds IP addresses, the names and addresses from the host keys of the .env and the machine name; other names, such as those of managed servers or webhook targets, stay even then. Redaction is best-effort: please look over the bundle before uploading.
