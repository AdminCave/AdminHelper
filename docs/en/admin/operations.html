Operations & Config

Where data lives, how logs are named, how to take consistent backups – the operational knobs you need to keep the system healthy over time.

Data Directories & Postgres Volume

State splits across two locations: DATA_DIR for file-based artifacts, the postgres-data Docker volume for the actual databases.

PathPurpose
postgres-data (volume)PostgreSQL cluster with two DBs: adminhelper (users, connections, servers, hooks) and adminhelper_monitor (checks, alerts, templates, agent keys).
/data/.bootstrap_tokenOne-time setup-token hash for the first admin (see installation guide).
/data/.secret_keyAuto-generated 256-bit secret; never delete without re-issuing all tokens.
frp-config (volume)Only the generated frps.toml (no cert material anymore). The FRP TLS material is provided by the ca-issuer (volume frps-certs, recoverable). The old server-run FRP master PKI (volume frp-pki) has been removed — see ca-pki below.
frps-state (volume)The frps supervisor's status file status.json (state, reason, heartbeat, the last 8 events) and, while frps runs with a dashboard port, the list of the frps dashboard for each proxy type as proxy-<type>.json (stcp, https, tcp, udp) for the tunnel status view (see FRP Tunnel). The supervisor in the frps container writes them, server and scheduler read them read-only, the proxy lists only the server. Not backed up: the supervisor rewrites them at every poll.
frps-active (volume)The checked working copy of frps.toml and the TLS material that frps starts from (like frp-config and frps-certs it holds the token and the key); mounted in the frps container only. Not backed up: the supervisor takes it over anew from frp-config and frps-certs.
ca-pki (volume)PKI hierarchy of the ca-issuer: root (passphrase-encrypted) + intermediates (tunnel/access/internal). The central backup target of the internal CA — losing it means every client must re-enroll. Issuer-private, never mounted into the gateway/frps.
gateway-certs (volume)The gateway's TLS material (access-signed leaf + key + CA trust bundle), provisioned by the ca-issuer. Recoverable — the issuer re-provisions it.
victoria-data (volume)VictoriaMetrics storage – 90 d retention (separate, not in this scope).

server, scheduler, ca-issuer and monitoring run as the user app (UID 10001) from programs this user can execute but not read. The UID 10001 should not belong to any other account or service on the host.

Backups

scripts/backup.sh bundles the whole state — including the CA crown jewel — into one tarball, with the stack running:

bash
./scripts/backup.sh                 # -> ./backups/adminhelper-backup-<ts>.tar.gz
./scripts/backup.sh --with-victoria # also the (large) metric history

Included: ca-pki (Root + intermediates), pg_dump of both DBs, monitoring-data, optionally victoria-data, and .env. Not included — and not needed — are gateway-certs/frps-certs: the ca-issuer re-provisions them from ca-pki on boot. Nor are frps-state and frps-active, which the frps supervisor sets up again itself. The archive is readable only by the user who runs the script (0600) and gets its name only once it is completely written; a target directory the script creates gets 0700.

Keep CA_ROOT_PASSPHRASE separately

The passphrase is intentionally not written into the backup — it encrypts the Root key, which IS in the backup; storing both together would defeat the encryption (ADR 0001 §5/D7). Keep it in a password manager. A restored stack runs without it; it is only needed to rotate intermediates.

For automatic daily DB backups, uncomment the pg-backup service in docker-compose.yml (DBs only, 7-day retention) — it does not replace the full backup.sh incl. the CA. A restore of the database alone with scripts/pg-restore.sh starts the transition of the certificate register again in the same way.

Restore

bash
./scripts/restore.sh ./backups/adminhelper-backup-<ts>.tar.gz

Stops the stack, restores the volumes + DBs and brings it back up. The restored Root is identical — already-enrolled agents stay trusted, no re-enrollment. The certificate register starts its transition again: certificates issued or renewed since the backup are not in the restored database; they are taken over at first contact, for 90 days from the restore (see “Certificate register and transition” below). The backed-up .env is written to .env.restored (it never overwrites an existing .env); on a fresh host, add the separately kept CA_ROOT_PASSPHRASE and move it to .env.

Logging

The containers write timestamped plain-text lines to stderr (stdout stays free for subprocess IPC); docker compose logs -f <service> is the fastest way to read them. Format: 2026-06-15 11:25:53 INFO adminhelper.auth … (date, time, level, logger, message).

The server container uses named loggers prefixed adminhelper.*; some modules log under their module path app.*. Useful logger names:

  • adminhelper.auth / adminhelper.auth_router – logins, refresh rotations, reuse detection
  • adminhelper.rate_limit – blocked requests
  • adminhelper.provisioning – server provisioning
  • adminhelper.servers / adminhelper.ansible – server and Ansible actions
  • app.modules.frp.pki / app.modules.frp.docker_manager – PKI actions and the FRP container
  • app.core.events – failed event hooks with name, event and error text, in the log of the server service
  • app.modules.hooks.scheduler – failed schedule hooks with name and error text, in the log of the scheduler service

The monitoring container logs under the monitor.* prefix (e.g. monitor.engine, monitor.scheduler, monitor.alerter, monitor.victoria). Both containers write plain-text lines to stderr, not JSON.

Log level: server and monitoring read the verbosity from the LOG_LEVEL env var (DEBUG/INFO/WARNING/ERROR, default INFO). For deeper diagnosis set LOG_LEVEL=DEBUG in .env and run docker compose up -d.

Rotation: container logs are bounded via Docker's json-file driver (max-size: 10m, max-file: 5 → max. 50 MB per service) so they don't grow unbounded. Configured through the x-logging anchor in docker-compose.yml.

Audit log

Security- and change-relevant actions are recorded in an append-only audit trail — with actor (user or API key; actions of the server CLI python -m app.cli appear as system with the label cli), source IP and timestamp. It captures, among others, creating/updating/deleting and using connections, changes to servers/users/API keys/FRP/Ansible, plus logins (success/failure), a logout that ends a session and the first-admin bootstrap.

Viewable in the web UI under Audit log (admins only; filterable by actor, object and action) or via the API: GET /api/audit (paginated; query params action, actor_type, object_type, object_id, status, q).

Retention

A daily job deletes entries older than AUDIT_RETENTION_DAYS (default 365) — the only delete path for the otherwise append-only table. 0 keeps everything forever.

Gap: local and sync workspaces

Only a server workspace of the desktop client reports the use of a connection to the server. What is opened in a local or sync workspace never reaches the server and therefore does not appear in the audit trail.

E-mail notifications (SMTP)

The notification hub can deliver notifications by e-mail in addition to the in-app bell. Configure an external SMTP relay via environment variables (no local mail server needed):

VariableMeaning
SMTP_HOSTRelay hostname. Empty = e-mail channel off (bell + desktop toasts stay active).
SMTP_PORT587 (STARTTLS, default) or 465 (implicit TLS / SMTPS).
SMTP_USER / SMTP_PASSWORDRelay credentials (optional, if the relay accepts without auth). Write a $ in the password as $$ or put the value in single quotes (see Environment Variables).
SMTP_FROMSender address (default adminhelper@localhost).
NOTIFICATION_MAX_ATTEMPTSDelivery attempts per e-mail with linear backoff, then "failed" (default 5).

Who receives which e-mails is controlled by each user via their notification rules (see Monitoring → Personal notifications). Delivery runs asynchronously through an outbox; a per-minute background job sends them.

Multi-Worker Notes

The default compose stack runs a single Uvicorn worker (WEB_CONCURRENCY=1). To scale across CPU cores:

  1. Set WEB_CONCURRENCY in .env to the desired worker count (rule of thumb (2×cores)+1, typically 4–12 — do not couple it to the number of concurrent clients). The entrypoint then runs uvicorn --workers ${WEB_CONCURRENCY}.
  2. REDIS_URL must be set (already the case in the default compose) — otherwise the rate limit counts per worker instead of globally; the server warns at startup.
  3. Mind the DB pool: DB_POOL_SIZE+DB_MAX_OVERFLOW (default 10+20) apply per worker. Lower them for many workers and check Postgres max_connections.
The scheduler runs as its own service

The periodic jobs (e-mail outbox delivery, retention cleanups, scheduled hooks) run in the separate scheduler service (exactly one instance, RUN_MODE=scheduler) — not in the web workers. If every web worker started the scheduler, every job would run once per worker (e.g. e-mails sent multiple times). The scheduler service ships in the default compose; do not scale it to multiple replicas.

Update flow

Use ./scripts/update.sh — release-bound, backup-first, verified bundle, auto-rollback (see Installation → Updates). The server runs alembic upgrade head on startup; downtime is typically below 10 seconds.

Timezone

TZ is passed to all containers. Default Europe/Berlin. The API returns timestamps in UTC with Z regardless (web and desktop show them in the browser's or machine's local time), and scheduled hooks run on UTC.

Renewing certificates

The gateway's TLS certificate is issued by the ca-issuer (access-signed, 365 days). It is provisioned into the gateway-certs volume on first start; a redeploy/restart of the ca-issuer renews it when needed. The FRP client certificates expire after 12 months – see FRP Tunnel for rotation. An frps certificate the ca-issuer renewed is taken over by frps itself, without restarting the container (see frps supervisor).

Certificate register and transition

The ca-issuer records every client certificate it issues or renews in a register; the server accepts recorded certificates only, also with MTLS_ENFORCE=false (see Users & Access → Devices and revocation). Certificates issued before the update to the register are not known to it yet. A transition applies to them:

  • They stay valid for 90 days from the update and are recorded at their first contact with the server or their first renewal. From then on they count like any other certificate until they expire.
  • A desktop or agent that reaches the server during this time is recorded that way; it renews its certificate as usual afterwards.
  • A .p12 that was not used during the 90 days is no longer accepted afterwards (ERR_CERT_REVOKED): export and import a new one.
  • A restore (restore.sh, pg-restore.sh) starts the transition again, 90 days from the restore, for the certificates the restored database does not know.

After the 90 days, only what is in the register counts.

frps supervisor

frps runs from the image ghcr.io/admincave/adminhelper/frps (source apps/frps/) under a supervisor (apps/frps/frps-supervisor.sh). The supervisor runs as root with the capabilities DAC_OVERRIDE, SETUID, SETGID and KILL; it starts frps as the user frps (UID 10002) without capabilities and asks the frps dashboard for its proxy lists as a user of its own, frps-fetch (UID 10003), both from programs these users can execute but not read. It reads the frps.toml the server writes (volume frp-config, read-only) and the ca-issuer's TLS material (volume frps-certs, read-only), checks both and starts frps only from a checked working copy in the frps-active volume, which frps can read but not change; no one but root and frps reads it. It writes its state to frps-state; from there the FRP page shows the frps state block (see FRP Tunnel). The UIDs 10002 (frps) and 10003 (frps-fetch) should not belong to any other account or service on the host.

  • Taking changes over: the supervisor polls the input every 5 s and takes a change over once it has stayed the same for two polls, i.e. after about 5–10 s. Valid: frps restarts from the new copy. Invalid: frps keeps running on the last valid copy; if there is none, it does not start (waiting). An unchanged input restarts nothing. docker compose restart frps is not needed for changes.
  • Check before every start, a restart after an exit included: the working copy must be unchanged and pass the check again; otherwise it is dropped (for a changed copy with the event copy_changed), and before a restart the supervisor takes the input over anew.
  • Exits: if frps ends on its own, the supervisor starts it again after 2, 4, 8 … at most 60 s; from the third exit within 60 s the state is crashloop, until frps has run for 60 s again.
  • Health check: docker compose ps shows frps as healthy in the states waiting, running and stopped, as unhealthy in degraded and crashloop.
  • Log: docker compose logs frps; the supervisor's lines start with [frps-supervisor] and carry codes and paths, never the token.

States

StateMeaning
waitingfrps is not running; the reason is shown next to it.
runningfrps runs on the configuration taken over last.
degradedfrps runs on the last valid configuration; a newer one was not taken over (reason next to it).
stoppedThe FRP server configuration was deleted, frps is stopped.
crashloopfrps exits repeatedly; the supervisor starts it again with a growing pause.

On top of these the server reports missing while there is no status file, and unreadable when it does not match the expected format. If the last heartbeat is older than 60 s, the details count as out of date (stale).

Events and notifications

The scheduler reads the status file every 15 s and writes a bell notification for every new event (at most 10 events per hour; an event older than one hour no longer counts as new). "Users with tunnel access" are the admins and the users assigned to a server with at least one enabled tunnel.

Keys allowed in extra_config

The supervisor takes over only an frps.toml in the layout the server generates. At top level, the server writes bindPort, vhostHTTPSPort, subDomainHost, maxPortsPerClient, detailedErrorsToClient, webServer.addr, webServer.port, webServer.user, webServer.password, auth.method and auth.token from the fields of the form. Via the FRP server configuration's extra_config only these can be added:

transport.maxPoolCount, transport.tcpMux, transport.tcpMuxKeepaliveInterval, transport.heartbeatTimeout, transport.tcpKeepalive, userConnTimeout, log.level, log.maxDays

Keys are compared exactly. Values are true, false, finite numbers or strings without quotes, backslashes, braces, control characters and lone surrogates (U+D800 to U+DFFF); the same character rule applies to the fields Subdomain host, Dashboard user, Dashboard password and Auth token. The server rejects other keys and values on saving with 422 (POST/PUT /api/frp/server-config); stored ones it cleans up at startup (see below).

Before an update

Before an update, check in the FRP server configuration:

  • extra_config and the fields Subdomain host, Dashboard user, Dashboard password and Auth token follow the rules above.
  • The Auth token has at least 16 characters.
  • A Dashboard port, if set, is neither 443 nor the Bind port nor FRP_BIND_PORT.

At startup, before it writes frps.toml, the server checks the stored configuration against these rules:

  • extra_config entries with another key (e.g. proxyBindAddr or log.to) or a value not allowed are removed from the stored configuration, and the admins get a bell notification naming the removed keys.
  • A field that ends up in frps.toml and breaks one of these rules (characters not allowed, an Auth token under 16 characters, a Dashboard port equal to 443, the Bind port or FRP_BIND_PORT) stays as it is. The admins get a bell notification naming the fields to set anew, once for as long as the same fields are affected. Its text is German (title "FRP-Server-Konfiguration: Felder neu setzen") and names each field by its label in the German form, with its rule in parentheses, e.g. "Der FRP-Server übernimmt die Konfiguration so nicht. Bitte neu setzen: Auth Token (mindestens 16 Zeichen), Dashboard Port (weder 443 noch der Bind Port noch FRP_BIND_PORT)." In English: the FRP server does not take the configuration as it is; set anew: Auth Token (at least 16 characters), Dashboard Port (neither 443 nor the bind port nor FRP_BIND_PORT).

Logs and notifications name keys and fields, never values. If the configuration fails the supervisor's check, frps keeps running on the last valid copy, if there is one. Without a valid copy, e.g. right after the update with an empty frps-active volume, frps does not start (state waiting, reason on the FRP page) until the configuration passes the check.

Enforcing mTLS (CERT_REQUIRED)

Since 0.29.0 the data plane (:443) runs enforced by default (MTLS_ENFORCE=true): the gateway requires a valid client certificate at the TLS handshake (CERT_REQUIRED) and the server rejects protected routes without a valid scope with 403. A fresh install is usable enforced via scripts/install.sh (it fetches the first admin's cert out-of-band). Permissive (MTLS_ENFORCE=false) lets certless clients through and only logs — needed only for a manual first bootstrap. Both are driven by one variable: MTLS_ENFORCE.

Enroll every client first, then flip

Only enforce once every client – agent, desktop and your own browser – holds a certificate, otherwise you lock yourself out. In the desktop this holds per server workspace that uses this installation; a sync workspace never presents a certificate, so whoever loads from this installation by sync takes a server workspace for it (Users & Access → API keys). Agent and desktop enroll automatically; prepare the browser via the desktop P12 export (Users & Access → Browser access). Test on real hardware first: Windows desktop enrollment and the browser import. Note that a browser leaf is long-lived (~1 year) and never renews. The server refuses a revoked one in both modes, but the revocation locks the browser out only under enforcement, because in permissive mode it reaches the login without a certificate as well.

Enforce:

bash
# in your .env:
MTLS_ENFORCE=true

# restart gateway + server (they read the variable at startup):
docker compose up -d gateway server

The gateway log confirms the mode at startup: mTLS ENFORCED (CERT_REQUIRED) or mTLS permissive.

Rollback (any time, lossless): set MTLS_ENFORCE=false and docker compose up -d gateway server – the data plane is permissive again immediately.

New clients after enforcing

The enrollment plane (:8444) always stays certless and token-gated – new agents and desktops fetch their first certificate there regardless of enforcement. A new user: an admin mints them an enrollment token (POST /api/enrollment/token/for) and hands it over out-of-band; in the desktop client the newcomer creates a server workspace with the server URL in the picker, picks "Enroll this device with a token" on its login screen, enters the token and enrolls – without a prior login. They then sign in normally (now with a certificate). No permissive window is needed for this (the decoupled enrollment door, ADR 0003).

Only the very first admin (there is no admin yet who could issue a token) is the special case — easiest via scripts/install.sh, which creates the admin + a first token out-of-band and then arms enforcement. Manually without the script: a one-time permissive setup window (MTLS_ENFORCE=false, enroll the first admin + desktop, then back to true).
