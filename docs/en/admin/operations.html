Operations & Config

Where data lives, how logs are named, how to take consistent backups – the operational knobs you need to keep the system healthy over time.

Data Directories & Postgres Volume

State splits across two locations: DATA_DIR for file-based artifacts, the postgres-data Docker volume for the actual databases.

PathPurpose
postgres-data (volume)PostgreSQL cluster with two DBs: adminhelper (users, connections, servers, hooks) and adminhelper_monitor (checks, alerts, templates, agent keys). Each service connects with a role of its own without superuser rights; the roles own the schema public of their database, the databases themselves stay with the superuser adminhelper.
/data/.bootstrap_tokenOne-time setup-token hash for the first admin (see installation guide).
/data/.bootstrap.lockEmpty; makes sure that with several server workers only one creates the setup token. May be deleted while the server is stopped.
/data/.secret_keyAuto-generated 256-bit secret; never delete without re-issuing all tokens.
frp-config (volume)Only the generated frps.toml (no cert material anymore). The FRP TLS material is provided by the ca-issuer (volume frps-certs, recoverable). The old server-run FRP master PKI (volume frp-pki) has been removed — see ca-pki below.
frps-state (volume)The frps supervisor's status file status.json (state, reason, heartbeat, the last 8 events) and, while frps runs with a dashboard port, the list of the frps dashboard for each proxy type as proxy-<type>.json (stcp, https, tcp, udp) for the tunnel status view (see FRP Tunnel). The supervisor in the frps container writes them, server and scheduler read them read-only, the proxy lists only the server. Not backed up: the supervisor rewrites them at every poll.
frps-active (volume)The checked working copy of frps.toml and the TLS material that frps starts from (like frp-config and frps-certs it holds the token and the key); mounted in the frps container only. Not backed up: the supervisor takes it over anew from frp-config and frps-certs.
ca-pki (volume)PKI hierarchy of the ca-issuer: root (passphrase-encrypted) + intermediates (tunnel/access/internal). The central backup target of the internal CA — losing it means every client must re-enroll. Issuer-private, never mounted into the gateway/frps.
gateway-certs (volume)The gateway's TLS material (access-signed leaf + key + CA trust bundle), provisioned by the ca-issuer. Recoverable — the issuer re-provisions it.
ca-trust (volume)One file <scope>.pem per scope with the current and the retired intermediates (certificates only, no keys). The ca-issuer writes them on every start, the server reads them read-only (CA_TRUST_DIR) and accepts only client certificates that one of them issued. If the file of a scope is missing, it refuses that scope's certificates and logs an error. Not backed up: the issuer writes them again from ca-pki.
victoria-data (volume)VictoriaMetrics storage – 90 d retention (separate, not in this scope).

server, scheduler, ca-issuer and monitoring run as the user app (UID 10001) from programs this user can execute but not read. The UID 10001 should not belong to any other account or service on the host, nor should UID 70 (Postgres in its container). install.sh and update.sh name such an account with a warning (they do not stop) and close the install directory to other accounts (at most 0750, a stricter 0700 stays); the owner stays whoever installs. Existing installations get this with their next update. A tool that looks into the install directory under another account (a backup agent, say) then needs the directory's group or root. An account that could reach data/ before may have read keys there; whoever sees such a warning removes the account or changes its UID.

Backups

scripts/backup.sh bundles the whole state — including the CA crown jewel — into one tarball, with the stack running:

bash
./scripts/backup.sh                 # -> ./backups/adminhelper-backup-<ts>.tar.gz
./scripts/backup.sh --with-victoria # also the (large) metric history

Included: ca-pki (Root + intermediates), pg_dump of both DBs, monitoring-data, optionally victoria-data, and .env. Not included — and not needed — are gateway-certs/frps-certs: the ca-issuer re-provisions them from ca-pki on boot, and ca-trust too. Nor are frps-state and frps-active, which the frps supervisor sets up again itself. The archive is readable only by the user who runs the script (0600) and gets its name only once it is completely written; a target directory the script creates gets 0700. The target must be able to hold a Unix owner and mode: if a mount does not keep them, as a CIFS, vfat or NTFS mount usually does not, the backup aborts with a hint. Back up to a local directory then and copy the archive to the network share.

Keep CA_ROOT_PASSPHRASE separately

The passphrase is intentionally not written into the backup — it encrypts the Root key, which IS in the backup; storing both together would defeat the encryption (ADR 0001 §5/D7). Keep it in a password manager. Only the first start of the ca-issuer needs it (it creates the hierarchy). After that, clear the value in .env and keep the line CA_ROOT_PASSPHRASE=, or docker compose up aborts; once the value is cleared, docker compose up -d recreates the ca-issuer without the passphrase file. If you change the value before the first successful start, run docker compose up -d --force-recreate ca-issuer. Updates do not generate a new one: init-secrets.sh generates it only in the run that also generates POSTGRES_PASSWORD, that is on a fresh install. If you set POSTGRES_PASSWORD by hand before installing, set CA_ROOT_PASSPHRASE by hand too. A restored stack runs without it (the line stays, empty); it is only needed to rotate intermediates.

For automatic daily DB backups, uncomment the pg-backup service in docker-compose.yml (DBs only, 7-day retention) — it does not replace the full backup.sh incl. the CA. A restore of the database alone with scripts/pg-restore.sh starts the transition of the certificate register again in the same way.

The backup reads as the superuser. restore.sh runs db-init before it restores and restores each database as its service role (ah_server, ah_monitor); it takes the role passwords from the host's .env. If one is missing, say on a host set up before the per-service roles, it aborts before the stack stops: then run ./scripts/init-secrets.sh and start the restore again. scripts/pg-restore.sh restores as the superuser: the restored tables then belong to the superuser, and server, scheduler, monitoring and ca-issuer fail on missing rights until the stack restarts. So run docker compose down && docker compose up -d afterwards: db-init hands the tables back to the roles, the server's start gives the ca-issuer its rights (grant-ca). Going back to an older version: it connects as the superuser again, the data stays usable, the roles stay in the cluster without effect.

Restore

bash
./scripts/restore.sh ./backups/adminhelper-backup-<ts>.tar.gz

Stops the stack, restores the volumes + DBs and brings it back up. The restored Root is identical — already-enrolled agents stay trusted, no re-enrollment. The certificate register starts its transition again: certificates issued or renewed since the backup are not in the restored database; they are taken over at first contact, for 90 days from the restore (see “Certificate register and transition” below). The backed-up .env is written to .env.restored (it never overwrites an existing .env). It lacks the line CA_ROOT_PASSPHRASE: if you move it to .env on a fresh host, run ./scripts/init-secrets.sh afterwards (a backup from before the per-service roles lacks their passwords) and add the line CA_ROOT_PASSPHRASE=, empty or with the separately kept passphrase, or docker compose up aborts. The restored hierarchy does not need the value to start.

Logging

The containers write timestamped plain-text lines to stderr (stdout stays free for subprocess IPC); docker compose logs -f <service> is the fastest way to read them. Format: 2026-06-15 11:25:53 INFO adminhelper.auth … (date, time, level, logger, message).

The server container uses named loggers prefixed adminhelper.*; some modules log under their module path app.*. Useful logger names:

  • adminhelper.auth / adminhelper.auth_router – logins, refresh rotations, reuse detection
  • adminhelper.rate_limit – blocked requests
  • adminhelper.provisioning – server provisioning
  • adminhelper.servers / adminhelper.ansible – server and Ansible actions
  • app.modules.frp.pki / app.modules.frp.docker_manager – PKI actions and the FRP container
  • app.core.events – failed event hooks with name, event and error text, in the log of the server service
  • app.modules.hooks.scheduler – in the log of the scheduler service: failed schedule hooks with name and error text; a warning about a schedule hook whose interval the scheduler cannot read (once per hook and interval; the hook does not run until it is fixed); the system jobs (cleanup of the token blacklist, enrollment tokens, certificate register, provision tokens, audit log and notifications, sending the notification outbox, watching the frps supervisor) with their result as INFO once a run did something, and a failure with traceback

The monitoring container logs under the monitor.* prefix (e.g. monitor.engine, monitor.scheduler, monitor.alerter, monitor.victoria). Both containers write plain-text lines to stderr, not JSON.

Log level: server and monitoring read the verbosity from the LOG_LEVEL env var (DEBUG/INFO/WARNING/ERROR, default INFO). For deeper diagnosis set LOG_LEVEL=DEBUG in .env and run docker compose up -d.

Rotation: container logs are bounded via Docker's json-file driver (max-size: 10m, max-file: 5 → max. 50 MB per service) so they don't grow unbounded. Configured through the x-logging anchor in docker-compose.yml.

Audit log

Security- and change-relevant actions are recorded in an append-only audit trail — with actor (user or API key; actions of the server CLI python -m app.cli appear as system with the label cli), source IP and timestamp. It captures, among others, creating/updating/deleting and using connections, changes to servers/users/API keys/FRP/Ansible, actions on hooks (creating, updating with the changed fields, deleting, enabling and disabling, token rotation, a manual run with success or failure), minting provisioning tokens, writes through the monitoring proxy (POST/PUT/DELETE with path and response status, with status error when forwarding breaks off after sending, without the request content), plus logins (success/failure), a logout that ends a session and the first-admin bootstrap; a hook's webhook trigger and reads of hooks, provisioning tokens and the monitoring proxy leave no entry. For a user update, detail (in the response of GET /api/audit) names the changed fields: password, admin right with its new value, server assignment.

Viewable in the web UI under Audit log (admins only; filterable by actor, object and action; each entry also with its detail, such as the fields changed) or via the API: GET /api/audit (paginated; query params action, actor_type, object_type, object_id, status, q).

Retention

A daily job deletes entries older than AUDIT_RETENTION_DAYS (default 365) — the only delete path for the otherwise append-only table. 0 keeps everything forever.

Gap: local and sync workspaces

Only a server workspace of the desktop client reports the use of a connection to the server. What is opened in a local or sync workspace never reaches the server and therefore does not appear in the audit trail.

E-mail notifications (SMTP)

The notification hub can deliver notifications by e-mail in addition to the in-app bell. Configure an external SMTP relay via environment variables (no local mail server needed):

VariableMeaning
SMTP_HOSTRelay hostname. Empty = e-mail channel off (bell + desktop toasts stay active).
SMTP_PORT587 (STARTTLS, default) or 465 (implicit TLS / SMTPS); every other port uses STARTTLS as well. Delivery checks the relay's certificate and hostname: no mail goes out through a relay without STARTTLS or with a certificate the container does not trust or that does not match SMTP_HOST; after the last delivery attempt the reason is in the log of the scheduler service.
SMTP_USER / SMTP_PASSWORDRelay credentials (optional, if the relay accepts without auth). Write a $ in the password as $$ or put the value in single quotes (see Environment Variables).
SMTP_FROMSender address (default adminhelper@localhost).
SMTP_CA_FILEOptional: path inside the container to a PEM file with the relay's CA (self-signed certificate or company CA). It applies in addition to the system CAs and only to SMTP, in the notification hub as well as in the e-mail channel of monitoring; certificate and hostname are still verified. Empty = system CAs only. Mounting it: see Relay with its own CA.
NOTIFICATION_MAX_ATTEMPTSDelivery attempts per e-mail with linear backoff, then "failed" (default 5).

Who receives which e-mails is controlled by each user via their notification rules (see Monitoring → Personal notifications). Delivery runs asynchronously through an outbox; a per-minute background job sends them.

The e-mail channel of the alert rules in monitoring uses the SMTP_* variables as well (see Monitoring → Notifications & alerting); a rule can set its own relay with its own credentials there.

Relay with its own CA

If the relay presents a certificate the containers do not trust (self-signed or issued by a company CA), put the CA as the PEM file smtp-ca.pem next to docker-compose.yml in the install directory and mount it, with a docker-compose.override.yml next to it, into the services server, scheduler and monitoring, which Compose also gives the other SMTP_* variables; add these entries to an existing docker-compose.override.yml (for instance one with FRPS_DASHBOARD_URL, see FRP Tunnel) instead of replacing it:

docker-compose.override.yml
services:
  server:
    environment:
      - SMTP_CA_FILE=/run/adminhelper/smtp-ca.pem
    volumes:
      - ./smtp-ca.pem:/run/adminhelper/smtp-ca.pem:ro
  scheduler:
    environment:
      - SMTP_CA_FILE=/run/adminhelper/smtp-ca.pem
    volumes:
      - ./smtp-ca.pem:/run/adminhelper/smtp-ca.pem:ro
  monitoring:
    environment:
      - SMTP_CA_FILE=/run/adminhelper/smtp-ca.pem
    volumes:
      - ./smtp-ca.pem:/run/adminhelper/smtp-ca.pem:ro

Then run docker compose up -d. Compose reads docker-compose.override.yml on every call, and scripts/update.sh leaves it in place. The PEM file must be readable by the container user (chmod 644; a CA is not a secret). If it cannot be loaded (missing, unreadable, not PEM), no e-mail goes out: for the hub the reason is in the log of the scheduler service after the last delivery attempt, monitoring records SMTP TLS failed in the alert log. A relay without STARTTLS stays out even with SMTP_CA_FILE.

Multi-Worker Notes

The default compose stack runs a single Uvicorn worker (WEB_CONCURRENCY=1). To scale across CPU cores:

  1. Set WEB_CONCURRENCY in .env to the desired worker count (rule of thumb (2×cores)+1, typically 4–12 — do not couple it to the number of concurrent clients). The entrypoint then runs uvicorn --workers ${WEB_CONCURRENCY}.
  2. REDIS_URL must be set (already the case in the default compose) — otherwise the rate limit counts per worker instead of globally; the server warns at startup.
  3. Mind the DB pool: DB_POOL_SIZE+DB_MAX_OVERFLOW (default 10+20) apply per worker. Lower them for many workers and check Postgres max_connections.
The scheduler runs as its own service

The periodic jobs (e-mail outbox delivery, retention cleanups, scheduled hooks) run in the separate scheduler service (exactly one instance, RUN_MODE=scheduler) — not in the web workers. If every web worker started the scheduler, every job would run once per worker (e.g. e-mails sent multiple times). The scheduler service ships in the default compose; do not scale it to multiple replicas.

Update flow

Use ./scripts/update.sh — release-bound, backup-first, verified bundle, auto-rollback (see Installation → Updates). The server runs alembic upgrade head on startup; downtime is typically below 10 seconds.

Container limits

Every service of the compose stack runs with no-new-privileges: no process in the container gains privileges when it starts a program, setuid bits and file capabilities have no effect. Each service also has a process limit (pids_limit, counting processes and threads). Once it is reached, starting further processes and threads fails in that container; the host and the other services are not affected.

Each service also has a memory limit (mem_limit), far above what it needs idle, so that a memory leak or a runaway query hits only its own container. Once it is reached, the kernel swaps out up to the same amount on a host with swap and then ends a process in that container; if that ends its main process, Docker restarts the container (restart: unless-stopped). The limits reserve no memory, and their sum may exceed the host's RAM. VictoriaMetrics sizes its caches by the memory it sees (-memory.allowedPercent, default 60 %): if the limit of victoria is below the host's RAM, that is 60 % of the limit, otherwise 60 % of the RAM; if you keep many metrics, raise the limit of victoria.

The monitoring ping check needs no special privileges for this: ping uses ICMP datagram sockets, which compose allows in the monitoring container through net.ipv4.ping_group_range.

Of the Linux capabilities, the gateway keeps only the four its nginx master needs to start (CHOWN, DAC_OVERRIDE, SETGID, SETUID); compose drops all others, and the nginx workers run as the user nginx without any.

To raise a limit, use a docker-compose.override.yml next to docker-compose.yml. Compose loads it by itself on every call in the install directory, and update.sh leaves it in place:

yaml
# docker-compose.override.yml
services:
  server:
    pids_limit: 8192
    mem_limit: 8g

Then run docker compose up -d server. If you raise WEB_CONCURRENCY a lot, check the server's limits: every Uvicorn worker brings its own thread pool and up to eight hook processes and needs memory of its own.

On the certless planes, the gateway caps concurrent requests: beyond 16 concurrent requests per client address on the enrollment plane (:8444) and beyond 64 on the package repo (:8445) it answers 429, likewise beyond 128 or 256 per plane in total. The 64 on :8445 leave room for many agent hosts behind one NAT address. If a request's header does not arrive completely within 10 s there, or its body stalls for more than 10 s, the gateway closes the connection; it closes an idle keep-alive connection after 15 s. The data plane :443 is not affected.

frps sits alone on the network frpedge, which compose creates without IP masquerading: the published ports of frps stay reachable, but packets that frps sends itself leave the host with the container's address as the source, not the host's. Docker drops the answers from version 28 on, because it does not pass packets addressed to a container directly, unless the daemon runs with allow-direct-routing or the network in gateway mode nat-unprotected or routed; so no connection beyond the host comes about. With older versions, a machine with a route back into this network could answer (not verified). What remains: packets without an answer still leave the host, and services listening on the Docker host itself stay reachable from the network; the host's firewall protects them, not Docker.

Optional: drop packets from frpedge on the host

To keep these packets inside the host as well, add a rule to the chain DOCKER-USER, which Docker provides for your own rules ahead of its own (Docker docs: Docker with iptables). The rule below drops everything that leaves the bridge of frpedge for another network and does not belong to a connection opened from outside; the published ports of frps keep working, services of the host itself are not covered. It lasts until the host restarts; the host's firewall management makes it permanent. When compose creates the network anew (after docker compose down, say), the bridge has a new name: set the rule again with the new name. Checked with Docker 29 and the iptables backend. With the nftables backend (experimental in Docker 29) there is no DOCKER-USER, the rule goes into a table of its own there (Docker docs: Docker with nftables); for that and for hosts with firewalld or ufw: not verified.

bash
# In the install directory, while frps runs: frps sits only on this project's network
# frpedge; its bridge is named br- and the first 12 characters of the network ID.
ID=$(docker inspect -f '{{range .NetworkSettings.Networks}}{{println .NetworkID}}{{end}}' "$(docker compose ps -q frps)" | grep .)
BR=br-$(printf '%s' "$ID" | cut -c1-12)
if [ -n "$ID" ] && [ "$(printf '%s\n' "$ID" | wc -l)" -eq 1 ] && ip link show "$BR" >/dev/null 2>&1; then
  sudo iptables -I DOCKER-USER -i "$BR" ! -o "$BR" -m conntrack ! --ctstate ESTABLISHED,RELATED -j DROP
else
  echo "bridge of frpedge not found unambiguously, no rule set" >&2
fi
# To remove it: the same iptables line with -D instead of -I (BR as above)

Timezone

TZ is passed to all containers. Default Europe/Berlin. The API returns timestamps in UTC with Z regardless (web and desktop show them in the browser's or machine's local time), and scheduled hooks run on UTC.

Renewing certificates

The gateway's TLS certificate is issued by the ca-issuer (access-signed, 365 days). It is provisioned into the gateway-certs volume on first start; the ca-issuer issues a new one on start when needed, and the gateway loads it with its own restart. Agent certificates are valid for 90 days and renew themselves at half their lifetime. An frps certificate the ca-issuer renewed is taken over by frps itself, without restarting the container (see frps supervisor).

The ca-issuer's PKI (volume ca-pki) consists of a root (10 years) and the intermediates tunnel, access and internal (5 years), all created on first start. No certificate is valid longer than its issuer: client and server certificates issued shortly before their intermediate expires come out shorter. An expired intermediate no longer signs; enrollment and renewal in its scope then answer with HTTP 503. From 180 days before the root or an intermediate expires, the ca-issuer warns in its log (docker compose logs ca-issuer): on every start under the logger ca-issuer.storage (“intermediate 'tunnel' expires on … (N days left)”, for the root with the note that a new root means enrolling every client again), while signing once a day per scope under ca-issuer.issuer.

On every start the ca-issuer checks the hierarchy: the root must be self-signed and valid, every intermediate signed by it, valid and matching its key (<scope>.key) and its chain (<scope>-chain.pem, intermediate and root). If a certificate has expired or something does not match, the ca-issuer does not start and names file, scope and reason in its log (“PKI hierarchy invalid — …”). This also applies when the host clock is before the start of validity (notBefore) of the root or an intermediate, e.g. after a restore onto a host with a wrong clock: the hierarchy is then not yet valid, and a server certificate due for the gateway or frps could not be issued. Fix: set the host clock (NTP), then docker compose up -d.

When each certificate expires is shown in the web admin panel under Certificates (admins only): one table for the infrastructure (root, the intermediates, the gateway and frps certificates) and one for the agents, each with expiry date, days left and a traffic light — yellow below 30, red below 7 days and once expired. The ca-issuer writes the infrastructure rows to the database on every start; if the table shows “No data”, it has not restarted since the update. For the agents, the newest certificate of each agent counts; revoked ones are left out.

Once a day the scheduler reports every certificate that turned yellow or red to the admins through the notification hub: in the bell and, where their subscription asks for it, by e-mail. Each certificate is reported once per level, a renewed one no more; at most 20 notices per run, critical ones first, the rest follows on the next days. If no admin has a matching subscription, the notice counts as not delivered and the next run tries again.

Rotating the intermediates

When: once the ca-issuer warns in its log that an intermediate expires (from 180 days ahead) or status shows it, at the latest when it no longer starts because an intermediate has expired. Take a backup first (scripts/backup.sh).

docker compose run --rm --no-deps ca-issuer python -m app.cli status
docker compose run --rm --no-deps ca-issuer python -m app.cli rotate-intermediates
docker compose restart ca-issuer
docker compose ps ca-issuer        # wait until it is healthy
docker compose restart gateway

The root passphrase comes from the service's secret file (CA_ROOT_PASSPHRASE_FILE); if that is empty, rotate-intermediates asks for it. Do not pass it with -e CA_ROOT_PASSPHRASE=…: it would end up in the shell history and in docker inspect. Restart the gateway only once the ca-issuer is healthy again.

What happens: tunnel, access and internal get new intermediates under the same root (named with the date, e.g. AdminHelper Access Intermediate 2031-05-04). The old ones stay trusted until they expire. Agents and desktops renew their certificates onto the new ones at half their lifetime; browser certificates stay valid until they expire. The ca-issuer issues a new gateway and frps certificate when it restarts; frps then restarts by itself, so tunnels drop briefly.

What not: the root is not renewed, and a stolen certificate does not become invalid at once. A --ca-fp that points at the root stays valid; one that points at the old access intermediate (the value in install commands of older desktop versions) no longer matches: provision and the installation stop with it. A current desktop shows the root's fingerprint in its provisioning tab; its commands stay valid across the rotation. A desktop that pinned the server certificate through the trust dialog before its enrollment asks again. Two rotations on the same day give intermediates with the same name; tell them apart by the key identifier (the intermediate's Subject Key Identifier equals its leaves' Authority Key Identifier, openssl x509 -noout -ext subjectKeyIdentifier,authorityKeyIdentifier).

After a leak: if the key of an intermediate may have leaked, rotate with --compromised <scope> (repeatable, e.g. --compromised access --compromised tunnel):

docker compose run --rm --no-deps ca-issuer python -m app.cli rotate-intermediates --compromised access

For that scope neither the replaced nor an earlier intermediate stays trusted: <scope>-retired.pem is empty afterwards, even if the host clock is wrong. After restarting ca-issuer and the gateway (frps follows), the ca-issuer renews no certificate of the old intermediate, and it is in no trust bundle. frps then refuses client certificates of the old one in the TLS handshake already, also when the client sends the intermediate along. The gateway checks against the root and lets them through the handshake, but the server answers with 403 ERR_CERT_REVOKED, also with MTLS_ENFORCE=false: it accepts only certificates that a listed intermediate of their scope issued (volume ca-trust). That alone does not close a leak: the root stays the same, and agents and desktops check the server against it. So still revoke the devices of the scope (Users & Access → Devices and revocation) and set them up again: for tunnel, provision every agent again; for access, enroll the desktops again and issue browser certificates anew; the ca-issuer issues the gateway leaf itself on start. Only a new root closes a leak completely. An unknown scope stops the run before anything changes.

Retired intermediates: they stay, without their keys, in <scope>-retired.pem in the ca-pki volume until they expire. If an entry there is not an intermediate of its scope under the root (after a restore with swapped files, say), the ca-issuer skips it on start with a WARNING in its log, status marks the line with SKIPPED (<reason>) and exits with 1, and the next rotation stops with a message naming the file and the entry. Then remove the entry from the file (backup first) and rotate again.

Certificate register and transition

The ca-issuer records every client certificate it issues or renews in a register; the server accepts recorded certificates only, also with MTLS_ENFORCE=false (see Users & Access → Devices and revocation). Certificates issued before the update to the register are not known to it yet. A transition applies to them:

  • They stay valid for 90 days from the update and are recorded at their first contact with the server or their first renewal. From then on they count like any other certificate until they expire.
  • A desktop or agent that reaches the server during this time is recorded that way; it renews its certificate as usual afterwards.
  • A .p12 that was not used during the 90 days is no longer accepted afterwards (ERR_CERT_REVOKED): export and import a new one.
  • A restore (restore.sh, pg-restore.sh) starts the transition again, 90 days from the restore, for the certificates the restored database does not know.

After the 90 days, only what is in the register counts.

frps supervisor

frps runs from the image ghcr.io/admincave/adminhelper/frps (source apps/frps/) under a supervisor (apps/frps/frps-supervisor.sh). The supervisor runs as root with the capabilities DAC_OVERRIDE, SETUID, SETGID and KILL; it starts frps as the user frps (UID 10002) without capabilities and asks the frps dashboard for its proxy lists as a user of its own, frps-fetch (UID 10003), both from programs these users can execute but not read. It reads the frps.toml the server writes (volume frp-config, read-only) and the ca-issuer's TLS material (volume frps-certs, read-only), checks both and starts frps only from a checked working copy in the frps-active volume, which frps can read but not change; no one but root and frps reads it. It writes its state to frps-state; from there the FRP page shows the frps state block (see FRP Tunnel). The UIDs 10002 (frps) and 10003 (frps-fetch) should not belong to any other account or service on the host.

  • Taking changes over: the supervisor polls the input every 5 s and takes a change over once it has stayed the same for two polls, i.e. after about 5–10 s. Valid: frps restarts from the new copy. Invalid: frps keeps running on the last valid copy; if there is none, it does not start (waiting). An unchanged input restarts nothing. docker compose restart frps is not needed for changes.
  • Check before every start, a restart after an exit included: the working copy must be unchanged and pass the check again; otherwise it is dropped (for a changed copy with the event copy_changed), and before a restart the supervisor takes the input over anew.
  • Exits: if frps ends on its own, the supervisor starts it again after 2, 4, 8 … at most 60 s; from the third exit within 60 s the state is crashloop, until frps has run for 60 s again.
  • Health check: docker compose ps shows frps as healthy in the states waiting, running and stopped, as unhealthy in degraded and crashloop.
  • Log: docker compose logs frps; the supervisor's lines start with [frps-supervisor] and carry codes and paths, never the token.

Keys allowed in extra_config

The supervisor takes over only an frps.toml in the layout the server generates. At top level, the server writes bindPort, vhostHTTPSPort, subDomainHost, maxPortsPerClient, detailedErrorsToClient, webServer.addr, webServer.port, webServer.user, webServer.password, auth.method and auth.token from the fields of the form. Via the FRP server configuration's extra_config only these can be added:

transport.maxPoolCount, transport.tcpMux, transport.tcpMuxKeepaliveInterval, transport.heartbeatTimeout, transport.tcpKeepalive, userConnTimeout, log.level, log.maxDays

Keys are compared exactly. Values are true, false, finite numbers or strings without quotes, backslashes, braces, control characters and lone surrogates (U+D800 to U+DFFF); the same character rule applies to the fields Subdomain host, Dashboard user, Dashboard password and Auth token. The server rejects other keys and values on saving with 422 (POST/PUT /api/frp/server-config); stored ones it cleans up at startup (see below).

Before an update

Before an update, check in the FRP server configuration:

  • extra_config and the fields Subdomain host, Dashboard user, Dashboard password and Auth token follow the rules above.
  • The Auth token has at least 16 characters.
  • A Dashboard port, if set, is neither 443 nor the Bind port nor FRP_BIND_PORT.

At startup, before it writes frps.toml, the server checks the stored configuration against these rules:

  • extra_config entries with another key (e.g. proxyBindAddr or log.to) or a value not allowed are removed from the stored configuration, and the admins get a bell notification naming the removed keys.
  • A field that ends up in frps.toml and breaks one of these rules (characters not allowed, an Auth token under 16 characters, a Dashboard port equal to 443, the Bind port or FRP_BIND_PORT) stays as it is. The admins get a bell notification naming the fields to set anew, once for as long as the same fields are affected. Its text is German (title "FRP-Server-Konfiguration: Felder neu setzen") and names each field by its label in the German form, with its rule in parentheses, e.g. "Der FRP-Server übernimmt die Konfiguration so nicht. Bitte neu setzen: Auth Token (mindestens 16 Zeichen), Dashboard Port (weder 443 noch der Bind Port noch FRP_BIND_PORT)." In English: the FRP server does not take the configuration as it is; set anew: Auth Token (at least 16 characters), Dashboard Port (neither 443 nor the bind port nor FRP_BIND_PORT).

Logs and notifications name keys and fields, never values. If the configuration fails the supervisor's check, frps keeps running on the last valid copy, if there is one. Without a valid copy, e.g. right after the update with an empty frps-active volume, frps does not start (state waiting, reason on the FRP page) until the configuration passes the check.

Enforcing mTLS (CERT_REQUIRED)

Since 0.29.0 the data plane (:443) runs enforced by default (MTLS_ENFORCE=true): the gateway requires a valid client certificate at the TLS handshake (CERT_REQUIRED) and the server rejects protected routes without a valid scope with 403. A fresh install is usable enforced via scripts/install.sh (it fetches the first admin's cert out-of-band). Permissive (MTLS_ENFORCE=false) lets certless clients through and only logs — needed only for a manual first bootstrap. Both are driven by one variable: MTLS_ENFORCE. Gateway and server read it the same way, case-insensitively: true, 1, yes and on enforce, false, 0, no and off are permissive, unset or empty means the default (enforced), and any other value enforces as well and logs a warning (fail-closed).

Enroll every client first, then flip

Only enforce once every client – agent, desktop and your own browser – holds a certificate, otherwise you lock yourself out. In the desktop this holds per server workspace that uses this installation; a sync workspace never presents a certificate, so whoever loads from this installation by sync takes a server workspace for it (Users & Access → API keys). Agent and desktop enroll automatically; prepare the browser via the desktop P12 export (Users & Access → Browser access). Test on real hardware first: Windows desktop enrollment and the browser import. Note that a browser leaf is long-lived (~1 year) and never renews. The server refuses a revoked one in both modes, but the revocation locks the browser out only under enforcement, because in permissive mode it reaches the login without a certificate as well.

Enforce:

bash
# in your .env:
MTLS_ENFORCE=true

# restart gateway + server (they read the variable at startup):
docker compose up -d gateway server

The gateway log confirms the mode at startup: mTLS ENFORCED (CERT_REQUIRED) or mTLS permissive.

Rollback (any time, lossless): set MTLS_ENFORCE=false and docker compose up -d gateway server – the data plane is permissive again immediately.

New clients after enforcing

The enrollment plane (:8444) always stays certless and token-gated – new agents and desktops fetch their first certificate there regardless of enforcement. A new user: an admin mints them an enrollment token (POST /api/enrollment/token/for) and hands it over out-of-band; in the desktop client the newcomer creates a server workspace with the server URL in the picker, picks "Enroll this device with a token" on its login screen, enters the token and enrolls – without a prior login. They then sign in normally (now with a certificate). No permissive window is needed for this (the decoupled enrollment door, ADR 0003).

Only the very first admin (there is no admin yet who could issue a token) is the special case — easiest via scripts/install.sh, which creates the admin + a first token out-of-band and then arms enforcement. Manually without the script: a one-time permissive setup window (MTLS_ENFORCE=false, enroll the first admin + desktop, then back to true).
