Users & Access

AdminHelper distinguishes three kinds of access: interactive users (web and desktop login), API keys (agents and scripts), and FRP provision tokens (single use). This page explains how to manage all three.

User roles

RoleCan
adminEverything: in the web panel manage users, create API keys, define hooks, the FRP server configuration and global settings; in the desktop client (server workspace) register servers and maintain connections, tunnels, monitoring, and Ansible.
userManage own connections, read servers and monitoring. No admin actions. In the web panel the role only sees a pointer to the desktop client.

Creating a user

User management is part of the web admin panel – Users is also the default page after login.

  1. Open Users → New in the web panel
  2. Assign username and password; the password is hashed with bcrypt
  3. Choose the role – admins see and edit everything

Admins can reset other users' passwords at any time. When an admin changes their own password in the web panel, the server ends every session of the account, and the panel signs them out at once with a notice; when they remove their own admin role, the admin pages disappear at once. Regular users can change their own password in the settings.

The assignment of servers to a user stays in the web panel: it is maintained directly in the user dialog (it controls which servers the user sees). The server entries themselves are created and edited in the desktop client (server workspace, Infrastructure).

Login flow

The login flow uses JWT (HS256) with refresh-token rotation:

  • Access token: valid for 8 h, sent on every request in the Authorization header.
  • Refresh token: valid for 7 days, rotated on every use (the old one is blacklisted immediately).
  • Reuse detection: if a blacklisted refresh token is submitted again, the request is rejected and the event is logged as a possible token theft.
  • Sign-out after inactivity: the web panel signs out in all open tabs once none of them has seen any input (mouse, keyboard, touch) for 30 minutes; a notice stays until you close it. WEB_IDLE_TIMEOUT_MINUTES sets the duration, 0 turns it off (environment variables). This also holds after a reload or reopening in the same browser: if the last input there lies further back than that duration, the session ends right on load with the same notice, and so it does when the stored time lies after the computer's clock (clock set back) or cannot be read.
  • Maximum session length: regardless of input, the server ends a web panel session 24 hours after sign-in; then a new sign-in is needed. WEB_SESSION_MAX_HOURS sets the duration, 0 turns it off (environment variables). The desktop app is not affected.
Login rate limit

5 failed login attempts per IP within 60 seconds → further attempts are rejected with 429. A successful login resets the counter. Implemented via Redis (fixed-window), with an in-memory fallback for single-worker setups.

Browser access (client certificate)

Once the data plane is switched to CERT_REQUIRED, every browser opening the web panel needs a valid client certificate from the internal CA. Unlike the agent and the desktop, a browser cannot fetch a certificate itself — you export one once from the desktop client and import it into the browser's certificate store.

  1. Export: Desktop client, signed in to a server workspace → Settings → This workspace → Export browser certificate. Choose a password (at least 12 characters) and click Export — pick a strong one: the .p12 container protects the private key with only a weak KDF, so a short password would be brute-forceable offline if the file leaks. The client enrolls a long-lived access certificate, packages it as a password-protected .p12 and asks via a save dialog where to write it (default name adminhelper-browser.p12).
  2. Import – Chrome/Edge: Settings → Privacy and security → Manage certificates → Your certificates → Import, pick the .p12, enter the password. (On Windows/macOS the certificate goes into the OS store; the exact menu wording varies by version.)
  3. Import – Firefox: Settings → Privacy & Security → Certificates → View Certificates → Your Certificates → Import, pick the .p12, enter the password.
  4. Connect: reload the web panel. On the first request the browser asks which client certificate to present — choose the imported one.
Browser cert under enforced mTLS

Since 0.29.0 the data plane runs enforced by default (CERT_REQUIRED) — a browser without an imported certificate is rejected at the TLS handshake and the web panel won't load. Every user who uses the panel in a browser exports their own .p12 from their desktop: the certificate belongs to the user it was issued for, and the server accepts it for that user's login only. The browser certificate is long-lived and does not auto-renew — just export and import a fresh one before it expires.

Onboarding a new user under enforced mTLS

Once the data plane is enforced (CERT_REQUIRED, see Operations & Config), a brand-new client without a certificate can't get through the :443 handshake — not even to log in. Onboarding therefore goes through the decoupled enrollment door (ADR 0003): cert first via a token, login second.

  1. Create the user (admin) – as under "Creating a user" above. The certificate CN will be exactly this username. Under mTLS the certificate belongs to this user: login, API and certificate issuing accept it for them only. In the desktop the device identity belongs to a server workspace, which is therefore assigned to one user; whoever wants to sign in on the same desktop as another user creates a server workspace of their own for it and enrolls it, or resets the device identity of the workspace and enrolls it anew for themselves.
  2. Issue an enrollment token (admin, who already holds a cert): in the web panel under Users, click Enrollment token in the new user's row, pick the validity (10 minutes, 1 hour or 24 hours; 10 minutes by default) and click Issue. The dialog shows the one-time token exactly once, with Copy and its expiry in local time; once closed, it cannot be retrieved again. Via the API: POST /api/enrollment/token/for with { "username": "<new-user>", "ttl_minutes": 60 } (ttl_minutes 1 to 1440, 10 if omitted); the response carries the token and its expiry expiresAt.
  3. Hand the token over out-of-band – via a secure channel to the new user (copy-paste). It is single-use and short-lived.
  4. Enroll the device (new user): in the desktop client create a server workspace with the server URL in the picker and open it, pick "Enroll this device with a token" on the login screen, enter the token → Enroll device. The client generates a key on-device, fetches its certificate at :8444 and stores it in the OS keyring as the device identity of this workspace. No login needed.
  5. Sign in – then the normal login (username/password); the client now presents its certificate at the handshake.
  6. Optional browser – for the web panel the user exports a .p12 from the desktop and imports it (see "Browser access" above).

If mTLS is not enforced and the user is already signed in, they enroll the device without signing out: in the Settings under This workspace enter the token → Enroll device. The tunnel then starts with the new certificate.

Once the device is enrolled, the Settings under This workspace (server workspace, signed in) show for whom and until when: “Enrolled as admin until 13/01/2027”. The name is the CN of the device certificate, the date its expiry in local time. The certificate is renewed at sign-in from half its lifetime on; with 14 days or fewer left, that has not succeeded so far, and the line adds “expires soon”. If the certificate has expired or cannot be read, the line says so as well: then Reset device identity and enroll the device with a new token.

Exception: the very first admin

For the first admin there is nobody yet who could issue a token. Easiest is scripts/install.sh (it creates the admin + a first token out-of-band and arms enforcement). Manually without the script: a one-time permissive window (MTLS_ENFORCE=false, create the first admin + enroll the desktop, then MTLS_ENFORCE=true). From then on every further onboarding goes through the token door — no more loosening.

Devices and revocation

Every client certificate the ca-issuer issues is recorded in a register and assigned to a device: a desktop (each server workspace that enrolls is a device of its own), an exported .p12 or an agent. A renewed certificate stays with the same device. The server accepts a certificate only while its device is not revoked; otherwise it answers 403 with ERR_CERT_REVOKED, also with MTLS_ENFORCE=false.

  • Deleting a user blocks every certificate issued for that user up to then, at the server as well as at renewal. If you later create a user with the same name, they register their devices anew; the old certificates stay blocked. The device list of the new user shows the devices of the deleted one as revoked. An enrollment token issued up to the deletion and not yet redeemed no longer works afterwards.
  • Revoking one device (admin): GET /api/users/{id}/devices lists the devices of a user with kind, fingerprint, lifetime and revocation; DELETE /api/users/{id}/devices/{device_id} revokes one. The user's other devices stay. A revocation through the API is recorded in the audit log (device.revoked).
  • “Reset device identity” (desktop) first revokes the device at the server, then deletes its certificate on the device. If the server does not revoke it, for example because it cannot be reached, the desktop says that it reset the identity locally only (see Troubleshooting).
  • Deleting a workspace (desktop, in the picker): if a server workspace has a device identity, the desktop first revokes the device at the server and then deletes the workspace on the device. If the server does not revoke it, the picker reports “On this device only”; the device then stays valid at the server until an administrator revokes it through the device API, because a later registration, of a new workspace too, does not replace it.
  • Registering again: when a server workspace registers again, the new certificate replaces the previous one of this device. A .p12 is a device of its own and replaces nothing; you revoke one that is no longer needed through the device API.

Deleting and revoking lock the API at once; they do not lock a tunnel whose visitor configuration the user already has (see FRP tunnel: revoking tunnel access).

API keys

API keys authenticate non-interactive clients (Go agent, scripts, CI jobs). Differences from user credentials:

  • No expiry, but revocable with one click
  • One of two permissions: read (read only) or read_write (read and write)
  • The server stores only the SHA-256 hash; the clear text is gone after it is shown once

Creating API keys:

  1. Web panel → API Keys → New
  2. Assign a name and choose the permission (read or read_write)
  3. Copy the clear-text key immediately – it is never shown again
  4. Send it as the HTTP header X-API-Key: <key>. The ?api_key=… fallback (for sync URLs) ends up in the access logs in cleartext and is logged server-side as a warning — prefer the header, and rotate a key exposed this way.

Sync workspace in the desktop: a sync workspace never presents a device certificate. Against an installation that enforces mTLS (the default of scripts/install.sh) its fetch therefore fails in the TLS handshake already: for your own installation take a server workspace there, which loads the same connections after the sign-in. A sync workspace against your own installation works only without enforced mTLS (--permissive or MTLS_ENFORCE=false).

IP restriction

With ALLOWED_IPS all access can be limited to a whitelist. Example:

.env
ALLOWED_IPS=10.0.0.0/8,192.168.1.0/24,203.0.113.42

ALLOWED_IPS applies to every request to the server, agents and desktop clients included, and checks the client address the gateway sees: the gateway passes it on in X-Forwarded-For, and the server evaluates that header only from the gateway (TRUSTED_PROXIES, see Installation). So the list holds the networks of the clients, not the Docker network of the gateway; with another proxy in front of the gateway, that proxy's address counts. Earlier versions checked the gateway's address here: if you set ALLOWED_IPS to it, add the networks of the clients before the update, or the server rejects them with 403. Until the server has resolved the name gateway — on the first requests after it starts, and up to 30 s after a restart of the gateway with a new address — it still sees the gateway's address and rejects such a request unless the list holds the Docker network.

If the list is left empty, access is open (for reverse-proxy- or VPN-protected setups).
