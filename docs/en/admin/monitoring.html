Monitoring

Define checks, set thresholds, wire alerts into hooks. Since v0.32.0 checks, alert rules, and templates are maintained in the desktop client (in a server workspace) – on the fleet-wide Monitoring page and per server in the Monitoring tab under Infrastructure. The actual evaluation happens in the separate monitoring service, backed by VictoriaMetrics for metric storage (configurable retention, default 90 days).

Check Types

The type identifier (check_type) is exactly the value the desktop client shows in its dropdown. Server-side probes (ping, tcp, http) run inside the monitoring container; all agent_* and plugin checks evaluate data pushed by the agent; disk_forecast reads the metric history from VictoriaMetrics.

Private targets: what is allowed

ping and tcp may probe private and internal addresses (10.x, 192.168.x, localhost) – that is exactly what they are for. http checks and alert webhooks still reject private/reserved targets (SSRF protection): they return resp. forward response content, which could be used to pull cloud-metadata credentials. Creating checks is admin-only in any case.

“Run now” exists for pull checks only

Push-evaluated checks (agent_resources, service_process, proxmox_backup, zfs_health, docker_health, smart_health, system_state) receive their data solely through the agent push and therefore cannot be triggered manually – the button is greyed out there and the API answers 409. The same applies to disabled checks. agent_ping is deliberately exempt: it measures the absence of a push and is evaluated by the scheduler, so it can be run manually.

Agent plugins are auto-detected

The plugin checks proxmox_backup, zfs_health and docker_health only evaluate data when the agent finds the subsystem's tool (pvesh, zpool, docker) on the host. If it is absent, the check simply has no data (unknown) – that is not an error. If Docker, ZFS or Proxmox is installed but cannot be read (the Docker daemon does not answer, a call fails or hangs, the output of Docker or pvesh is unreadable, a backup storage of the Proxmox host is not active), that is an outage: docker_health, zfs_health or proxmox_backup goes warning and notifies (see Docker, ZFS and Proxmox outages). So an unreadable Proxmox does not report VMs without a backup. The agent also logs the reason of a Docker, ZFS or Proxmox outage as a warning (also in the adminhelper-agent diagnostics report). The agent_* and plugin checks require the Go agent on the target; ping/tcp/http need no agent.

Service check (service_process)

The check has two modes (mode, list if not set):

  • auto reports failed services (units with .service and Windows services) as critical, other failed units such as a mount, timer or socket and units that are enabled but not running as warning. The message names them separately, e.g. Failed: nginx.service; Failed units: data.mount; Inactive (autostart): cron.service. Services that are not running by design are not reported: a oneshot service that finished normally, a unit whose condition (Condition…=) did not hold at start, and a service started by a timer, socket or path. The agent does this re-check, so a freshly installed host no longer sits on warning for good. A unit whose start was never attempted, for example because a dependency failed or its target was never reached, is still reported. ignore hides units, with or without .service and as glob patterns (*, ?, […], case-sensitive), e.g. drkonqi-coredump-processor@* for all instances of a template unit. If the agent cannot query the services (systemctl list-units fails), the check is unknown with the reason instead of ok.
  • list checks the services entered under services, with or without .service; aliases such as sshd for ssh.service work. The monitoring service evaluates the list itself from the agent's service inventory, nothing needs to be set up on the agent (no monitor init --services). The agent sends the full inventory as soon as a service state changes and otherwise at least once an hour; in between, the last evaluated state applies. A newly entered name may therefore have no data for up to an hour. If an entered service is not running, the check is critical. A name without data (a typo, not installed on the host, not in the inventory yet) does not count as down; it is listed as “not found”, and the check only becomes unknown when no name has data at all.

In the desktop client, a server's services line shows the number of problems, red or yellow according to the check's status (a first failing measurement that is still damped, see consecutive_fails, does not color it). In auto mode it adds “x/y active” (running of loaded services) when the agent sends these numbers – older agents do not –, in list mode “x/y running”. Below it are the affected services, each name once: “failed” (red for services, yellow for other units such as a mount, timer or socket), “inactive (autostart)”, “not running” or, in grey, “not found”. While the check has no data yet, the line says “No data yet”; when it is unknown, “No data”. In the check editor, hints below the Services and Ignore fields explain which names and patterns are allowed; the editor removes duplicate entries when you leave the field.

Docker check (docker_health)

The check rates every container by how it ended. The restart policy only decides whether a container that ended was stopped on purpose: with always or unless-stopped Docker restarts a crashed container, so one that sits at exited was stopped by hand. With no and on-failure a crash and a stop cannot be told apart, so the exit code decides.

The check's status is the worst rating of its containers; stopped ones count as ok. The message is in English and counts running and stopped containers, e.g. “Container problems: web: exited with code 3 (2 running, 0 stopped)”. Of a list, the message names at most ten entries and at most 1000 characters, each entry at most 500 characters long, and sums up the rest as “(+N more)”; the check's container list shows them all. This holds for every check whose message names a list, such as VMs without a backup, pools, disks or services. ignore_containers hides containers by their exact name, say an old container that ended with an error and is meant to stay, or one that restarts on schedule. With an older agent, OOM and the restart counter are missing; the check then reads the exit code from the docker ps status text.

The check spots a restart by Docker's restart counter: if it is higher than at the previous push of the same container, the container is restarted. In the standard template “Docker Host” (consecutive_fails 2) a single restart therefore only shows in the container list; status and notification stay damped. Only when the container restarted at two pushes in a row, as in a crash loop, does the check go warning.

In the desktop client the Docker line counts running and stopped containers separately (“3 running · 1 stopped”) and names the reason per container, also while the check is ok: “exited with code 3”, “out of memory (OOM)”, “restarted 2×”, “health check failing”, “paused”, “never started”, “stopped”. Stopped containers are grey and at the end of the list.

System state (system_state)

The check rates the system_state block the agent sends with every report from report version 3 on, on Linux. Each of the four points makes it warning, never critical: each is a maintenance task, not an outage. The message is in English and names all points, e.g. “Reboot required; 3 security updates pending”, otherwise “System state OK”.

PointSwitchSource on the hostMessage
Reboot requiredcheck_rebootDebian family (apt-get on the search path): the file /var/run/reboot-required; RPM family: needs-restarting -r (exit 1)Reboot required

Pending security updatescheck_security_updatesapt-get -s dist-upgrade (simulated only; counts the packages from a security source) or dnf -C -q updateinfo list --security; at most once an hour3 security updates pending
OOM killscheck_oomgrowth of the oom_kill counter in /proc/vmstat since the last report sent successfully; in a container the counter of its own cgroup in /sys/fs/cgroup/memory.events2 OOM kills since last report

The agent only asks the host itself, without network access: apt-get -s and dnf -C read the local package lists, and the agent does not refresh them (no apt update, no dnf makecache). The number of security updates is therefore as current as the host's last package list refresh. The agent counts at most once an hour and sends the last value in between; after the updates are installed the warning may thus stay for up to an hour. If both apt-get and dnf are present, apt-get wins. The check rates the clock only from 15 minutes of uptime, since the NTP client needs a while after boot; if the agent reports no uptime, it rates it right away.

An OOM kill is in the one report after the kill only; with the next report the check is ok again. It therefore reports OOM kills only with consecutive_fails 1; from 2 on a single kill stays damped. The check from the standard template "Linux Server — Standard" has 1, and the check form and the template editor in the desktop suggest 1 as soon as you pick the type system_state there (editable; switching to another type with the 1 unchanged brings back the value from before the pick, 3 for a check already stored that way); without a value, e.g. via the API, it stays at 3. The counter only counts as sent after a successful push, so a lost push loses no kill. On the agent's first run there is no previous counter and so no point; if the counter is smaller than the saved one (the host rebooted), it counts in full.

In a container, /proc/vmstat counts the OOM kills of the whole host. There the agent therefore reads the oom_kill counter of its own cgroup from /sys/fs/cgroup/memory.events (cgroup v2); it counts the kills inside the container, including those in sub-cgroups such as the services of a systemd in the container. A container is what the agent detects as its virtualization (the same detection as in the report's host block): lxc, docker, openvz or rkt with the role guest. This detection does not know Podman containers; there the host's kills still count (not verified). Without cgroup v2 (cgroup v1, no memory.events) the point is missing in a container, with a warning in the log, rather than reporting the host's kills. If the counter's source changes, say because the agent only detects a container after an update, the point is missing from one report; after that the agent counts from the new source. Checked in Docker; not verified in an LXC on Proxmox VE.

If the agent could not determine a point (a call fails or hangs, the output is unreadable), it is missing from the block and the check rates the others; the agent logs the reason as a warning (also in the adminhelper-agent diagnostics report). If a point has no source on the host (for the reboot neither apt-get nor needs-restarting, for the updates neither apt-get nor dnf), it is missing without a warning. Without the block, that is with an agent before report version 3, on Windows or when not a single point could be determined, the check stays ok with “Not evaluated: no system state in report”, without unknown. The switches (true each) turn single points off, e.g. check_reboot: false on a host that a fixed maintenance window reboots; the check details (reboot_required, time_synchronized, security_updates, oom_kills, null when not determined, plus problems) keep showing the value.

In the desktop client the check sits in the “System state” section of the server dashboard. Its line shows one pill per problem (“Reboot required”, “Clock not synchronized”, “Security updates: 3”, “OOM kills: 2”), yellow once the check is warning and grey while consecutive_fails still damps the problem; without a problem it says “All OK”, without the block “Not evaluated”. Expanded, it lists the four points with their value or “not determined”; a value the check does not count as a problem (point switched off, clock in the first 15 minutes of uptime) shows grey.

Two gaps: whether Debian and Proxmox VE create the file /var/run/reboot-required on a kernel update is not established; there a required reboot may go unreported, a missing hint, not a false alarm. The path for RPM distributions (needs-restarting, dnf) has not been tested on a real host (not verified).

Docker, ZFS and Proxmox outages

If docker, zpool or pvesh is installed, the agent sends the Docker, the ZFS and the Proxmox block with every push, even when it cannot read the subsystem. Instead of the containers, pools or VMs the block then carries an error code:

CodeMeaning
daemon_unreachableDocker: docker info fails, the daemon is not running or cannot be reached.
timeoutA call hangs: docker for more than 10 s, zpool list or a pvesh get for more than 15 s (on a suspended pool or a Proxmox cluster without quorum, say).
cli_faileddocker ps, docker inspect, zpool list or a pvesh get ends with an error or does not start, e.g. in an LXC container without the ZFS module; for Proxmox also an unreadable hostname of the host.
parse_failedThe output of docker ps, docker inspect or a pvesh get is unreadable.
backup_index_incompleteProxmox: a backup storage of the host is not active (an unreachable NFS share, say). Without it the backups of the VMs on it would be missing, and the check would report them as “no backup”.

For Proxmox the agent reads the node status, the host's backup storages, their backups and the VM list with pvesh get; any of these calls can trigger the outage. The check then goes warning and notifies like any warning (after consecutive_fails). The message is in English and names the code and the call, e.g. “Docker unavailable (daemon_unreachable): docker info failed: exit status 1”, “ZFS unavailable (timeout): zpool list timed out after 15s” or “Proxmox unavailable (backup_index_incomplete): backup storage nas not active”. In the desktop client the line shows the error for Docker, ZFS and Proxmox (“Docker daemon unreachable”, “zpool timed out”, “Backup storage not active”) instead of the container, pool or VM list. If Docker is not meant to run on a host or the ZFS module is missing (in an LXC container, say), alert_on_unavailable: false switches the alert off; proxmox_backup has the same switch. In the check editor it is the “Report outage” checkbox for all three. During an outage the check is then unknown with the same message and does not notify; the desktop client then shows the error in grey.

Not an outage: a reachable Docker daemon without containers, ZFS without pools and a readable Proxmox without VMs/CTs are all ok. If the block is missing altogether (tool uninstalled, or an older agent cannot read Docker, ZFS or Proxmox), the check is unknown, and the display clears the container, pool or VM list it showed last.

Creating a check

  1. Desktop client (server workspace) → Monitoring → New check (or per server: Infrastructure → Server → Monitoring tab)
  2. Pick the type, choose the target (server or URL)
  3. Fill in the parameters – type-specific, e.g. for http: URL, expected status code, timeout
  4. Set the interval, severity (severity), consecutive_fails and consecutive_oks (1–100, default 2) – the thresholds themselves live in the type-specific configuration (next section)

Thresholds & status

Every check evaluates to one of four states: ok, warning, critical or unknown. The thresholds live in the type-specific check configuration – there is no global threshold field. The configuration is validated strictly: unknown keys and out-of-bounds values are rejected at save time (instead of silently degrading to unknown). Switches such as verify_ssl, exclude_stopped and alert_on_unavailable take only true or false; "false", 0 or "no" are rejected. Any other value stored earlier counts as the default, as the check editor shows it. Number fields such as cpu_warn or timeout take only finite numbers, integer fields such as port and expected_status only whole numbers without a decimal point (22, not 22.0); "85", true, Infinity or NaN are rejected. A number in exclude_vmids is a VMID from 100 to 999999999, the Proxmox VE range. A number string stored earlier stays until the configuration is saved with a number in its place: the check editor shows the field empty, and whoever changes the configuration enters a number there.

In addition, every check carries three damping parameters: severity (how the check is classified), consecutive_fails (how many failing measurements in a row are needed before the status flips – anti-flapping; at a 5-minute interval a value of 3 means the condition must hold for ~15 minutes) and consecutive_oks (how many ok measurements in a row a check with a reported problem needs before it returns to ok; default 2). Until then the check keeps its status. One exception: a new check whose first result is unknown shows unknown right away instead of ok, for example a Docker check on a host whose agent sends no Docker block. A first warning or critical stays damped, and an existing check keeps its status on a single unknown.

Only a reported problem is held: once the alerter has reported warning or critical, the check shows that reported status until the recovery, with the message of the ok measurement and the suffix “(recovery n/m)”, e.g. “(recovery 1/2)” – also if it stood worse in between, muted during a maintenance window for instance, or comes back via unknown; the display can rise as well, from a muted warning or an unknown back to the reported critical with “(recovery 1/2)” for instance, without anything being reported. The notification and the all-clear in the bell come only with the change to ok, so with the default 2 one check interval later than without the hold. A problem that was never reported, because it stayed muted during maintenance or host-down for instance, recovers silently on the first ok; a new check and a check that is already ok are never held. Any other measurement in between starts the count over: a check that flaps, or alternates between ok and unknown (because the agent leaves out a block now and then, say), does not recover until consecutive_oks ok measurements come in a row. consecutive_oks 1 recovers on the first ok, as before the hold. In the standard templates only Disk Forecast sets consecutive_oks 1: it runs hourly and so reports the all-clear on the first ok instead of an hour later; every other check of the standard templates, SMART Health included, uses the default 2.

Alert behavior: damping & suppression

Hysteresis

The agent_resources check applies a per-metric release threshold: once a server's CPU sits at warning, its thresholds drop by hysteresis_pp (default 10 percentage points) until the metric clears. A server hovering around the 90 % mark produces one notification instead of a flapping series – only dropping below 80 % counts as recovery. The same holds for swap and for the inodes of each mount, each with its own release threshold (a disk at warning does not lower the thresholds of its inodes). The load per CPU has none: it is no percentage, load_5m already averages over five minutes, and it clears as soon as it is below load_warn.

Disks: minimum free GB and mounts

A large disk at 85 % still has hundreds of GB free. A disk's percentage alarm (disk_warn/disk_crit) therefore counts only when, in addition, less than disk_min_free_gb is free (default 20 GB, for existing checks without the key too; 0 turns the gate off, then the percentage alone counts). The message then names the free GB, e.g. "Disk / 85%, 15 GB free (>=85%)". The agent reports the free GB from report version 3 on, on Linux and Windows; for older agents the percentage alone counts, as before. Once the free GB rise above the gate, the disk clears, from its release band too; the gate does not touch the inodes. Per mount, disk_overrides sets its own values, e.g. {"/data": {"warn": 90, "crit": 95, "min_free_gb": 100}}; each of the three keys is optional, a missing one takes the global value. A mount in ignore_mounts is rated neither on usage nor on inodes; the check details still list it, with ignored: true. Both take exact mount paths such as /boot/efi, no patterns.

In the check editor, the ignored mounts are a comma-separated list in the “Ignore mounts” field and the per-mount values a table, “Thresholds per mount”: one row per mount with “Warning (%)”, “Critical (%)” and “Min. free GB”, added with “Add mount” and removed with “×”. An empty field is left out of the entry, so the global value applies there; a row without a mount is not saved. If the same mount is in two rows, the editor shows a hint and only the first row counts. Without a single row, disk_overrides is left out of the configuration.

unknown never notifies

Transitions into unknown (missing agent data, unreachable data source, incomplete configuration) never trigger a notification – the state stays visible on the dashboard, but it is not an incident. One exception: Docker, ZFS or Proxmox that is installed but cannot be read (the daemon does not answer, zpool list or pvesh hangs, a backup storage is not active) is not unknown but warning and notifies, unless alert_on_unavailable is switched off (see Docker, ZFS and Proxmox outages). A real "agent gone" is reported by the agent_ping check going critical. If the monitoring service's clock jumps (NTP correction, resumed VM), the heartbeat subtracts the jump and keeps grading on the real silence — a fresh agent stays ok, a genuinely dead one stays critical. Only if the service restarts right after a jump does it lose the reference point: until the next agent report (5 min by default) the plain wall clock decides again. unknown → ok only produces a recovery notification when a problem was actually reported before – a check flapping between ok and unknown stays entirely silent.

Host-down suppression

While a server's agent_ping or its Host Ping (the ping check of the standard template “Host Ping”, see Templates) stands at critical, the other checks of that server stay silent (inhibition): one incident, one notification. So that the two never silence each other, a rank order applies:

Checkstays silent while … stands at critical on the same server
Host Pingnothing (only a maintenance window silences it)
agent_pingthe Host Ping
all othersthe agent_ping or the Host Ping

When the host goes down, only the Host Ping reports; when the agent falls silent on a host that still answers ping, the agent_ping reports. Only an enabled check of the template counts as Host Ping: a ping check set up by hand, on a gateway for instance, silences nothing. The suppression lifts once the suppressing check is back at ok, that is only after its hold if its outage was reported: it then needs consecutive_oks fresh measurements in a row (default 2; in the standard templates the agent_ping runs every 5 minutes, the Host Ping every minute). After that the next evaluation cycle catches suppressed reports up – even without a new status change. This holds for the heartbeat too, but only after its next check, as until then its status dates from the outage: once the Host Ping is back and the agent is still silent, the bundled alert catches its outage up; if the agent reports again by that check, the outage never reported recovers in silence. A check that went critical during the outage and stays critical is therefore reported within consecutive_oks intervals of the suppressing check plus its own check interval at the latest.

Bundled alert for silent agents

When a site or an uplink goes down, many agents often fall silent at once. Instead of one notification per server, a bundled alert goes out. For this the agent_ping no longer reports on its own: a background job looks every 30 seconds for heartbeats with a discrepancy not reported yet, split into “silent” (critical) and “back” (ok).

  • With 3 or more of one kind, one bundled alert covering all of them goes out at once. When a third agent falls silent while the first two are still waiting (next point), one notification therefore covers all three; their return is bundled the same way.
  • With fewer, each one waits for more after its status change: 5 minutes, but at most until a minute before its next check, so 4 minutes for the standard heartbeat (interval 5 minutes) and not at all for an interval of 1 minute. Then it is reported on its own as before, with the job's period up to 30 seconds later. An outage is thus reported before the next check can set the agent back to ok, and its return is then reported as well.
  • Maintenance windows and host-down suppression apply as for any check: a muted agent does not count and stays open. Once the suppression ends, it counts again only after the next check of its heartbeat, as until then its status dates from the suppression: the heartbeat was last checked in the maintenance window or before the Host Ping of its server last changed. If the agent is still silent at that check, it counts again: from three on bundled at once, otherwise on its own as soon as its wait since the status change is over, so at once after a suppression that lasted longer than the wait. If it is back, the outage never reported recovers in silence. Since the heartbeats are not all checked at the same time, several notifications may come after a suppression instead of one.

Bundling happens per channel:

  • Alert rules (webhook, email): a rule that matches three or more of the agents sends one message with the subject [AdminHelper Monitor] CRITICAL: <n> agents not reporting or [AdminHelper Monitor] RECOVERY: <n> agents reporting again; the level in the subject is the highest severity of the agents. The text has one line per agent with the server and the heartbeat's message, at most 50, then … and <k> more; the server is named as in a template assignment, otherwise by its server_id. Agents for which the rule is in its cooldown do not count when they fall silent; the return bypasses the cooldown. The alert log gets one row per agent, so the cooldown still applies per check. A rule that matches fewer than three, because it is filtered to one server for instance, sends the usual single messages.
  • The webhook of a bundled alert carries the fields of a single one, but check_name and server_id are null. The agents are listed in the additional field members, each with check_id, check_name, server_id, server_name, old_status, new_status and message, also beyond the 50 lines of the text.
  • Bell: three or more agents make one entry “[AdminHelper Monitor] Agents not reporting (n)” or “[AdminHelper Monitor] Agents reporting again (n)” with one line per server. Each user sees only the servers they may see and one of their rules covers, and n counts only those. The agents are split by the level they reach the bell with (their severity, on the return the level of their alert): when agents with severity critical and with warning fall silent together, two separate entries come, one per level from three agents on; below that each agent of the level gets an entry of its own. The bell's cooldown still applies per agent.
  • E-mail of a personal rule (notification hub, below): the mail for the bell entry has its own n and its own lines. It names only the servers a rule with e-mail covers; a server that only a rule without e-mail covers is in the bell but not in the mail. When no rule with e-mail covers any of the servers, no mail goes out. Telegram, once enabled, follows the same rule.

Maintenance windows

Maintenance windows are defined per server – one-off (start/end) or weekly (weekdays + time window in an IANA time zone, e.g. Europe/Berlin; daylight-saving transitions are handled correctly). They are managed in the server's Monitoring tab (Infrastructure → Server → Monitoring); active windows show as a badge on the monitoring overview. The semantics are collect-but-mute: checks keep running and keep writing metrics/status, only notifications (alert rules and the notification hub) are suppressed.

Catch-up after the window ends

The alerter remembers, per check, the last reported status: a problem that outlasts the window, and a recovery of an alert reported before the window, are caught up after the window ends (within the check interval at the latest). A transition that happens entirely inside the window (e.g. ok → critical → ok during maintenance) stays permanently silent – there never was a reported discrepancy.

SMART monitoring

The agent auto-detects SATA, SAS and NVMe disks (smartctl --scan). For NVMe the critical-warning bits are decoded individually:

BitMeaning
0Available spare below threshold
1Temperature above critical
2NVM subsystem reliability degraded
3Media placed in read-only mode
4Volatile memory backup device failed
5Persistent memory region unreliable

In the smart_health check and its series, each disk goes by its device name, such as /dev/sda. Disks behind a MegaRAID or sssraid controller share the controller's device name (/dev/bus/N or /dev/bsg/sssraidN) and are therefore named as smartctl names them, such as /dev/bus/0 [megaraid_disk_00] or /dev/bsg/sssraid0 [sssraid_disk_00_01]. ignore_devices (“Ignore devices” in the check editor, comma-separated) leaves a disk out of the evaluation by exactly this name. The series carry the name with _ for every character other than letters, digits and _, such as monitor_smart_temp_dev_bus_0__megaraid_disk_00_value, likewise monitor_smart_reallocated_… and monitor_smart_pending_…. Older agents report all disks of a controller under its device name: after the agent update an ignore_devices entry /dev/bus/0 no longer matches, and the series of these disks start under the new names; monitor_smart_temp_dev_bus_0_value gets no more values.

Without a single disk with readable SMART data, the agent sends the reason instead of the values. smart_health stays ok and names it in the message (in English):

ReasonMessageWhen
not_installedNo SMART data: smartctl is not installedsmartctl (package smartmontools) is missing, typical on VMs.
scan_failedNo SMART data: the SMART query failedThe scan fails, hangs or prints no JSON, or no disk it found gives readable SMART data, for instance because smartctl cannot open the disk.
no_devicesNo SMART data: no SMART-capable devices foundThe scan finds no devices.

Older agents send no reason; the message is then “No SMART data (VM or smartctl not available)”. The agent package (deb and rpm) recommends smartmontools (Recommends, not a hard dependency): apt-get install and dnf install pull it in on a first install unless recommendations are switched off. On an existing host an upgrade of the agent does not reliably bring the new recommendation along (apt-get upgrade and dpkg -i do not install it); if the host has disks with SMART, install smartmontools by hand there (apt-get install smartmontools or dnf install smartmontools).

Disk forecast (time-until-full)

The disk_forecast check computes, per mountpoint, the time until "disk full" from the fill-rate history in VictoriaMetrics (linear regression over window_hours, default 24 h): warning when full within warn_hours (24), critical within crit_hours (8). Stable or shrinking usage is ok; with less than min_history_hours (6) of history the check stays unknown – and therefore never notifies (see above). It warns well before the static disk_warn/disk_crit thresholds fire. If VictoriaMetrics is unreachable, it is unknown as well, but with “Metrics store unavailable” instead of “No disk history yet”; the metrics request then answers HTTP 502, and the expanded chart of a check shows “Error loading” in the desktop client instead of empty series.

VictoriaMetrics

VictoriaMetrics stores the time series; retention is controlled by the compose variable VM_RETENTION (-retentionPeriod=${VM_RETENTION:-90d}, default 90 days). It is independent of the alert log (ALERT_LOG_RETENTION_DAYS, see below) – the two knobs do not sync. Check results carry the labels check_id, check_type, name and, for server checks, server_id; the agent metrics monitor_agent_* carry server_id, disks also mount, temperatures sensor. VictoriaMetrics stores the field value as <measurement>_value. Direct access (debug): http://victoria:8428/api/v1/query?query=monitor_check_status_value.

Ingest authentication

The agent sends its metrics via POST /api/monitoring/agent/{server_id}/report to the AdminHelper server (port 443, tunnel-free) and authenticates with its server-specific X-API-Key (issued at provisioning). The shared MONITOR_API_KEY is separate from that: it only secures the internal server→monitoring proxy leg (X-Internal-Key) and must be identical between the server and monitoring containers.

Overview: list, tiles & heartbeat

The desktop client's Monitoring page offers two switchable views (the choice is remembered):

  • List: server list with dashboard – uPlot line charts, checks overview, alert rules and the alert log. Selectable time windows: 1h, 6h, 24h, 7d, 30d; clicking a line opens the detail view with raw data.
  • Tiles: one tile per server, colored by the worst check status, with a heartbeat bar – the bar shows the availability of the last 24 h from the agent_ping timeline (servers without an agent_ping check show no bar).

If servers exist that have no check at all, the overview shows a banner ("N servers without monitoring") with a direct bulk-assign dialog: servers preselected, template selectable (standard templates first). The view refreshes automatically every 30 seconds.

Templates

A monitoring template bundles several check and alert definitions and is assigned to a server instead of creating each check by hand. On assignment the definitions are materialized into real checks and alert rules for that server.

  1. Desktop client → Monitoring → Templates → create a template, add check and alert definitions
  2. Assign the template to a server – AdminHelper creates all contained checks and alert rules
  3. When the template is edited later, a live sync runs: every assigned server is updated automatically (checks created, updated or deleted). Each definition carries a stable def_id the sync uses to match. Fields customized on a single check and deleted template checks are left out by the sync (see Customizing template checks).

Definitions may use placeholders that are substituted per server at assignment time:

PlaceholderReplaced with
{{hostname}}Server hostname
{{server_name}}Server display name
{{server_id}}Internal server ID

Each assignment keeps the hostname and display name. When either changes on the server, the reconciliation that also maintains the tag assignments (immediately after the server change and every 15 minutes) writes the new values into every assignment of the server, manual and tag-based alike, and syncs its checks and alert rules again; customized check fields stay.

Removing an assignment deletes the checks and alerts it created. Deleting a template removes them on all assigned servers.

Customizing template checks

A check created by a template can be edited, switched on and off or deleted like any other. Setting one of the fields name, description, type, configuration, enabled, interval, severity, consecutive fails before alarm or consecutive OKs before recovery to a value other than the template's marks that field on the check as customized: no sync overwrites it any more, all other fields keep following the template. A sync runs when the template changes (also through the update of a standard template, see below), when the server's hostname or display name changes (see above) and when deleted checks are restored; each one sets every field that is not customized to the template's value. Setting a field back to the template's value lifts the customization. Type and configuration belong together: a changed type also counts as a changed configuration, and with a customized configuration the sync does not take the template's type either. If the definition is removed from the template, the sync still deletes the check, customized or not.

  • Spot and reset: in a server's dashboard (Monitoring, view List) a customized check carries the badge "customized", its tooltip names the fields. The action "Reset to template" on the same line asks for confirmation, then sets every field to the template's value and lifts all customizations of the check.
  • Deleted template checks: a deleted template check stays deleted, the sync does not create it again. The server's Monitoring tab then shows "Restore N deleted checks" at the assignment ("Restore 1 deleted check" for one); the click creates these checks again with the template's values. Removing and re-adding the assignment brings all checks back as well.
Customizations from before the update

On the first start after the update the monitoring service compares every template check with its template once and marks every field that differs as customized, by the same rules as above. It resolves the template with the hostname and display name the check was created with: a server renamed since does not count as a customization, its checks follow the new name on the next reconciliation. This happens before any sync; if it failed at startup, the next sync catches up on it first, and if it fails there too, that sync does not happen until the detection succeeds. A check that cannot be compared (unreadable configuration or template definition) counts as customized in all fields; the service names it in the log.

Limits

If a template change was never synced to a check before the update, it shows there as a customization after the first start; "Reset to template" takes the template's values. The protection covers checks only: every sync sets alert rules from a template to the template's values, and the next sync creates a deleted alert rule again.

Standard templates

On first startup the monitoring service seeds six standard templates (English names). The thresholds distill the consensus of common tools (Zabbix, Netdata, Checkmk) plus Backblaze SMART statistics:

TemplateContents
Linux Server — StandardAgent Heartbeat (stale after 15 min ≈ 3 missed pushes), System Resources (CPU 90/95, RAM 90/98, disk 80/90 with less than 20 GB free, swap 80/95, inodes 80/90, load per CPU 1.5/3 – with consecutive_fails 3 ≈ 15 min anti-flap), Service Health (systemd, auto mode: failed services critical, other failed units as well as enabled but inactive units warning, see Service check), System State (warning with consecutive_fails 1, because an OOM kill is in one report only, see System state), SMART Health, Disk Forecast. Swap, inodes, load, the 20 GB and System State came with version 3.
Windows Server — StandardAgent Heartbeat, System Resources (CPU 90/95, RAM 90/98, disk 80/90, here too only with less than 20 GB free, the check's default; the agent does not report swap, inodes and load on Windows), SMART Health, Disk Forecast; without Service Health and System State
Proxmox HostProxmox Backups (backup age < 26 h; from version 2 with consecutive_fails 2 like Docker and ZFS: the check alerts only after two failed runs in a row, so a single read error of pvesh does not, see Docker, ZFS and Proxmox outages)

A critical Host Ping suppresses all other alerts of its server (host-down suppression, see Alert behavior). If the monitoring service cannot reach the host by ICMP, for instance because it is reachable only through FRP or a firewall filters ICMP, the ping sits at critical for good: then only it reports, and every other alert of the server stays silent. The ping check does not take an IPv6 literal as hostname (letters, digits, ., _ and - are allowed); the check then stays at unknown and reports no outage.

Seeding is one-time per template: a later restart does not create a deleted standard template again. A standard template that an update newly ships (like Host Ping) is created by the next start in an existing installation as well. The plugin templates (Proxmox/Docker/ZFS) are deliberately separate: on a host without the subsystem the check would sit at unknown forever. Host Ping, too, belongs to neither “— Standard” template and is never suggested (see below): you assign it on purpose.

Every standard template carries a version. When an AdminHelper update ships a newer version, the monitoring service does this at startup:

  • Unedited (check and alert definitions as last shipped): the service takes the new definitions and syncs all assigned servers; customized fields of single checks stay. The template's name and description do not count: a standard template that was only renamed is updated and keeps its name.
  • Edited (definitions changed): the template stays as it is. Monitoring → Templates shows "Update available" next to its name. The click opens a comparison of the current with the shipped check and alert definitions: "new", "removed" or "changed" per definition, for changed ones the fields in the columns "Current" and "Shipped". "Apply" replaces all definitions of the template, the alert definitions included, with the shipped ones and syncs the servers. Your own changes to the definitions are lost; customized fields of single checks stay, checks of removed definitions are deleted, alert rules get the shipped values.

A standard template created before versions were introduced counts as version 1; if its definitions differ from those of version 1, it counts as edited. Otherwise it follows a newer version like any unedited standard template.

When "Linux Server — Standard" follows version 3, every assigned server gets the System State check and its System Resources check the new thresholds. If someone customized that check's configuration on a server, it stays as it is, without the new keys; since the check takes the same value as the template for each of the new keys that is missing, it still rates swap, inodes, load and the free GB the same way.

Assigning templates

There are four ways to assign:

  • Template modal (Monitoring → Templates): server multi-select for bulk assignment, removal via the assignment pill.
  • Server-create dialog: optional template dropdown – hand a standard template to a server right at creation (opt-in, no automatic assignment by OS type).
  • Server → Monitoring tab: view, add and remove the assignments of a single server, and restore deleted template checks there; also assign or ignore suggested standard templates (see below).
  • Overview banner: the bulk dialog for all servers without checks (see above).

Suggestion in the Monitoring tab: with every report the agent sends its host's operating system and the subsystems whose program it finds on the search path: Docker (docker), ZFS (zpool) and Proxmox (pvesh). From these the server's Monitoring tab suggests matching standard templates. The top of the tab then shows "Suggested:" with a checkbox per template, its name and the reason (such as "detected: Docker"); all of them start checked. The tab fetches the suggestions when it opens.

  • Assign assigns the checked templates like an assignment by hand: their checks and alert rules are created right away, and their suggestion goes away.
  • Ignore remembers the refusal per server and template; that template is not suggested to the server again. This cannot be undone for now. The template can still be assigned by hand at any time.
  • A standard template is suggested only if it exists, is not assigned to the server yet (manually or via a tag) and was not ignored there. So a deleted standard template is not suggested, even when it fits. Removing the assignment of a standard template again brings its suggestion back.

Nothing happens unasked: AdminHelper assigns no template automatically, not by the detected operating system either. The suggestion appears only in the server's Monitoring tab, not in the monitoring overview. Agents before this version do not report the operating system and subsystems; their server gets no suggestion until the updated agent has reported once.

Tag assignment

A template can additionally be bound to a server tag (in the template modal): every server carrying the tag gets the template automatically – including servers that receive the tag later. The sync runs immediately on server changes and additionally every 15 minutes. When a server loses the tag, the tag-created assignment (and its materialized checks) is removed again. Tag-assigned servers are marked "via tag" in the template modal; a manually created assignment stays manual: the tag sync never removes it, it only refreshes its hostname and display name when these changed on the server (see Templates).

Notifications & alerting

Alert rules fire when a check changes status (e.g. ok → critical). Each rule optionally filters by severity and server and dispatches over one channel. A check's severity is also the highest level it reports with: a check with severity warning, such as Disk Forecast, reports a critical as WARNING in the subject and as warning in the bell, and does not fire the event hook; a check with severity info never shows up in the bell. The message text still names the real transition (e.g. Status: ok → critical) and the check's severity.

ChannelConfiguration
webhookurl – AdminHelper sends a JSON POST with check name, type, server, severity, old/new status and a plain-text message (10 s timeout, no redirects, success on HTTP < 300). For security (SSRF), targets that resolve to private/reserved addresses (e.g. 127.0.0.0/8, 10/8, 169.254.0.0/16) are rejected — reach an internal webhook receiver via a publicly resolvable name. The request goes to one of the addresses checked there, one after the other until one accepts the connection; Host header and TLS name (SNI and certificate check) stay the URL's hostname. If the monitoring service's environment sets a proxy for the URL's scheme (HTTP_PROXY, HTTPS_PROXY or ALL_PROXY), the request takes the previous path: the proxy connects and resolves the name itself; the target is still checked first. A target that does not go through the proxy because of NO_PROXY connects, as without a proxy, to one of the checked addresses. A bundled alert also carries the list members (see Bundled alert for silent agents).
emailrecipients (or to, also as CSV). SMTP defaults from the environment variables SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASSWORD, SMTP_FROM; overridable per rule with the keys smtp_host, smtp_port, smtp_user, smtp_password and from. A stored smtp_password is returned as ***; creating a rule with *** as the password is refused with 422. The stored password is kept on edit as long as smtp_host and smtp_port stay the same. If you change the relay of a rule or of a template's alert definition, enter the password again: *** is then refused with 422, and without a password the stored one is dropped. The credentials from the environment apply to SMTP_HOST only: if a rule sets a different smtp_host (compared case-insensitively; another name for the same relay, such as its IP, counts as a different host), it logs in only with its own smtp_user and smtp_password, and sends without logging in if either is missing. Port 465 uses implicit TLS (SMTPS); every other port uses STARTTLS. Both verify the server certificate (if TLS cannot be established the send fails rather than sending credentials in the clear), against the system CAs and, if set, the CA from SMTP_CA_FILE, which applies to every relay, a rule's own included (see Operations & Config → Relay with its own CA).

Cooldown: After a successfully sent alert, cooldown_minutes (default 30) suppresses further alerts from the same rule for the same check – including an escalation catch-up shortly after an actually sent alert. The bell (notification hub, its personal emails and the alert.triggered event hook below too) has a cooldown of its own, a fixed 30 minutes per check: it gets at most one problem report of a check in 30 minutes. Whatever falls into that time is dropped and not caught up, and the bell does not get the all-clear of a problem it never showed either. The escalation from warning to critical and the all-clear of a problem it showed always go through. Checks with severity info do not reach the bell.

Recovery: When a check returns to ok, a recovery notification is sent – it deliberately bypasses the cooldown so the all-clear always gets through. Its subject reads [AdminHelper Monitor] RECOVERY: <check>, like the alerts' [AdminHelper Monitor] <LEVEL>: <check>, where the level (INFO, WARNING or CRITICAL) is the new status, at most the check's severity. Line breaks and other control characters in the check name appear as spaces in the subject, and with it in the bell's title; the text and the webhook's check_name field carry the name unchanged. Every dispatch is recorded in the alert log with success/error, an error with its reason (e.g. No recipients configured). When the send itself fails, the reason names only the kind of error: for a webhook Webhook request timed out, Webhook connection failed or Webhook request failed (<error class>), for email SMTP connection timed out, SMTP connection failed, SMTP TLS failed, SMTP authentication failed (<SMTP code>), SMTP server refused the message or SMTP error (<error class>); if the rule itself cannot be processed (e.g. an smtp_port that is not a number), Dispatch failed (<error class>). The details, such as the mail server's reply, are in the log of the monitoring service (docker compose logs monitoring). The alert log is pruned automatically every day (retention configurable via ALERT_LOG_RETENTION_DAYS, default 90 days).

Event hook: On transitions into critical of a check with severity critical the server additionally fires the alert.triggered event hook (payload: server_id, severity, title, message); checks with severity warning or info never fire it. A bundled alert of silent agents fires it once per server whose heartbeat has severity critical, each time with that server's server_id. The hook follows the bell, so the bell's cooldown (see above) applies to it as well: when a check goes critical again within 30 minutes, e.g. critical → ok → critical, the hook fires only the first time, and an agent of a bundled alert for which the bell is in its cooldown fires no call. The escalation from warning to critical fires it in the cooldown too. Hook configuration details: Hooks & Events.

Personal notifications (notification hub)

Independently of the rule-based alert channels above, the notification hub fans events out per user: each user decides what they are notified about and how. Where the webhook/email rules above send to fixed destinations (e.g. a team webhook), the hub targets the people assigned to a server.

What is delivered

  • Bell in the desktop client (header): a personal feed with an unread counter that refreshes in real time (server push, while a server session is active) — a new notification appears immediately, without waiting for the next poll. Opening it marks the entries as read. Each signed-in server workspace has a bell of its own with the feed of its sign-in.
  • Desktop notifications (native OS alerts): optional, enabled under Settings → All workspaces on this device → Notifications (asks for the system permission once); the switch applies to all workspaces of the device, and the title of each alert names the workspace (“[<name>] …”).
  • Email: additionally, when enabled in a rule and a contact email is set.

Configure your own rules

Under Settings → This workspace → Notification rules in the desktop client (in a server workspace you are signed in to; the rules are kept at the server of this workspace) every user maintains a contact email and any number of rules. Each rule consists of:

FieldMeaning
ScopeAll servers (all the user may see), Tag (all servers with that tag) or Single server.
Minimum severityFrom which level on to notify: info, warning or critical.
ChannelThe bell receives every match; email can be enabled on top. (Telegram is prepared in the data model but not yet exposed in the UI.)

Multiple rules of one user are merged – one event produces exactly one feed entry, and the channels are the union of all matching rules.

Starter rule for admins: Newly created admin users automatically get a rule All servers / minimum severity warning / bell only – so on a fresh install every alert reaches at least the admins. The rule can be edited or deleted like any other; existing users do not receive one retroactively.

What triggers a notification

  • Monitoring: every divergence from the last reported status of a check – usually a status transition (e.g. ok → critical and the recovery back), after maintenance windows or host outages also as a catch-up without a current transition; at most one problem report per check in 30 minutes (see Cooldown above); the alert.triggered event hook follows the bell and with it this cooldown. The severity is the worse of the reported and new state, but at most the check's severity; the all-clear carries the level the bell showed the problem with, so it reaches every subscriber who saw the alert, also when the check's severity has changed since. Checks with severity info do not reach the bell. The unknown policy, maintenance windows and host-down suppression apply here too (see Alert behavior). When three or more agents fall silent or come back together, one entry comes with a line per affected server that you may see and one of your rules covers (see Bundled alert for silent agents).
  • Security: a new admin user was created (also via python -m app.cli create-admin) or a user was promoted to admin.
  • Lifecycle: a server was removed from the inventory, an FRP tunnel was created.
Only what you may see

The hub only delivers events for servers the user is allowed to see – all of them for admins, otherwise only the assigned ones (see Users & Access). "All servers" accordingly means "all servers visible to me", not the whole inventory.

Email delivery: outgoing emails are delivered via an external SMTP relay (SMTP_HOST/SMTP_PORT/SMTP_USER/SMTP_PASSWORD/SMTP_FROM, see Operation & Configuration). Delivery runs asynchronously through an outbox with automatic retry (linear backoff up to NOTIFICATION_MAX_ATTEMPTS, default 5); without a configured SMTP relay the bell remains fully functional.
