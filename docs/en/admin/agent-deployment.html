Agent Deployment

The Go agent runs on every monitored server. It handles two jobs: metric collector runs and FRP client auto-provisioning. It ships as DEB, RPM (Linux) or a single .exe (Windows).

What does the agent do?

  • Monitoring: runs every 5 minutes (systemd timer with jitter), collects CPU, RAM, disk, SMART, Docker container status and ZFS pools, and sends the metrics tunnel-free to the AdminHelper server (port 443) at POST /api/monitoring/agent/{server_id}/report, with the server's monitor key in the X-API-Key header; the server forwards them internally to the monitoring service. No separate monitoring port needs to be reachable.
  • FRP client: when provisioned with a provision token, it fetches its client certificate in the mTLS enrollment, which frpc uses as well, and starts frpc.service only when the host has an active FRP tunnel.
  • Updates: see the Upgrade section. Upgrade note: when moving to the internal-only monitoring (server proxy instead of the host port 8480), existing agents must be re-provisioned once so their stored MONITOR_URL switches to /api/monitoring.

Quick rollout (one command, recommended)

The desktop client generates a ready-made one-liner in Infrastructure → Server → Provisioning, based on scripts/agent-install.sh — with the server ID and the installation's CA fingerprint. The one-time token is not in the one-liner: the tab shows it beside it to copy, and the script asks for it with the input hidden when it runs.

bash
curl -fsSL https://raw.githubusercontent.com/AdminCave/AdminHelper/main/scripts/agent-install.sh \
  | sudo bash -s -- \
  --server https://srm.example.com \
  --server-id <server-id> \
  --ca-fp <sha256-from-the-tab>

The script performs the whole rollout fail-closed: it fetches the repo signing key from the :8445 plane and hard-compares its OpenPGP fingerprint against the project key pinned in the script (self-built repos: --gpg-fp); only the key with that fingerprint is installed, even if the fetched file carries others. It then writes the apt/dnf source (deb822 with Signed-By, resp. a .repo with a locally verified gpgkey), installs adminhelper-agent and provisions it right away. With --ca-fp (shown in the provisioning tab — the desktop knows the internal CA from its own enrollment) the first contact is verified inside the TLS handshake instead of blindly pinned; the token only leaves the host after the check passes. After a successful mTLS enrollment the script automatically flips the repo source to CA pinning (CAInfo/sslcacert to /etc/adminhelper/identity/ca.crt) — the hardened steady state for apt upgrade/dnf upgrade. Without --token/--server-id it only installs the package; omitting just --token makes it prompt via /dev/tty with the input hidden (keeps the secret out of the shell history) — that is how the desktop's one-liner works. Unattended rollouts (Ansible, cloud-init) keep --token. The script hands the token to the agent on stdin (provision --token-stdin), not as a program argument that would sit in the process list during provisioning; an older agent without --token-stdin gets it as --token, with a warning. If the server runs without a signed repo (:8445 answers 404), --from-github falls back to the minisign-verified release package (apt only). The script also ships in the runtime bundle at /opt/adminhelper/scripts/agent-install.sh — scp-able for hosts without GitHub access.

Install the package (Debian/Ubuntu)

The DEB and RPM packages are attached as assets to every GitHub release. Download the file and install it locally:

bash
VERSION=0.43.0  # adjust to the current release
curl -fsSLO "https://github.com/AdminCave/AdminHelper/releases/download/v${VERSION}/adminhelper-agent_${VERSION}_amd64.deb"

# Installs deps and supersedes the old srm-* packages (Replaces/Conflicts):
sudo apt install "./adminhelper-agent_${VERSION}_amd64.deb"

Install the package (Rocky/Alma/RHEL)

Grab the matching .rpm asset from the releases page, then install it locally:

bash
sudo dnf install ./adminhelper-agent-*.x86_64.rpm

From the AdminHelper package repo (apt upgrade / dnf upgrade)

The AdminHelper server itself hosts a GPG-signed apt/rpm repo on the gateway's repo plane (port REPO_PORT, default 8445, certless). Agent hosts then pull new versions through the normal package manager instead of a manual download — meant mainly for ongoing updates across many servers. Prerequisite: the server runs with a configured repo signing key (see CI/CD & Release); otherwise the /apt and /rpm paths just return 404.

The trust root is the GPG fingerprint, not the transport: package authenticity rests on the signature (like any distro mirror). Check the fingerprint of the fetched key against the published value (912E1EC637F49C978EAD47DF926B404297E9DC1C) before you continue.

Debian/Ubuntu (apt)

bash
SERVER=srm.example.com                 # your AdminHelper server
REPO="https://${SERVER}:8445"

# 1) Fetch the signing key and COMPARE the fingerprint mechanically (trust root!)
#    Stage to /tmp, check against the published value, then install — a bare
#    "--show-keys" only prints the fingerprint, it compares nothing.
FPR=912E1EC637F49C978EAD47DF926B404297E9DC1C
sudo install -d -m 0755 /usr/share/keyrings
curl -fsSL "${REPO}/apt/adminhelper-archive-keyring.gpg" -o /tmp/ah-keyring.gpg
gpg --show-keys --with-colons /tmp/ah-keyring.gpg \
  | awk -F: '/^fpr:/{print $10; exit}' | grep -qx "$FPR" \
  || { echo "ERROR: keyring fingerprint mismatch — aborting!"; exit 1; }
sudo install -D -m 0644 /tmp/ah-keyring.gpg /usr/share/keyrings/adminhelper-archive-keyring.gpg

# 2) Repo source (deb822); Signed-By binds the repo to exactly this key
sudo tee /etc/apt/sources.list.d/adminhelper.sources >/dev/null <<EOF
Types: deb
URIs: ${REPO}/apt
Suites: stable
Components: main
Architectures: amd64
Signed-By: /usr/share/keyrings/adminhelper-archive-keyring.gpg
EOF

# 3) TLS against the internal server cert. Option A (hardened, host already
#    enrolled -> the internal CA sits at /etc/adminhelper/identity/ca.crt):
echo 'Acquire::https::'"${SERVER}"'::CAInfo "/etc/adminhelper/identity/ca.crt";' \
  | sudo tee /etc/apt/apt.conf.d/99adminhelper-ca >/dev/null
#    Option B (simplest bootstrap, no CA file) — the GPG signature still carries
#    authenticity:
# echo 'Acquire::https::'"${SERVER}"'::Verify-Peer "false";' \
#   | sudo tee /etc/apt/apt.conf.d/99adminhelper-ca >/dev/null

sudo apt update
sudo apt install adminhelper-agent     # later updates: apt upgrade

Rocky/Alma/RHEL (dnf)

bash
SERVER=srm.example.com
REPO="https://${SERVER}:8445"
sudo tee /etc/yum.repos.d/adminhelper.repo >/dev/null <<EOF
[adminhelper]
name=AdminHelper Agent
baseurl=${REPO}/rpm
enabled=1
gpgcheck=1
repo_gpgcheck=1
gpgkey=${REPO}/rpm/RPM-GPG-KEY-adminhelper
# Option A (hardened, host already enrolled -> internal CA present):
sslcacert=/etc/adminhelper/identity/ca.crt
# Option B — only for the very first bootstrap of a not-yet-enrolled host;
# remove after enrollment and use option A:
# sslverify=0
EOF
sudo dnf install adminhelper-agent     # later updates: dnf upgrade
CA pinning vs. first install

Option A requires the host to be provisioned/enrolled already (then the internal CA sits at /etc/adminhelper/identity/ca.crt). For the very first install of a not-yet-enrolled host use Option B or the local .deb/.rpm download above; after provisioning you can switch to CA pinning. Package integrity is covered by the GPG signature either way.

Windows

Every GitHub release carries the agent as a single file, adminhelper-agent-windows-x86_64.exe, with no MSI and no installer; the MSI on the release page belongs to the desktop client. In a PowerShell as Administrator, service install sets the agent up:

powershell
# PowerShell as Administrator, in the download folder
.\adminhelper-agent-windows-x86_64.exe service install

The command copies the binary to %ProgramFiles%\AdminHelper\adminhelper-agent.exe, registers the service AdminHelper-Agent (auto-start, LocalSystem account, restarted 60 s after a failure) and starts it. It also registers the source of the same name for the Windows event log (Application), so that the agent's entries there have a description (see Logs); service uninstall removes the service and the source again. If the source cannot be registered or removed, the command prints a warning; the service is not affected. Then provision the host as in the next section. The agent sets up no frpc service on Windows.

Provisioning

In the desktop client, in the server workspace of the installation the agent is to report to: Infrastructure → Add server, then open the Provisioning tab of that server entry. The token is valid for 24 h and redeemable exactly once. You also need the server ID shown for that server entry.

bash
# Linux. The token is read from stdin (first line), not passed as an argument, so it
# stays out of the process list: paste it after the call and press Enter.
sudo adminhelper-agent provision \
  --url       https://srm.example.com \
  --token-stdin \
  --server-id SERVER_ID
powershell
# Windows (PowerShell, as Admin)
& 'C:\Program Files\AdminHelper\adminhelper-agent.exe' provision `
    --url       https://srm.example.com `
    --token-stdin `
    --server-id SERVER_ID
# Paste the token after the call and press Enter (stdin, not an argument)

After provisioning the agent enables the adminhelper-agent.timer systemd unit (Linux). To provision, it calls /api/servers/{id}/provision/activate and receives, depending on the configuration, the server API key, the monitor key, frpc.toml and an enrollment token. If the host has an active FRP tunnel, the agent (Linux) writes frpc.toml and starts frpc.service for good (systemctl enable --now); a running frpc is restarted. Without an active tunnel the agent stops and disables frpc.service and removes frpc.toml, also one from an earlier provisioning. The token becomes invalid once redeemed.

mTLS enrollment (automatic): during provisioning the agent also fetches its own client certificate from the ca-issuer — an ECDSA key generated on-device (never leaves the host), CSR sent to the gateway's enroll plane on port 8444. Cert + key are stored under /etc/adminhelper/identity/ (key 0600) and the internal root CA is pinned. The agent then presents this cert, valid for this server only, on all server pushes and auto-renews it at ~50 % of its lifetime. Best-effort: if enrollment fails (e.g. port 8444 unreachable) the agent keeps working with the API key for now.

Provisioning again: when you provision a server again (a new token from the Provisioning tab, then adminhelper-agent provision … once more), the new agent replaces the previous one. The server deletes the API key of the previous provisioning; only the key the agent gets now counts. Global and manually created keys and the keys of other servers stay. If the agent already ran on this host, its new certificate replaces the previous one. When the host is provisioned for another server, the agent first drops the identity of the previous one, which the new server would not accept; if the enrollment fails after that, it keeps working with the API key for now.

Tunnels after provisioning (Linux): on every run (adminhelper-agent.timer, about every 5 minutes) the agent syncs the host's tunnels with the server. A tunnel you create after the provisioning takes effect on the next run, without provisioning again: the agent writes frpc.toml and enables frpc.service for good (systemctl enable --now, so frpc also runs after a reboot). A running frpc takes over the new config: when only tunnels change, it loads them by a reload, and open sessions over unchanged tunnels stay up; when the frps address, token or TLS change, the agent restarts frpc, as it does on every provisioning. For the reload frpc opens an admin API on 127.0.0.1 only, with a random password from /etc/frp/admin.conf (0600, readable by root only). If frpc does not run despite a tunnel, for instance because another process holds its admin port after a reboot, the next run moves the admin API to a new port with a new password and starts frpc. The same goes for an frpc you stop or disable locally (systemctl stop or disable --now): as long as the host has tunnels, the next run starts and enables it again, within about 5.5 minutes. Without a tunnel no frpc runs: when the last tunnel is gone (deleted, or all of the host's tunnels disabled) or the server has no FRP config for the host, the agent stops and disables frpc.service and deletes frpc.toml, since it holds the frps token. To keep frpc off on a host for good, delete or disable its tunnels on the server; locally, systemctl mask frpc remains as an emergency stop, and every agent run then logs an frpc error. The agent puts loginFailExit = false in front of the server's frpc.toml: if frps is unreachable at start, frpc does not exit but keeps trying. Older hosts: if an older agent provisioned the host without a tunnel, the host lacks the server API key for the sync, and later tunnels never arrive. Provision it once more; until then the agent log points this out on every run. Refused configuration: if the server's configuration departs from the form the server generates, the agent does not take it and stops frpc until the server sends one that fits; line and key are in the agent log.

Ansible / cloud-init

For rollouts to many hosts the quick-rollout one-liner is the right building block: one command:/runcmd: step with agent-install.sh --server … --token … --server-id … --ca-fp … per host (mint the token once per host). Idempotent: without a token/server ID the same call only updates the package.

Subcommand reference

All subcommands of the agent binary. Required flags are marked with *.

CommandFunctionImportant flags
versionPrint the version—
runRun FRPC sync + monitor push (without flag: continuous, every 5 minutes)--once
provisionProvision the server against AdminHelper (server API key + optional monitor + FRP)--url*, --token* or --token-stdin* (one of the two), --server-id*, --ca-fp, --cacert, --insecure
frpc syncOne-off config sync—
monitor initFirst-time setup of the monitor agent--url*, --api-key*, --server-id*, --services, --cacert, --insecure
monitor pushOne-off metrics push—
service installRegister and start the OS service—
service uninstallDeregister the OS service—

--ca-fp <sha256> is the preferred trust anchor for the first contact: the agent only accepts the connection if the presented certificate chain contains a certificate with exactly this fingerprint and the server leaf cryptographically chains to it — checked inside the TLS handshake, before the one-time token ever leaves the host. The server leaf must also name the host from --url, because every later call checks that: if it does not, provision aborts before the token leaves the host, and the message lists the certificate's names — it names an IP address only if that address was in the server's EXTRA_SANS when the certificate was issued. The desktop shows the value in the provisioning tab (the commands generated there already include it). Cannot be combined with --cacert/--insecure.

--insecure applies only to the one-off provision or monitor init call: the agent captures the certificate the server presents and pins it (trust-on-first-use), so the recurring sync/push loop verifies again — instead of disabling TLS verification permanently. With --cacert nothing is skipped at all, so provision and monitor init refuse --cacert together with --insecure. If the server presents no certificate to pin during the provision call, provision aborts instead of turning verification off; likewise monitor init aborts if it cannot fetch or store the certificate. Trust-on-first-use trade-off: if an attacker is already on-path during that first call, --insecure pins the attacker's certificate as the permanent trust anchor. To detect this, provision prints the pinned certificate's SHA-256 fingerprint — verify it out-of-band against the CA fingerprint shown in the provisioning tab, or use --ca-fp/--cacert to avoid the risk entirely.

Check that the agent is running

bash
systemctl status adminhelper-agent.timer   # Linux – next activation
systemctl status frpc.service              # only with an active FRP tunnel
journalctl -u adminhelper-agent.service --since "1 hour ago"
sudo adminhelper-agent run --once          # one run by hand: sync + push

Logs

The agent also writes its logs to a rotating file — independent of the service manager, handy for a bug report:

  • Linux: /var/log/adminhelper/agent.log
  • Windows: %ProgramData%\AdminHelper\logs\agent.log

Same format as stdout/journal: time=… level=INFO msg="…" component=frpc (component: agent, frpc or monitor). Rotates at 10 MB, 5 compressed archives. Verbosity is set via LOG_LEVEL (env) or --log-level debug|info|warn|error.

On Windows the agent secures the log directory before it opens the file. If that fails, it logs to stdout only and writes no agent.log until its next start; the FRP sync changes nothing as long as the data directory cannot be secured. When it runs as a service, the reason is in the Event Viewer under Windows Logs → Application: a warning from the source AdminHelper-Agent (event ID 1) with the directory, the error and these consequences. The entry has a description if service install registered the source; for a service set up by an earlier version it has none, and the text is in the event data. A run by hand, for example without administrator rights, writes no entry.

For a bug report, adminhelper-agent diagnostics writes a redacted report (version, OS, config without secrets, log excerpt) to /tmp/ — review it and attach it to a GitHub issue.

Upgrade

With the package repo set up, apt upgrade or dnf upgrade on every server is enough. During provisioning the agent writes /etc/adminhelper/monitor.conf, /etc/adminhelper/identity/, /etc/frp/adminhelper.conf and /etc/frp/frpc.toml; the package does not ship these files, so an upgrade keeps them. On every install and upgrade the package enables adminhelper-agent.timer again, and frpc.service only if /etc/frp/frpc.toml exists.

Migration from legacy agents

The DEB carries Replaces and Conflicts, the RPM Obsoletes and Conflicts for srm-frpc-client, srm-monitor-agent and srm-agent. A single apt install adminhelper-agent or dnf install adminhelper-agent replaces the three legacy packages; the package's install script (postinst or %post) stops, disables and removes their systemd units.
