Agent Deployment

The Go agent runs on every monitored server. It handles two jobs: metric collector runs and FRP client auto-provisioning. It ships as DEB, RPM (Linux), as a pkg package (FreeBSD) or as a single .exe (Windows).

What does the agent do?

  • Monitoring: runs every 5 minutes (Linux: systemd timer with jitter, FreeBSD: cron), collects CPU, RAM, disk, SMART, Docker container status and ZFS pools, and sends the metrics tunnel-free to the AdminHelper server (port 443) at POST /api/monitoring/agent/{server_id}/report, with the server's monitor key in the X-API-Key header; the server forwards them internally to the monitoring service. No separate monitoring port needs to be reachable.
  • FRP client: when provisioned with a provision token, it fetches its client certificate in the mTLS enrollment, which frpc uses as well, and starts frpc (Linux: frpc.service, FreeBSD: the rc.d service adminhelper_frpc) only when the host has an active FRP tunnel.
  • Updates: see the Upgrade section. Upgrade note: when moving to the internal-only monitoring (server proxy instead of the host port 8480), existing agents must be re-provisioned once so their stored MONITOR_URL switches to /api/monitoring.

Quick rollout (one command, recommended)

The desktop client generates a ready-made one-liner in Infrastructure → Server → Provisioning, based on scripts/agent-install.sh — with the server ID and the installation's CA fingerprint. The one-time token is not in the one-liner: the tab shows it beside it to copy, and the script asks for it with the input hidden when it runs.

bash
curl -fsSL https://raw.githubusercontent.com/AdminCave/AdminHelper/main/scripts/agent-install.sh \
  | sudo bash -s -- \
  --server https://srm.example.com \
  --server-id <server-id> \
  --ca-fp <sha256-from-the-tab>

The script performs the whole rollout fail-closed: it fetches the repo signing key from the :8445 plane and hard-compares its OpenPGP fingerprint against the project key pinned in the script (self-built repos: --gpg-fp); only the key with that fingerprint is installed, even if the fetched file carries others. It then writes the apt/dnf source (deb822 with Signed-By, resp. a .repo with a locally verified gpgkey), installs adminhelper-agent and provisions it right away. With --ca-fp (shown in the provisioning tab — the desktop knows the internal CA from its own enrollment) the first contact is verified inside the TLS handshake instead of blindly pinned; the token only leaves the host after the check passes. After a successful mTLS enrollment the script automatically flips the repo source to CA pinning (CAInfo/sslcacert to /etc/adminhelper/identity/ca.crt) — the hardened steady state for apt upgrade/dnf upgrade. Without --token/--server-id it only installs the package; omitting just --token makes it prompt via /dev/tty with the input hidden (keeps the secret out of the shell history) — that is how the desktop's one-liner works. Unattended rollouts (Ansible, cloud-init) keep --token. The script hands the token to the agent on stdin (provision --token-stdin), not as a program argument that would sit in the process list during provisioning; an older agent without --token-stdin gets it as --token, with a warning. If the server runs without a signed repo (:8445 answers 404), --from-github falls back to the minisign-verified release package (apt only). The script also ships in the runtime bundle at /opt/adminhelper/scripts/agent-install.sh — scp-able for hosts without GitHub access.

Install the package (Debian/Ubuntu)

The DEB and RPM packages are attached as assets to every GitHub release. Download the file and install it locally:

bash
VERSION=0.43.0  # adjust to the current release
curl -fsSLO "https://github.com/AdminCave/AdminHelper/releases/download/v${VERSION}/adminhelper-agent_${VERSION}_amd64.deb"

# Installs deps and supersedes the old srm-* packages (Replaces/Conflicts):
sudo apt install "./adminhelper-agent_${VERSION}_amd64.deb"

Install the package (Rocky/Alma/RHEL)

Grab the matching .rpm asset from the releases page, then install it locally:

bash
sudo dnf install ./adminhelper-agent-*.x86_64.rpm

From the AdminHelper package repo (apt upgrade / dnf upgrade)

The AdminHelper server itself hosts a GPG-signed apt/rpm repo on the gateway's repo plane (port REPO_PORT, default 8445, certless). Agent hosts then pull new versions through the normal package manager instead of a manual download — meant mainly for ongoing updates across many servers. Prerequisite: the server runs with a configured repo signing key (see CI/CD & Release); otherwise the /apt, /rpm and /freebsd paths just return 404.

The trust root is the GPG fingerprint, not the transport: package authenticity rests on the signature (like any distro mirror). Check the fingerprint of the fetched key against the published value (912E1EC637F49C978EAD47DF926B404297E9DC1C) before you continue.

Debian/Ubuntu (apt)

bash
SERVER=srm.example.com                 # your AdminHelper server
REPO="https://${SERVER}:8445"

# 1) Fetch the signing key and install ONLY the key with the published
#    fingerprint (trust root!). The fetched file may carry more keys: import it
#    into a throwaway directory, export only $FPR, CHECK the export mechanically,
#    install only that (as agent-install.sh does).
FPR=912E1EC637F49C978EAD47DF926B404297E9DC1C
TMP=$(mktemp -d)
curl -fsSL "${REPO}/apt/adminhelper-archive-keyring.gpg" -o "$TMP/download.gpg"
gpg --homedir "$TMP" --batch --no-autostart --import "$TMP/download.gpg"
gpg --homedir "$TMP" --batch --no-autostart --export "$FPR" > "$TMP/pinned.gpg"
[ "$(gpg --homedir "$TMP" --batch --no-autostart --show-keys --with-colons "$TMP/pinned.gpg" \
     | awk -F: '$1=="pub" {p=1} p && $1=="fpr" {print $10; p=0}')" = "$FPR" ] \
  || { echo "ERROR: no key with this fingerprint — aborting!"; rm -rf "$TMP"; exit 1; }
sudo install -d -m 0755 /usr/share/keyrings
sudo install -D -m 0644 "$TMP/pinned.gpg" /usr/share/keyrings/adminhelper-archive-keyring.gpg
rm -rf "$TMP"

# 1b) Keyring set up earlier (older version of this recipe)? Check it: the
#     file carries exactly one key, the one with $FPR; otherwise run step 1
#     again (it replaces the file).
FPR=912E1EC637F49C978EAD47DF926B404297E9DC1C
CHK=$(mktemp -d)
[ "$(gpg --homedir "$CHK" --batch --no-autostart --show-keys --with-colons \
       /usr/share/keyrings/adminhelper-archive-keyring.gpg \
     | awk -F: '$1=="pub" {n++; p=1} p && $1=="fpr" {f=$10; p=0} END {print n ":" f}')" = "1:$FPR" ] \
  && echo "Keyring ok" \
  || echo "WARNING: the keyring does not carry exactly the key $FPR — run step 1 again!"
rm -rf "$CHK"

# 2) Repo source (deb822); Signed-By binds the repo to exactly this key
sudo tee /etc/apt/sources.list.d/adminhelper.sources >/dev/null <<EOF
Types: deb
URIs: ${REPO}/apt
Suites: stable
Components: main
Architectures: amd64
Signed-By: /usr/share/keyrings/adminhelper-archive-keyring.gpg
EOF

# 3) TLS against the internal server cert. Option A (hardened, host already
#    enrolled -> the internal CA sits at /etc/adminhelper/identity/ca.crt):
echo 'Acquire::https::'"${SERVER}"'::CAInfo "/etc/adminhelper/identity/ca.crt";' \
  | sudo tee /etc/apt/apt.conf.d/99adminhelper-ca >/dev/null
#    Option B (simplest bootstrap, no CA file) — the GPG signature still carries
#    authenticity:
# echo 'Acquire::https::'"${SERVER}"'::Verify-Peer "false";' \
#   | sudo tee /etc/apt/apt.conf.d/99adminhelper-ca >/dev/null

sudo apt update
sudo apt install adminhelper-agent     # later updates: apt upgrade

Rocky/Alma/RHEL (dnf)

bash
SERVER=srm.example.com
REPO="https://${SERVER}:8445"
sudo tee /etc/yum.repos.d/adminhelper.repo >/dev/null <<EOF
[adminhelper]
name=AdminHelper Agent
baseurl=${REPO}/rpm
enabled=1
gpgcheck=1
repo_gpgcheck=1
gpgkey=${REPO}/rpm/RPM-GPG-KEY-adminhelper
# Option A (hardened, host already enrolled -> internal CA present):
sslcacert=/etc/adminhelper/identity/ca.crt
# Option B — only for the very first bootstrap of a not-yet-enrolled host;
# remove after enrollment and use option A:
# sslverify=0
EOF
sudo dnf install adminhelper-agent     # later updates: dnf upgrade
CA pinning vs. first install

Option A requires the host to be provisioned/enrolled already (then the internal CA sits at /etc/adminhelper/identity/ca.crt). For the very first install of a not-yet-enrolled host use Option B or the local .deb/.rpm download above; after provisioning you can switch to CA pinning. Package integrity is covered by the GPG signature either way.

Windows

Every GitHub release carries the agent as a single file, adminhelper-agent-windows-x86_64.exe, with no MSI and no installer; the MSI on the release page belongs to the desktop client. In a PowerShell as Administrator, service install sets the agent up:

powershell
# PowerShell as Administrator, in the download folder
.\adminhelper-agent-windows-x86_64.exe service install

The command copies the binary to %ProgramFiles%\AdminHelper\adminhelper-agent.exe, registers the service AdminHelper-Agent (auto-start, LocalSystem account, restarted 60 s after a failure) and starts it. It also registers the source of the same name for the Windows event log (Application), so that the agent's entries there have a description (see Logs); service uninstall removes the service and the source again. If the source cannot be registered or removed, the command prints a warning; the service is not affected. Then provision the host as in Provisioning. The agent sets up no frpc service on Windows.

FreeBSD

For FreeBSD 14 and 15 on amd64 the AdminHelper server hosts a signed pkg repo per ABI on its repo plane (port 8445, see above): https://<server>:8445/freebsd/${ABI}; pkg fills in ${ABI} itself, for example FreeBSD:15:amd64. The adminhelper-agent package brings the agent (/usr/local/bin/adminhelper-agent), frpc (/usr/local/libexec/adminhelper/frpc) and the rc.d script adminhelper_frpc. There is no quick rollout for FreeBSD; you set it up by hand as root.

The trust root is the repo's public RSA key, not the transport: pkg accepts only a catalogue whose signature matches this key. Check the SHA-256 of the key file against the value published under CI/CD & Release before you go on. If a catalogue's signature does not match, pkg update reports “Invalid signature, removing repository” and still exits with 0; pkg then installs nothing from that repo.

sh
SERVER=srm.example.com                 # your AdminHelper server
VERSION=0.47.0                         # match the server's release
PUBSHA=<sha256-from-cicd>             # published value (CI/CD & Release)

# 1) Fetch the public repo key, check it (ENFORCED), install it only then
TMP=$(mktemp -d)
fetch -o "$TMP/adminhelper-pkg.pub" \
  "https://raw.githubusercontent.com/AdminCave/AdminHelper/v${VERSION}/apps/agent/freebsd/adminhelper-pkg.pub"
[ "$(sha256 -q "$TMP/adminhelper-pkg.pub")" = "$PUBSHA" ] \
  || { echo "ERROR: key does not match the published value — aborting!"; rm -rf "$TMP"; exit 1; }
install -d -m 0755 /usr/local/etc/pkg/keys /usr/local/etc/pkg/repos
install -m 0644 "$TMP/adminhelper-pkg.pub" /usr/local/etc/pkg/keys/adminhelper-pkg.pub
rm -rf "$TMP"

# 2) TLS against the internal server cert. Option A (hardened, host already
#    enrolled -> the internal CA is at /usr/local/etc/adminhelper/identity/ca.crt):
TLSENV='SSL_CA_CERT_FILE: "/usr/local/etc/adminhelper/identity/ca.crt"'
#    Option B (only for the very first bootstrap of a host not yet enrolled,
#    switch to A afterwards) — the signature still carries authenticity:
# TLSENV='SSL_NO_VERIFY_PEER: "1"'

# 3) Repo file; ENV applies to this repo only, pkg fills in ${ABI} itself
cat > /usr/local/etc/pkg/repos/adminhelper.conf <<EOF
adminhelper: {
  url: "https://${SERVER}:8445/freebsd/\${ABI}",
  signature_type: "pubkey",
  pubkey: "/usr/local/etc/pkg/keys/adminhelper-pkg.pub",
  enabled: yes,
  ENV: { ${TLSENV} }
}
EOF

pkg update -r adminhelper
pkg install -r adminhelper adminhelper-agent   # later updates: pkg upgrade

Then provision the host as in Provisioning, as root and without sudo. What differs from Linux on FreeBSD:

  • Paths: configuration and identity live under /usr/local/etc/adminhelper/ (monitor.conf, identity/), the FRP files under /usr/local/etc/adminhelper/frp/ (frpc.toml, adminhelper.conf, admin.conf). The log is /var/log/adminhelper/agent.log, as on Linux.
  • Schedule: instead of adminhelper-agent.timer, the agent writes /usr/local/etc/cron.d/adminhelper on provision, monitor init and service install: adminhelper-agent run --once as root every 5 minutes, without jitter. cron reads the file without a restart; service uninstall deletes it.
  • frpc: the rc.d service adminhelper_frpc carries the tunnel instead of frpc.service. It runs under daemon(8), which restarts frpc five seconds after it exits. If the host has tunnels, the agent enables the service (service adminhelper_frpc enable) and starts it; without tunnels it stops and disables it. Everything else under Tunnels after provisioning applies, with /usr/local/etc/adminhelper/frp/admin.conf instead of /etc/frp/admin.conf. There is no local emergency stop like systemctl mask: to keep frpc off for good, delete or disable the host's tunnels on the server.
  • Upgrade and removal: pkg upgrade keeps configuration, cron entry and tunnel, and restarts frpc only if adminhelper_frpc is enabled. A fresh install starts nothing and writes no cron entry; provisioning does that. pkg delete adminhelper-agent stops frpc and deletes adminhelper_frpc_enable and the cron entry; /usr/local/etc/adminhelper/ with configuration and identity stays.
  • Monitoring: what the agent reports on FreeBSD and what it does not is under Monitoring → System state.

OPNsense

On an OPNsense firewall (26.1 on FreeBSD 14, 26.7 on FreeBSD 15, amd64) the same agent runs as on FreeBSD, tied in by the plugin os-adminhelper from the same signed pkg repo of the server. The plugin pulls in adminhelper-agent as a dependency, adds the page Services → AdminHelper, runs the tunnel client as an OPNsense service and keeps the repo file pointed at the server the agent is registered with. The agent reads the firewall's state through OPNsense's read-only configd actions, without an API key (see Monitoring → OPNsense).

Third-party repo, not supported by OPNsense

OPNsense does not support additional repositories under /usr/local/etc/pkg/repos/ (OPNsense manual, Software included). The AdminHelper repo is such a third-party repo: questions about the plugin go to AdminHelper, not to OPNsense. It carries only adminhelper-agent and os-adminhelper, and its priority 5 is below the 11 of the OPNsense repo: if both carry a package of the same name, pkg takes OPNsense's.

Install as root in an sh (console or SSH; if your shell is another one, start sh first). You check the key as under FreeBSD; the repo file is named AdminHelper.conf, because the plugin later writes it under this name itself. Before registration there is no internal CA yet, so TLS stays unverified and the signature carries the authenticity.

sh
SERVER=srm.example.com                 # your AdminHelper server
VERSION=0.47.0                         # match the server's release
PUBSHA=<sha256-from-cicd>             # published value (CI/CD & Release)

# 1) Fetch the public repo key, check it STRICTLY, install it only then
TMP=$(mktemp -d)
fetch -o "$TMP/adminhelper-pkg.pub" \
  "https://raw.githubusercontent.com/AdminCave/AdminHelper/v${VERSION}/apps/agent/freebsd/adminhelper-pkg.pub"
[ "$(sha256 -q "$TMP/adminhelper-pkg.pub")" = "$PUBSHA" ] \
  || { echo "ERROR: key does not match the published value — aborting!"; rm -rf "$TMP"; exit 1; }
install -d -m 0755 /usr/local/etc/pkg/keys /usr/local/etc/pkg/repos
install -m 0644 "$TMP/adminhelper-pkg.pub" /usr/local/etc/pkg/keys/adminhelper-pkg.pub
rm -rf "$TMP"

# 2) Repo file under the name the plugin later writes itself
cat > /usr/local/etc/pkg/repos/AdminHelper.conf <<EOF
AdminHelper: {
  url: "https://${SERVER}:8445/freebsd/\${ABI}",
  signature_type: "pubkey",
  pubkey: "/usr/local/etc/pkg/keys/adminhelper-pkg.pub",
  env: { SSL_NO_VERIFY_PEER: "1", SSL_NO_VERIFY_HOSTNAME: "1" },
  priority: 5,
  enabled: yes
}
EOF

pkg update -r AdminHelper
pkg install -r AdminHelper os-adminhelper     # pulls in adminhelper-agent

Register as under Provisioning, as root without sudo: adminhelper-agent provision --url … --token-stdin --server-id …. You enter the token in the shell only; the settings page asks for none, and none is stored in config.xml (and so in configuration backups). Paths, schedule and tunnel are those of FreeBSD.

Repo file after registration: the plugin writes /usr/local/etc/pkg/repos/AdminHelper.conf itself: at boot, on every reload of the firmware settings (at once with configctl firmware reload) and on every install or upgrade of the plugin. It takes the host of the agent's server URL (ADMINHELPER_URL in /usr/local/etc/adminhelper/frp/adminhelper.conf, else MONITOR_URL in monitor.conf; https only), port 8445, the shipped key /usr/local/etc/pkg/keys/AdminHelper.pub, priority 5 and, once the agent is enrolled, the internal CA (identity/ca.crt) to verify TLS; until then TLS stays unverified as above. It overwrites your own changes to the file. As long as the agent has no such URL, it leaves a hand-written file alone.

Updates: pkg upgrade -r AdminHelper fetches new versions of agent and plugin from this repo only. Whether OPNsense's firmware page offers them among its updates has not been checked.

Settings page and service

Services → AdminHelper (/ui/adminhelper/general/index, privilege Services: AdminHelper) has a switch Enabled (on by default) and a status table:

RowMeaning
RegisteredThe agent has a configuration from the server (frp/adminhelper.conf or monitor.conf).
ServerScheme, host and port of the server URL, without a path.
Agent versionVersion of the installed adminhelper-agent.
ScheduledThe cron entry /usr/local/etc/cron.d/adminhelper exists; the agent runs every 5 minutes.
Tunnel clientnone without a tunnel, else running or stopped.
Last monitoring runWhen the last monitoring run saved its state, after a push as after a failed one.

Save writes the setting, renews the template and applies the switch. On: if the agent is registered, the agent writes its cron entry (service install); if it has a tunnel, frpc starts. Off: the cron entry goes (service uninstall), then frpc stops. The registration and the agent's files stay either way.

OPNsense runs the tunnel client as the service AdminHelper tunnel client (adminhelper_frpc), only while the switch is on and the agent has a tunnel (frpc.toml). Start, stop and restart go through OPNsense's service list or configctl adminhelper start|stop|restart|status. A stop lasts only until the agent's next run, which starts an existing tunnel again; the switch keeps frpc off for good. The rcvar lives in /etc/rc.conf.d/adminhelper_frpc, which a template of the plugin writes: YES only with the switch on and a tunnel. OPNsense writes its templates at boot before the rc.d scripts, so a switch turned off also holds after a reboot.

Limits: a run of the agent already in progress when you turn the switch off can set frpc and its rcvar once more; that lasts until the next save or reboot. Registering with the switch off still writes the cron entry; the next save removes it again.

Removal: pkg delete os-adminhelper removes the plugin, page, service entry, configd actions and the repo file AdminHelper.conf. The agent stays with its configuration, cron entry and running tunnel; the rcvar file stays as the template last wrote it. pkg delete adminhelper-agent then removes it entirely, as under FreeBSD.

Provisioning

In the desktop client, in the server workspace of the installation the agent is to report to: Infrastructure → Add server, then open the Provisioning tab of that server entry. The token is valid for 24 h and redeemable exactly once. You also need the server ID shown for that server entry.

bash
# Linux. The token is read from stdin (first line), not passed as an argument, so it
# stays out of the process list: paste it after the call and press Enter. On a
# terminal the agent asks with "Provision token:" and does not show what you type.
sudo adminhelper-agent provision \
  --url       https://srm.example.com \
  --token-stdin \
  --server-id SERVER_ID
powershell
# Windows (PowerShell, as Admin)
& 'C:\Program Files\AdminHelper\adminhelper-agent.exe' provision `
    --url       https://srm.example.com `
    --token-stdin `
    --server-id SERVER_ID
# Paste the token after the call and press Enter (stdin, not an argument);
# after "Provision token:" nothing you type is shown

After provisioning the agent enables the adminhelper-agent.timer systemd unit (Linux). To provision, it calls /api/servers/{id}/provision/activate and receives, depending on the configuration, the server API key, the monitor key, frpc.toml and an enrollment token. If the host has an active FRP tunnel, the agent (Linux) writes frpc.toml and starts frpc.service for good (systemctl enable --now); a running frpc is restarted. Without an active tunnel the agent stops and disables frpc.service and removes frpc.toml, also one from an earlier provisioning. The token becomes invalid once redeemed. On FreeBSD the cron entry and the rc.d service take the place of the timer and frpc.service (FreeBSD).

mTLS enrollment (automatic): during provisioning the agent also fetches its own client certificate from the ca-issuer — an ECDSA key generated on-device (never leaves the host), CSR sent to the gateway's enroll plane on port 8444. Cert + key are stored under /etc/adminhelper/identity/ (key 0600) and the internal root CA is pinned. The agent then presents this cert, valid for this server only, on all server pushes and auto-renews it at ~50 % of its lifetime, after a rotation of the intermediates or the root already on its next run (Operations). Best-effort: if enrollment fails (e.g. port 8444 unreachable) the agent keeps working with the API key for now.

Provisioning again: when you provision a server again (a new token from the Provisioning tab, then adminhelper-agent provision … once more), the new agent replaces the previous one. The server deletes the API key of the previous provisioning; only the key the agent gets now counts. Global and manually created keys and the keys of other servers stay. If the agent already ran on this host, its new certificate replaces the previous one. When the host is provisioned for another server, the agent first drops the identity of the previous one, which the new server would not accept; if the enrollment fails after that, it keeps working with the API key for now.

Tunnels after provisioning (Linux; for FreeBSD see FreeBSD): on every run (adminhelper-agent.timer, about every 5 minutes) the agent syncs the host's tunnels with the server. A tunnel you create after the provisioning takes effect on the next run, without provisioning again: the agent writes frpc.toml and enables frpc.service for good (systemctl enable --now, so frpc also runs after a reboot). A running frpc takes over the new config: when only tunnels change, it loads them by a reload, and open sessions over unchanged tunnels stay up; when the frps address, token or TLS change, the agent restarts frpc, as it does on every provisioning. For the reload frpc opens an admin API on 127.0.0.1 only, with a random password from /etc/frp/admin.conf (0600, readable by root only). If frpc does not run despite a tunnel, for instance because another process holds its admin port after a reboot, the next run moves the admin API to a new port with a new password and starts frpc. The same goes for an frpc you stop or disable locally (systemctl stop or disable --now): as long as the host has tunnels, the next run starts and enables it again, within about 5.5 minutes. Without a tunnel no frpc runs: when the last tunnel is gone (deleted, or all of the host's tunnels disabled) or the server has no FRP config for the host, the agent stops and disables frpc.service and deletes frpc.toml, since it holds the frps token. To keep frpc off on a host for good, delete or disable its tunnels on the server; locally, systemctl mask frpc remains as an emergency stop, and every agent run then logs an frpc error. The agent puts loginFailExit = false in front of the server's frpc.toml: if frps is unreachable at start, frpc does not exit but keeps trying. Older hosts: if an older agent provisioned the host without a tunnel, the host lacks the server API key for the sync, and later tunnels never arrive. Provision it once more; until then the agent log points this out on every run. Refused configuration: if the server's configuration departs from the form the server generates, the agent does not take it and stops frpc until the server sends one that fits; line and key are in the agent log.

Ansible / cloud-init

For rollouts to many hosts the quick-rollout one-liner is the right building block: one command:/runcmd: step with agent-install.sh --server … --token … --server-id … --ca-fp … per host (mint the token once per host). Idempotent: without a token/server ID the same call only updates the package. After the switch of a root renewal, renew the stored --ca-fp from the provisioning tab before the finish, after a switch --compromised right away (Operations → Renewing the root).

Subcommand reference

All subcommands of the agent binary. Required flags are marked with *.

--ca-fp <sha256> is the preferred trust anchor for the first contact: the agent only accepts the connection if the presented certificate chain contains a certificate with exactly this fingerprint and the server leaf cryptographically chains to it — checked inside the TLS handshake, before the one-time token ever leaves the host. The server leaf must also name the host from --url, because every later call checks that: if it does not, provision aborts before the token leaves the host, and the message lists the certificate's names — it names an IP address only if that address is 127.0.0.1, equals the server's DOMAIN or is in its EXTRA_SANS. If DOMAIN or EXTRA_SANS change, the ca-issuer issues the certificate again on its next start; then run docker compose restart gateway, because the gateway reads it only when it starts. The desktop shows the value in the provisioning tab (the commands generated there already include it). It is the fingerprint of the root of the internal CA and stays valid across a rotation of the intermediates. A root renewal changes it with the switch; the fingerprint of the old root works until the finish (Operations → Renewing the root). Older commands carry the fingerprint of the intermediate and work until it is rotated. Update desktop and server together: the command of a new desktop fails against a server whose chain lacks the root, with the fingerprint message. There is no revocation: a certificate under the root is valid until it expires. Cannot be combined with --cacert/--insecure.

--insecure applies only to the one-off provision or monitor init call: the agent captures the certificate the server presents and pins it (trust-on-first-use), so the recurring sync/push loop verifies again — instead of disabling TLS verification permanently. With --cacert nothing is skipped at all, so provision and monitor init refuse --cacert together with --insecure. If the server presents no certificate to pin during the provision call, provision aborts instead of turning verification off; likewise monitor init aborts if it cannot fetch or store the certificate. Trust-on-first-use trade-off: if an attacker is already on-path during that first call, --insecure pins the attacker's certificate as the permanent trust anchor. To detect this, provision prints the pinned certificate's SHA-256 fingerprint — verify it out-of-band against the SHA-256 fingerprint of the server certificate (the gateway certificate, not the CA; on the server for example with openssl x509 -noout -fingerprint -sha256; the same digits, without colons and regardless of letter case). The CA fingerprint shown in the provisioning tab never equals it. Or use --ca-fp/--cacert to avoid the risk entirely.

Check that the agent is running

bash
systemctl status adminhelper-agent.timer   # Linux – next activation
systemctl status frpc.service              # only with an active FRP tunnel
journalctl -u adminhelper-agent.service --since "1 hour ago"
sudo adminhelper-agent run --once          # one run by hand: sync + push

cat /usr/local/etc/cron.d/adminhelper      # FreeBSD – the schedule
service adminhelper_frpc status            # FreeBSD – only with an active FRP tunnel

Logs

The agent also writes its logs to a rotating file — independent of the service manager, handy for a bug report:

  • Linux and FreeBSD: /var/log/adminhelper/agent.log
  • Windows: %ProgramData%\AdminHelper\logs\agent.log

Same format as stdout/journal: time=… level=INFO msg="…" component=frpc (component: agent, frpc or monitor). Rotates at 10 MB, 5 compressed archives. Verbosity is set via LOG_LEVEL (env) or --log-level debug|info|warn|error.

On FreeBSD frpc does not write to this file but, through daemon(8), to /var/log/adminhelper/frpc.log (0600, readable by root only). newsyslog rotates it at 1000 KB and keeps 7 bzip2-compressed archives; the package installs the entry for that as /usr/local/etc/newsyslog.conf.d/adminhelper.conf.

On Windows the agent secures the log directory before it opens the file. If that fails, it logs to stdout only and writes no agent.log until its next start; the FRP sync changes nothing as long as the data directory cannot be secured. When it runs as a service, the reason is in the Event Viewer under Windows Logs → Application: a warning from the source AdminHelper-Agent (event ID 1) with the directory, the error and these consequences. The entry has a description if service install registered the source; for a service set up by an earlier version it has none, and the text is in the event data. A run by hand, for example without administrator rights, writes no entry.

For a bug report, adminhelper-agent diagnostics writes a redacted report (version, OS, config without secrets, log excerpt) to /tmp/ — review it and attach it to a GitHub issue.

Resource limits

The agent must not be noticeable on the host it monitors. On Linux, adminhelper-agent.service therefore runs with Nice=19, IOSchedulingClass=idle, CPUQuota=50% (at most half a core) and MemoryMax=256M. The limits also cover the tools it starts (pvesh, docker, smartctl …). If a tool goes over the memory limit, the kernel ends only that process, not the whole unit (OOMPolicy=continue): the run reports the failed call and still sends the report. Whether the idle IO class has an effect depends on the disk's IO scheduler (bfq yes, mq-deadline and none no); this has not been checked per scheduler. On Windows the service sets its process priority to “Low” (IDLE_PRIORITY_CLASS) when it starts. On FreeBSD cron starts the run with nice -n 19, which also covers the tools it starts, and stops it after 270 seconds; there is no memory or CPU limit there.

If a limit is too tight on a large host (very many containers or VMs), it shows as a missing report or as an oom-kill of a tool in the journal. An override raises it; a package update does not overwrite it:

bash
sudo systemctl edit adminhelper-agent.service
# add in the editor:
[Service]
MemoryMax=512M
CPUQuota=100%

Upgrade

With the package repo set up, apt upgrade or dnf upgrade on every server is enough (FreeBSD: pkg upgrade, see FreeBSD; OPNsense see OPNsense). During provisioning the agent writes /etc/adminhelper/monitor.conf, /etc/adminhelper/identity/, /etc/frp/adminhelper.conf and /etc/frp/frpc.toml; the package does not ship these files, so an upgrade keeps them. On every install and upgrade the package enables adminhelper-agent.timer again, and frpc.service only if /etc/frp/frpc.toml exists.

Migration from legacy agents

The DEB carries Replaces and Conflicts, the RPM Obsoletes and Conflicts for srm-frpc-client, srm-monitor-agent and srm-agent. A single apt install adminhelper-agent or dnf install adminhelper-agent replaces the three legacy packages; the package's install script (postinst or %post) stops, disables and removes their systemd units.
