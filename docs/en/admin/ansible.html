Ansible

Ansible management separates central maintenance from local execution: playbooks are stored and versioned on the server; they are created, edited, deleted and run via the desktop client (in a server workspace, Ansible page) using a locally installed ansible-playbook. The server itself runs no playbooks.

Playbook CRUD in the desktop client

Playbooks are managed via /api/ansible/playbooks — all write operations are admin-only. Each playbook has metadata in the database (table ansible_playbooks) and a YAML file on disk at DATA_DIR/ansible/playbooks/<id>/<filename>.

FieldMeaning
nameDisplay name in the desktop client
filenameName of the YAML file — must end in .yml or .yaml, no path separators
descriptionOptional description
tagsList of tags for filtering/search
contentThe YAML content — written to disk, not stored in the DB

On create (POST) and on edit (PUT, if content is included) the server validates the YAML via yaml.safe_load; invalid YAML returns 422. If the filename changes, the server renames the file on disk or deletes the old one. On delete (DELETE) the entire <id>/ directory is removed.

HTTP
GET    /api/ansible/playbooks              # List all playbooks
POST   /api/ansible/playbooks              # Create playbook (admin)
GET    /api/ansible/playbooks/{id}         # Playbook metadata
GET    /api/ansible/playbooks/{id}/content # Fetch YAML content
PUT    /api/ansible/playbooks/{id}         # Update playbook (admin)
DELETE /api/ansible/playbooks/{id}         # Delete playbook (admin)

CRUD operations fire hooks: playbook.created, playbook.updated and playbook.deleted (payload: id + name). For hook configuration details: Hooks & Events.

Running a playbook (Desktop)

The Ansible page shows the list of playbooks on the left and the selected playbook on the right. Until a playbook is selected, the right side only shows a hint.

  • List — all playbooks maintained on the server, with name, description, filename and tags; the + Playbook button above it creates a new one.
  • Targets — two modes: By servers (individual checkbox selection, name and host per server) or By tags (one chip per tag selects all servers carrying that tag). Below, the page states on how many servers the playbook will run.
  • Run — the button in the playbook's header (next to Edit) becomes active once at least one target server is selected and launches ansible-playbook: with Settings → Terminal → Console for SSH set to AdminHelper terminal (the default), the playbook runs in a session tab with its name (without Reconnect), otherwise in a native terminal. Dry run (--check) below the targets starts it with --check on both ways: Ansible reports what it would change and changes nothing.

On run, the desktop itself fetches the playbook's file name and YAML content fresh from the signed-in server (/{id} and /{id}/content), writes inventory and playbook into a temporary directory of their own per run and starts the run; from the UI it only gets the playbook id and the selected targets. In a session tab the desktop deletes this directory after the run ends, on every platform. In a native terminal on Linux the terminal deletes this directory with the playbook and the inventory as soon as ansible-playbook ends, whatever the result, and also when the terminal is closed during the run. If the start (no ansible-playbook, no terminal) or a step before it fails, the client deletes the directory at once, a half-written file with it. In a native terminal on Windows it stays in the temp directory after a started run. The server inventory and playbooks are sourced directly from the AdminHelper server of the workspace — nothing is maintained locally.

Inventory Generation

The desktop client automatically builds a JSON-format inventory file (inventory.json, read by the yaml plugin that Ansible enables by default) from the selected servers in the run's temporary directory. All selected hosts go under all.hosts; in addition, one group per server tag is created under all.children listing the matching hosts. A tag all becomes no group of its own, since every host already belongs to all.

Each host keeps its hostname field as its name, so playbooks, host_vars and output see the same names as before. If the server has an SSH connection, the inventory sends Ansible where Connect opens that connection: ansible_host and ansible_port (after tunnel resolution; port 22 is left out, as with Connect), ansible_user and ansible_ssh_private_key_file if set, and in ansible_ssh_common_args the connection's other switches (jump host as -o ProxyJump=…, auth method). Forwards and agent forwarding are not taken along.

JSON
{
  "all": {
    "hosts": {
      "web01.example.com": {
        "ansible_host": "127.0.0.1",
        "ansible_port": 23001,
        "ansible_user": "ops",
        "ansible_ssh_private_key_file": "/home/ops/.ssh/id_ed25519",
        "ansible_ssh_common_args": "'-o' 'ProxyJump=jump@192.0.2.10'"
      },
      "db01.example.com": {}
    },
    "children": {
      "database": { "hosts": { "db01.example.com": {} } },
      "web": { "hosts": { "web01.example.com": {} } }
    }
  }
}

Groups are derived directly from the servers' tags — the same tags set on the server entry (desktop client, Infrastructure) that drive selection in tag mode.

Which SSH connection Ansible takes

  • Exactly one SSH connection on the server: that one.
  • None: the hostname as before; in the targets the server carries the mark Hostname.
  • Several: a choice appears below the server, preset to the first connection by name.

The mark and the choice show in the By servers mode. In the By tags mode the same rule applies per server without being shown: the choice made there, otherwise the first connection by name, without a connection the hostname.

Before the start the client resolves each chosen connection like Connect, through an FRP tunnel too. If the tunnel visitor of an STCP connection is not running, the run does not start and the message names the server; there is no fallback to the hostname. The desktop checks each connection as when opening an SSH session and also refuses a local port that belongs to the tunnel of another workspace, as well as users or key paths containing { or } (Ansible renders inventory values as Jinja templates).

Requirements

  • ansible-playbook must be installed on the desktop machine and on the PATH. If missing, the run aborts with an error message.
  • Target servers must be created in the desktop client under Infrastructure — only hosts maintained there appear in the targets of the Ansible page.
  • Playbook maintenance (create/edit/delete) requires an admin session.
SSH reachability

Execution runs on the desktop machine against the target of each server's SSH connection, as Connect opens it. For servers without an SSH connection (mark Hostname) you handle access, keys and optionally ansible_user as usual via your Ansible/SSH configuration. If one of the connections uses password login, the run starts with --ask-pass: Ansible asks for the password once in the terminal, as Connect does, and uses it for the servers of the run with password login; ssh does not offer it to the others. Depending on the Ansible version this needs sshpass on the desktop machine.
