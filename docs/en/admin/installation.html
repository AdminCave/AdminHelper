Admin Guide

Installation

AdminHelper ships as a Docker Compose stack: a TLS gateway (nginx), server, ca-issuer, Postgres, Redis, FRP server (frps), monitoring service and VictoriaMetrics. The gateway is the single public TLS edge — no external reverse proxy is required.

Prerequisites

  • Linux host (Debian 12+, Ubuntu 22.04+, Rocky 9)
  • Docker Engine 24+ and Docker Compose v2.6+; update.sh needs Compose v2.17+ (docker compose up --wait and --wait-timeout) and otherwise stops before it changes anything. frps binds port 443 inside its container without root: for that, compose sets net.ipv4.ip_unprivileged_port_start=0 in the frps container. If the engine or the kernel cannot set this value, docker compose up fails with an error message.
  • Public IPv4/IPv6 with DNS A records for srm.example.com (panel) and frp.example.com (tunnel endpoint)
  • Open ports (all TCP, inbound): 443 (web/API), 8444 (enrollment), 7000 (FRP control channel, mTLS) and 7443 (FRP HTTPS tunnels on the subdomain host) when FRP tunnels are used, 8445 (agent package repo, recommended). The STCP visitor port range (6000-6999) binds locally on the desktop client — it is never exposed on the server.
  • FRP tunnels are set up in the web interface (FRP page, see FRP Tunnel); frps runs on that FRP server configuration.

Environment Variables

VariableDefaultPurpose
DOMAINlocalhostMain FQDN of the server. Used as SAN/CN in the gateway's TLS certificate issued by the ca-issuer, and in links.
SECRET_KEYautoJWT signing key. Set it manually or let it auto-generate (persisted to data/.secret_key, mode 0600). If group or others may read the file, the server logs a warning at startup and keeps using the key; chmod 600 fixes it.
ADMIN_PASSWORDemptyOptional. Empty/'admin' triggers the bootstrap-token flow (see above). Any other value of 8–128 characters creates an admin directly (CI/dev); shorter or longer: a warning and the bootstrap-token flow.
POSTGRES_PASSWORDautoGenerated by ./scripts/init-secrets.sh. Postgres refuses to start if empty. The password of the superuser adminhelper: only postgres and the one-shot service db-init get it, no service connects with it.
SERVER_DB_PASSWORD, SCHEDULER_DB_PASSWORD, MONITOR_DB_PASSWORD, CA_DB_PASSWORDautoOne Postgres role per service, without superuser rights (ah_server, ah_scheduler, ah_monitor, ah_ca). db-init creates them on every start of the stack and sets their passwords from these values; only then do the services start. init-secrets.sh fills missing values, install.sh and update.sh call it. update.sh --redeploy and a restore from a backup older than this version leave the .env alone: run ./scripts/init-secrets.sh first, or no service starts.
CA_ROOT_PASSPHRASEautoEncrypts the cold PKI root key of the ca-issuer at rest. Only needed on first start (hierarchy creation). Generated by init-secrets.sh — store it separately, keep it out of backups. Compose hands it to the ca-issuer as a compose secret, a file under /run/secrets, not as an environment variable: it is not in the container's environment (docker inspect, /proc/<pid>/environ); compose sets CA_ROOT_PASSPHRASE_FILE itself. After the first start, clear the value and keep the line CA_ROOT_PASSPHRASE=: without it, docker compose up aborts. Once the value is cleared, docker compose up -d recreates the ca-issuer, and the file is gone.
DATABASE_URLfrom composepostgresql+psycopg://ah_server:$SERVER_DB_PASSWORD@postgres:5432/adminhelper (ah_ca for the ca-issuer) – set automatically by the compose service.
DATA_DIR/app/dataData directory for bootstrap token, .secret_key, FRP config (the DB lives in Postgres; the TLS certificate is managed by the gateway).
REDIS_URLemptyRedis URL for rate-limiting. Without Redis an in-memory fallback is used (only safe for single-worker). Compose sets it to redis://redis:6379/0.
TRUSTED_PROXIESgatewayComma-separated addresses, networks (CIDR) or host names of the peers whose X-Forwarded-For the server evaluates; it resolves host names from the start and again every 30 s, as absolute names without a search domain: a host name counts as written (proxy.example.org, not proxy for proxy.example.org). A name known only to /etc/hosts (for instance through extra_hosts) does not resolve this way; enter its address instead. An entry the system reads as an address (such as 0x7f000001) is not a host name and is ignored. Compose always puts the gateway service in front: behind the gateway, the per-address rate limits, ALLOWED_IPS and the address in the audit log refer to the client. A value in .env only adds further direct peers of the server; a proxy in front of the gateway does not belong here (see TLS gateway).
TRUST_PROXY_HEADERSfalseLegacy switch, trusts all proxy headers. Has no effect under compose: there TRUSTED_PROXIES is always set and takes precedence.
ALLOWED_IPSemptyWhitelist of IPs/CIDRs allowed to access the server, checked against the client address the gateway sees (see Users & Access). Empty = no filter.
MONITOR_SERVICE_URLhttp://monitoring:8080URL of the monitoring service (container-internal).
MONITOR_API_KEYemptyShared secret between server and monitoring. Must be identical in both containers.
VISITOR_PORT_START / _END6000 / 6999Port range for STCP visitor tunnels in the desktop client.
FRP_BIND_PORT7000TCP port for the FRP bind (control channel); must match the bind_port in the FRP-config UI (otherwise every tunnel breaks); the FRP form warns when its bind port differs from it.
FRP_HTTPS_PORT7443HTTPS port for the FRP tunnel.
WEB_IDLE_TIMEOUT_MINUTES30Minutes without input (mouse, keyboard, touch) in all open tabs after which the web panel signs out; 0 turns it off; an invalid value counts as 30 (warning in the log).
WEB_SESSION_MAX_HOURS24Hours after sign-in at which the server ends a browser session, even while it is in use; then a new sign-in is needed. Desktop, CLI and scripts are not affected. 0 turns it off; an invalid value counts as 24 (warning in the log).

A $ in a value: Docker Compose treats unquoted and double-quoted values in .env as templates (Compose docs: Interpolation). $NAME or ${NAME} is substituted, an unknown name by an empty string (Compose only prints a warning), and a ${ that starts no valid placeholder ends every docker compose call with "Invalid template". So avoid a $ in a value, a password for instance, or write it as $$; single-quoted values ('…') are taken literally. Likewise, a quote that never closes and a key Compose does not accept end every docker compose call, text right after a closing quote included, which Compose reads as the next key; a key consists of letters, digits and _ . - [ ], without spaces. update.sh checks all of this before its first compose call (see Updates).

Quick install (one command)

The installer fetches only the runtime files (the self-contained docker-compose.yml + a few ops scripts, not the source tree), brings up the stack, creates the first admin with a one-time enrollment token, and leaves mTLS enforced by default:

bash
curl -fsSL https://raw.githubusercontent.com/AdminCave/AdminHelper/main/scripts/install.sh \
  | bash -s -- --domain srm.example.com
# installs the latest release; pin a specific one with --ref vX.Y.Z.
# prompts for the admin password. Non-interactive: --admin-password-file <file> --yes
# (password on the first line; keep the file readable only by you, e.g. chmod 600).
# --permissive leaves the stack permissive (no enforced mTLS).
# --reset wipes volumes from a failed attempt (docker compose down -v).

A password file without shell history: do not write the password into the file with echo, or it ends up in the history. Read it without echo and create the file readable only by you right away (or write it with an editor under umask 077), and delete it after the install:

bash
( umask 077; read -rs -p 'Admin password: ' pw; echo; printf '%s\n' "$pw" > ~/ah-admin.pw )
curl -fsSL https://raw.githubusercontent.com/AdminCave/AdminHelper/main/scripts/install.sh \
  | bash -s -- --domain srm.example.com --admin-password-file ~/ah-admin.pw --yes
rm -f ~/ah-admin.pw

The script closes the install directory to other accounts (at most 0750, the owner stays whoever installs), so --dir names a directory of its own, not a shared one like /opt; a host account with UID 10001 or 70, which the containers use, is named in a warning (see Operations).

The script prints the credentials: URL, admin login, and an enrollment token. Redeem the token in the desktop client: create a server workspace with the server URL in the picker and open it, then "Enroll this device with a token" — the client generates its mTLS cert on-device — then log in normally. Export the browser .p12 afterwards from the desktop's export button. Updates: ./scripts/update.sh inside the created adminhelper/ directory.

Why the token? Under enforced mTLS the data plane :443 (including login) rejects certless clients at the TLS handshake. The very first admin therefore cannot fetch a cert via login; the script mints the token out-of-band over the internal network. The admin onboards follow-up users afterwards (ADR 0003).

Start the Stack (manual)

The official docker-compose.yml lives in the repository root. For a quick test this is enough:

bash
git clone https://github.com/AdminCave/AdminHelper.git
cd AdminHelper

cp .env.example .env

# Generate secure random secrets (SECRET_KEY, MONITOR_API_KEY,
# POSTGRES_PASSWORD, the four *_DB_PASSWORD, CA_ROOT_PASSPHRASE).
# Idempotent: leaves any value already set untouched.
./scripts/init-secrets.sh

# Then edit the non-secret values in .env:
#   DOMAIN, ADMIN_PASSWORD, TZ, TRUSTED_PROXIES, ALLOWED_IPS

docker compose pull
docker compose up -d
MONITOR_API_KEY without the init script = dead monitoring UI

Server and monitoring containers share MONITOR_API_KEY as an internal shared secret. If the value in .env stays empty, the monitoring container generates its own random — but the server sends an empty key, so every /api/monitoring/* call ends in a 401. ./scripts/init-secrets.sh prevents this.

Just as important: SECRET_KEY. If it stays at change-me-in-production or empty, the server generates a random value into ./data/.secret_key on first start — it works, but it is not portable between hosts. The init script writes a fixed value into .env so the stack stays reproducibly migratable.

TLS gateway (built-in)

The stack contains its own gateway (nginx) that acts as the single public TLS edge on 443 and forwards internally to the server (plain-HTTP, no host port). server and ca-issuer are reachable only on the compose network; the ca-issuer sits on the internal pki network, which besides it only the gateway and postgres are on (the ca-issuer connects to the database over it as the role ah_ca) — this is what makes the client identity (mTLS header) the gateway sets unforgeable from the outside.

The gateway's TLS certificate is issued by the internal ca-issuer on first start (signed by the internal CA's access intermediate, SAN = DOMAIN). Since this CA is not publicly trusted, browsers show a certificate warning at first — expected; the root CA is pinned in the clients' trust model (see Troubleshooting). An external reverse proxy is not required; if you still want one in front, terminate its own TLS and forward to the gateway on 443. The server then sees the address of that proxy as the client address: the gateway sets X-Forwarded-For to the address of its peer and does not evaluate the proxy's header, and an entry in TRUSTED_PROXIES does not change that. The per-address rate limits and ALLOWED_IPS then apply to all clients behind the proxy together.

Client certificates (mTLS). The agent and the desktop fetch their client certificate from the internal CA automatically (enrollment, see the developer overview "Unified PKI & mTLS"). For the browser, the desktop client exports a PKCS12 (.p12, password-protected) that you import into the browser's certificate store (step by step under Users & Access → Browser access). The data plane has been enforced since 0.29.0 — the gateway requires a client cert (CERT_REQUIRED), MTLS_ENFORCE=true is the default; permissive (MTLS_ENFORCE=false) is needed only for a manual first bootstrap (see Operations & Config).

First Login – Bootstrap Token (manual)

Note: this manual path goes to :443 — under the enforced default (since 0.29.0) it is rejected certless at the handshake. Use scripts/install.sh (Quick install above) or set MTLS_ENFORCE=false for the manual bootstrap, create the admin + enroll, then arm again.

There is no default login anymore. With an empty ADMIN_PASSWORD, the server generates a one-time setup token. The raw token is not written to the log (where it would persist), but to data/.bootstrap_setup (0600) — read it with:

bash
docker compose exec server cat /app/data/.bootstrap_setup

Use the token to create the first admin:

bash
curl -k -X POST https://srm.example.com/api/auth/bootstrap \
  -H 'Content-Type: application/json' \
  -d '{"token":"<TOKEN>","username":"admin","password":"<your-password>"}'

The response contains access_token and refresh_token immediately. The token file is deleted after a successful bootstrap and the endpoint can no longer be called once a user exists (returns 409).

CI / power users: set ADMIN_PASSWORD directly

Setting any value other than admin or empty in .env (e.g. ADMIN_PASSWORD=initialpw) creates an admin user with that password on first start – no bootstrap step needed. Convenient for CI pipelines. The password needs 8–128 characters; if it is shorter or longer, the server warns and writes the bootstrap token instead.

Health check

The server exposes a short JSON status at /api/health. Use this endpoint for monitoring systems or Docker health checks.

Updates

Updates are release-bound: every published release ships a verified runtime bundle (adminhelper-runtime-vX.Y.Z.tar.gz — the docker-compose.yml, all ops scripts, a MANIFEST.sha256 and a VERSION marker). scripts/update.sh resolves a target version, downloads that one asset, verifies it against the release's SHA256SUMS, and swaps the runtime files into place atomically. So whatever a release changes (new/changed/removed scripts, a new compose) lands on the host — "which files belong to release X" lives in the release, not in the script.

bash
# Default: move to the latest published release (prereleases excluded),
# only if newer — no silent downgrade:
./scripts/update.sh

# Pin to a specific version (re-apply / down- or upgrade explicitly):
./scripts/update.sh --ref v0.34.0

# Dry run: print installed vs. available, change nothing:
./scripts/update.sh --check

# Self-heal: no version jump, just re-pull the pinned images:
./scripts/update.sh --redeploy

# More flags: --skip-backup  --with-victoria  --no-rollback  --yes

The installer pins the images in .env to the installed version (e.g. :0.34.0) — so an install stays reproducible and never silently jumps. update.sh lives locally in the adminhelper/ directory after install.

Built to be safe — backup, verification, automatic rollback

Before the swap, update.sh backs up first (data incl. the CA crown jewel) and snapshots the current runtime files (backups/runtime-prev-*.tar.gz). The bundle is checked against SHA256SUMS — which also catches truncated downloads that a plain curl --fail misses. When release signing is armed, update.sh first verifies the minisign signature of SHA256SUMS against a public key pinned in the script (authenticity, not just transport) and aborts on an invalid/missing signature. If swapping the runtime files into place, migrating the .env (new keys, secrets), refreshing the agent package repo, pulling the images (network, rate limit, an image not published), restarting the stack or the health check after it (docker compose up --wait waits until every service with a healthcheck is healthy) fails, the script auto-rolls-back both the runtime files and the image pins, also with a floating tag (:latest, :main): the pins come from a copy of the old .env taken beforehand, so the next run tries the update again. It reports “rolled back” only once the old state runs healthy again, otherwise “incomplete”. If it fails before the restart, the containers stay unchanged. After the restart it rolls back this way only if the Alembic revisions of both databases are unchanged: once the new state has migrated them, or they cannot be read, the old images do not start on them. The script then puts the runtime files and image pins back, stops the stack and names ./scripts/restore.sh with this run's backup (with --skip-backup the last one before it) and ./scripts/update.sh --ref for another try. update.sh writes the image pins to .env only once every image is pulled. An abort by Ctrl-C, kill or a dropped SSH session rolls back as well; after a dropped session the output is in backups/update-<time>.log. --no-rollback keeps the new state for debugging and names the way on (--ref, after the restart also --redeploy); if it fails before the restart, .env keeps the old image pins; a data restore stays deliberately manual via restore.sh. Without a .env in the install directory, update.sh aborts before the backup and the snapshot, changing nothing. Before its first compose call, update.sh checks the .env and aborts on a ${ that starts no valid placeholder, a quote that never closes or a key Compose does not accept, again before it changes anything; the message names only the line number, never the key or the value (see Environment Variables).

The updater updates itself: if a release ships a newer update.sh, it re-execs into the new version before performing the swap — so future updater improvements reach every host. One-time migration for installs before 0.34.0: their old update.sh doesn't know about the bundle yet; re-fetch it once via the install one-liner (or run a --ref v0.34.0 update), after which it is self-updating.

Database migrations run automatically on container start via Alembic (see apps/server/alembic/versions/). The entrypoint first waits for pg_isready, then runs alembic upgrade head, and only then starts uvicorn. Compose starts the ca-issuer only once the server is healthy, i.e. after the migration: /enroll and /renew thus never hit a schema without their tables. The agent has its own release cycle — see Agent Deployment.

Uninstall

scripts/uninstall.sh removes a server install completely. By default it is interactive: it asks per category, and only deletes once every question has been answered. Run it from the install directory (where docker-compose.yml lives):

bash
# Interactive — asks per category (stack, volumes, ./data+./certs, .env,
# backups, images):
./scripts/uninstall.sh

# Non-interactive (e.g. inside a script): stack + volumes + ./data/./certs
# + .env go, backups and images are kept:
./scripts/uninstall.sh --yes

# "Really wipe everything" — images and backups too (--rmi/--purge-backups also
# pre-set the matching question to YES):
./scripts/uninstall.sh --rmi --purge-backups --yes

Asked/removed individually: every container of the compose project and the network, all named volumes (including ca-pki with the root CA, postgres-data and victoria-data), the host bind mounts ./data, ./certs and ./repo, the secrets file .env along with .env.restored and the working copies .env.ah-*, and optionally ./backups/ and the Docker images. Since ./data/./certs are owned by the in-container user (uid 10001), the script deletes them as root in a throwaway container — without requiring sudo.

Irreversible — and the root CA goes with it

Dropping ca-pki destroys the internal root CA: already-enrolled agents/clients are no longer trusted afterwards. If you intend to rebuild on the same host and keep that trust, run ./scripts/backup.sh first and restore with restore.sh.

Protected by default: ./backups/ (it holds the CA + DB dumps) is kept and the images stay — only --purge-backups / --rmi remove those too. The runtime files themselves (compose + scripts/) are not deleted; the script prints the exact rm -rf command for the rest at the end.
