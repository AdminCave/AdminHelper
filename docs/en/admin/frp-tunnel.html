FRP Tunnel

FRP (Fast Reverse Proxy) builds encrypted, bidirectional tunnels between agent and server. That lets you reach RDP/SSH/HTTP on servers behind NAT or firewalls without port forwarding.

Where things are managed (since v0.32.0)

The individual tunnels of a server are created and edited in the desktop client (in a server workspace), in the Tunnel tab under Infrastructure; when creating a tunnel you pick the FRP server configuration to use. The FRP server configuration (frps settings) itself stays in the web admin panel (the FRP page) — the desktop only references it.

Architecture

Three components:

  • frps – runs in the server stack from its own image (ghcr.io/admincave/adminhelper/frps, source apps/frps/) under a supervisor and exposes port 7000 (control channel) and 7443 (HTTPS tunnels); it runs on the FRP server configuration from the web interface. The supervisor takes over changes to the configuration and to the frps certificates by itself, checks the configuration before every start and starts frps as a user of its own (details under Operations → frps supervisor).
  • frpc – runs on every agent host, connects to frps and registers services.
  • PKI – the ca-issuer's internal tunnel intermediate signs the frps server cert and the agent tunnel certs; every frpc authenticates via mTLS (as of A7 a single trust root instead of a frps-run CA).

PKI Setup

The tunnel PKI is part of the unified internal CA (ADR 0001):

  • frps server cert: issued by the ca-issuer under tunnel (ECDSA P-256, SAN = the public frps address), provisioned into the frps volume on first start. The CA key never reaches the internet-facing frps.
  • Agent tunnel cert: the agent enrolls it on-device during provisioning (A4) — the same tunnel cert serves server pushes and the frp tunnel.
  • trustedCaFile: frps trusts only the listed tunnel and access intermediates (current and retired), not the root, so it takes no certificate of a revoked intermediate. access is in it because the desktop visitor presents its access certificate. frpc (agent and desktop) checks the frps certificate against the chain file ca.crt from its enrollment.
Don't forget the CA backup

The security asset is now the ca-issuer's ca-pki volume (Root + intermediates). Losing it means every client must re-enroll. Back it up encrypted, off-site; backup details under Data directory backup.

Rotating Client Certificates

The agent renews its tunnel cert automatically once it reaches ~50 % of its lifetime, calling /ca/renew with the current cert as proof — no manual rotation trigger. An expired cert can no longer be renewed; only a fresh enrollment helps then. Since the PKI migration the desktop visitor presents its enrolled access identity (the device identity of its server workspace, the same one it uses for web/API access) and renews it automatically — no more server-minted visitor cert.

Rotating the FRP auth.token

Caution — breaking change: the global auth.token (in the FRP server config) flows identically into frps.toml, every agent frpc.toml and every desktop visitor.toml. In token mode frps knows exactly one token; there is no overlap/dual-token mechanism. A rotation therefore breaks all agents and visitors at once, until each has re-synced / re-downloaded its bundle. The actual tunnel security is enforced mTLS (transport.tls.force) plus the STCP secretKey anyway — the token is only the weaker second factor.

So rotate only deliberately, in a maintenance window:

  1. Set the new auth.token in the FRP server config (web interface, FRP page → Edit, or PUT /api/frp/server-config/{id}). An empty or missing auth_token in the PUT leaves the stored token unchanged; a new one needs at least 16 characters, not counting whitespace at the start and end. The form asks before saving and points out that agent tunnels take up to ~5 minutes.
  2. frps takes the new configuration over by itself after a few seconds (about 5–10 s) and restarts; no manual restart is needed. All tunnels drop briefly. Admins and users with tunnel access get a bell notification that the FRP server restarted, with a new token also the hint about agent tunnels.
  3. The agents pull the new frpc.toml on their next run (about every 5 minutes) and restart frpc with it; their tunnels stay down until then, so up to ~5 minutes. Signed-in desktop clients need no action: they fetch the new token themselves within 60 s and restart their frpc for it; the tunnel drops briefly, and open sessions over it end. Until frps knows the new token, frpc keeps trying.

Rejected configuration: if the new configuration fails the supervisor's check, frps does not take it over and keeps running on the last valid one, i.e. with the previous token. The frps state block on the FRP page then shows "Running on the last valid configuration" with the reason, and admins get a bell notification that the new FRP configuration was not taken over. Agents and desktops that already have the new token reconnect only once frps has taken over a valid configuration with that token. Reasons and events are explained under Operations → frps supervisor.

Applies to every change to frps.toml and to the frps certificates: not only token rotation — changed ports, dashboard credentials, vhost settings, max_ports_per_client or extra_config and an frps certificate the ca-issuer renewed are taken over by frps the same way: a short restart, all tunnels down for a few seconds, a notification to admins and users with tunnel access. Name and server address are not in frps.toml; changing them, or saving the configuration unchanged, does not restart frps. If the FRP server configuration is deleted, frps stops (admins get a notification that the FRP server stopped).

Revoking tunnel access

Deleting a user, revoking a device, removing a server assignment or the admin role locks the API, but not the tunnel. When a connection is set up, frps only checks auth.token and that the client certificate fits the chain; frp has no revocation list.

A user's visitor configuration carries auth.token and the secretKey of every STCP tunnel they can see (an admin all active STCP tunnels, anyone else those of their servers). The desktop keeps it while the tunnel runs, and a copy stays valid. Whoever has it reaches these tunnels until their secretKeys are rotated (see Tunnel Types below), and frps until their client certificate expires or auth.token is rotated (section above, with its maintenance window).

So: rotate the secretKeys of every tunnel the user could see; if they must not reach frps at all, rotate auth.token as well.

Editing the FRP server configuration

You maintain the FRP server configuration in the web interface on the FRP page. When editing:

  • Question before the restart: if saving changes anything that ends up in frps.toml (everything but name and server address), or a new token or dashboard password has been typed in, the form asks first: "Saving restarts the FRP server; all tunnels are disconnected for a few seconds." With a new token it adds that agent tunnels take up to ~5 minutes to reconnect. Cancel or Escape saves nothing.
  • Port warning: if the Bind port differs from the port the stack publishes for frps (FRP_BIND_PORT, default 7000), a warning shows at the field: with a different bind port, frps cannot be reached from outside. Saving stays possible.
  • Bounds: Bind port, vHost HTTPS port and Dashboard port take 1–65535 only, Max ports/client (max_ports_per_client) only values from 0 (0 or empty: default 16); the server rejects other values with 422, as well as an explicit "bind_port": null in the PUT. A value outside these bounds that is already stored stays in the database; the generator replaces it when it writes the configuration (bind port 7000, vHost and dashboard port left out, max_ports_per_client 16) and logs a warning in the server log.
  • Dashboard port: not 443, not the bind port and not FRP_BIND_PORT; frps does not take such a configuration over (reason verify_failed). The server rejects such a port on create and on update with 422, also when only a changed bind port makes it clash. A configuration already stored with such a port stays as it is: the check at server startup reports it to the admins, and a PUT that sends neither dashboard_port nor bind_port still goes through. The form always sends both ports when saving, so there such a port has to be changed before saving.

Provision Token

Every new agent gets a one-time token when it is registered. Token properties:

  • Valid for 24h
  • Single use (invalidated server-side right after use)
  • Bound to a server ID, i.e. the token fits only a single agent entry

Tunnel Types

TypeDescriptionUse case
httpsHTTPS tunnel with virtual-host routing (idrac.srv1.example.com) under the subdomain host of the FRP server configuration (subDomainHost in frps.toml).Web UIs behind NAT (e.g. IPMI, home automation).
stcpSecure TCP: only a visitor with the matching secretKey gets through. The visitor runs on the client side – the desktop client takes care of that automatically.SSH, RDP, VNC, any TCP service as a private tunnel – zero public port exposure.

The Secret key field of an STCP tunnel: left empty on create, the server generates a secret; left empty on edit, the stored one stays unchanged (the server never hands it back, so the field starts empty). To rotate it, enter a new value (at least 16 characters, not counting whitespace at the start and end); the desktop needs no restart for it. Every signed-in desktop client takes new, changed and deleted STCP tunnels over by itself, right away after saving in its own tunnel dialog, otherwise within 60 s; the other tunnels and their open connections stay up. Switching to HTTPS deletes the secret; switching back to STCP gets a new one.

The local port of a tunnel is a port from 1 to 65535; the server rejects any other value with 422 on create and on update. A value outside that range that is already stored stays in the database; the server leaves that tunnel out of the agent's frpc configuration and logs a warning in the server log, while the other tunnels of the host stay up. To fix it, correct the port in the tunnel dialog.

Visitor Ports

STCP tunnels need a local port on the admin PC for the visitor, which binds it to 127.0.0.1. The server assigns it when the tunnel is created, unless one is given: the first free port from the VISITOR_PORT_START–VISITOR_PORT_END range (default 6000–6999). A port given lies between 1 and 65535; the server rejects any other value, 0 included, with 422 on create and on update; the tunnel dialog of the desktop client already rejects such a value before saving. A visitor port outside 1–65535 that is already stored, and an STCP tunnel without a visitor port, stay in the database; the server leaves the visitor of such a tunnel out of the visitor configuration and logs a warning in the server log, while the tunnel stays up on the agent. This holds until the tunnel is next changed: a change without a visitor port gives such an STCP tunnel a free port, also for the connection created automatically. To fix it, enter a port in the tunnel dialog or clear the field, and the server assigns a free one. The port stays assigned to the tunnel; two STCP tunnels never share one. With firewall restrictions, narrow the range via .env.

For the desktop client this visitor port is the preferred port. The local port belongs to the workspace whose tunnel runs the visitor: the port map of the desktop client covers all workspaces on the admin PC and records the workspace as the owner of each visitor. If the preferred port is free on the admin PC and no other workspace has it, the visitor listens there. If it is taken, for instance by another program, if another workspace has it already (say the server workspace of a second AdminHelper installation with the same visitor port), or if it is below 1024, the desktop client falls back to a free port from 23000–23999. A workspace gets ports for at most 500 visitors, at most 250 of them from the fallback range, so that range is enough for at least four workspaces; beyond that the desktop client neither starts nor updates the tunnel and reports an error. A visitor keeps a port once assigned as long as the tunnel exists, also while the workspace is closed in between; only if another program holds it when the tunnel starts does it get a new one. Deleting the workspace releases its ports. The desktop client resolves connections to the actual port: the one created automatically with the tunnel (127.0.0.1:<visitor port>) for every user, one linked by hand for admins and for users the tunnel's server is assigned to. While the tunnel of a workspace runs, every connection there to 127.0.0.1 or localhost at the visitor port of one of its tunnels goes through that tunnel, one you created yourself too.

If a connection still points to this machine after this resolution, at a local port the port map gives to another workspace, the desktop client does not open it: it would reach the tunnel of the other workspace and through it a machine of that workspace's installation. This mostly affects workspaces without a running tunnel, that is sync and local workspaces and a server workspace while its tunnel is not connected. The desktop client reports port <port> on this machine belongs to the tunnel of another workspace; … instead (see Troubleshooting below).

7443/tcpInboundHTTPS tunnels on the subdomain host (FRP_HTTPS_PORT, frps port 443 inside the container; requires a wildcard cert)

The visitor ports (default 6000–6999, 23000–23999 when taken) bind only locally on the admin PC to 127.0.0.1 and need no rule on the server.

Status Dashboard

The tunnel status view shows the proxies the frps dashboard reports; for that the FRP configuration needs a dashboard port. In Compose, frps sits in a network of its own that the server cannot reach. So the frps supervisor queries the dashboard inside the frps container over loopback, every 5 s while frps runs, and puts the answers into the frps-state volume, from which the server reads them. If they are missing or older than 60 s, for instance because frps is not running, the view reports "frps not reachable: frps dashboard: no current data from the frps supervisor".

If frps runs in a different topology (its own host), set the base URL via FRPS_DASHBOARD_URL; the server then queries the dashboard itself. The variable only takes effect in the environment of the server service, for instance through a docker-compose.override.yml. An entry in .env alone does not reach the server, because Compose does not pass it on.

The FRP page also shows the frps state block with the supervisor's state, reason, since when and its last event (source GET /api/frp/supervisor-status, admins only). It refreshes when the page opens and every 30 s while the tab is visible. "Running on the last valid configuration" means a newer configuration was not taken over; the reason is shown next to it. If the supervisor has not responded for more than 60 s, the block says the details may be out of date. The codes are explained under Operations → frps supervisor.

Troubleshooting

  • Agent does not connect: check the cert expiry (openssl x509 -in /etc/adminhelper/identity/agent.crt -noout -enddate), server reachability via nc -vz srm.example.com 7000.
  • frps does not answer on port 7000: check the frps state block on the FRP page. With "Waiting, frps is not running" the reason is shown next to it; the codes are explained under Operations → frps supervisor. Log: docker compose logs frps (lines with [frps-supervisor]).
  • "Tunnel not found": is the tunnel enabled in the desktop client (Infrastructure → Server → Tunnel tab)? FRP logs: docker compose logs -f frps.
  • STCP does not work: check the tunnel indicator at the bottom of the sidebar of the workspace window, then the log of this workspace (adminhelper-<id>.log, lines with [frpc). Which local port each visitor has is in port-registry.json in the desktop client's app data directory (owner is the id of the workspace, serverPort the visitor port, localPort the actual one). If another program takes the port just as the tunnel starts, the visitor does not listen although the indicator shows the tunnel connected: sign out of the workspace and sign in again; at the start the desktop client tests the ports again and falls back.
  • Desktop reports port <port> on this machine belongs to the tunnel of another workspace; start the tunnel of this workspace to connect: the connection goes to this machine (127.0.0.1, localhost and the like) at a port the port map gives to the tunnel of another workspace, and no visitor of the tunnel of this workspace listens there. This holds while the other workspace is closed too, as its ports stay its own. The desktop client then opens nothing and loads no stored password. Remedy: start the tunnel of this workspace, that is sign in to the server workspace and wait until the tunnel indicator shows it connected (on “Tunnel disconnected”, Reconnect), then open the connection again; the desktop client resolves it to the port of its own visitor. Sync and local workspaces have no tunnel; open connections through a tunnel in the server workspace of the installation. If the message comes while the tunnel is connected, the tunnel runs no visitor at this port: if the connection carries a fallback port from 23000–23999, say one copied by hand from port-registry.json, the visitor port of the tunnel belongs there, the desktop client resolves the actual port itself; otherwise the connection aims at the tunnel of another installation and belongs in that installation's server workspace. Related is the host of this connection cannot be read and may lead to the tunnel of another workspace on this machine; …: the check cannot read the host of the connection (for example IPv6 with a zone, or a user in the RDP host), and another workspace has ports in the port map; write the host as a name or an address, and the user and the port in their own fields.
  • Desktop shows "Tunnel disconnected": the desktop reconnects by itself and tries again at least every 60 s; the Reconnect button next to the indicator at the bottom of the expanded sidebar does it right away.
  • Desktop reports "Tunnel: the server refuses access (HTTP 403); the tunnels are stopped.": the server no longer hands this device or this user any tunnels, for example after the device identity was revoked. The desktop stops its frpc and says so once; it keeps asking every 60 s and starts the tunnels by itself as soon as the server hands them out again. Remedy: check the device identity in the settings and enroll the device again if needed, otherwise clear up the user's rights with the admin.
