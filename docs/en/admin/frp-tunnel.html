FRP Tunnel

FRP (Fast Reverse Proxy) builds encrypted, bidirectional tunnels between agent and server. That lets you reach RDP/SSH/HTTP on servers behind NAT or firewalls without port forwarding.

Where things are managed (since v0.32.0)

The individual tunnels of a server are created and edited in the desktop client (server mode), in the Tunnel tab under Infrastructure; when creating a tunnel you pick the FRP server configuration to use. The FRP server configuration (frps settings) itself stays in the web admin panel (the FRP page) — the desktop only references it.

Architecture

Three components:

  • frps – runs in the server stack, exposes port 7000 (control channel) and 7443 (HTTPS tunnels).
  • frpc – runs on every agent host, connects to frps and registers services.
  • PKI – the ca-issuer's internal tunnel intermediate signs the frps server cert and the agent tunnel certs; every frpc authenticates via mTLS (as of A7 a single trust root instead of a frps-run CA).

PKI Setup

The tunnel PKI is part of the unified internal CA (ADR 0001):

  • frps server cert: issued by the ca-issuer under tunnel (ECDSA P-256, SAN = the public frps address), provisioned into the frps volume on first start. The CA key never reaches the internet-facing frps.
  • Agent tunnel cert: the agent enrolls it on-device during provisioning (A4) — the same tunnel cert serves server pushes and the frp tunnel.
  • trustedCaFile: the tunnel chain (intermediate + root) on both sides.
Don't forget the CA backup

The security asset is now the ca-issuer's ca-pki volume (Root + intermediates). Losing it means every client must re-enroll. Back it up encrypted, off-site; backup details under Data directory backup.

Rotating Client Certificates

The agent renews its tunnel cert automatically once it reaches ~50 % of its lifetime, calling /ca/renew with the current cert as proof — no manual rotation trigger. An expired cert can no longer be renewed; only a fresh enrollment helps then. Since the PKI migration the desktop visitor presents its enrolled access identity (the same one it uses for web/API access) and renews it automatically — no more server-minted visitor cert.

Rotating the FRP auth.token

Caution — breaking change: the global auth.token (in the FRP server config) flows identically into frps.toml, every agent frpc.toml and every desktop visitor.toml. In token mode frps knows exactly one token; there is no overlap/dual-token mechanism. A rotation therefore breaks all agents and visitors at once, until each has re-synced / re-downloaded its bundle. The actual tunnel security is enforced mTLS (transport.tls.force) plus the STCP secretKey anyway — the token is only the weaker second factor.

So rotate only deliberately, in a maintenance window, in this mandatory sequence:

  1. Set the new auth.token in the FRP server config (PUT /api/frp/server-config/{id}).
  2. Restart frps manually (e.g. docker compose restart frps): the server writes the new frps.toml but does not reload frps itself — until the restart frps keeps running with the old token.
  3. Let all agents re-sync (the next sync pulls the new frpc.toml) and all desktop visitors reload the tunnel bundle.

Applies to every FRP server-config change: not only token rotation — changed dashboard credentials, ports or vhost settings also write the new frps.toml immediately but only take effect after docker compose restart frps (frps has no config hot-reload, and the server container has no docker socket to restart it). The server logs a warning on every runtime change.

Provision Token

Every new agent gets a one-time token when it is registered. Token properties:

  • Valid for 24h
  • Single use (invalidated server-side right after use)
  • Bound to a server ID, i.e. the token fits only a single agent entry

Tunnel Types

TypeDescriptionUse case
httpsHTTPS tunnel with virtual-host routing (idrac.srv1.example.com) under the subdomain host of the FRP server configuration (subDomainHost in frps.toml).Web UIs behind NAT (e.g. IPMI, home automation).
stcpSecure TCP: only a visitor with the matching secretKey gets through. The visitor runs on the client side – the desktop client takes care of that automatically.SSH, RDP, VNC, any TCP service as a private tunnel – zero public port exposure.

The Secret key field of an STCP tunnel: left empty on create, the server generates a secret; left empty on edit, the stored one stays unchanged (the server never hands it back, so the field starts empty). To rotate it, enter a new value (at least 16 characters), then restart the tunnel in the desktop. Switching to HTTPS deletes the secret; switching back to STCP gets a new one.

Visitor Ports

STCP tunnels need a local port on the admin PC for the visitor, which binds it to 127.0.0.1. The server assigns it when the tunnel is created, unless one is given: the first free port from the VISITOR_PORT_START–VISITOR_PORT_END range (default 6000–6999). The port stays assigned to the tunnel; two STCP tunnels never share one. With firewall restrictions, narrow the range via .env.

Firewall

PortDirectionPurpose
7000/tcpInboundFRP control channel (FRP_BIND_PORT): agents and desktop visitors connect here, with token auth and mTLS (client cert required)
7443/tcpInboundHTTPS tunnels on the subdomain host (FRP_HTTPS_PORT, frps port 443 inside the container; requires a wildcard cert)

The visitor ports (default 6000–6999) bind only locally on the admin PC to 127.0.0.1 and need no rule on the server.

Status Dashboard

The tunnel status view queries the frps dashboard. By default the server reaches it via the Compose service name (http://frps:PORT, with a 127.0.0.1 fallback). If frps runs in a different topology (its own host), set the base URL via FRPS_DASHBOARD_URL in .env instead of editing the code.

Troubleshooting

  • Agent does not connect: check the cert expiry (openssl x509 -in /etc/adminhelper/identity/agent.crt -noout -enddate), server reachability via nc -vz srm.example.com 7000.
  • "Tunnel not found": is the tunnel enabled in the desktop client (Infrastructure → Server → Tunnel tab)? FRP logs: docker compose logs -f frps.
  • STCP does not work: visitor port already taken? Check the desktop client log.
